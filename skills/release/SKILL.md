---
릴리즈를 진행해줘. "$ARGUMENTS"로 버전과 (선택) 게시 모드를 지정할 수 있어
(예: `/tide:release v0.1.0`, `/tide:release v0.1.0 pr`, `/tide:release v0.1.0 release`).
버전을 생략하면 판정 근거 보고서(리뷰보고서 또는 debug 보고서 — 아래 프리플라이트 1)의 추천 버전으로,
그것도 없으면 버전 파일의 현재 버전을 기준으로 판단해줘.
인자에서 버전 토큰(`v…`)과 모드 토큰(`pr`/`release`)을 분리 파싱해줘 — 모드 토큰은 선택이고,
없으면 아래 "게시 모드 해석"의 우선순위로 정한다.

**대상 레포**: 산출물·테스트·git은 모두 대상 레포 루트 기준/cwd다 — `git push`의 remote·기본 브랜치도 **그 레포의 실제 값**에 맞춘다(`origin main` 가정 금지). 규약은 `docs/conventions.md`의 "멀티 레포 / 대상 레포" 절.

프리플라이트 (하나라도 실패하면 git 작업 없이 중단하고 사유를 보고):
1. **판정 근거 보고서의 릴리즈 판정이 "가능"인지 확인** — 근거 후보는 대상 마일스톤(M{N})의
   `docs/reports/M{N}-review.md`와 debug 보고서 `docs/reports/debug-{N}.md`다. 두 보고서는
   판정 형식이 동일하므로 (`## 릴리즈 판정` 섹션의 `가능`/`불가`와 `추천 버전: **vX.Y.Z**`)
   같은 방식으로 읽는다.
   규약의 단일 원본은 `docs/conventions.md`의 "debug 세션" 절이다 — 아래는 그 절차다.
   a. **열린 세션 차단** — `.tide/debug-session`이 존재하면(미종결 debug 세션) 중단하고
      `/tide:debug done`을 먼저 실행하라고 안내한다. 미완결 보고서에는 판정 섹션이
      없으므로 근거가 없다
   b. **릴리즈 여부 판정** — 보고서 파일이 **마지막 릴리즈 태그의 트리에 이미 포함돼 있으면**
      릴리즈된 것, 아니면 미릴리즈다 (`git tag`·`git ls-tree <태그> docs/reports/` 등 **읽기**로
      확인 — 가드는 읽기를 통과시킨다). 태그가 하나도 없으면 전부 미릴리즈. `CHANGELOG.md`
      게재 여부는 보조 확인일 뿐 판정 기준이 아니다(산문이라 출처를 기계적으로 되짚을 수 없다)
   c. **근거 집합 = 미릴리즈인 것 전부** — 리뷰보고서와 **미릴리즈인 모든 debug 보고서**를
      근거로 삼는다(최대 번호 하나가 아니다 — 세션을 두 번 돌고 한 번에 릴리즈하면 이전 세션의
      수정도 이번 커밋에 실린다). **근거가 여럿이면 전부 판정이 "가능"이어야** 진행하고,
      CHANGELOG에 **모든 출처**를 반영한다(아래 3번) — 하나라도 빠뜨리면 그 수정이 근거 없이
      배포된다
   d. 근거로 삼은 보고서의 판정이 "불가"이거나 근거가 될 보고서가 하나도 없으면 중단.
      단, 사용자가 버전 인자를 주며 강행 의사를 명시한 경우에만 경고를 남기고 진행
   e. **하위 호환** — debug 보고서가 하나도 없고 열린 세션도 없으면 현행과 완전히 동일하게
      동작한다(대상 마일스톤의 리뷰보고서 판정만 확인 — 기존 경로 불변)
2. 프로젝트 테스트 명령(cargo test / npm test / pytest 등) 실행 — 실패 시 중단
3. git status로 워킹트리 확인 — 이번 사이클과 무관해 보이는 변경이 있으면
   목록을 보여주고 사용자 확인을 받은 뒤 진행. **`.tide/autonomy`가 `continuous`면 확인 없이
   진행하되 목록은 그대로 보고한다** — 이 게이트는 되돌릴 수 있고(스테이징 전) 아래 프리플라이트 5가
   같은 집합을 한 번 더 보므로 「형식」으로 판정됐다(근거는 `docs/reports/M52-impl.md`의 T01 측정표).
   선언이 없으면 `manual`이므로 **종전대로 확인을 받는다**(부재가 곧 현행 동작이다).
   **나머지 프리플라이트는 자율 수준과 무관하다** — 실패하면 그대로 중단한다
4. **사이트 빌드 출력 제외 용어 0건 확인** (사이트가 있는 프로젝트에 한함) —
   `site/mkdocs.yml` 등 사이트 설정이 있으면, 사이트를 빌드(예: `mkdocs build`)한
   **산출물(소스가 아니라 빌드 출력)** 을 스캔해 제외 용어(외부 저장소명 등)가 0건인지
   확인한다. 검출되면 release를 중단하고 누수 위치를 보고한다. 사이트가 없는 프로젝트
   (일반 tide 사용)에는 이 단계가 적용되지 않는다 — 건너뛰고 진행. 제외 용어 처리·검증의
   상세는 `docs/conventions.md`의 "릴리즈 빌드 출력 검증" 절을 따른다.
5. **릴리즈 커버리지 체크 (advisory — 차단 아님)** — **이번 태그에 실릴 실질 파일 중**
   **어떤 미릴리즈 보고서도 설명하지 않는 것**을 드러낸다(리뷰·CHANGELOG 없이 태그에 편승하는지 노출).
   범위는 두 경로의 **합집합**이다 — ⑴ **커밋 편승**: `git tag`로 마지막 태그를 찾고(태그가 없으면 전체
   추적 파일) `git diff --name-only <태그>..HEAD`로 변경 파일을 모은다. ⑵ **미커밋 편승**:
   `git status --porcelain`으로 미커밋 변경(추적 파일 수정·삭제 + 미추적 파일)을 함께 모은다 —
   **아래 게시 분기의 스테이징이 이것들을 그대로 커밋·태그에 싣기 때문이다**(⑵가 없으면 정상 사이클에서
   범위가 사실상 항상 비어 검사가 아무것도 보지 못한다. `.gitignore`는 이 명령이 이미 존중하므로
   `.tide/phase` 등은 자동 제외).
   합집합에서 **bookkeeping**(집합의 단일 선언처는 `docs/conventions.md`의 "릴리즈 커버리지 체크" 절
   `coverage-bookkeeping:` 선언이며 **여기서 다시 열거하지 않는다** — 대상 레포에 그 파일이나 그 선언이 없으면
   플러그인 설치본을 읽는다)을 뺀 나머지가 **미릴리즈 보고서 전부**(impl + 리뷰 + 미릴리즈
   debug) 본문에 **경로로 언급되는지** 확인한다 — 커버리지 집합은 판정 근거 집합(프리플라이트 1의
   review·debug)보다 **넓다**: 변경을 설명하는 1차 문서인 **impl 보고서를 포함**해야 정상 사이클의
   impl 변경이 오경고되지 않는다. 언급 0인 파일이
   있으면 그 목록을 **advisory 경고**로 보고한다(태그엔 실리나 리뷰·CHANGELOG 누락 가능). **release를
   중단하지 않는다** — 사용자가 강행/보완을 판단한다. git **읽기만** 쓴다(`git tag`·`git diff --name-only`·
   `git status --porcelain` 셋 다 읽기 — phase 무관 통과·가드 무수정).
   매칭은 경로 부분일치 휴리스틱이라 위양성·위음성 여지를 수용한다(정밀 게이트가 아니라 편승 노출이
   목적). 다만 **매칭 전에 중괄호 확장 정규화(`brace-expansion`)를 적용한다** — 보고서가
   `skills/{impl,review}/SKILL.md`처럼 계열을 묶어 적은 것을 펼쳐서 대조한다(펼치는 것은 중괄호 토큰뿐이며
   글롭 `*`는 펼치지 않는다). 이어서 **역방향 선언 대조(`declared-change-set`)** 도 함께 낸다 — impl
   보고서의 `변경 파일 요약` 표에 적혔는데 **실제 변경 집합에 없는** 파일을 같은 advisory 블록에
   보고한다(표의 백틱 토큰 중 실재하는 것만 선언으로 인정하며, `추가`·`수정` 행은 **현재 트리**로
   `삭제` 행은 **마지막 태그의 트리**로 실재를 묻는다 — 그러지 않으면 삭제 선언이 한 건도 대조되지
   않는다). 이 축도 **차단하지 않는다**.
   보고서 **산문 전역**으로 역방향을 넓히지 않는다 — 그 경계와 측정치의 단일 원본은 아래 규약 절이다.
   규약·판정 상세의 단일 원본은 `docs/conventions.md`의 "릴리즈 커버리지 체크" 절이다.

프리플라이트 통과 후 다음을 수행한다. **`.tide/phase`에 `release`를 쓰는 시점은 아래 「게시 분기」의
git 쓰기 직전이다** — 버전 파일·CHANGELOG 편집은 git이 아니므로 그 동안 가드를 열어 둘 이유가 없다.
*"git 쓰기는 release 단계에서만"* 불변에 **오히려 더 충실한 형태**이고, `.tide/autonomy`와 무관하게
적용된다(규약은 `docs/conventions.md`의 "자율 진행 (.tide/autonomy)" 절).
「게시 분기」에 들어가기 직전에 .tide/phase 파일에 `release` 한 줄을 기록하고
(.tide/ 디렉터리가 없으면 생성) 다음을 수행:
**게시 규약의 단일 원본은 `docs/conventions-release.md`의 "릴리즈 게시 (gh)" 절**이다 — 아래는 결정
지점만 적고 사유·상세는 그 절을 읽는다(재서술하지 않는다).

1. **게시 모드 해석·검증** — **버전 파일·CHANGELOG를 건드리기 전에** 끝낸다.
   - **모드 우선순위**: 명시 인자(`pr`/`release`) > `.tide/release-mode` 저장값 > (검증 통과 시)
     대화형 질문(`release`/`pr`/"이번엔 그냥 push"). `gh` 부재·검증 실패면 모드 질문 없이 push-only로
     가고 불가 사유를 한 줄 알린다. 인자·저장값 없이 첫 대화형 선택을 했으면 직후 "이후에도 같은
     모드를 쓸지"를 물어 예이면 `.tide/release-mode`에 한 줄 기록한다.
   - **검증 게이트**: `git`·`gh` 가용·서브커맨드·인증(`gh auth status`)·대상 원격 GitHub 등록
     (`gh repo view`). **모드를 명시했는데 검증이 실패하면 — 파일 편집 전에 중단하고 사유를 보고한다**
     (작업 트리 무변경 · 조용한 강등 금지).
   - **`pr` 모드 상태 인지**: mode=`pr`이면 검증 후·**파일 편집 전에** 릴리즈 PR(`release/v{버전}` 또는
     제목 `Release v{버전}`)을 `gh`로 조회해 분기한다 — **merged**→마무리 / **open**→대기 /
     **closed(미머지)**→중단 / **없음**→생성. **마무리·대기·중단은 아래 2·3을 건너뛴다**(머지로 이미
     반영 — 재편집 금지). 버전은 인자가 기본이고, 인자가 없으면 열린/머지된 릴리즈 PR이 **유일할 때만**
     추론하며 모호하면 명시를 요청하고 중단한다.
2. 버전 파일 업데이트(`Cargo.toml`/`package.json`/`pyproject.toml`/`.claude-plugin/plugin.json` 등).
3. `CHANGELOG.md` 최상단에 릴리즈 노트 추가 — CHANGELOG가 노트의 단일 원본이고 `README.md`는
   포인터만 두므로 건드리지 않는다(`docs/conventions.md`의 "버전 · CHANGELOG" 절). 프리플라이트 1에서
   **debug 보고서도 근거가 됐다면 두 출처를 함께 반영한다**(리뷰의 사이클 변경 + debug의 증상·수정).
4. **게시 분기** (1에서 정한 모드로):
   - **스테이징 범위 (세 모드 공통 — 여기서만 정의한다)**: `git add`는 **대상 레포 루트 기준 전체
     스테이징**이다(추적 파일의 수정·삭제 + 미추적 파일, `.gitignore` 존중). **프리플라이트 5가 범위
     ⑵로 본 집합이 그대로 커밋·태그에 실린다.** 좁혀야 하면 임의로 줄이지 말고 프리플라이트 3·5의
     보고를 근거로 사용자가 판단한다.
   - **push-only**: git add → commit(`Release {버전}: {핵심 변경 한 줄}`) → `git tag {버전}` →
     `git push {remote} {기본 브랜치}` → `git push {remote} {버전}`.
   - **`release` 모드**: push-only를 그대로 하고 **그 뒤** `gh release create {버전}`(노트 = CHANGELOG
     발췌 · 제외 용어 규약 준수). 이미 push된 태그를 참조해 중복 생성을 피한다.
   - **`pr` 모드**: 기본 브랜치에 **직접 push하지 않는다**. 1에서 조회한 상태로 분기한다.
     - **없음 → 생성**: `release/v{버전}` 브랜치에 add → commit → push → `gh pr create`(제목
       `Release v{버전}: …`, 본문 = CHANGELOG 발췌). **태그·릴리즈는 머지 후로 미루고** PR URL과
       "머지 후 같은 명령 재실행" 안내를 남긴다.
     - **open → 대기**: 부수효과 없이(태그·릴리즈·push 없음) 안내만.
     - **closed(미머지) → 중단**: 머지 없이 닫혔음을 보고하고 중단(임의 재생성·태그 금지).
     - **merged → 마무리**: 기본 브랜치 최신화(`git fetch`→checkout/`pull`) → **PR CI 확인**
       (`gh pr checks {번호}` — **태그 전에** 결과를 보고하고, 실패·미완료가 있으면 목록을 보여주고
       **사용자 확인을 받은 뒤** 진행한다. 새 게이트가 아니며 프리플라이트 ①②③은 불변. `gh` 부재·조회
       실패면 **그 사실을 한 줄 알리고** 진행 — 조용히 건너뛰지 않는다) → **버전 sanity**(머지된 버전
       파일이 `v{버전}`과 일치하지 않으면 **태그 없이 중단**) → 태그를 머지 tip에 달고
       `git push {remote} v{버전}` → `gh release create {버전}` → **릴리즈 브랜치 정리**.
       **2·3은 건너뛴다.** 태그와 릴리즈는 **각각 독립 선확인**해 없는 것만 만든다(부분 실패 복구).
       **미머지엔 태그 금지.** 정리는 멱등·비차단·현재 브랜치 안전이다.

완료 후 .tide/phase를 `idle`로 되돌리고 결과를 보고해줘. `gh`가 가용한데 모드 미지정으로 push-only를
한 경우, 보고 말미에 "`pr`/`release` 모드로 게시할 수 있다"는 안내를 한 줄 덧붙일 수 있다(자동 실행 금지).

## 운영 주의

최근 release에서 반복된 함정이다. 위 절차 자체는 그대로 두고, 실행 시 아래를 지킨다:

1. **`.tide/phase`=`release` 기록은 git 명령과 별도 단계로 먼저** 실행한다. tide-guard는
   명령 실행 *전*에 phase를 읽으므로, `phase 기록 && git ...`처럼 한 명령에 합치면 직전
   phase(예: `idle`/`review`)가 읽혀 git 작업이 차단된다. 반드시 phase를 먼저 한 단계로
   기록하고, 그다음 별도 명령으로 git을 실행한다.
2. **커밋 메시지가 여러 줄이면 실행 환경의 멀티라인 문법에 맞춘다.** `-m`을 반복하거나
   환경에 맞는 here-doc/here-string을 쓴다. 셸이 불일치하면(예: POSIX sh ↔ PowerShell)
   메시지에 따옴표·토큰이 그대로 섞여 오염될 수 있다.
3. **CHANGELOG/README 릴리즈 노트에 사이트에서 제외하기로 한 용어(외부 저장소명 등)를
   literal로 쓰지 않는다.** 이 문서들은 단일 원본화(snippets)로 사이트 콘텐츠에 그대로
   유입될 수 있다. 제외 용어 처리는 `docs/conventions.md`의 규약을 따른다.
4. **버전은 버전 파일(`plugin.json`)만 범프한다.** `docs/project-context.md`는 버전 숫자를
   복제하지 않으므로 release가 갱신하지 않는다 — 드리프트 차단은 갱신 단계 추가가 아니라
   복제 제거로 해결된다.
5. **게시 명령(`gh release create`/`gh pr create`)도 `.tide/phase`=`release` 동안에만 실행한다.**
   "게시는 release에서만"이라는 불변은 tide-guard가 아니라 이 절차가 보존한다(가드는 git 토큰만
   차단, `gh`는 게이트하지 않음). 릴리즈 노트·PR 본문이 여러 줄이면 실행 환경 멀티라인 문법
   (here-doc/here-string)에 맞추고, CHANGELOG 발췌를 그대로 쓰므로 제외 용어 literal을 피한다(3번과
   동일 규약). 검증 게이트는 commit/push **전에** 두어 명시 모드 실패 시 작업이 어중간하게 새지 않게 한다.
   `pr` 모드 마무리(finalize)의 태그·`gh release create`도 phase=`release`에서만 실행하고, **`gh`로 머지를
   확인(merged)한 뒤에만 태그를 단다**(미머지 태그 금지). 태그·릴리즈는 각각 독립 선확인해 없는 것만 생성한다(멱등·부분 실패 복구).
