# tide 규약 (conventions)

tide는 porpoise의 개발 방법론(마일스톤 → 구현 → 리뷰 → 릴리즈)을 프로젝트
독립적인 슬래시 커맨드로 옮긴 워크플로우다. 이 문서는 각 단계가 따르는 규약을 정의한다.

## 사이클

```
/tide:kickoff  →  /tide:milestone  →  /tide:impl  →  /tide:review  →  /tide:release vX.Y.Z
   (세팅)           (계획)             (구현·테스트)    (리뷰·판정)       (배포)

                  └──────────── /tide:cycle ────────────┘  (release 직전 정지)

                          /tide:status      — 언제든 현재 위치 확인 (읽기 전용)
                          /tide:debug       — 발견한 에러를 세션으로 수정·기록 (사이클 밖 행위, 출구는 release)
                          /tide:fleet       — 여러 자식 레포 교차 개요 (읽기 전용)
                          /tide:fleet-cycle — 그 순서대로 milestone→review 자동 실행 (멀티 레포, release 제외)
                          /tide:fleet-verify — 통합 훅으로 레포 간 통합 검증 (멀티 레포, verification-only)
```

`/tide:status`·`/tide:fleet`은 **사이클 단계가 아니다** — kickoff→…→release 흐름 밖에 있는
읽기 전용 보조 커맨드다(`status`는 현재 레포 위치, `fleet`은 여러 자식 레포 교차 개요).
`/tide:fleet-cycle`은 그와 짝을 이루는 **멀티 레포 자동화 보조** 커맨드다 — fleet이 읽기 전용
개요라면, fleet-cycle은 그 발견·순서대로 각 레포의 `milestone → review`를 자동 실행한다
(release는 제외 — 아래 "멀티 레포 오케스트레이션" 절).

`/tide:debug`도 **사이클 단계가 아니다** — 다만 `status`·`fleet`이 사이클 밖 **읽기 전용** 보조라면
`debug`는 사이클 밖 **행위** 커맨드다(파일을 고치고 보고서를 남긴다). 계획 우선 사이클과 달리
**발견 우선** 진입점이며, git 쓰기 금지·산출물 추적은 그대로 적용되고 **출구는 같은 `release`**다
(아래 "debug 세션" 절). `/tide:cycle` 자동 체이닝의 대상은 **아니다** — 체이닝은 계획 우선 전용이다.

**수동 단계별 호출 vs `/tide:cycle` 자동 체이닝**: 평소엔 각 단계를 직접 호출하지만,
`/tide:cycle`은 `milestone → impl → review`를 한 번에 이어 실행한다(필요 시 milestone부터,
`M{N}` 인자면 impl부터). `release`만은 자동 체이닝에서 **제외** — git 작업을 하는 유일한
단계이므로 review "가능" 판정 후 사이클을 끝내고 사용자에게 `/tide:release vX.Y.Z`를
넘긴다. cycle은 각 단계의 전제조건을 그대로 검사하고, 한 단계가 미충족·실패로 멈추면
사이클 전체를 중단하며 중단 지점·사유를 보고한다. impl 단계에서는 마일스톤 태스크의
`(deps:)` 표기를 읽어 **독립 태스크를 서브에이전트로 동시 디스패치(실제 병렬)**, 의존
태스크는 순차로 스케줄링한다. 병렬 메커니즘·파일 충돌 안전장치·결과 병합·폴백은
`skills/impl/SKILL.md`의 "병렬 디스패치" 절이 단일 원본이다(`/tide:impl`·`/tide:cycle`
공통).

**핵심 원칙 — 부수효과 분리**: `impl`·`review`·`debug`는 **절대 git 작업을 하지 않는다**(문서·코드만
남김). git commit/tag/push는 오직 `release`에서만 일어난다. impl/review/debug가 남긴 보고서는
다음 `release` 커밋에 함께 포함된다. 이 원칙은 프롬프트 지시에 더해 **tide-guard hook**으로
기계적으로 강제된다(아래 참조).

## 상태 파일 (.tide/phase)

- 위치: `.tide/phase` — 현재 단계명 한 줄
  (`milestone` / `impl` / `review` / `release` / `debug` / `idle`)
- **phase 기록 커맨드 6종**(`milestone`·`impl`·`review`·`release`·`debug`·`cycle`)은 자기 단계명을
  기록하고 최종 보고 직전 `idle`로 되돌린다. **기록 시점은 각 커맨드의 절차가 정한다** — 전제조건을
  먼저 검사하는 커맨드는 그 검사를 통과한 뒤에 기록하므로, 검사에서 중단되면 phase가 기록되지 않는다.
  어느 커맨드가 어느 시점에 쓰는지는 **해당 SKILL이 단일 원본**이고, 규약은 그 시점 목록을 복제하지
  않는다. **나머지 6종은 이 레포의 phase를 쓰지 않는다** —
  `status`·`fleet`은 읽기 전용, `retro`는 회고 문서만 쓰고, `fleet-verify`는 verification-only이며,
  `kickoff`는 `.gitignore` 항목만 손대고, `fleet-cycle`은 **자식 레포의** phase만 쓴다(부모·세션 레포는
  건드리지 않는다). 6종도 **대상 레포**의 phase를 쓴다 — 상위 폴더 세션이 자식 레포를 대상으로 잡으면
  그 자식의 phase가 기록되고 세션 레포는 그대로다(위 "멀티 레포 / 대상 레포" 절의 앵커링 규율).
- **이 절은 phase를 쓰는 6종과 쓰지 않는 6종을 열거하는 유일한 곳이다.** 다른 규약 절·문서·훅 주석은
  이 절을 가리키기만 하고 명단을 다시 적지 않는다 — 같은 명단이 여러 곳에 적히면 고칠 때 일부만
  고쳐져 발산한다. **예외는 발행 페이지 `site/docs/concepts.md` 하나다**: 독자에게 규약으로 점프를
  강요하지 않으려고 목록을 유지하되, **두 목록(기록·비기록) 각각의 이름 집합이 두 파일에서
  일치하는지와 열거처가 그 둘뿐인지를 `tests/discover` Part C-3이 집행한다**(수기 동기화에 기대지
  않는다). **집행 범위는 이 선언과 같은 넓이여야 한다** — 한쪽 목록만 덮으면 규약이 사실보다 넓게
  주장하는 것이고, 그 자체가 아래 "리뷰 검증 규율" 절이 정한 `vacuous-pass` 부류다. 하니스가 무는 정확한
  표면과 그 한계(줄·창 단위 스코프)는 `tests/discover/README.md`의 C-3 항목이 단일 원본이다.
- **`.tide/debug-session`** — 열린 debug 세션의 **활성 보고서 번호 한 줄**(예: `3`). 파일 존재 =
  세션 열림이고, `/tide:debug done`이 세션을 닫으며 삭제한다(아래 "debug 세션" 절이 단일 원본).
  세션 번호는 **별도 파일**에 둔다 — `.tide/phase`는 종전 계약대로 **단계명 한 줄**만 담고
  `debug` 역시 단계명일 뿐이다(phase 계약 불변).
- `.gitignore` 대상은 **`.tide/phase`와 `.tide/debug-session` 둘**이다 (로컬 상태일 뿐 커밋하지
  않는다). `.tide/` 전체가 아니라 이 두 파일만 무시하므로, 같은 `.tide/` 아래의
  **`.tide/deps`(의존성 선언)와 `.tide/release-mode`(게시 모드 선호도)는 종전대로 커밋된다**
  (위 "의존성 선언 (`.tide/deps`)" 절과
  `docs/conventions-release.md`의 "선호도 기억 (`.tide/release-mode`)" 절). `.tide/phase`의 의미
  (단계명 한 줄)와 tide-guard 계약은 **불변**이다(아래 "2.0 안정성" 절이 phase/guard 계약을 1.0
  그대로 유지) — `debug` 값 가산도 `debug-session` 추가도 그 계약을 바꾸지 않는다.

## tide-guard hook

- PreToolUse(Bash|PowerShell 매처) hook. **플러그인이 직접 제공한다** —
  `hooks/hooks.json`이 `${CLAUDE_PLUGIN_ROOT}/hooks/tide-guard.sh`를 등록하므로
  플러그인 설치만으로 활성화되고, 프로젝트별 설치 절차는 없다.
- 동작: `.tide/phase`가 `release`가 **아닌** 동안 git **쓰기** 명령만 차단한다(exit 2) —
  서브커맨드가 `commit`·`push`이거나 `tag`의 *생성/삭제* 형태일 때. git **읽기는 phase와 무관하게
  통과**한다(맥락 파악용): 커밋 읽기(`git log`·`show`·`diff` 등)·**태그 목록/조회**(`git tag`·`-l`·
  `--list`·`-n`·`--contains`·`--points-at`·`--sort`·`--column`·`--format`·`-v` 등 읽기 옵션만)·
  메시지 검색(`--grep=…`)·이력 파일 읽기(`HEAD:<path>`)는 막지 않는다. 안내 메시지(한국어): "'{phase}'
  단계에서는 git 쓰기(commit·태그 생성/삭제·push)가 차단됩니다 — 읽기는 허용됩니다. git 쓰기는
  /tide:release 단계에서만 가능합니다."
- **서브커맨드 위치 판정**: verb(`commit`·`tag`·`push`)는 git **서브커맨드**일 때만 본다 — `git` 뒤
  전역 옵션(`-C <dir>`·`-c <kv>`·`--git-dir`·`--work-tree`·`--namespace`·`--super-prefix`·`--exec-path`
  등 인자 소비형은 그 인자까지)을 건너뛴 첫 비-옵션 토큰. verb 글자가 옵션 값(`--grep=commit`)·경로
  (`HEAD:src/tag.rs`)·복합 서브커맨드 이름(`commit-graph`·`cat-file commit`)에 들어가도 서브커맨드가
  아니면 차단하지 않는다(부분 문자열 매칭 아님). `tag`의 읽기/쓰기 구분: 읽기 옵션만 있거나 인자가
  없으면 **목록(읽기)**, 쓰기 옵션(`-a`·`-s`·`-u`·`-m`·`-F`·`-e`·`-f`·`-d`·`--delete`·`--create-reflog`)이
  있거나 *목록 옵션 없이* 위치 인자(태그명)가 오면 **생성/삭제(쓰기)**. 차단되던 *쓰기* 집합은 줄지
  않고(보호 불변) *읽기 오차단*만 풀린다. 차단/통과 케이스는 `tests/multi-repo`가 집행한다.
- **범위(백스톱이지 샌드박스 아님)**: 가드는 **직접 git 호출**(서브커맨드 위치의 `commit`·`tag`·`push`)을
  본다. `sh -c 'git push'`·`eval`·따옴표로 감싼 실행 등 **간접·우회 실행**은 파싱하지 않으므로 잡지 않는다
  (이를 잡으려면 셸 전체를 파싱해야 하고, 그러면 `echo 'git push'` 같은 무해한 문자열까지 오차단하던 옛
  부분일치로 회귀한다). 가드의 역할은 *우발적 직접 git 쓰기*를 막는 기계적 백스톱이며, "impl·review는 git
  금지"의 **실제 보장은 단계 규율**이다(M18·M19와 동일 — 규율이 1차, 가드는 백스톱). 같은 이유로 plumbing
  쓰기(`commit-tree` 등 ref를 옮기지 않는 저수준 명령)도 비대상이다.
- **phase 읽기 위치**: 가드는 **명령이 실행되는 레포 루트의 `.tide/phase`를 읽는다**(단일
  레포에선 `CLAUDE_PROJECT_DIR`와 동일). 레포를 못 찾으면 `CLAUDE_PROJECT_DIR` 폴백,
  그래도 없으면 무차단. 이는 단일 레포 동작을 바꾸지 않는 **하위 호환 일반화**이며(아래
  "2.0 안정성"·"멀티 레포 / 대상 레포" 절 참조), 차단 규칙·메시지·exit 2는 불변이다.
- 상태 파일이 없으면 아무것도 차단하지 않는다 — tide를 쓰지 않는 프로젝트나
  사용자의 수동 git 작업(idle 상태가 아니라 파일 자체가 없는 경우)에 영향을 주지 않는다.
- **보호 창(window)과 우회 표면 — 고지하고 수용한다**: 바로 위 항의 "부재 시 무차단"은 **tide 미사용
  레포**와 **tide 레포인데 phase가 아직 없는 상태**를 구분하지 않는다. 구분해 적으면 이렇다.
  - **fresh clone 창**: `.tide/phase`는 `.gitignore` 대상이라 **fresh clone·신규 머신·플러그인 설치
    직후에는 git 쓰기 보호가 0**이다. 창은 **phase 기록 커맨드 6종 중 하나가 실제로 phase를 기록할 때**
    닫힌다(위 "상태 파일 (.tide/phase)" 절의 6종) — **호출만으로는 닫히지 않는다.** 두 가지 이유가
    겹친다.
    - **쓰지 않는 커맨드**: 절반은 이 레포의 phase를 아예 쓰지 않는다(명단은 위 절). fresh clone 후
      가장 자연스러운 첫 커맨드인 `kickoff`(골격 세팅)와 `status`(현재 위치 확인)가 거기 들어가므로,
      `kickoff`만 돌린 신규 레포는 창이 계속 열려 있다.
    - **쓰기 전에 중단되는 경로**: 기록 시점은 커맨드마다 다르고, **전제조건을 먼저 검사하는 커맨드는
      그 검사를 통과한 뒤에** 기록한다. 검사에서 중단되면 phase 파일이 생기지 않아 창은 그대로다.
      **어느 커맨드가 어느 시점에 쓰는지는 각 스킬의 절차가 정한다** — 규약은 창이 *기록될 때* 닫힌다는
      규칙만 정하고 시점 목록을 여기 복제하지 않는다(스킬은 절차, 규약은 conventions).
  - **Edit/Write 우회 표면**: hook 매처가 `Bash|PowerShell`이라 **파일 조작 도구 경로는 훅을 타지
    않는다** — Edit/Write로 파일을 직접 쓰는 경유는 가드가 보지 않는다(위 백스톱 범위 항이 적은
    간접·우회 실행과 같은 층이며, 같은 이유로 잡지 않는다).
  - **전제조건이 프롬프트 규율**: phase를 기록하는 주체가 **LLM**이므로 **기계적 가드의 전제조건
    자체가 프롬프트 규율**이다 — 보호는 무조건이 아니라 **조건부**다.
  - **결론 = 수용**: 창은 **좁지만 자동으로 닫히지 않는다**(phase가 실제로 기록돼야 닫힌다). 그래도
    앞당겨 닫으려면 **부재 시 무차단**(2.0 stable 계약)과
    **phase 삭제로 해제**(아래 `idle` 항이 적은 공표된 수단) **둘 다**를 건드려야 하므로 3.0 사안이다
    (아래 "2.0 안정성" 절에 후보로 등재). 그래서 고치는 대신 **고지하고 수용**하며, 규약이
    **집행력을 사실보다 넓게 주장하지 않도록** 창을 여기 명시한다 — 아래 "차단 등급 판례" 절이
    판례로 박은 것과 같은 원칙을 가드 쪽에 적용한 결과다.
- **`idle`에서도 (쓰기는) 차단된다** — tide 도입 후에는 Claude를 통한 git **쓰기**(commit·태그
  생성/삭제·push)가 항상 `/tide:release`로만 일어나는 것이 의도된 동작이다(읽기는 `idle`에서도 통과).
  tide 사이클 밖에서 Claude에게 git 쓰기를 시키려면 `.tide/phase` 파일을 삭제해 가드를 해제한다.
- **`debug`에서도 (쓰기는) 차단된다 — 가드는 무수정**: `debug`는 phase≠release이므로 **가드 코드에
  한 줄도 손대지 않고** 기존 규칙이 그대로 적용된다(쓰기 차단·진단용 읽기 통과). **새 phase 값이
  가드에 분기를 더하지 않는다는 것이 이 설계의 핵심**이다 — 차단 규칙·메시지·exit 2는 2.0 stable
  계약 그대로 불변이다(아래 "2.0 안정성" 절). "급할 땐 debug에서 commit 허용"은 **하지 않는다**
  (백스톱을 가장 필요한 순간에 푸는 역방향 — 규율이 1차, 가드는 백스톱). `tests/multi-repo`가
  `phase=debug`의 쓰기 차단·읽기 통과를 양 셸 회귀로 집행한다.
- 스크립트 원본은 `hooks/tide-guard.sh` **한 곳**이다 (`tide-guard.ps1`은 sh를 쓸 수
  없는 환경을 위한 보조 사본 — 로직·메시지 수정 시 함께 갱신). Windows에서는 Git for
  Windows의 sh로 실행된다.
- **인코딩 규약**: 두 사본의 인코딩이 다르다 — `tide-guard.sh`는 **BOM 없는 UTF-8**
  (Git Bash가 shebang을 정상 처리하도록), `tide-guard.ps1`은 **BOM 포함 UTF-8**
  (Windows PowerShell 5.1이 한글 메시지를 ANSI로 오인해 깨뜨리지 않도록). 메시지를
  수정할 때 각 파일의 인코딩을 유지한다.
- **입력 견고화(판정 불변)**: 가드는 hook 입력(stdin JSON)을 파싱하기 전에 **선두 UTF-8
  BOM(`EF BB BF`)을 제거**한다 — 일부 환경이 stdin 선두에 BOM을 붙이면 `jq`/`ConvertFrom-Json`이
  throw해 `cwd` 추출이 어긋나기 때문이다(`read_deps`의 선두 BOM 무시와 같은 결). jq 부재 시 raw
  입력에서 `cwd`를 뽑는 sed 폴백은 **키를 JSON 구조 경계로 앵커링**해 부분일치 오인을 줄인다.
  이 견고화는 **차단/통과 판정·메시지·exit 2 계약을 바꾸지 않고**(동일 입력에 동일 판정) 두 사본
  (`.sh`·`.ps1`)에 동일 의미로 적용되며, `tests/multi-repo`가 선두 BOM 입력 회귀로 집행한다.

## 멀티 레포 / 대상 레포

앵커링·cwd 규율의 **단일 원본**이다. 스킬·가드·실증이 모두 이 절을 따른다.

- **대상 레포(target repo) 해석**: 각 tide 커맨드는 시작 시 "대상 레포 루트"를 정한다.
  - 기본(단일 레포): 세션을 레포 루트에서 구동한 경우 대상 = 그 레포(`CLAUDE_PROJECT_DIR`).
    **현행과 동일** — 이 절은 그 동작을 바꾸지 않는다.
  - 멀티 레포: 상위 폴더에서 띄운 단일 세션이 특정 자식 레포를 작업하라고 지시받으면(인자
    또는 대화 맥락) 그 **자식 레포의 절대 루트**를 대상으로 삼는다. 인자 지원은 가산이며
    기존 `argument-hint`를 깨지 않는다(선택 인자 — 없으면 기본 동작).
- **산출물 앵커링**: `docs/milestones/`·`docs/reports/`·`.tide/phase`·버전 파일·`CHANGELOG.md`
  등 **모든 상대경로 산출물은 대상 레포 루트 기준**으로 읽고 쓴다. 상위 폴더에 흩뿌리지 않는다.
- **cwd 규율**: 모든 git·테스트·빌드 명령은 **대상 레포 루트를 작업 디렉터리로** 실행한다.
  서브에이전트 위임 시에도 대상 레포 루트를 전달해 동일 규율을 상속한다.
- **세 규약의 맞물림**: cwd를 대상 레포 루트로 두면 tide-guard의 레포 루트 해석이 같은
  루트를 가리키므로, 스킬이 쓰는 `.tide/phase`와 가드가 읽는 phase가 같은 레포로 일치한다 —
  이것이 멀티 레포 격리가 성립하는 핵심이다.
- **격리 보장**: 자식 A를 release(phase=release)해도 자식 B의 phase는 독립이며 B로의 git
  commit/tag/push는 계속 차단된다(가드가 각 레포 루트의 phase를 따로 읽으므로).

이 절의 추가는 전부 가산이다 — 단일 레포 동작은 불변이고, 대상 레포가 곧 세션 레포인
일반 경우엔 위 규율이 현행과 같은 결과를 낸다.

## 멀티 레포 오케스트레이션

상위 폴더 단일 세션에서 그 아래 여러 tide 자식 레포를 가로질러 보고 조정하는 규약의
**단일 원본**이다. fleet 커맨드·발견·계획이 모두 이 절을 따른다.

### 계층 로드맵

오케스트레이션은 안전·고가치인 아래층부터 4층으로 쌓았고 **1~4층이 모두 구현됐다**. 각 층의
규약은 아래 해당 절이 단일 원본이며 여기서는 층의 이름과 경계만 둔다.

- **① 가시성** — 읽기 전용 fleet 개요(발견 + 교차 상태 집계 + advisory 계획). git·파일 변경 없음.
- **② 의존성/계약 선언** — `.tide/deps`로 처리 순서를 인식한다(아래 "의존성 선언 (`.tide/deps`)"·
  "의존성 인식 순서 규칙" 절).
- **③ 교차 사이클 자동화** — 여러 레포의 `milestone → review`를 의존성 순서로 실행하되
  **release는 제외**한다(아래 "교차 사이클 자동화" 절).
- **④ 통합 검증** — 부모 레벨 훅 `.tide-fleet/integration`으로 cross-repo 통합을
  **verification-only**로 검증한다(아래 "통합 검증" 절).

### 부수효과 분리 불변

멀티 레포 토대에서도 부수효과 분리 원칙(위 "사이클" 절)은 **모든 층에서** 그대로다 — 아래 셋이
층별로 그것이 무엇을 뜻하는지 못박는다.

- 오케스트레이션은 **cross-repo `git commit/tag/push`를 자동화하지 않는다**. release는 항상
  **레포별 수동**(`/tide:release`)이며, tide-guard와 레포별 격리(위 "멀티 레포 / 대상 레포"
  절)가 그대로 적용된다.
- fleet은 **advisory만** 한다 — 위상정렬한 권장 처리 순서를 **제안**할 뿐 어떤 레포에도
  사이클·git을 **자동 실행하지 않는다**. 실제 처리 순서·시점은 사용자가 판단한다.
- fleet-cycle은 **milestone→review만**, fleet-verify는 **verification-only**로 돈다 — 둘 다
  `release`·git commit/tag/push·cross-repo git을 자동 실행하지 않고 **어떤 레포의 `.tide/phase`도
  `release`로 쓰지 않는다**. 실제 보장은 그 **규율**이며, tide-guard는 phase≠release인 레포의 git을
  막는 **백스톱**(release 차단기가 아님 — `/tide:release`가 phase=release를 먼저 써서 가드를 푼다)
  이다. 백스톱이 풀린 채 도는 것을 막기 위해 fleet-cycle은 처리 전 **phase=release 잔재 레포를
  제외**하고(필수 사전 점검), fleet-verify는 훅에 cross-repo git을 두지 않되 **의심 시** 자식 phase의
  release 잔재를 점검한다(각 절의 규정이 정확한 형태다).
  순서 release 핸드오프는 **제안**이며 release 시점·실행은 사용자가 판단한다.

### 의존성 선언 (`.tide/deps`)

레포 간 의존을 선언하는 매니페스트의 **단일 원본**이다. fleet 스킬·실증이 이를 인용한다.

- **위치·포맷**: 각 자식 레포 루트의 `.tide/deps`. 한 줄에 **의존하는 형제 레포 디렉터리명**
  하나. 빈 줄과 `#`로 시작하는 주석 줄은 무시하고, 줄 앞뒤 공백은 트림한다.
- **선두 BOM 무시**: 파일을 읽을 때 **선두 UTF-8 BOM(`EF BB BF`)을 제거**한 뒤 줄 단위로
  파싱한다 — BOM이 붙은 첫 줄(주석·의존)도 올바로 파싱된다(Windows 편집기·`Set-Content
  -Encoding utf8`로 만든 deps 파일 내성). 주석·빈 줄 무시·트림 규칙은 그대로다.
- **의미**: "이 레포는 나열된 형제 레포들에 **의존**한다"(의존 대상이 먼저 처리되어야 한다).
  예 — `svc-orders/.tide/deps`에 `svc-auth` 한 줄 → orders는 auth에 의존, 순서상 auth가 먼저.
- **옵트인·하위 호환**: 파일이 없거나 유효 줄이 0이면 **의존 0**(현행 동작 그대로). 선언은 순수
  가산이며 단일 레포·미선언 멀티 레포 동작을 바꾸지 않는다.
- **커밋 대상**: `.tide/deps`는 레포의 **선언**이므로 **커밋한다**. 반면 `.tide/phase`·
  `.tide/debug-session`은 종전대로 로컬 상태라 gitignore다 — gitignore 범위는 `.tide/`가 아니라
  **그 두 파일만**이다(`deps`·`release-mode`는 커밋, phase·debug-session은 무시).
  범위의 단일 원본은 위 "상태 파일 (.tide/phase)" 절이다.
  `.tide/phase`의 의미·tide-guard 계약은 **불변**이다("2.0 안정성" 절이
  phase/guard 계약을 1.0 그대로 유지).
- **계약 버전 (옵트인 확장)**: 의존 줄에 선택적 버전 제약을 붙일 수 있다 —
  `<형제 레포명>[ <op> <버전>]`. 예: `svc-auth >= v0.3.0`. 연산자·버전이 없으면 **이름 의존만**
  (M16 동작 그대로). 토큰 사이 공백은 트림한다.
  - **연산자**: 전체 비교 연산자를 지원한다 — `>=`·`>`·`=`(또는 `==`)·`<=`·`<`. `>=`는 "이 버전
    이상 필요"(의존 계약의 지배적 의미)이고, 나머지도 같은 방식으로 만족 여부를 판정한다.
    그 외 **알 수 없는 연산자**는 **무시하고 경고**한다(안전 측 — 위반으로 단정하지 않는다).
  - **버전 파싱·비교**: 버전은 `vX.Y.Z`(선행 `v` 선택)로 보고 **major.minor.patch를 숫자로**
    비교한다. 버전 파싱 불가(비표준)면 **비교를 생략하고 경고**한다(차단·위반으로 단정하지 않는다).
  - **옵트인·하위 호환**: 버전 제약 없는 줄·`>=`만 쓰던 기존 deps·deps 미선언은 현행 동작 불변
    (연산자 확장은 순수 가산).

### 계약 비교 규칙

- 의존 줄에 `<op> 버전` 제약이 있으면, fleet은 **의존 대상 레포의 현재 버전**(아래 "발견 규약"의
  버전 파일, 상태 조회 4번 항목)을 읽어 요구 버전과 `vX.Y.Z` major.minor.patch 숫자로 비교한다 —
  연산자(`>=`·`>`·`=`(또는 `==`)·`<=`·`<`) **만족이면 무표기, 불만족이면 위반**으로 본다.
  `>=` 위반은 통상 **upstream behind**(의존 대상이 요구보다 낮음)다.
- **순서 불변**: 위상정렬 순서·의존 그래프는 버전 제약과 무관하게 M16·M17 그대로다(버전 제약은
  순서를 바꾸지 않는다 — 경고는 줄 표기일 뿐).
- **위반 표기**: 불만족이면 권장 처리 순서/advisory의 의존 레포 줄에 `⚠ contract` 경고를 한 줄
  덧붙이며, **연산자·요구·현재를 함께 적는다** — 예:
  `svc-orders → ⚠ contract svc-auth 0.2.0 < 요구 >= 0.3.0 (upstream behind — svc-auth를 먼저 올릴 것)`.
- **알 수 없는 연산자·비표준/파싱 불가 버전**: **무시하고 경고**한다 — 차단·위반으로 단정하지
  않는다(안전 측, M17 기조 유지).
- **advisory만**: 이 경고는 제안일 뿐이다 — fleet은 위반을 이유로 어떤 레포도 **차단·실행하지
  않는다**(위 "부수효과 분리 불변").

### 의존성 인식 순서 규칙

- 발견된(아래 "발견 규약": 직속·git·tide 산출물·숨김 제외) 자식 레포들의 `.tide/deps`를 모아
  **방향 그래프**(의존→피의존)를 만들고 **위상정렬**해 권장 처리 순서를 산출한다 — **피의존(먼저
  필요한 레포)이 의존하는 레포보다 앞**에 온다.
- **순환 의존**(직간접 A→B→…→A): **감지해 보고하고 상태 기반 순서로 폴백**한다(impl `(deps:)`
  순환 폴백과 동일 기조). 순환 고리에 든 레포를 명시한다.
- **미선언 레포**: 의존 0인 독립 노드로 두고 순서는 상태로 산출한다(다른 노드와 위상 관계 없음).
- **존재하지 않는 형제명**: `.tide/deps`가 발견 집합에 없는 이름을 가리키면 **무시하고 경고**한다
  (안전 측 — 잘못된 선언이 순서를 깨지 않게).
- fleet은 **advisory만** — 위상정렬 순서를 **제안**할 뿐 어떤 레포에도 사이클·git을 자동 실행하지
  않는다(위 "부수효과 분리 불변").

### 자식 tide 레포 발견 규약

"대상 부모"의 **직속 하위 디렉터리**(기본 = 세션 cwd, 선택 인자로 경로 지정 가능) 중 다음을
**모두** 만족하는 것을 자식 tide 레포로 본다.

- git 레포일 것, **그리고**
- tide 산출물을 가질 것 — `docs/milestones/` **또는** `.tide/` **또는** 버전 파일 중 하나 이상.

**이름이 `.`으로 시작하는 숨김(dot) 디렉터리는 무시한다**(`.git`·`.claude` 등) — 직속 1단계
스캔에서 제외 대상이다.

**깊은 재귀는 하지 않는다 — 직속 1단계만**(단순·예측 가능). 손주 이하 디렉터리는 보지 않는다.

### 발견성(discoverability) 힌트

`/tide:status`·`/tide:kickoff`가 멀티 레포 맥락에 들어선 순간 fleet 입구를 한 줄로 가리키는
advisory 힌트의 **단일 원본**이다 — 두 스킬은 이 절을 인용한다(중복 정의 금지).

- **트리거**: `/tide:status`·`/tide:kickoff`가 자기 본래 작업을 마친 뒤, **현재 세션 위치(cwd)의
  직속 1단계 하위 디렉터리** 중 **자식 tide 레포**를 센다. 무엇이 자식 tide 레포인지는 위
  "자식 tide 레포 발견 규약" 절(git 레포 AND tide 산출물 보유, `.`으로 시작하는 숨김 디렉터리
  제외, 직속 1단계)을 **그대로 재사용**한다 — 여기서 다시 정의하지 않는다.
- **출력 조건**: 발견된 자식 tide 레포가 **2개 이상**이면 출력 **맨 끝에** 한 줄을 advisory로
  덧붙인다 — `여러 자식 tide 레포 N개 감지 — 교차 개요는 /tide:fleet`(N=발견 수). **2개
  미만(0·1개, 단일 레포 세션 포함)이면 아무 것도 덧붙이지 않는다**(소음 0).
- **불변(읽기 전용·advisory)**: 힌트는 **읽기 전용·advisory**다 — status는 종전대로 완전 읽기
  전용(파일·git·phase 무변경)이고, kickoff는 골격 생성 외 동작 불변이며, 힌트가 fleet/cycle을
  **자동 실행하지 않는다**. fleet 입구를 한 줄로 가리킬 뿐 사용자의 호출을 강제하지 않는다.
- **status·kickoff 공통**: 이 규약이 두 스킬의 단일 원본이며, 트리거·출력 조건·불변은 양쪽에
  동일하게 적용된다. 자식 tide 레포 2개 미만인 모든 세션(단일 레포 포함)에서 두 스킬 출력은
  현행과 바이트 동일하다(순수 가산·하위 호환).

### advisory 계획 규칙

각 자식 레포의 **사이클 위치(position)**를 `/tide:status`의 다음 커맨드 판단 규칙을 그대로
**재사용**해 정확히 하나로 분류한다. 이 절이 분류 taxonomy·교차 요약·advisory 인자의 **단일
원본**이며, fleet 스킬은 이를 인용한다(임의로 합산·분리하지 않는다).

- **정규 position 5종과 advisory 다음 커맨드**(각 위치는 인자까지 포함한 정확한 커맨드로 매핑):
  - `milestone 필요`(`docs/milestones/M*.md` 없음) → `/tide:milestone`
  - `impl 진행`(M{N} 있고 `M{N}-impl.md` 없음) → `/tide:impl M{N}`(반드시 마일스톤 번호 포함)
  - `review 대기`(`M{N}-impl.md` 있고 `M{N}-review.md` 없음) → `/tide:review`
  - `보완 필요`(`M{N}-review.md` 판정 "불가") → 보완 후 `/tide:impl M{N}`
  - `release 가능`(`M{N}-review.md` 판정 "가능") → `/tide:release v{추천}`
- **교차 요약은 이 5 position을 1:1로 집계한다**(합산·분리 금지). 고정 형식:
  `release 가능 N / review 대기 N / impl 진행 N / milestone 필요 N / 보완 필요 N`
  (해당 0건 버킷도 0으로 명시한다).
- **권장 처리 순서**: 위 "의존성 인식 순서 규칙"의 위상정렬 결과를 번호/화살표 목록으로 제시하고,
  각 레포의 의존 대상을 표기한다(예: `1) svc-auth  2) svc-orders(→auth)  3) svc-gateway(→auth)`).
  순환·미선언으로 폴백하면 그 사유를 한 줄로 덧붙인다. 레포별 표 + 교차 요약(5버킷)은 그대로
  유지하고 이 순서를 새 항목으로 더한다.
- **의존성 인식**(`.tide/deps` 선언 시 위상정렬, 순환·미선언은 폴백) — `.tide/deps`를 선언한
  레포들의 의존 그래프로 순서를 산출하고, 순환·미선언·미존재명은 위 규칙대로 폴백·무시한다.
  선언이 전혀 없으면 종전처럼 각 레포의 상태로만 순서를 산출한다(옵트인·하위 호환).

### 교차 사이클 자동화

3층(`/tide:fleet-cycle`)의 **단일 원본**이다. `/tide:fleet-cycle` 스킬·실증이 이를 인용한다.
fleet이 **읽기 전용 개요**(발견·순서·계약을 보기만)라면, fleet-cycle은 **그 순서대로
milestone→review를 자동 실행**하는 행위 커맨드다 — release는 제외(아래 불변).

- **대상·발견·순서**: 대상 부모(기본 = 세션 cwd, 선택 인자로 경로)의 자식 tide 레포를
  위 "발견 규약"으로 발견(직속 1단계·git·tide 산출물·숨김 무시)하고, `.tide/deps` 위상정렬
  (위 "의존성 인식 순서 규칙")로 **처리 순서**(피의존 먼저)를 정한다. 순환이면 보고 + 상태
  기반 순서로 폴백, 미선언 레포는 독립 노드.
- **레포별 실행(앵커)**: 처리 순서대로 각 레포를 **그 레포 루트에 앵커**(위 "멀티 레포 /
  대상 레포"의 cwd 규율)해 `/tide:cycle` 의미를 실행한다 — 즉 그 레포의 보고서 상태로
  시작점을 정해(impl 보고서 없음→impl부터, 있고 review 없음→review부터, 둘 다 있음→새
  milestone) `milestone → impl → review`를 잇는다. 산출물·`.tide/phase`·테스트·서브에이전트는
  그 레포 루트 기준(레포별 격리). **release는 실행하지 않는다**(아래 불변).
  - **리뷰 검증 규율 전이 상속**: 각 레포의 review 단계는 `/tide:review` 규칙을 그대로 돌리므로
    **반증 시도(refutation)·in-review 재검증·판정 계측이 레포마다 적용된다**(위 "리뷰 검증 규율" 절).
    즉 처리 대상 N개 레포면 반증 패스도 N번 돈다 — 비용은 레포 수에 비례하며, 생략하지 않는다
    (규모가 크면 깊이를 줄이되 건너뛰지 않는다는 규모 비례 규율이 그대로 적용된다).
- **release 제외(불변)**: fleet-cycle은 **milestone→review까지만** 자동화한다 — 어떤 레포에서도
  `release`를 실행하지 않고 **어떤 레포의 `.tide/phase`도 `release`로 쓰지 않으며**, git
  commit/tag/push·cross-repo git을 자동 실행하지 않는다(위 "부수효과 분리 불변" 절). release는
  아래 핸드오프로 넘긴다 — 순서·핸드오프는 **제안**이며 시점·실행은 사용자가 판단한다.
- **사전 점검(필수)**: 처리 시작 전 각 자식 레포의 `.tide/phase`를 읽어, **`release`로 남아 있는
  레포(이전 중단된 수동 release의 잔재)는 처리에서 제외하고 경고**한다 — 그 레포는 가드가 풀린
  상태라 사이클을 돌리지 않는다(수동 정리: 그 레포 phase를 idle로). 이로써 백스톱이 풀린 채
  도는 경로를 막는다.
- **계약 인식(M17)**: 레포 X가 의존 Y에 `>= 버전` 계약을 두고 Y가 **upstream-behind**(위
  "계약 비교 규칙")면, X의 사이클은 돌리되 release 핸드오프에서 X를 **"contract-blocked:
  Y를 먼저 release/upgrade 필요"**로 표기한다(X를 release-ready로 단정하지 않는다).
- **실패·중단 처리**: 한 레포의 사이클이 중단되면(전제조건 미충족·테스트 실패·review 판정
  "불가") 그 레포를 **"중단"으로 기록**하고, 위상정렬상 **그 레포에 의존하는 downstream
  레포는 건너뛴다**(upstream 미완 → downstream 처리 보류, 사유 기록). 그와 무관한 독립 레포는
  계속 진행한다(전체 중단이 아니라 부분 진행 + 명확한 보고). 각 레포 사이클 자체의 중단
  처리는 `/tide:cycle` 규칙을 그대로 따른다.
- **출력(집계)**: ① **처리 순서 표** — 레포명 | 시작 단계 | 도달 단계 | review 판정/추천
  버전 | 비고(중단·skip·contract-blocked). ② **의존성 순서 release 핸드오프** — review "가능"인
  레포를 위상정렬 순서로 `1) /tide:release vX.Y.Z (repo)` 나열하되, contract-blocked·중단·
  downstream-skip은 사유와 함께 보류로 표기한다. release는 사용자 몫임을 명시한다.
- **발견 0 강등**: 자식 tide 레포를 못 찾으면 단일 레포로 graceful 강등한다(현재 레포
  `/tide:cycle` 권유) — 단일 레포·미선언 동작 불변(옵트인 가산).

### 통합 검증

4층(`/tide:fleet-verify`)의 **단일 원본**이다. `/tide:fleet-verify` 스킬·실증이 이를 인용한다. 자식 레포가
각자 사이클을 통과해도 "각 서비스가 각자 통과"와 "서비스들이 **함께** 동작"은 다르다 —
fleet-verify는 release 전에 레포를 가로지르는 통합을 프로젝트 정의 훅으로 한 번 검증한다.
**verification-only**(git·release 없음, 아래 불변).

**통합 훅 (`.tide-fleet/integration`, 옵트인·parent-level)** — 레포 간 통합 검증 명령의 단일
원본이다.

- **위치·형식**: 대상 부모(기본 = 세션 cwd, 선택 인자로 경로)의 `.tide-fleet/integration` 파일.
  내용은 통합 검증으로 실행할 **명령(들)**(셸 명령 한 줄 이상, 빈 줄·`#`로 시작하는 주석 무시,
  선두 UTF-8 BOM 제거). **부모 cwd에서 실행**한다(예: `docker compose up -d && npm run
  integration-test`).
- **parent-level(설계 결정)**: 의존 선언(`.tide/deps`)은 레포별(탈중앙, 각 레포가 자기 의존을
  선언)이지만, **통합은 단일 레포가 소유하지 않는 cross-repo 개념**(어느 한 레포의 통합이 아니라
  fleet 전체의 통합)이므로 훅은 **대상 부모 레벨**에 둔다.
- **옵트인·하위 호환**: 파일이 없거나 유효 줄이 0이면 **통합 훅 미선언** — fleet-verify는
  "통합 훅 미선언, 검증 생략"을 안내하고 graceful 종료한다. 단일 레포·미선언 동작은 현행 그대로.
- **발견 무시**: `.tide-fleet/`는 **숨김(dot) 디렉터리**라 fleet 발견(직속·git·tide 산출물·숨김
  무시, 위 "발견 규약")에서 자식 레포로 잡히지 않는다 — 1~3층과 충돌하지 않는다.

**`/tide:fleet-verify` — 통합 검증 실행**

- **발견·대상**: fleet 규약으로 자식 tide 레포를 발견(직속 1단계·git·tide 산출물·숨김 무시)해
  통합 대상 레포 목록을 보고한다. 발견 0이면 단일 레포로 graceful 강등(현재 레포 `/tide:status`
  권유).
- **git-verb 가드라일(advisory)**: 통합 훅을 **실행하기 전에** 훅 명령(들)에 git
  commit/tag/push·release로 보이는 토큰이 있는지 점검해, 있으면 **경고**한다(예:
  `⚠ 통합 훅에 git/release로 보이는 토큰 — fleet-verify는 verification-only`). 훅 실행을 강제
  차단하진 않는다 — 검증 훅에 git이 합법적으로 필요한 변형이 있을 수 있어(major-safe), 사용자가
  cross-repo git 누수를 인지하도록 알릴 뿐이다(M19 적대 검증이 짚은 훅 공격 표면을 advisory로 좁힘).
- **실행·보고**: 통합 훅을 **부모 cwd에서 실행**하고 결과를 보고한다 — **exit 0 = 통합 pass**,
  비0 = **통합 fail**(실패 출력 요약 + 관련 레포). 훅 미선언이면 검증 생략 안내.
- **verification-only(불변)**: fleet-verify는 git commit/tag/push·release·cross-repo git을 하지
  않고 **어떤 레포의 `.tide/phase`도 `release`로 쓰지 않는다**(위 "부수효과 분리 불변" 절). 통합
  훅도 검증/테스트 명령이어야 한다(git·release 금지 — 훅 작성자 책임). 단, **훅이 자식 레포에서
  git을 시도하고 그 자식이 stale phase=release**(중단된 수동 release 잔재)면 백스톱이 풀릴 수
  있으므로, 훅에 **cross-repo git을 두지 않으며** 의심 시 처리 전 자식 phase의 release 잔재를
  점검·정리한다(위 사전 점검과 같은 취지).
- **출력**: ① 통합 대상 레포 목록(발견), ② 통합 훅 명령(요약), ③ **통합 결과**(pass/fail + 실패
  시 요약), ④ 다음 안내(pass면 "이제 release 핸드오프 순서대로 수동 `/tide:release`", fail이면
  "통합 수정 후 재검증").

**fleet-cycle ↔ fleet-verify 흐름**

- 권장 순서: **`/tide:fleet-cycle`**(각 레포 milestone→review 의존성 순서 자동) →
  **`/tide:fleet-verify`**(통합 검증) → 통합 pass면 fleet-cycle의 release 핸드오프 순서대로
  **수동 `/tide:release`**.
- fleet-cycle은 통합을 자동 실행하지 않는다 — release 핸드오프 출력에 "release 전
  `/tide:fleet-verify`로 통합 확인(통합 훅 선언 시)" 안내만 두고, fleet-verify가 별도 명시 호출이다.

## 템플릿

- 각 스킬 디렉터리에 동봉된 `template.md`가 마일스톤·보고서 **형식의 단일 원본**이다:
  `skills/milestone/template.md` / `skills/impl/template.md` / `skills/review/template.md`
- milestone/impl/review 스킬은 `${CLAUDE_SKILL_DIR}/template.md`를 읽어 그 구조 그대로
  문서를 생성한다. 템플릿을 읽을 수 없으면 스킬에 내장된 한 줄 폴백(섹션 목록)으로
  동작한다.
- 형식을 바꾸려면 템플릿 파일을 수정한다 — 스킬·규약 문서의 산문을 고치는 것이 아니라.

## 전제조건 · 프리플라이트

| 커맨드 | 시작 전 검사 | 실패 시 |
|---|---|---|
| `/tide:impl` | 대상 마일스톤 문서 존재 | 구현 없이 `/tide:milestone` 안내 후 중단 |
| `/tide:review` | `docs/reports/M{N}-impl.md` 존재 | 리뷰 없이 `/tide:impl` 안내 후 중단 |
| `/tide:release` | ① 판정 근거 보고서(review 또는 debug)의 판정 "가능" ② 테스트 통과 ③ 워킹트리 확인 | git 작업 없이 사유 보고 후 중단 |

release 1번 검사의 판정 근거는 리뷰 보고서 또는 debug 보고서다(선택 규칙·열린 세션 차단·하위
호환은 아래 "debug 세션" 절이 단일 원본). 이 검사는 사용자가 버전 인자와 함께 강행 의사를 명시한
경우에만 경고 후 통과할 수 있다.

## 릴리즈 커버리지 체크

`/tide:release` 프리플라이트가 **이번 태그에 실릴 실질 파일 중 어떤 미릴리즈 보고서도 설명하지 않는
것**을 드러내는 **advisory 검사**의 단일 원본이다 — release 스킬은 절차에서 이 절을 참조한다(스킬은
절차, 규약은 conventions — 기존 분담과 동일). 태그는 트리 전체를 담으므로 tide를 거치지 않은 변경도
**배포엔 실리나** 판정 근거·CHANGELOG는 미릴리즈 보고서의 합집합만 보므로 **미검토·미기록으로
편승**할 수 있다 — 이 검사는 그 편승을 **릴리즈 시점에** 노출한다. 편승 경로는 둘이다: tide 밖에서
**따로 커밋된 것**과, release 자신의 스테이징에 쓸려 들어가는 **미커밋 변경**. 아래 범위는 그 둘을
모두 덮는다(하나만 덮으면 목적을 사실보다 넓게 주장하는 것이 된다 — 아래 "차단 등급 판례"의
`vacuous-pass`).

- **대상 범위 = 태그에 실릴 집합**: 이 검사의 범위는 "이미 커밋된 것"이 아니라 **이번 태그의 트리에
  실릴 것**이다. 둘의 합집합으로 모은다.
  - ⑴ **커밋 편승**: 마지막 릴리즈 태그를 찾아(`git tag` 읽기 — 아래 "debug 세션" 절의 릴리즈 경로
    항목이 정한 태그-트리 포함 기준을 **재사용**, 새 기준을 만들지 않는다) `git diff --name-only
    <태그>..HEAD`로 변경 파일을 모은다. **태그가 하나도 없으면(첫 릴리즈)** HEAD 트리의 커밋된 추적
    파일 전체를 같은 판정에 넣는다 — 브라운필드 첫 릴리즈에서는 tide 이전 코드가 어느 보고서에도
    없어 **대량 미상**으로 뜰 수 있으나, 이는 첫 릴리즈 1회성 특성이다(advisory·비차단이라 수용 —
    사용자가 훑고 넘긴다).
  - ⑵ **미커밋 편승**: `git status --porcelain`이 보고하는 **미커밋 변경**(추적 파일의 수정·삭제 +
    미추적 파일)을 함께 모은다. **근거 — release는 프리플라이트를 통과한 *뒤에* 스테이징·커밋하므로,
    검사 시점에 미커밋인 것도 그대로 태그 트리에 실린다.** 이 명령은 `.gitignore`를 존중하므로
    `.tide/phase`·`.tide/debug-session` 같은 로컬 상태 파일은 **자동으로 빠진다**(별도 제외 규칙을
    새로 만들지 않는다 — 아래 bookkeeping 제외는 종전 그대로 적용).
    - **경로 추출 규칙**: porcelain 출력은 `XY <경로>` 한 형태가 아니다. ⓐ **이름 변경·복사**(`R`·`C`)는
      `old -> new`로 나오므로 **화살표 오른쪽(새 경로)만** 취한다 — 줄 전체를 경로로 쓰면 존재하지
      않는 경로가 미상으로 오경고된다. ⓑ **삭제**(`D`)는 **범위에 남긴다**: 파일은 안 실려도 그
      **삭제가** 태그에 실리므로 설명되지 않은 삭제도 편승이다. ⓒ 공백·비ASCII가 든 경로는 큰따옴표로
      감싸여 나오므로 **따옴표를 벗긴다**(또는 `-z`로 받아 NUL로 가른다). 이 규칙은 프롬프트 규율이라
      하니스가 집행하지 않는다 — 규약에 적는 것이 유일한 집행 수단이다.
  - **왜 ⑵가 필요한가(정직 고지)**: 이 절이 ⑴만 보던 동안 **정상 tide 사이클에서 범위는 사실상 항상
    공집합**이었다 — impl·review는 커밋하지 않고 release가 커밋하므로, 프리플라이트 시점의 HEAD는
    직전 릴리즈 상태 그대로이기 때문이다. 즉 검사는 "tide 밖에서 **따로 커밋된 것**"만 볼 수 있었고,
    정작 release 자신이 스테이징으로 태그에 싣는 경로는 보지 못했다. 외부 프로젝트 실측에서 그 경로로
    편집기 임시 파일이 실제로 태그에 실렸고(되돌린 주체는 이 검사가 아니라 `git status`를 읽은
    사람이었다), 그것이 이 정정의 출처다(M39).
- **bookkeeping 제외**: `docs/reports/*`·`docs/milestones/*`·`CHANGELOG.md`·버전 파일·`.tide/*`는
  tide 자체 산출물이라 커버리지 대상에서 뺀다(자기 자신으로 경고를 만들지 않게).
- **커버 판정(휴리스틱)**: 남은 실질 변경 파일 각각이 **미릴리즈 보고서 전부**(대상 마일스톤의
  `M{N}-impl.md`·`M{N}-review.md` + 미릴리즈인 모든 `debug-{N}.md`)의 본문(특히 변경 파일 요약)에
  **경로로 언급되는지** 확인한다. 어느 보고서에도 언급이 없는 파일 = **커버리지 미상**.
  - **커버리지 근거 집합 ≠ 판정 근거 집합**: 릴리즈 *판정*(가능/불가)의 근거는 판정 섹션을 가진
    review·debug 보고서뿐이지만(아래 "debug 세션" 절의 릴리즈 경로 항목), 변경을 *설명*하는 1차 문서는
    `변경 파일 요약` 표를 담는 **impl 보고서**다. 커버리지는 "이 변경이 어떤 보고서에든 기록됐는가"를
    보므로 **impl 보고서를 포함**한다 — 포함하지 않으면 정상 사이클의 impl 변경이 매번 '미상'으로
    오경고돼 검사가 정상 경로에서 소음이 된다.
- **경고(차단 아님)**: 미상 파일이 있으면 한 블록으로 advisory 경고를 낸다 — 예:
  `⚠ 커버리지 미상: {태그} 이후 변경됐으나 어떤 미릴리즈 보고서에도 없는 파일 N개 — 태그엔 실리나
  리뷰·CHANGELOG에서 누락될 수 있음: {목록}`. **release를 차단하지 않는다**(프리플라이트 ①②③ 게이트와
  별개의 순수 advisory) — 사용자가 강행/보완을 판단한다.
- **불변**: git **읽기만** 사용하므로 phase와 무관하게 통과한다(`git tag`·`git diff --name-only`·
  `git status --porcelain` 셋 다 읽기 — 가드 무수정·새 기준 없음). 매칭은 경로
  부분일치 **휴리스틱**이라 위양성(보고서가 파일을 안 적었을 뿐)·위음성 여지를 수용한다 — 정밀
  게이트가 아니라 "편승 변경을 드러냄"이 목적이다(fleet-verify의 git-verb 가드라일과 동형 — advisory·
  비차단). 실제 발화 정확성은 프롬프트 규율이므로, 하니스는 **선언 정합만** 집행하고(아래 "규약↔실행
  동기화" — `tests/discover` Part D) 발화 자체는 라이브 도그푸딩 영역이다.
- **하위 호환(소음 0의 근거가 바뀌었다)**: 범위 ⑵가 생기면서 정상 사이클의 **미커밋 impl 산출물이
  이제 범위에 들어온다** — 그러나 그것들은 impl 보고서 본문에 경로로 언급되므로 **커버 판정을 통과해
  경고가 없다**(소음 0 유지). 즉 소음 0은 "범위가 비어서"가 아니라 "커버돼서" 성립한다 — 정정 전에는
  전자였고, 그래서 검사가 정상 경로에서 아무것도 보지 못했다. 반대로 어느 보고서에도 없는 미추적
  파일(편집기 임시 파일·스크래치 산출물 등)은 이제 **경고에 뜬다** — 그것이 이 검사의 목적이며,
  종전대로 **advisory·비차단**이라 릴리즈를 막지 않는다. 기존 프리플라이트 게이트(판정·테스트·
  워킹트리·사이트 용어)의 순서·판정 로직은 불변이고, 이 검사는 그 뒤에 붙는 **게이트 아닌 advisory
  단계**다(중단시키지 않음).

## 마일스톤 문서

- 위치: `docs/milestones/M{N}.md` (가장 큰 번호 + 1, 없으면 M1)
- 필수 섹션 7개: **목표 / 배경 / 태스크 목록 / 태스크 상세 / 파일 변경 요약 / 완료 기준 / 메타데이터**
- 태스크 ID: `M{N}-T01`, `M{N}-T02` …
- 태스크는 한 번에 끝낼 수 있는 크기로 분해하고, 가능한 한 서로 독립적으로 설계
  (특히 **변경 파일이 겹치지 않게** — 독립 태스크는 병렬 디스패치되므로 파일 비중첩이
  병렬 안전과 직결된다. 겹치면 그 부분만 순차 폴백)
- 선행 의존이 있으면 태스크 끝에 `(deps: M{N}-T01, …)` 로 표기
- `/tide:impl M{N}` 처럼 번호를 지정해 특정 마일스톤을 재실행·이어하기 할 수 있다
- **번호 사전경고(브랜치 간 충돌 예방 — advisory·읽기 전용)**: `/tide:milestone`은 다음 번호 `M{N}`을
  정한 **직후, `M{N}.md`를 만들기 전에** `git log --all --diff-filter=A -- "docs/milestones/M{N}.md"`로
  그 번호가 **다른 ref에 이미 도입됐는지** 확인한다(git 읽기 — 가드 통과). 있으면 그 ref를 밝혀 한 줄로
  advisory 경고를 낸다 — 예: `⚠ M{N}이 이미 다른 ref({branch})에 도입됨 — 병렬 브랜치 번호 충돌 가능
  (머지 시 파일·본문·CHANGELOG 재할당 캐스케이드). 조정 후 진행하거나 다음 번호를 쓸 것`. **경고는
  번호를 자동 변경하지 않는다**(놀라운 재할당 금지 — 사용자 판단). 원격 브랜치를 보려면 **최신 fetch가
  전제**임을 함께 알린다. 번호가 파일명에 박혀 있어 경로 충돌 자체는 git이 머지에서 이미 막지만, 이
  사전경고는 **재할당 캐스케이드를 파일 생성 전에** 예방한다. 충돌이 없으면 경고가 없어 단일 레포·단일
  브랜치 통상 출력은 현행과 동일하다(소음 0).

### 변경 파일 요약 기준선

보고서의 `변경 파일 요약`(과 마일스톤 문서의 `파일 변경 요약`)이 쓰는 추가/수정/삭제의 **기준선
단일 원본**이다 — `skills/{milestone,impl,debug}/template.md` 세 템플릿이 이 규약을 따른다.

- **기준선 = 해당 단계·세션이 시작될 때의 워킹트리**다. 추가/수정/삭제는 **그 트리 대비 이 단계가
  한 행위**를 뜻한다 — git `HEAD`나 마지막 릴리즈 태그 대비가 **아니다**. 보고서는 *이 단계가 무엇을
  했는가*의 기록이므로, 이미 트리에 있던 파일을 고쳤으면 git 이력과 무관하게 **수정**이다.
- **어긋남 고지(필수)**: 기준선 트리에 **미커밋 산출물이 섞여 있으면**(직전 단계가 만든 파일이 아직
  커밋되지 않은 경우) 표 아래에 **한 줄**로 그 사실과 원인을 적는다. 예 — "기준선 = 세션 시작
  워킹트리. `a.ts`·`b.ts`는 직전 M9 impl의 미커밋 산출물이라 git 기준으로는 신규 파일이다."
- **debug에서는 이것이 기본 경로다**: 부수효과 분리(커밋은 release에서만) 때문에 debug 세션은 거의
  항상 **미커밋 산출물 위에 얹힌다**. 고지가 없으면 독자가 보고서와 git을 손으로 대조해야 한다
  (근거: `/tide:debug` 첫 라이브 도그푸딩에서 실제로 발생 — 세션이 "수정"으로 적은 세 파일이 git
  기준으로는 전부 신규였고, 보고서가 어긋남을 설명하는 문단을 따로 써야 했다).
- **재실행·이어하기에서는 최초 착수 시점을 유지한다**: 보고서는 갱신형(누적 — 위 "동일 마일스톤
  재실행 시 기존 보고서를 갱신한다")이므로, `/tide:impl M{N}` 재실행처럼 같은 단계를 다시 돌릴 때
  기준선을 **재실행 시점으로 다시 잡지 않는다** — 그러면 앞선 실행이 고친 파일이 표에서 증발한다.
  debug는 **세션이 단위**라 `.tide/debug-session`이 열려 있는 동안 기준선이 자연히 고정된다
  (이어가기가 기준선을 바꾸지 않는다).
- 릴리즈가 담는 범위는 이 기준선과 **무관**하다 — 그것은 **미릴리즈 보고서 전부의 합집합**이다
  (아래 "debug 세션" 절의 릴리즈 경로 항목이 단일 원본. 여기서 재정의하지 않는다).

### 정오표 (errata)

릴리즈된 보고서가 사실과 어긋난 채 남지 않게 하되 **증거를 지우지 않는** 경로다 — impl·review·debug
보고서 **모두**에 적용된다.

- **릴리즈된 보고서의 본문은 소급 수정하지 않는다.** 그 시점의 판정으로 이미 태그가 나갔으므로
  본문은 "그때 무엇을 알았고 무엇을 근거로 릴리즈했는가"의 증거다.
  - **적용 범위 = 사실 오류 정정**이다. 릴리즈된 마일스톤을 `/tide:impl M{N}`으로 **재실행**해 새
    작업을 한 경우는 정정이 아니라 **새 산출물**이므로, 위 "보고서" 절대로 기존 보고서를 갱신한다
    (갱신했다는 사실을 개요에 남긴다). 이 규칙이 재실행 경로를 막지 않는다.
- 사실 오류가 발견되면 그 보고서 **말미에 `## 정오표` 섹션을 append**한다(본문 무수정). 항목마다
  **날짜 / 무엇이 틀렸는지(본문 위치) / 실제 사실 / 확인 근거**를 적는다. **정오표 자체도
  append-only**다 — 기존 정오표 항목을 고치지 않는다.
- **미릴리즈 보고서는 본문을 직접 고친다** — 아직 배포되지 않았으므로 정오표를 쓸 이유가 없다.
- **릴리즈 여부 판정은 기존 기준을 그대로 쓴다**: 보고서 파일이 마지막 릴리즈 태그의 트리에 이미
  포함돼 있으면 릴리즈된 것이다(아래 "debug 세션" 절의 릴리즈 경로 항목이 정한 결정적 기준이 단일 원본 —
  **새 기준을 만들지 않는다**). git **읽기**로 판단하며 가드는 phase와 무관하게 읽기를 통과시킨다.
- **누가**: 오류를 발견한 세션(주로 `/tide:debug`, 또는 `/tide:review`)이 append하고, **그 사실을
  자기 보고서에도 한 줄 남긴다**(무엇을 정정했는지 추적). 정오표 append는 debug의 금지에 걸리지
  않는다 — debug가 만들거나 고치지 않는 것은 **마일스톤 문서**·버전 파일·`CHANGELOG.md`이지
  보고서가 아니다.
- **판정·릴리즈 경로 불변**: 정오표는 그 보고서의 `## 릴리즈 판정`을 **바꾸지 않는다**(이미 소진된
  판정이다). 이미 릴리즈된 보고서는 release 근거 집합에 다시 들어가지 않으므로(아래 릴리즈 경로 절)
  정오표 append는 프리플라이트에 아무 영향이 없다.

## 리뷰 검증 규율

`/tide:review`가 판정을 **만들어내는 절차**의 단일 원본이다 — 리뷰 스킬·리뷰 템플릿·impl 스킬·
impl 템플릿·`/tide:cycle`이 이 절을 인용하고 재정의하지 않는다(스킬은 절차, 규약은 conventions —
기존 분담과 동일).

근거: M1~M31 리뷰 판정이 **31/31 "가능"**이었고 통산 차단 이슈는 1건(M1)뿐이다. 리뷰어가 결함을
스스로 고치고 스스로 판정하는 구조(판정자 = 실행자)에서는 `불가`가 구조적으로 나오지 않아,
프리플라이트 게이트 ①(판정 "가능")이 **항상 참인 조건**이 된다. 아래 다섯은 판정을 다시 신호로
만들되 **보고서 섹션 구조·판정 파싱·tide-guard·프리플라이트 게이트는 건드리지 않는** 절차 가산이다.

### 반증 시도 (refutation) — 판정 전 독립 패스

- **발동**: `/tide:review`는 판정을 내리기 **직전**, 자기 판정 후보를 **반박하는** 패스를 한 번 거친다.
  모든 리뷰의 **기본 경로**다 — 회고(M18·M19·M20·M28)가 "계약·안전 사이클"에 한정해 재량으로 써 온
  적대 검증을, 그린 테스트가 못 잡는 결함을 실제로 적발해 온 실적을 근거로 승격한 것이다.
- **독립성 규율**: Agent 도구가 가능하면 **서브에이전트로 디스패치**하고, 전달하는 것은 **판정 후보와
  그 근거뿐**이다 — 리뷰의 추론 과정을 요약해 넘기지 않는다(같은 결론을 되풀이시키면 독립성이 사라진다).
  서브에이전트는 마일스톤 문서·impl 보고서·실제 변경 파일·검증 결과를 **직접 읽어** "이 판정이 틀렸다면
  어디서 틀렸는가"를 독립적으로 답한다. 전달 계약(대상 레포 루트·부수효과 분리 상속)은 impl "병렬
  디스패치"와 동형이며, 서브에이전트도 phase=`review`라 가드가 백스톱으로 받친다.
- **읽기 전용(필수)**: 반증 패스는 **아무것도 고치지 않는다** — 파일 수정·생성·삭제 없이 성립한 지적을
  **목록으로 돌려주고**, 수정은 메인 리뷰어가 한다(git 금지는 물론이다). 반증자가 스스로 고치면 ①
  리뷰어가 검증하지 않은 변경이 트리에 들어가고 ② 계측의 `in-review 수정` 건수가 실제와 어긋나며
  ③ **반증자가 자기 발견을 스스로 닫아** 이 절이 고치려는 판정자=실행자 구조가 반증 패스 안에서
  재현된다. impl 서브에이전트에 "코드·테스트만 남겨라"를 못박는 것과 **대칭**으로, 반증 서브에이전트에는
  "아무것도 남기지 마라"를 못박는다.
- **폴백**: Agent 도구를 쓸 수 없으면 메인이 반증 패스를 **명시 절차로** 수행하고(판정 후보를 적어 놓고
  그것을 공격하는 항목을 따로 나열), **폴백 사실을 보고서에 기록**한다 — 조용히 생략하지 않는다
  (impl 병렬 폴백과 동형).
- **규모 비례(생략 아님)**: 변경이 작으면 반증 패스의 **깊이는 줄일 수 있으나 생략하지 않는다** —
  "이번엔 사소하니 건너뛴다"는 규율 이탈이다. 예외 경로를 두면 31사이클 동안 판정을 의례로 만든 바로 그
  침식이 다시 시작된다(가드에 "급할 땐 commit 허용"을 두지 않는 것과 같은 이유).
- **결과 반영**: 반증이 성립한 지적은 비판점(차단/권장/사소)에 편입하고 판정을 재산정한다. **성립 0건도
  유효한 결과**이며 그대로 판정한다 — 판정을 뒤집어야 성공인 패스가 아니라, 시도했다는 사실과 결과가
  기록되는 것이 목적이다.

### in-review 수정 후 재검증 (re-verify)

- 리뷰가 in-review 수정을 **1건이라도** 했으면 수정 후 **프로젝트 검증(테스트·하니스)을 재실행**하고 그
  결과를 `## 검증`에 적은 뒤에만 판정한다. 수정 0건이면 이 요구는 발동하지 않는다(소음 0).
- 재실행이 환경상 불가능하면 **"미검증 잔여 리스크"로 명시**한다 — 템플릿이 권해 온 솔직 명시를
  **조건부 의무**로 올린 것이다.

### 판정 계측

- `## 릴리즈 판정` 섹션의 판정 줄 아래에 계측 한 줄을 **필수**로 둔다. 고정 형식:
  `계측: in-review 수정 차단 {n}/권장 {n}/사소 {n} · 반증 시도 {수행|폴백} 성립 {n}건 · 재작업 라운드(rework) {n}`
- 목적은 `가능`의 의미 구분(**처음부터 깨끗** vs **고쳐서 깨끗**)과 추이 관측이다 — 구분이 없으면
  판정 인플레가 측정되지 않는다.
- **파싱 불변**: 계측 줄은 `## 릴리즈 판정` 섹션 **안**에 들어가며 판정 표기(`**가능**`/`**불가**`)와
  `추천 버전`의 형식·위치를 바꾸지 않는다 — release 프리플라이트·`/tide:status`·fleet 계열의 판정 읽기는
  현행 그대로 동작한다. **debug 보고서 형식은 건드리지 않는다** — 계측은 review 전용 가산이고, "두 보고서를
  같은 방식으로 읽는다"는 계약(위 "debug 세션")은 판정 표기·추천 버전에 걸린 것이라 그대로 성립한다.

### 재작업 라운드 (rework) 와 수렴 조건

- **정의**: 같은 마일스톤 `M{N}`에서 리뷰 판정 `불가` 이후 impl을 재실행한 횟수. 최초 impl→review는
  **라운드 0**이다.
- **기록**: impl 보고서 개요와 리뷰 보고서 계측 줄에 같은 값을 적으며 **개요가 단일 출처**다. 증가는
  **판정 `불가` 이후의 재실행에서만** 일어난다 — 그때 값은 **직전 impl 보고서에 적힌 값 + 1**이고,
  `불가`가 아닌 재실행(이어하기·부분 보완)은 **값을 올리지 않고 그대로 승계**한다(그러지 않으면
  이어하기마다 라운드가 올라 수렴 조건이 오발동한다). 값이 없는 기존 보고서(M1~M31)는 **0으로 본다** —
  하위 호환이며 소급 갱신하지 않는다(릴리즈된 보고서 본문 불변 — 위 "정오표 (errata)" 절과 정합).
- **수렴 조건(advisory·비차단)**: 라운드가 **2를 초과하면**(3회차 재작업) 리뷰는 판정과 **별개로**
  `다음 단계`에 **마일스톤 재분해(`/tide:milestone`) 권고**를 한 줄 적는다. 같은 마일스톤을 세 번째로
  다시 구현하고 있다면 문제는 구현이 아니라 분해일 가능성이 높다는 신호다.
- **자동 중단·자동 재분해는 하지 않는다** — 권고만 하고 판단은 사용자 몫이다(마일스톤 번호 사전경고가
  번호를 자동 변경하지 않는 것, fleet이 advisory만 하는 것과 동형).

### 차단 등급 판례

무엇이 **차단**인지를 새 루브릭이 아니라 **이미 내려진 판정**으로 고정한다. 위 넷이 판정을 만드는
**절차**를 다룬다면 이 소절은 **등급 판단의 근거**를 다룬다 — 판정 밸브만 조이면 압력이 등급 밸브로
옮겨가기 때문이다(M32~M35 리뷰 본문을 독립 재채점하니 4건 중 3건이 아래 기준으로 `불가`였다).

- **판례 부류 `vacuous-pass`**: 가드·검증이 **공허하게 통과**하거나(결함이 있는데 green), 규약·문서가
  **집행력을 사실보다 넓게 주장**하는 것이 확인되면 **차단**이다.
- **판례 3건** — 새 기준을 만드는 것이 아니라 이미 내려진 판정의 명시다:
  - **M34 리뷰 차단 #1** — G1이 옵션형 인용에서 stdin을 소비해 miss=0으로 통과했다.
  - **M32 리뷰 #3** — 재검증 절을 세 파일에서 지워도 45/45 그린이었는데 규약·완료 기준은
    "집행한다"고 적고 있었다.
  - **M33 리뷰 #2** — 케이스 수 대조가 실제로는 한 하니스에서만 도는데 규약은 "각 러너가"라고
    단정했다.
  - 뒤 두 건은 당시 **권장**으로 매겨졌으나 같은 부류이며, 이 판례가 **앞으로의** 기준을 정한다 —
    **과거 판정은 바꾸지 않는다**(위 "정오표 (errata)" 절의 취지. 릴리즈된 판정은 증거다).
- **부인 기록 `precedent-waiver`**: 판례 부류에 해당한다고 보면서 차단으로 매기지 않으면 `다음 단계`에
  **왜 부인하는지**를 한 줄 남긴다. **부인 기록 없는 하향은 규율 이탈이다.** 근거는 이 저장소 자신의
  기록이다 — M33 리뷰 #2는 그것이 M32 #3과 **동형의 결함**임을 본문에 적고도 권장으로 매겼다.
  동형임을 인식한 리뷰어조차 등급을 올리지 않았으므로 루브릭만으로는 막히지 않는다.
- **수정 권한 제한**: 차단 등급 결함은 **리뷰가 고치지 않는다** — 판정 `불가` + impl로 반환한다.
  권장·사소는 종전대로 in-review 수정을 허용한다(위 재검증 요구가 그대로 걸린다). 근거는 위 반증 시도
  절이 반증자에게 "아무것도 고치지 마라"를 못박은 것과 **대칭**이라는 것이다 — 자기 발견을 자기가
  닫으면 판정자=실행자 구조가 그 안에서 재현된다.
- **불변**: 판정 표기(`**가능**`/`**불가**`)·`추천 버전` 형식·계측 줄 형식·프리플라이트 3게이트·
  `.tide/phase`·tide-guard 계약은 바뀌지 않는다. 바뀌는 것은 **누가 무엇을 고칠 수 있는가**와
  **등급 판단의 근거**뿐이다.
- **집행**: 위 넷과 같은 `tests/discover` Part E다 — 위 두 병기어가 **각자 선언된 파일 집합**에 전부
  등장하는지를 대조한다(집합은 토큰마다 다르다 — 정확한 결합은 `tests/discover/README.md`의 Part E
  표가 단일 선언처다). 등급 판단이 런타임에 실제로 판례를 따랐는지는 프롬프트 규율이라 라이브
  도그푸딩 영역이다(Part C·D와 같은 분담).

### 불변 (리뷰 검증 규율)

이 절은 **절차 가산**이다 — 보고서 **섹션 구조**(2.0 stable), `.tide/phase`·tide-guard 계약,
프리플라이트 3게이트의 순서·판정 로직, debug 세션 규약, 커맨드 12종(2.0 stable 11종)은 전부 불변이다.
집행은 `tests/discover` Part E(규약↔스킬↔템플릿 선언 정합)이며, 반증 시도가 런타임에 실제로 디스패치되는지는
프롬프트 규율이라 라이브 도그푸딩 영역이다(Part C·D와 같은 분담).

## debug 세션

발견 우선 작업(`/tide:debug`)의 **단일 원본**이다 — 스킬·프리플라이트·status가 이 절을 따른다.
빌드 후 사용자 테스트에서 나오는 에러는 계획 우선 사이클의 전제(태스크·`deps`·완료 기준을 미리
안다)가 성립하지 않아 마일스톤이 의례가 된다. debug는 그 의례를 걷어내되, tide가 실제로 지키는
두 가지 — **부수효과 분리**(git 쓰기는 release에서만)와 **산출물 추적**(무엇을 왜 고쳤는지가
문서로 남고 CHANGELOG로 간다) — 는 그대로 보존한다.

- **산출물 = 역방향 보고서**: `docs/reports/debug-{N}.md`. 다른 단계는 문서 → 행동이지만 debug는
  **행동 → 문서**다 — 세션 중 발견-수정을 누적하고 닫을 때 보고서 하나를 남긴다. 번호 `{N}`은
  **독립 증가 수열**이다(마일스톤 번호와 무관 — 기존 `debug-*.md`의 최대 번호 + 1, 없으면 1).
  형식의 단일 원본은 `skills/debug/template.md`다(위 "템플릿" 절과 동일 규약).
- **세션 수명(열기 → 누적 → `done`)**:
  - **열기** — `/tide:debug [증상]`이 `.tide/debug-session`에 활성 보고서 번호 N을 기록하고
    `.tide/phase`에 `debug`를 쓴다. 파일이 이미 있으면 그 세션을 **이어간다**(번호 재사용).
  - **누적** — 증상마다 재현 → 진단 → 수정 → 검증을 수행하고 **그 항목이 끝날 때마다 보고서에
    append**한다(세션 종료를 기다려 한꺼번에 쓰지 않는다 — 세션이 길어지면 **파일이 유일하게 믿을
    수 있는 누적 저장소**다). 세션이 중단돼 방치돼도 그때까지의 발견이 파일에 남는 것이 의도된
    동작이다. 못 고친 것·원인만 밝힌 것도 상태(아래 "항목 상태값")를 달아 항목으로 남긴다 —
    "고친 것만 기록"하면 발견 우선 작업의 절반이 증발한다.
  - **`done`** — `/tide:debug done`이 개요·판정을 채워 보고서를 마무리하고, `.tide/debug-session`을
    삭제한 뒤 `.tide/phase`를 `idle`로 되돌린다. **열린 세션이 없으면 보고서를 만들지 않고 안내만
    하고 중단**한다(빈 보고서 방지).
  - 한 테스트 세션의 여러 수정을 **한 보고서·한 patch 릴리즈**로 묶는 것이 세션형의 목적이다.
    대가로 세션이 열린 채 방치되면 `phase=debug` 잔재가 남으므로, `/tide:status`가 열린 세션과
    잔재 phase를 드러내고 `done`을 권한다(status는 읽기 전용 — `.tide/debug-session`을 읽기만 하고
    지우지 않는다).
- **항목 상태값(네 가지)**: 각 항목은 `수정함` / `미해결` / `원인만 규명` / `확인함` **중 하나**를
  단다. 앞의 셋은 발견한 결함의 처리 결과이고, **`확인함`**은 **결함이 아니었거나 실측만 한 항목**
  (검증 기록)이다 — 증상·재현·원인·수정은 "해당 없음"으로 두고 **검증**만 채운다.
  - **`확인함`의 용도 경계**: 발견-수정 세션 중 **그 작업과 같은 맥락에서** 잔여 리스크를 실측한
    경우에만 쓴다(예: 같은 릴리즈 전 테스트에서 리뷰가 "실행 미검증"으로 남긴 항목을 함께 돌려
    닫음). **검증만 하러 debug 세션을 열지는 않는다** — 그것은 `impl`·`review`의 일이며, 허용하면
    debug가 아무거나 담는 자루가 된다.
  - 근거: 첫 라이브 도그푸딩에서 세션이 리뷰의 "실행 미검증" 잔여 리스크를 debug에서 함께 닫았고
    (유용했다), 그것을 담을 상태값이 없어 계약을 벗어났다. 규약이 현실을 담지 못하면 세션이 규약을
    나가고, 나간 것은 추적되지 않는다.
  - 상태값 집합은 이 절 · `skills/debug/SKILL.md` · `skills/debug/template.md` **세 곳**이 함께
    선언하며 `tests/discover`(Part C)가 드리프트를 집행한다.
- **판정 형식 = 리뷰보고서와 동일(계약)**: debug 보고서는 리뷰보고서와 **같은 형식**의 판정을
  쓴다 — `## 릴리즈 판정` 섹션에 **`가능`/`불가`**와 `추천 버전: **vX.Y.Z**`. 형식을 맞추는 이유는
  release 프리플라이트가 두 종류 보고서를 **같은 방식으로 읽게** 하기 위함이다(파서 이중화 방지).
  판정 규칙은 미해결 **차단급** 항목이 없고 검증이 통과하면 **가능**, 아니면 **불가**. 추천 버전
  기본은 **patch**(버그 수정 묶음)이며, 수정 과정에서 관찰 가능한 동작이 더해졌으면 minor를
  제안하되 사유를 적는다.
- **릴리즈 경로(프리플라이트 수용 — 이 절이 단일 원본)**: `/tide:release`의 판정 근거는 **리뷰
  보고서(`docs/reports/M{N}-review.md`)와 debug 보고서(`docs/reports/debug-{N}.md`)** 다(가산 확장 —
  기존 review 경로 불변).
  - **근거 집합 = 미릴리즈인 것 전부**: 대상 마일스톤의 리뷰보고서와 **미릴리즈인 모든 debug
    보고서**를 근거로 삼는다(최신 하나가 아니다 — 세션을 두 번 돌고 한 번에 릴리즈하면 이전 세션의
    수정도 이번 커밋에 함께 실리므로, 최대 번호만 보면 그 판정이 검사 없이 배포된다). **근거가
    여럿이면 전부 "가능"이어야** 진행하고 CHANGELOG에 **모든 출처**를 반영한다 — 하나라도 빠뜨리면
    그 수정이 근거 없이 배포된다.
  - **릴리즈 여부 판정(결정적)**: 보고서 파일이 **마지막 릴리즈 태그의 트리에 이미 포함돼 있으면
    릴리즈된 것**, 아니면 미릴리즈다(`git tag`·`git ls-tree`·`git log` 등 **읽기**로 판단 — 가드는
    phase와 무관하게 읽기를 통과시킨다). 태그가 하나도 없으면(첫 릴리즈) 전부 미릴리즈다. release가
    사이클 산출물을 함께 커밋하므로 "태그에 포함됨 = 그 수정이 배포됨"이 성립한다. `CHANGELOG.md`
    게재 여부는 **보조 확인**일 뿐 판정 기준이 아니다 — 항목은 산문이라 어떤 보고서에서 나왔는지
    기계적으로 되짚을 수 없다.
  - **열린 세션 차단**: `.tide/debug-session`이 존재하면 release는 **중단**하고 `/tide:debug done`을
    먼저 하라고 안내한다(미완결 보고서에는 판정 섹션이 없어 근거가 없다).
  - **하위 호환**: debug 보고서가 하나도 없고 열린 세션도 없으면 **현행과 완전히 동일하게 동작**한다.
- **금지**: debug는 `git commit`·`git tag`·`git push`를 하지 않고(위 "부수효과 분리"), 마일스톤
  문서를 만들거나 고치지 않으며, 버전 파일·`CHANGELOG.md`를 편집하지 않는다(그것은 release의
  일이다). 가드는 phase≠release라 이를 백스톱으로 받치지만 **규율이 1차**다(위 "tide-guard hook").
  **보고서는 금지 대상이 아니다** — 자기 보고서 append는 물론이고, 릴리즈된 다른 보고서에 정오표를
  다는 것도 debug의 정상 행위다(위 "정오표 (errata)" 절).
- **변경 파일 요약 기준선**: 세션 시작 시점의 워킹트리 기준이며, 미커밋 산출물 위에 얹혔으면 표
  아래 한 줄로 고지한다 — debug에서는 이것이 **기본 경로**다(위 "변경 파일 요약 기준선" 절이 단일 원본).

## 프로젝트 컨텍스트 (docs/project-context.md)

- `/tide:kickoff`는 대상 저장소가 신규인지 진행 중인지 판별한다(git 커밋 이력·기존
  산출물·소스 규모 기준).
- **진행 중 프로젝트**로 판별되면 코드베이스를 조사해 `docs/project-context.md`를
  생성한다 — 스택·언어·의존성, 최상위 디렉터리 구조와 역할, 진입점·빌드/테스트 방법,
  핵심 도메인 개념. 불확실한 항목은 "확인 필요"로 표기하고, 구조 파악이 어려우면 최소
  골격만 남긴다.
- **신규(빈) 프로젝트**로 판별되면 이 문서는 생성하지 않고 골격만 세운다.
- `/tide:milestone`·`/tide:impl`은 이 문서가 있으면 먼저 읽어 기존 구조를 파악한 뒤
  작업한다(없으면 평소대로 진행 — 필수 전제조건은 아니다).

## 버전 · CHANGELOG

- 버전 파일은 프로젝트 스택에 맞춤: `Cargo.toml` / `package.json` / `pyproject.toml` 등
- 버전은 SemVer. 리뷰 단계에서 major/minor/patch를 추천한다.
- **`CHANGELOG.md`가 릴리즈 노트의 단일 원본**이다. 릴리즈 노트는 `CHANGELOG.md` 최상단에만
  추가하고, `README.md`의 `## CHANGELOG` 섹션은 `CHANGELOG.md`로 가는 **포인터만** 둔다(노트
  본문을 중복 보관하지 않는다 — 이중 갱신·불일치 방지). 사이트 변경 이력은 이미 `CHANGELOG.md`를
  단일 원본으로 인클루드한다.
- 커밋 메시지: `Release {버전}: {핵심 변경사항 한 줄 요약}`
- **메타 용어 누수 방지**: 사이트에서 제외하기로 한 용어(외부 저장소명 등)는 본문 콘텐츠뿐
  아니라 CHANGELOG·conventions의 **검증을 서술하는 메타 문장**(예: "제외 용어가 누수되지
  않는지 확인한다" 류)에서도 literal로 쓰지 않는다 — 본문이 단일 원본(snippets)으로 사이트
  콘텐츠가 되므로, 메타 문장에 박힌 제외 용어 역시 그대로 사이트에 유입된다. 검증을 서술할
  때는 실제 단어 대신 "제외 용어"·"외부 저장소명" 같은 일반 표현을 쓴다.

### 릴리즈 빌드 출력 검증

release 프리플라이트에서 사이트를 빌드한 **산출물 기준**으로 제외 용어 0건을 확인한다(소스가 아니라
빌드 출력을 스캔) — 누수 회귀를 다음 사이클이 아니라 **release 시점에** 잡는다. **3분담**으로 집행된다:
① release 스킬 프리플라이트의 수기 스캔(사이트 있는 프로젝트 한정), ② CI의 `mkdocs build --strict`
(실제 렌더·nav/link·스니펫 `check_paths` — `deploy-pages.yml`), ③ 로컬 결정적 가드
`tests/site-includes`(mkdocs 없이 인클루드 타깃 존재·섹션 마커 균형·**마커 구획 본문의 제외 용어
0건**을 정적 검증). ③은 풀빌드의 대체가 아니라 로컬 사각지대를 메우는 프록시이고, 실제 렌더 검증은
②에 남는다.

## 릴리즈 게시 (분리된 조각)

**릴리즈 게시 (gh)** 규약은 `docs/conventions-release.md`로 분리했다 — 규약 문서 집합의 첫 조각이다
(조각 요건·인용 규칙은 아래 "상호참조 무결성" 소절). 이 자리를 제목으로 남기는 이유는 본체만 읽는
독자·목차에서 절이 사라진 것처럼 보이지 않게 하기 위함이다(조각 요건 ③ 포인터).

## 규약 ↔ 실행/인프라 동기화

규약이나 단일 원본(단일 원본화한 문서·인클루드 대상 등)을 **새로 더하거나 바꾸면**, 그것을
강제·반영할 **실행 수단도 같은 사이클에 함께 손본다** — 스킬 프리플라이트, hook, CI 트리거,
빌드 설정 중 해당하는 것. 규약만 적어두고 그것을 집행할 배선을 다음 사이클로 미루지 않는다.

- 근거: 빌드 출력 검증 규약을 정해두고 release 배선이 따라오지 않아 한동안 규약↔실행 간극이
  남았고, 문서를 단일 원본으로 인클루드하기 시작했으나 배포 트리거가 그 루트 파일을 감시하지
  않아 사이트가 낡는 간극이 반복됐다. 둘 다 "규약·원본"과 "그것을 집행하는 실행/인프라"를
  같은 사이클에 묶었다면 생기지 않았을 군집이다.
- 적용 예: 사이트가 인클루드하는 루트 파일을 새로 추가하면 → 그 변경을 빌드·배포로 반영할
  CI 트리거가 그 파일을 누락하지 않는지 같은 사이클에 확인한다. 프리플라이트에 새 검증 규약을
  적으면 → release 스킬 절차에 그 검증 단계를 같은 사이클에 배선한다.
- 이력(사건 기록): 커맨드 카탈로그를 `docs/commands.md` 단일 원본으로 옮기며 드리프트 가드
  `tests/discover` Part B를 같은 사이클에 확장했고(M22), 발견·위상정렬·BOM 제거 참조 구현을
  `tests/lib/{encoding,discover,deps,toposort}.{sh,ps1}` 공유 라이브러리로 모으며 전 하니스가 동일
  PASS 수로 통과함을 확인했으며(M23·M26), 빌드 출력 검증 규약의 **로컬 집행 배선**을
  `tests/site-includes`로 더했고(M26), `pr` 모드 finalize·가드 입력 견고화를 규약에 더하면서 release
  스킬 절차·hook 두 사본·`tests/multi-repo` 회귀를 같은 사이클에 함께 손봤다(M27).
- 회고 아카이브 관례: `docs/reports/retro.md`는 최근 사이클만 두고 과거 섹션은 `retro-archive.md`로
  분리한다(열람·입력 비용 감소). `/tide:retro`는 종전대로 `retro.md`를 **입력에서 제외**하고 새 섹션을
  `retro.md` 최상단에 누적하므로, 분할은 집계에 영향이 없다(behavior-neutral·과거 보존).

## 실행 환경 축

**"우리가 어디서 돌리는가"는 문장 안에 숨을 수 없다.** 검증이 도는 실행 환경에는 여러 **축**이 있고,
각 축의 두 극에서 **같은 코드가 다른 답을 낸다**. 이 절은 그 축들을 **이름을 붙여 선언**하는 단일
원본이며, 축마다 **무엇이 그것을 집행하는가**를 함께 적는다.

근거(실측): M37 한 사이클이 같은 부류로 다섯 라운드를 썼고 결함은 매번 **다른 축**에 있었다 —
언어 의미론 2회, PowerShell 런타임 1회(네 라운드 생존), 워크플로 문법 1회(CI 첫 푸시가 잡 0개 생성),
POSIX 셸 방언 1회(일곱 라운드 생존). 넷 다 **조용한** 결함이었고(틀린 것이 에러가 아니라 green을 냈다),
넷 다 "양 셸"·"전 하니스" 같은 표현이 **뭉뚱그린 자리**에 있었다. 축에 이름이 없으면 그 자리를 아무도
묻지 않는다.

- **정직하게 적는다**: 집행이 없는 축은 **"미집행"이라고 쓴다.** 집행 없는 축을 집행되는 것처럼 적는
  것이 `vacuous-pass` 부류다(아래 "차단 등급 판례" 절).
- **고지 재산정 규율(M40)**: 아래 "기계가 묻지 않는 것"에서 **항목을 지우거나 수를 줄이려면**, 그
  구멍을 재현하는 **공격이 이제 FAIL함을 실측으로 보이고 그 근거를 여기 적는다.** 표기·배선·잡이
  생겼다는 **사실만으로 항목을 줄이는 것은 `vacuous-pass`다** — M39가 `job:` 표기를 넣은 뒤 실측 없이
  고지를 넷에서 셋으로 줄였다가 리뷰의 반증(산문 위장이 그대로 초록)으로 **차단·반환**됐다. 그 판정을
  규약 문장으로 승격시킨 것이 이 항목이다. 반대 방향(항목을 **더하는** 것)에는 이 절차가 필요 없다 —
  못 무는 자리를 새로 알게 되면 즉시 적는다.
- **축 이름 표기(`axis:<이름>`)**: 표의 **축 이름 칸**은 축마다 `axis:<ASCII 이름>` 토큰을 **정확히
  하나** 갖는다(`job:` 표기와 같은 형태 — 기계가 푸는 표기다). 표기가 없는 데이터 행은 축이 아니라
  **표 안에 들어온 산문**이고, 표기가 있는데 `env-axes:` 선언에 없으면 **미선언 축**이다 — Part H가
  **양쪽 다 FAIL**로 잡는다(M40에서 도입. 그 전에는 선언에 없는 표 행이 무엇을 적든 아무 검사도
  걸리지 않았다).
- **축 이름 집합의 집행**: 위 `env-axes:` 선언 줄이 축 **ASCII 이름**의 단일 원본이고,
  `tests/discover`의 **Part H**가 ⑴ 각 이름이 위 표의 행에 `axis:` 토큰으로 실재하는지 ⑵ 그 집합이
  `tests/discover/README.md`의 같은 선언과 **일치**하는지 ⑹ 표의 `axis:` 토큰 집합이 선언 집합과
  **양방향으로 일치**하는지 대조한다(가짜 이름 음성 통제 포함).
  축을 더하면서 한쪽만 고치면 **양 셸이 FAIL**한다.
- **집행 칸 표기(`job:<이름>`) — 매핑의 단일 원본**: CI 잡을 지목하는 집행은 표의 집행 칸에
  **`job:<잡키>` 토큰**으로 적는다(ASCII, 워크플로의 잡 키 그대로, 한 칸에 여러 개 가능).
  **이 토큰이 축 → CI 잡 매핑의 단일 원본이다** — 별도 매핑 선언 줄은 두지 않는다(M39에서 표로
  흡수해 선언처를 하나로 줄였다. 두 곳에 적으면 갈라진다). 토큰이 **없는 칸은 "CI 잡 집행 없음"**을
  뜻하며, 그 자리는 산문으로 무엇이 집행하는지(또는 미집행인지) 정직하게 적는다.
- **CI 잡 집행 칸의 집행**: Part H가 ⑶ 표의 각 `job:<이름>`이 `.github/workflows/tests.yml`의
  **잡 키로 실재**하는지 ⑷ 그 토큰이 **선언된 축의 행**에 있는지 대조한다(가짜 잡 이름 음성 통제
  포함). CI에서 잡을 지우거나 이름을 바꾸면서 표를 그대로 두면 **양 셸이 FAIL**한다.
- **매핑 커버리지의 집행**: 매핑은 **옵트인이 아니다** — 워크플로에 **실재하는** 잡은 ⑸ 어느 축 행의
  `job:` 토큰으로 등재되거나, **환경 축이 아님을 선언**(위 `env-axis-exempt-jobs:` 줄)해야 한다
  (둘 다 아니면 FAIL). 이것이 없으면 표에 올리지 않는 것만으로 ⑶⑷를 피해 갈 수 있다.
  - **면제는 침묵이 아니라 선언이다**: CI 잡 중에는 실행 환경 축이 아닌 것도 있다(예: `pairing` —
    양 셸 하니스 **집합**이 짝을 이루는지 보는 레포 정합 잡이지, 어떤 환경의 두 극을 도는 잡이
    아니다). 그런 잡을 축인 척 표에 올리는 것도, 아무 데도 안 적어 조용히 빠지게 두는 것도 틀렸다 —
    **면제 목록에 이름을 적어 결정을 남긴다.** 그래서 CI에 잡을 더하면 "축인가, 면제인가"를 **반드시
    한 번 결정하게** 된다. 면제 목록의 이름도 워크플로에 실재해야 한다(⑹ — 잡을 지우거나 이름을
    바꾸면서 면제만 남기는 낡은 선언을 막는다).
  - **`job:` 표기가 닫은 것과 닫지 않은 것(실측)**: 표기 이전에는 집행 칸이 산문이라 기계가 "백틱
    토큰이 잡을 지목한 것인지"를 구별할 수 없었다(집행 칸에는 파일 경로 같은 정당한 백틱 토큰도
    온다). `job:` 접두사는 그 모호함을 없애 **토큰으로 지목한 참조**를 검사 대상으로 만든다.
    - **닫힌 것**(M39 리뷰가 양 셸로 실측): `job:`으로 지목한 잡이 워크플로에 **없으면** FAIL ·
      **미선언 행**에 적힌 `job:` 토큰(고아)은 FAIL · 실재 잡을 표에서 **빼면** FAIL · **낡은 면제**
      선언은 FAIL.
    - **닫지 않은 것**: 집행 칸의 **산문**이 실재하지 않는 잡을 주장하는 경우는 **여전히 걸리지
      않는다.** 실측 — ⑴ `job:posix`를 그대로 둔 채 같은 칸에 "CI `nowhere` 잡도 집행"을 덧붙이면
      **초록**, ⑵ 토큰이 없는 축의 집행 칸을 통째로 "CI `nowhere` 잡이 집행"으로 바꿔도 **초록**이다.
      바뀐 것은 **무엇을 잡 참조로 셀 것인가라는 정의**이지, 표를 읽는 사람이 오도되는 표면이
      사라진 것이 아니다. 이 사실은 아래 "묻지 않는 것" ⑶에 그대로 남아 있다 — **표기가 생겼다고
      고지를 지우지 않는다.**
- **기계가 묻지 않는 것(정직 고지)**: 위 다섯이 무는 것은 **선언된 축**의 **이름 집합 · 표 행 실재 ·
  `job:` 토큰의 실재와 매핑 커버리지 · `axis:` 표기의 양방향 정합**까지다. 묻지 **않는** 것은 셋이다 —
  - ⑴ CI 잡을 **지목하지 않는** 집행 칸(`launch-context`의 러너 자기 탐침 · `workflow-syntax`의
    "실제 푸시 뿐 + `pr` 마무리의 PR CI 조회")이 오늘도 사실인지. M40에서 `external-tool`이 이
    목록을 떠났다 — 미집행이던 자리에 `job:posix`의 macOS 레그가 붙어 ⑶⑸의 집행 대상이 됐다.
  - ⑵ CI 잡을 지목한 칸의 **나머지 서술**(예: "3 OS" · "매트릭스" · "macOS 레그")이 실제 구성과
    맞는지. **매트릭스 레그는 기계에 보이지 않는다** — `job:` 토큰의 해상도는 **잡 키**까지이고,
    한 잡의 매트릭스가 몇 개의 어떤 레그를 도는지는 어느 검사도 읽지 않는다. 그래서 `external-tool`
    처럼 **집행처가 특정 레그인 축**은 그 레그를 매트릭스에서 지워도 **아무것도 FAIL하지 않는다**
    (M40 리뷰 실측: `macos-latest`를 빼도 107/0 초록). 잡을 통째로 지우는 것은 ⑶⑸가 물지만
    **레그 단위는 사람이 본다** — 이 자리를 뭉뚱그려 "축이 집행된다"로만 적지 않는다.
  - ⑶ **집행 칸의 산문이 실재하지 않는 잡을 주장하는 경우.** `job:` 표기는 **토큰으로 지목한 참조**만
    문다 — 같은 칸의 산문은 여전히 검사 밖이다. 실측(M39 리뷰 · **FAIL 0**): 토큰을 그대로 둔 채 "CI
    `nowhere` 잡도 집행"을 덧붙여도 초록이고, 토큰 없는 축의 칸을 "CI `nowhere` 잡이 집행"으로 바꿔도
    초록이다. 반대로 **실재하는** 잡을 표기 없이 산문으로만 적으면 그 잡이 미등재가 되어 **⑸ 커버리지가
    문다**(실측) — 그래서 남는 구멍은 정확히 **"실재하지 않는 이름을 산문으로 주장하는 경우" 하나**다.
    M38 리뷰가 `nowhere`로 연 자리는 **토큰 경로에서만** 닫혔다.
  - **닫힌 항목(M40 — 선언되지 않은 표 행)**: 직전까지 이 자리에 ⑷ "`env-axes:`에 선언되지 않은 표
    행"이 있었다. 축 이름의 `axis:` 표기와 **데이터 행 수 == 표기 수** 대조가 그것을 닫았고, **실측이
    근거다**(위 "고지 재산정 규율"이 요구하는 절차) — ⓐ 미선언 행에 `axis:` 표기를 적으면 H15 FAIL,
    ⓑ **표기가 아예 없는 순수 산문 행**을 끼워 넣으면 H17b FAIL, ⓒ 선언에 있는 축의 표기를 지우면
    H2·H15·H17b가 함께 FAIL. 셋 다 양 셸에서 재현했다. M38이 "미선언 `ghost-axis` 행이 실재 잡을
    지목해도 96/0 초록"이라 적은 자리가 이로써 닫혔다.
  - 셋 다 **사람의 리뷰 영역**이다(Part C·D와 같은 분담). 이 고지를 지우거나 항목 수를 줄이면서
    "표가 러너·CI의 실제 구성과 어긋나면 기계가 문다"고 뭉뚱그리는 것이 `vacuous-pass` 부류다 —
    M38 리뷰가 두 번, **M39 리뷰가 한 번 더** 실측으로 반증한 자리다(잡 실재 대조 이전에는 `posix`
    잡을 통째로 지워도 90/0 초록, ⑸ 이전에는 **선언된** 미등재 축이 실재 잡을 지목해도 초록,
    그리고 ⑶은 `job:` 표기를 넣은 뒤에도 여전히 초록이다).
- **`workflow-syntax` 축의 확인 지점(누가·언제 — M40에서 배선됐다)**: 이 축은 로컬에서 닫을 수 없다.
  확인이 가능한 자리는 `/tide:release`를 **`pr` 모드로** 돌렸을 때 생기는 `release/vX.Y.Z` 브랜치의
  PR CI뿐이다(v2.11.0이 그 자리에서 두 번 붉은 뒤 초록이 됐다).
  - **M40이 그 조회를 절차에 넣었다** — `pr` 모드 **마무리(finalize)**가 태그를 달기 전에
    `gh pr checks`로 머지된 릴리즈 PR의 체크를 조회하고, 실패·미완료가 있으면 목록을 보여준 뒤
    사용자 확인을 받는다. 조회 불가(`gh` 부재·실패)는 **한 줄 알리고 진행**한다. 이것은 **게이트가
    아니다** — 프리플라이트 게이트 ①②③의 집합·순서·판정 로직은 불변이고, 마무리 경로 안의 사용자
    확인이다. 절차의 단일 원본은 `docs/conventions-release.md`의 "`pr` 모드" 절.
  - **남은 것(정직 표기)**: ⑴ `pr` 모드는 **기본이 아니다**(모드 우선순위: 인자 >
    `.tide/release-mode` > 대화형이고, `gh` 부재·검증 실패면 push-only로 강등된다).
    push-only·`release` 모드는 기본 브랜치에 직접 push하므로 **PR도 머지 전 CI도 없어 이 축이
    그 경로에서는 여전히 닫히지 않는다.** ⑵ **붉은 CI 위에서 사용자 확인을 받는 경로는 아직
    라이브로 밟히지 않았다** — v2.14.0에서 CI가 붉어 릴리즈가 멈춘 것은 그 상황의 예행이었으나,
    사람이 아니라 절차가 멈춰 세웠는지는 다음 마무리에서 확인된다.
  - 완료 기준 3의 후단(**짝 없는 하니스로 `pairing` 잡이 실제로 붉어지는지**)은 일부러 깬 브랜치를
    밀어야 해 어느 경로로도 닫히지 않는다 — **이월**하고, 로컬에서는 그 잡의 스텝 스크립트를
    `bash -eo pipefail`로 **verbatim 재현**해 논리만 확인한다.
- **`external-tool` 축은 M40에서 집행처를 얻었다**(두 사이클 연속 "미집행"이던 자리다): `posix` 잡
  매트릭스에 **`macos-latest`**를 더해 BSD `sed`·`awk` 환경이 두 번째 극이 됐다. 잡 키는 `posix`
  그대로라 표의 토큰이 늘지 않는다.
  - **첫 실행에서 값을 했다** — v2.14.0 릴리즈 PR의 macOS 레그가 `109/1`로 붉었고, 걸린 것은
    `tests/discover/run.sh`에서 **유일하게 `LC_ALL=C`가 빠져 있던** `sort`/`uniq` 한 자리였다
    (ps1 사본은 `HashSet[string]` = ordinal이라 두 셸의 비교 의미가 갈려 있었다).
  - **남은 것(정직 표기)**: 그 수정의 **기전은 확정되지 않았다** — BSD에서 무엇이 묶였는지는 GNU
    환경에서 재현되지 않았고, **다음 macOS 레그 실행이 결론을 낸다**(그때도 붉으면 이번에 넣은
    진단이 중복 앵커 **이름을 찍는다**). 이 불확실성이 감춰지지 않는 것이 이 표기의 목적이다.
- **축이 아닌 것**: 언어 의미론(변수명 대소문자 · 경로 API · 문화권 문자열 비교)은 축이 아니라 **코드
  결함**이다 — 두 극이 있는 것이 아니라 한쪽이 틀렸다. 문화권 비교는 `Ordinal` 명시로 닫는다(M38-T03).

## 문서 자기서술 정합

문서가 **자기 자신에 대해 하는 서술**(하니스 케이스 수 · 커맨드 역할)과 **문서 사이의 인용**이
조용히 낡거나 끊기지 않게 하는 규약의 단일 원본이다 — `README.md`·사이트·`docs/project-context.md`·
하니스 README가 이 절을 인용하고 재정의하지 않는다(스킬은 절차, 규약은 conventions — 기존 분담과 동일).

근거: 이 층에만 가드가 없어 같은 드리프트가 반복됐다 — 계획 문서가 하니스 기준선을 틀린 수로
인용했고(14/14 인용, 실측 19/19), 한 사이클 안에서 PASS 수를 세 번 고쳤으며(29→41→45→48), 캐노니컬
카탈로그만 바뀌고 README·사이트의 **역할 서술**이 갈렸다. 커맨드 **수**(B1)와 **이름**(B3)은 이미
가드가 있으나 **수치와 역할 문구**는 무방비였다.

### 카운트 단일 선언처

- **선언처**: 하니스 케이스 수(총계·파트별)는 **각 하니스의 `tests/{name}/README.md`가 유일한
  선언처**다. 선언 줄은 ASCII 골격 `cases: {N}`을 포함한다(예: `현재 케이스 수 (cases: N)`) — 러너가
  이 골격으로 값을 **추출**한다. 같은 파일의 산문에서 이 골격을 다시 쓰지 않는다(첫 매치가 선언으로
  읽히므로, 산문이 앞서면 엉뚱한 수가 잡힌다 — 실제로 이 규약을 처음 배선할 때 그렇게 걸렸다).
- **다른 문서는 수를 적지 않는다**: `docs/project-context.md`·규약·사이트·스킬은 수 대신 선언처를
  가리킨다(수를 옮겨 적는 순간 두 번째 선언처가 생긴다).
- **집행**: 선언을 가진 하니스의 러너가 자기 README의 선언과 **자신의 실제 케이스 수**를 대조한다 —
  어긋나면 **FAIL**(advisory가 아니다). 추출 실패(선언 부재가 아니라 **골격 이형**)도 FAIL이다 —
  조용한 skip을 두면 가드가 공허해진다. 총계와 함께 **파트별 내역의 합**도 대조한다(총계만 고치고
  내역을 두면 한 겹 아래에서 갈라진다).
- **현행 배선 범위**: **하니스 6종 전부**가 이 검사를 실제로 돈다(M38-T01). `tests/discover`는 Part F의
  F1·F1b(총계 + 파트별 내역)이고, 나머지 5종(`fleet`·`fleet-cycle`·`fleet-verify`·`multi-repo`·
  `site-includes`)은 러너 종료 직전의 마지막 케이스 `case-count: README cases declaration == actual`
  로 총계를 대조한다(파트 구조가 없어 내역 합은 대상이 아니다). 새 하니스를 더하면 **같은 사이클에**
  그 러너에도 이 케이스를 배선한다(위 "규약 ↔ 실행/인프라 동기화" 원칙).
  - **이 검사가 무는 것은 "덜 돎"이다**: 완주 가드(M37)는 러너가 **중단**되는 것을 잡고, 이 케이스는
    러너가 죽지 않고 **덜 도는** 것을 잡는다 — 조건 분기가 파트를 건너뛰거나 발견형 스캔이 0건을
    집으면 수가 어긋나 FAIL한다. 둘은 같은 가드의 두 절반이다.
  - **자기 공허 금지**: 선언을 **못 읽는 경우**(파일 없음·`cases` 토큰 없음)도 FAIL이다. "못 읽어서
    대조를 건너뛰고 통과"는 `vacuous-pass` 부류 그 자체다(아래 "차단 등급 판례" 절).
- **소급 금지 예외**: `docs/milestones/M*.md`·`docs/reports/*`는 **그 시점의 역사 기록**이므로 수를
  적어도 되고 **소급 갱신하지 않는다**(위 "정오표"·재작업 라운드 하위 호환과 같은 취지). 이 규약은
  **현행 상태를 서술하는 살아 있는 문서**에만 적용된다.
- **이력 서술 예외**: 살아 있는 문서 **안**이라도 특정 시점의 처분·사건을 기록하는 **이력 항목**은
  **그 시점의 값**을 적어도 되며 소급 갱신하지 않는다(예: `docs/project-context.md`의 이월 처분 원장
  행, 회고 섹션, 규약이 근거로 인용하는 과거 수치) — "M27이 12/12로 집행했다"는 사건 기록이지 현행
  상태 서술이 아니다. 금지되는 것은 **현재를 서술하는 문장**이 수를 옮겨 적는 것이다(같은 문서라도
  그 문장은 선언처를 가리킨다). 판단 기준은 문서의 종류가 아니라 **그 문장이 현재를 말하는가**이다.
- **복제 선언 수 — 세는 규칙(지표 정의)**: 위 케이스 수가 **선언처가 하나로 정해진** 수치라면, 이
  지표는 **아직 여러 곳에 흩어져 선언된 사실**이 몇 곳에 있는지를 센다. 사이클이 그 수를 늘렸는지
  줄였는지를 보고서가 계측하므로(지표가 후퇴를 표시하지 못하면 지표가 아니다), 세는 규칙을 먼저
  고정한다 — 규칙이 없으면 같은 부채를 두 사람이 다른 수로 세고 어느 쪽도 틀렸다고 말할 수 없다.
  - **1건의 단위 = 파일**: 한 파일이 같은 사실을 몇 문장·몇 줄로 적든 **1건**이다. 부채의 실체는
    문장 수가 아니라 **그 사실을 고칠 때 찾아가야 하는 파일 수**이고, 한 파일 안의 여러 문장은 한
    번의 방문으로 함께 고쳐지기 때문이다.
  - **원본은 복제가 아니다**: 한 사실의 **복제 선언 수 = 그 사실을 선언한 파일 수 − 1**(단일 원본
    하나를 뺀다). 원본까지 포함한 수를 적을 때는 **선언처 수**라고 이름을 달리 적는다.
  - **포인터는 복제가 아니다**: 사실을 다시 적지 않고 단일 원본을 **가리키기만 하는** 문장
    (`단일 원본은 … 절`)은 세지 않는다. 선언을 포인터로 바꾸는 것이 이 지표를 줄이는 정규 수단이므로
    포인터를 세면 지표가 개선을 표시하지 못한다. 다만 사실을 **다시 서술한 뒤** 포인터를 덧붙인
    문서는 선언으로 센다 — 기준은 포인터의 유무가 아니라 **재서술의 유무**다.
  - **집계 대상 = 살아 있는 문서·스킬·훅**: 규약 문서 집합·`docs/project-context.md`·
    `docs/orchestration.md`·`README.md`·`site/docs/`·`skills/`·`hooks/`를 센다. 세 부류는 뺀다 —
    ① `docs/milestones/`·`docs/reports/`는 **시점 기록물**이라 갱신 대상이 아니다(위 소급 금지 항과
    같은 취지이며 "정오표 (errata)" 절이 본문 불변을 정한다 — 고칠 일이 없는 곳은 부채가 아니다)
    ② `tests/`의 하니스 코드·하니스 README는 **집행 수단**이고 그 비용은 위 케이스 수가 이미 세므로
    같은 비용을 두 지표에 이중 계상하지 않는다(집행되는 사실은 어긋나면 FAIL로 드러나므로 이 지표가
    재는 **조용한 발산**의 대상이 아니다) ③ 도구가 생성하는 로컬 설정·캐시는 사람이 유지하는 선언이
    아니다.
  - **무엇에 대한 지표인가**: 같은 **사실** 하나가 단위다 — 커맨드 명단, phase를 기록하는 커맨드
    명단, 병기어(ASCII 토큰)의 정의처럼 **바뀌면 여러 곳을 함께 고쳐야 하는 서술**이다. 서로 다른
    사실의 복제는 합산해 보고해도 되나 **어느 사실의 몇 건인지 내역을 함께 적는다**(합만 적으면 어느
    사실이 발산 중인지 사라진다).
  - **지표의 정의일 뿐 새 집행이 아니다**: 이 규칙은 하니스 케이스를 늘리지 않는다 — 값은 보고서가
    위 규칙대로 세어 내역과 함께 적는다. 집행이 필요한 사실에는 별도로 드리프트 가드를 배선한다
    (위 "규약 ↔ 실행/인프라 동기화" 절).
  - **언제 적는가(발동 조건)**: **그 사이클이 이 수를 바꿨을 때**(늘렸거나 줄였을 때)만 impl 보고서가
    적는다. 값이 그대로인 사이클까지 요구하면 기재가 **의례**가 되고, 의례는 지켜지지 않는다 — 이것은
    추정이 아니라 관측이다. **M37이 이 지표를 신설한 뒤 M38·M39·M40 세 사이클이 값을 적지 않았고**
    (보고서 전체에서 이 지표의 등장은 M36·M37뿐), 원인은 게으름이 아니라 **발동 조건과 기재 위치가
    이 절에 없었다는 것**이다. 위 문장이 "보고서가 계측한다"고만 적고 *언제·어디에*를 정하지 않아,
    집행력을 사실보다 넓게 주장하는 형태였다. 집행 부재를 감추지 않는 것이 이 규약의 형식이다
    (아래 "실행 환경 축"의 미집행 표기와 같은 취지).
  - **어디에 어떤 형식으로 적는가**: impl 보고서의 **`## 미해결·후속 메모` 직전**에 한 줄 —
    `복제 선언 수: {부호}{N}`에 **내역**을 잇는다. 내역은 위 "무엇에 대한 지표인가"가 정한 대로
    **어느 사실의 몇 건인지**를 적는다(합만 적으면 어느 사실이 발산 중인지 사라진다). 값이 0이어도
    발동 조건에 걸렸다면 적는다 — 늘리지도 줄이지도 않았다는 것과 **재지 않았다**는 것은 다르다.
    형식의 참조 선례는 `docs/reports/M36-impl.md`의 자기 부채 표 행이다(그 시점 기록물이므로 소급
    갱신 대상이 아니다).
  - **스킬에 배선하지 않는다(분류)**: 이 지표는 **tide 자신의 기여자 규율**이다 — `skills/impl/`의
    절차·템플릿에 슬롯을 두지 않으며, 따라서 **사용자 프로젝트의 impl 보고서에 이 계측을 요구하지
    않는다**. 그래서 이것은 **라이브 도그푸딩 항목이 아니다**(사용자 프로젝트로 측정되지 않는 것이
    결함이 아니라는 판단은 아래 "실행 환경 축"에 내린 분류와 같은 근거다). 배선하지 않는 두 번째
    이유는 자기참조적이다 — 템플릿에 슬롯을 두면 **그 슬롯 자체가 이 지표가 세는 복제를 하나 늘린다**.

### 역할 앵커 전파

- **발동**: 커맨드의 **역할**을 바꿀 때. 캐노니컬 카탈로그(`docs/commands.md`)의 역할 셀에 그 변화를
  대표하는 **ASCII 병기어(역할 앵커)**를 남기고, 같은 커맨드의 역할을 소개하는 **소비자 문서**에 그
  앵커를 전파한다.
- **선언**: 앵커 맵은 캐노니컬 파일 안 주석 한 줄 `<!-- role-anchors: name=token … -->`에 둔다
  (렌더에 보이지 않고 기계 파싱이 가능하다). 가드는 ① 앵커가 캐노니컬의 **그 커맨드 행에 실재**하는지,
  ② 소비자 문서가 그 커맨드를 **언급하면** 앵커가 있는지를 검사한다.
- **소비자 범위(소음 0)**: 커맨드 역할을 표·목록으로 **소개하는** 문서 — `README.md`,
  `site/docs/getting-started.md`. `docs/orchestration.md`는 오케스트레이션 **사용 흐름** 문서이지 역할
  카탈로그가 아니라 대상이 아니다(그 파일의 카운트 드리프트는 B1이 이미 덮는다). 소비자가 그 커맨드를
  언급하지 않으면 그 문서는 대상이 아니다.
- **앵커를 발명하지 않는다**: 모든 커맨드에 영문 토큰을 붙이는 의례가 아니다 — 앵커가 없는 행은 검사
  대상이 아니며, 역할이 바뀔 때마다 자연스럽게 늘어난다. **얇게 시작해 두꺼워지는 가드**다.
- **ASCII인 이유**: `run.ps1`의 **byte > 127 = 0**(ASCII-only 원본 규율) 때문이며, 원칙의 단일 원본은
  위 "리뷰 검증 규율" 절의 ASCII 병기 결정이다(재정의하지 않는다).
- **경계 매칭**: 앵커는 **영문·하이픈 경계**로 찾는다(짧은 앵커가 다른 단어 안에 우연히 걸리지 않도록)
  — B3가 `/tide:fleet`과 `/tide:fleet-cycle`을 구분하려고 경계를 요구하는 것과 동형이다.
- **판정 단위의 비대칭(의도된 것)**: 캐노니컬 쪽은 **그 커맨드의 표 행**에서 앵커를 찾고, 소비자 쪽은
  **파일 단위**로 찾는다. 소비자 서술은 여러 줄에 걸치는 산문이라(사이트 시작하기의 항목은 커맨드
  이름과 앵커가 다른 줄에 있다) 줄 단위로 좁히면 정상 문서가 FAIL한다. 대가는 명확하다 — **같은
  파일 다른 자리에 앵커가 남아 있으면 역할 서술에서 사라져도 통과한다**(구현 중 실측). 앵커의 존재를
  보는 가드이지 문구의 정확성을 보는 가드가 아니다(문구 품질은 사람의 리뷰 영역).

### 상호참조 무결성

문서가 규약을 가리키는 **인용**이 개명·삭제로 조용히 끊기지 않게 하는 규약이다. 위 두 규약이
"자기 자신에 대한 서술"을 집행한다면, 이것은 **문서 사이를 잇는 참조**를 집행한다.

- **규약 문서 집합**: 규약은 한 파일이 아니라 **파일 집합**이다 — `docs/conventions.md`(본체)와
  `docs/conventions-{주제}.md`(조각)로 이뤄진다. 조각 이름의 주제 부분은 그 조각이 담는 주제 하나를
  가리키는 소문자 ASCII 토큰이다. **발견 글롭은 `docs/conventions*.md`**이며, 파일 목록을 스크립트·
  문서에 **하드코딩하지 않는다** — 조각을 더할 때 손으로 갱신해야 하는 목록을 만들지 않는 것이 이
  규약의 요점이다.
- **인용 골격**: 다른 문서가 규약을 가리킬 때는 `` `docs/conventions.md`의 "{앵커 이름}" 절 `` 형태를
  쓴다(따옴표 안이 앵커 이름). 가드는 파일명이 든 줄에서 따옴표 구획을 **추출**한다. 두 가지는
  인용이 아니라 제외한다 — **스니펫 인클루드 지시어 줄**(`8<--`)과 **중괄호가 든 따옴표**
  (`{앵커 이름}` 같은 골격 예시 자리표).
- **인용은 그 앵커가 실제로 사는 파일을 가리킨다**: 절이 조각으로 옮겨 가면 인용의 파일명도 같이
  바꾼다 — 조각에 사는 절은 `` `docs/conventions-release.md`의 "{앵커 이름}" 절 ``로 인용한다.
  골격 자체(따옴표 안이 앵커 이름 · 한 줄 안에)는 그대로다. 조각에서 본체의 절을(또는 그 반대를)
  가리키는 참조도 파일을 건너뛰므로 같은 골격을 쓴다 — 그 순간 G1의 사정권에 든다(같은 파일 안의
  자기참조는 골격에 파일명이 없어 G1이 아니라 **아래 "자기참조도 집행한다" 항목의 G4**가 문다).
- **인용은 한 줄 안에 쓴다**: 파일명과 따옴표 구획이 줄바꿈으로 갈리면 줄 단위 추출에서 **조용히
  빠진다**. 후보 줄의 따옴표가 미종결이면 FAIL이며(줄바꿈이 구획 안에서 일어난 경우), 파일명만 있고
  구획이 통째로 다음 줄인 형태는 정상 경로 언급과 구별할 수 없어 **가드가 잡지 못한다** — 한 줄
  규율이 1차이고 가드는 백스톱이다.
- **인용 가능한 앵커 = `##`·`###` 제목만**이다. 볼드 항목을 인용하려면 **소절로 승격**한다. 승격이
  문맥을 해치면(목록 한가운데 항목 등) 반대로 **인용 쪽을 실재 앵커로 고친다** — 어느 경로든 인용
  대상 층위가 둘로 고정되는 것이 기계 대조의 성립 조건이다.
- **이름 유일성 — 범위는 규약 문서 집합 전체**: 앵커 이름은 집합 **전체**에서 유일해야 한다. 파일이
  갈려도 같은 이름을 두 곳에 두지 않는다 — 인용이 파일명을 함께 적더라도 이름이 겹치면 사람이 읽을
  때 결정 불가가 된다. 겹치면 상위 맥락을 괄호로 붙여 유일화한다
  (예: `불변 (리뷰 검증 규율)` / `불변 (문서 자기서술 정합)`).
- **정규화**: 대조 전에 **공백만 제거**하고 비교한다(`버전·CHANGELOG` ≡ `버전 · CHANGELOG`).
  구두점·괄호·백틱은 **그대로** 비교한다 — 정규화를 넓히면 오탐이 는다.
- **조각 파일의 요건 셋**: ① 저장소 원본에 `[start:body]`/`[end:body]` 마커를 두고 **도입 문단은
  마커 밖**에 둔다(본체·`docs/orchestration.md`와 같은 형태 — 사이트는 본문만 인클루드한다)
  ② 사이트 셸 페이지와 nav 항목을 **같은 사이클에** 만든다(위 "규약 ↔ 실행/인프라 동기화" 절)
  ③ 본체에 그 조각을 가리키는 **포인터 한 줄**을 남긴다 — 독자가 본체만 읽고 절이 통째로 사라졌다고
  오해하지 않도록. 포인터는 앵커가 아니라 파일을 가리키는 문장이므로 따옴표 인용 골격을 쓰지 않는다.
- **집행**: `tests/discover` Part G가 **FAIL**로 집행한다(advisory 아님). 대조는 **파일별 앵커 집합**
  기준이다 — 인용 줄에 등장한 규약 파일명으로 대조할 집합을 고르고, 한 줄에 두 파일명이 있으면 어느
  쪽 집합에든 있으면 통과로 본다(안전 측 — 오탐을 만들지 않는다). 추출 0건도 FAIL이고(공허 통과
  차단), 집합 전체에 정규화 후 중복 이름이 있어도 FAIL이다.
- **범위**: 대상은 규약을 인용하는 **살아 있는 문서**다. `docs/milestones/*`·`docs/reports/*`는 역사
  기록이라 대상이 아니다(위 "카운트 단일 선언처"의 소급 금지와 같은 취지).
- **자기참조도 집행한다(M41)**: 같은 파일 **안의** 자기참조(`위/아래 "{앵커 이름}" 절`)는 골격에
  파일명이 없어 여섯 사이클 동안 가드 밖이었으나, Part G의 **G4**가 집행한다.
  - **집행 범위 = 위 "범위" 항목의 살아 있는 문서 전부**(G1과 같다). 규약 문서 집합만 보면 이 절이
    "닫혔다"고 적은 층이 `skills/`·`README.md`·`tests/*/README.md`에서 **그대로 열려 있다** — 그것이
    M41 라운드 1이 차단을 받은 자리이며(규약 밖에 깨진 자기참조를 심어도 초록이었다), 범위를 적지 않고
    닫혔다고 쓰는 것이 `vacuous-pass`다.
  - **대조는 그 파일 자신의 앵커 집합**이다. 자기참조는 정의상 같은 파일을 가리키므로, 집합 전체와
    대조하면 **다른 파일의 절을 가리켜도 통과**한다(좁은 범위에서는 안전 측이던 선택이 범위를 넓히면
    과대 허용으로 뒤집힌다).
  - **기계가 무는 것(양쪽 중 이쪽)**: `"{앵커 이름}" 절` 형태이면서 ⑴ 백틱 파일 경로가 없고 ⑵ 그 줄에
    규약 파일명이 없으며 ⑶ **앞 줄에도** 규약 파일명이 없는 줄. 표지는 전부 실측으로 정했다 —
    살아 있는 문서 전체에서 후보 **46건·미해소 0건**이고, 표지 ⑵를 빼면 후보 50건 중 **마크다운 링크
    인용 4건**이, ⑶을 빼면 후보 50건 중 **줄바꿈 인용 3건**이 오탐이 된다.
  - **기계가 묻지 않는 것(양쪽 중 저쪽 — 넷)**: ① `절` 표지를 쓰지 않은 자기참조. **이 표지 없이는
    닫을 수 없다** — 조건을 빼면 규약 문서 집합만으로도 후보가 47 → 165건으로 늘고 그중 100건 넘게
    평범한 인용부호 산문이다(`"가능"`·`"확인했다"`). ② 백틱 파일 경로를 함께 언급하는 자기참조
    (그 줄은 다른 파일로의 인용과 구별할 수 없다). ③ **규약 파일이 아닌 다른 파일로의 인용**
    (예: 스킬 파일의 절을 가리키는 인용) — G1의 대조 집합이 규약 문서 집합뿐이라 어느 가드도 보지
    않는다. ④ **파일명 없이 쓴 규약 인용 중, 그 이름이 자기 파일에도 앵커로 있는 것** — 아래 항목이
    이유다. 넷 다 **위반이 아니라 경계 밖**이고 사람의 리뷰 영역이다.
  - **자기참조와 파일명 없는 인용은 원리상 구별되지 않는다(④의 근거)**: 그 줄에 규약 파일명이 없으면
    **자기참조인지 규약 인용인지 알 수 없다** — 구별에 필요한 정보가 그 줄에 없기 때문이다. 파일명이
    없어지는 길은 **둘**이고 둘 다 같은 자리로 떨어진다:
    - **㉮ 줄바꿈으로 떨어져 나간 경우** — 파일명이 앞 줄에 있고 따옴표 구획이 다음 줄에 있다. 위
      "인용은 한 줄 안에 쓴다" 항목이 G3의 사각으로 이미 고지한 성질이며, 앞줄 검사(⑶)는 **한 줄**만
      보므로 두 줄 이상 앞의 파일명은 못 본다.
    - **㉯ 애초에 파일명을 적지 않은 경우** — `규약의 "{앵커 이름}" 절`처럼 골격을 쓰지 않은 인용이다.
      **G1도 보지 못한다**(G1의 후보 줄 조건이 파일명이다). 이 부류가 실재한다는 것은 이 사이클이
      실증했다 — M41이 고친 두 결함이 정확히 그 형태였다.
    그때 G4는 그 구획을 **자기참조로 취급해 자기 파일 앵커에 대조**하고, 결과는 **이름이 우연히 그
    파일에도 있는가**에 갈린다 — 있으면 조용히 통과하고(④), 없으면 붉어진다.
    - **실측(둘 다 확인)**: `site/docs/concepts.md`에서 그 파일이 **자기 앵커로도 가진 이름**
      (`tide-guard hook`)을 ㉮ 파일명을 두 줄 앞에 두고 끊어 쓰거나 ㉯ 한 줄로 파일명 없이 쓰면
      **둘 다 초록**이다. 각각 그 파일에 **없는 이름**으로 바꾸면 **둘 다 FAIL**한다. 발행 페이지가
      규약 절 이름을 미러링하는 것은 이 레포의 정상 형태이므로 **이 예외는 드물지 않다.**
    - **예시는 자리표로 쓴다**: 위 ㉯의 골격 예시가 `{앵커 이름}` 자리표인 것은 장식이 아니다 —
      실제 이름을 적으면 G4가 그것을 **살아 있는 자기참조로 읽어** 그 문서가 붉어진다(이 규율을
      쓰는 도중 실측으로 걸렸다). 위 "인용 골격" 항목의 중괄호 제외가 그 자리다.
    - **창을 넓혀도 닫히지 않는다**: 앞줄 창을 1 → 2 → 3으로 넓혀도 살아 있는 문서 전체에서
      후보 46건·미해소 0건으로 **값이 바뀌지 않고**(실측), 창이 N이면 N+1줄 앞의 파일명은 여전히
      못 본다 — **경계가 옮겨질 뿐 부류가 닫히지 않는다.** 그래서 창은 1로 두고 이 항목을 고지한다.
    - **붉어질 때의 진단은 두 가지를 뜻한다** — 러너가 찍는 이름은 "미해소 자기참조 **또는** 끊긴
      인용"이며, 어느 쪽인지는 사람이 그 줄과 앞 줄들을 보고 판단한다. 어느 쪽이든 고칠 것이 있다
      (해소되지 않는 자기참조이거나, 한 줄 규율이 깨진 인용이다).

### 불변 (문서 자기서술 정합)

이 절은 **문서 위생 규약**이다 — 커맨드 12종·`.tide/phase`·tide-guard 계약·프리플라이트 게이트·
보고서 섹션 구조·판정 표기와 계측 줄 형식은 전부 불변이다. 집행은 `tests/discover` Part F·G이며,
문구의 **품질**(설명이 정확한지)은 여전히 사람의 리뷰 영역이다 — 가드가 보는 것은 **선언의 존재와
값의 일치**뿐이다(Part B~E와 같은 분담).

## 2.0 안정성

tide는 **v2.0.0부터 아래를 안정(stable) 계약으로 재선언(재기준)**한다. 안정 계약은 하위 호환을
지키며, **하위 호환을 깨는 변경은 다음 major(3.0)에서만** 한다(minor·patch는 가산·정리·견고화에
한한다). 2.0은 v1.0.0의 "안정 선언" major와 동형인 **비파괴 계약 재기준**이다 — 오케스트레이션
에픽 완성 surface(아래 11종 커맨드 + 오케스트레이션 규약)를 동결 선언할 뿐 동작 변경은 없다.

- **커맨드 11종의 호출명·역할**: 기존 8종 — `/tide:kickoff`·`/tide:milestone`·`/tide:impl`·
  `/tide:review`·`/tide:cycle`·`/tide:release`·`/tide:retro`·`/tide:status` — 에 더해
  `/tide:fleet`·`/tide:fleet-cycle`·`/tide:fleet-verify` **3종을 안정 계약으로 승격**해 **총 11종**의
  호출명·역할을 stable로 동결한다(종전 "8종 + 가산" 서술의 재기준). 현재 커맨드는 **총 12종**이며
  그중 **11종이 2.0 stable**이다 — `/tide:debug`는 **v2.7.0 가산**이라 동결 집합에 들지 않는다
  (**다음 major에서 stable 승격 후보**). 가산 이력은 아래 v1.x·v2.x 절이 보존한다.
  - **열거처는 둘이다 — 이 절과 `README.md`**: stable 11종의 **이름 명단**을 열거하는 살아 있는
    문서는 이 절과 `README.md`의 "2.0 안정성" 절 **정확히 둘**이며, 다른 문서는 명단을 다시 적지 않고
    **이 절을 가리킨다**. 하나로 줄이지 않는 이유는 위 "상태 파일 (.tide/phase)" 절이 phase 기록
    명단에 쓴 것과 같다 — 소비자
    문서에서 명단을 빼면 읽는 사람이 동결 집합을 확인할 경로가 사라지므로, **하나로 줄이는 대신 집합
    일치를 집행**한다.
  - **집행(FAIL — advisory 아님)**: `tests/discover` Part C-4가 ① 두 열거처의 **이름 집합이 문자열로
    동일**한지 ② 살아 있는 문서 전체에서 명단을 가진 파일이 **그 둘뿐**인지 ③ 존재하지 않는 이름이
    두 명단 **어디에도 없는지**를 문다. 훑는 범위는 C-3이 정한 것과 **같은 범위**이며 여기서 다시
    정의하지 않는다. **양쪽이 다 비면 통과가 아니라 FAIL**이다(공허 통과 차단).
  - **추출 단위 = 창(최대 4줄)**: 열한 이름이 **모두 드는 가장 짧은 연속 줄 묶음**을 뽑는다. 실측
    스팬은 **이 절 3줄 · `README.md` 1줄**이고 상한은 C-3과 같은 **4**다. **상한을 넘으면 창을 찾지
    못해 개수 케이스가 크게 FAIL한다** — 이것이 집행 경계이며 양 셸이 같은 값을 쓴다. 명단을 5줄
    이상으로 흩으면 그 사실이 FAIL로 드러난다(조용히 빠지지 않는다).
  - **`12종`과 `11종`은 다른 사실이다**: 전자는 **실제 스킬 파일 수**라 기계가 `skills/*/SKILL.md`를
    세어 대조하고(Part B의 B1), 후자는 **동결 선언**이라 파일 시스템으로 셀 수 없어 **명단 대조로만**
    집행된다. 그래서 `11종`을 B1에 얹을 수 없다 — 두 사실을 한 검사에 묶으려는 시도는 실패한다.
- **단계별 규약**: 위 "사이클"·"부수효과 분리"·"전제조건·프리플라이트"·"단계별 금지 행위 요약"이
  정의하는 단계 순서·금지·강제 수단.
- **오케스트레이션 규약(2.0 신규 stable)**: 위 "멀티 레포 오케스트레이션" 절이 정의하는 다음을
  안정 계약에 추가한다 —
  - **부수효과 분리 불변**: fleet은 **advisory만**, fleet-cycle은 **release 제외**(milestone→review만),
    fleet-verify는 **verification-only**(어떤 레포 phase=release 미기록). cross-repo git 비자동화.
  - **`.tide/deps`(의존 선언·계약 비교)**: 레포별 의존 매니페스트(커밋 대상)와 전체 연산자
    (`>=`·`>`·`=`·`<=`·`<`) 계약 버전 비교 — 위반은 advisory 경고, 순서는 불변(위 "계약 비교 규칙").
  - **`.tide-fleet/integration`(통합 훅)**: 부모 레벨·옵트인 통합 검증 훅의 위치·형식.
  - **tide-guard 백스톱 정밀**: 가드는 **phase 잠금**(phase≠release 레포의 git 차단)이지 release
    차단기가 아니며, fleet-cycle/fleet-verify는 처리 전 **phase=release 잔재를 사전 점검**한다.
- **`.tide/phase`·tide-guard 계약**: 상태 파일 `.tide/phase`의 의미(단계명 한 줄)와 tide-guard
  hook의 차단 규칙(release 단계가 아니면 git commit/tag/push 차단, 상태 파일 부재 시 무차단). 이는
  **1.0 그대로 유지(불변)**다. phase는 **명령의 레포 루트 기준**으로 읽으며(단일 레포에선
  `CLAUDE_PROJECT_DIR`와 동일), 레포를 못 찾으면 `CLAUDE_PROJECT_DIR` 폴백 — 이는 하위 호환
  일반화로 단일 레포 동작을 바꾸지 않는다(상세는 "멀티 레포 / 대상 레포" 절).
- **3.0 후보 (가드 창 닫기)**: kickoff가 반드시 만드는 **커밋 대상 마커** + 마커 존재 + phase 부재 =
  **차단** — 위 "tide-guard hook" 절이 고지한 fresh clone 창을 닫는 설계다. **부재 시 무차단**을
  뒤집으므로 `/tide:debug` stable 승격과 같은 **다음 major 후보로만** 등재한다. 함께 남기는 제약 둘:
  ① 차단 메시지가 **해제 방법을 자기서술**해야 한다(tide를 모르는 상속·fork 레포 사용자가 걸리며,
  그 사용자는 설치하지 않은 플러그인의 커맨드를 안내받게 된다) ② 마커 검사를 **`rev-parse` 루트에
  앵커**해야 한다(모노레포·벤더링에서 마커 위치와 루트가 어긋나면 무관한 형제 디렉터리 작업까지
  차단된다). 제약 둘 다 충족해야 안전한 설계이므로 등재와 함께 남긴다.
- **보고서·마일스톤 형식**: 마일스톤 문서·완료보고서·리뷰보고서·회고 문서의 섹션 구조(위 해당 절).
  이 역시 **1.0 계약 그대로 유지(불변)**다.

호환을 깨지 않는 추가(새 커맨드·새 선택 필드·새 검증 단계 등)와 정리·견고화는 minor·patch로
계속한다 — 안정 선언은 "이제부터 위 계약을 함부로 깨지 않는다"는 약속이지 기능 동결이 아니며,
연산자 확장·가드라일·정리는 전부 하위 호환 가산이다(단일 레포·미선언·기존 11종 동작 불변).

**v1.x 가산 이력(보존)** — fleet 3종은 아래 순서로 v1.x에서 가산된 뒤 2.0에서 stable로 동결됐다.

- **`/tide:fleet` (v1.2.0부터)** — 읽기 전용 멀티 레포 개요.
- **`/tide:fleet-cycle` (v1.5.0부터)** — 의존성 순서로 `milestone → review` 자동 실행, **release 제외**.
- **`/tide:fleet-verify` (v1.6.0부터)** — 부모 레벨 훅(`.tide-fleet/integration`, 옵트인)으로 cross-repo
  통합을 **verification-only** 검증.

셋 다 부수효과 분리 불변을 지키며, 상세 규약은 위 "멀티 레포 오케스트레이션" 절이 단일 원본이다.

**v2.x 가산 이력(보존)** — 2.0 stable 동결 집합(11종) 위에 더해진 커맨드다.

- **`/tide:debug` (v2.7.0부터)**: 발견 우선 작업의 세션형 진입점(상세는 위 "debug 세션" 절).
  **기존 11종·`.tide/phase`·tide-guard 계약을 깨지 않는 순수 가산**이다 — phase에 `debug` 값이
  더해질 뿐 의미(단계명 한 줄)는 그대로이고 **가드는 한 줄도 고치지 않는다**(phase≠release라 기존
  규칙이 그대로 쓰기를 차단한다 — 위 "tide-guard hook" 절). 아직 stable 동결 집합에는 들지 않으며
  다음 major에서 승격 후보다.
