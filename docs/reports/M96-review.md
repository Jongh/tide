# M96 리뷰보고서 (review)

## 비판점

### 차단 (0건)

없습니다. 완료 기준 1~8을 원자료로 대조했고, 반증 패스에서도 차단 사유는 나오지 않았습니다.

- 금지 구분자 판정(`bad_seps` · `BadSeps` → `F26` · 축마다의 `seps` 행)은 여전히 원문 꼬리(`decl_tail_raw` · `DeclTailRaw`)만 읽습니다. 그래서 공용 읽기의 정규화가 M42 교훈(지우는 문자와 금지하는 문자가 겹치면 금지가 집행되지 않는다)을 깨지 않습니다. 등록표 `seps` 행이 모두 `bad_seps`를 거치는 것은 `tests/discover/run.sh`의 등록표 분기(`seps)` 갈래)에서 확인했습니다.
- 정규식 `[ \t\v\f\r]*[\t\v\f\r][ \t\v\f\r]*`는 awk(최좌단 최장 일치)와 .NET에서 같은 결과를 냅니다. 끝 처리(`sub` · `TrimEnd`)와 이어 붙인 혼합 연속(`a\t `)에서도 같습니다(반증 패스 확인).

### 권장 (2건)

1. **`rt_done_key` · `RtDoneKey`의 「최상단 표에도 있는 키」 조건을 아무 케이스도 고정하지 않았다** — M96이 셋째 칸(`dropdone`)에 더한 두 갈래 가운데 하나입니다. 이 조건을 지워도 하니스가 초록이었습니다. 반증 패스가 ps1 사본에서 `Part O` 128/0을 실측했습니다.
   - `O126`은 실물 문서에서 어느 쪽이든 0을 기대합니다.
   - `O128`의 `nodone` 사본은 직전 표에 `반영` 행이 아예 없습니다.
   - 합성 행 `rf-0`은 직전 표와 최상단 표 양쪽에 들어갑니다.
   그래서 셋 다 그 조건을 시험하지 못합니다. 결과적으로 생명주기 상태 ⒟(직전 `반영` 키가 최상단 표에서 빠진 회고)에서, `rf-119`가 닫으려던 공허한 0이 조건이 빠지는 회귀와 함께 소리 없이 되살아날 수 있었습니다. `vacuous-pass` 부류이지만 하니스 자기 코드를 훼손해야만 발동합니다. 그래서 `reachability-weighting`에 따라 권장으로 매기고 고쳤습니다(아래 부인 기록).
2. **하니스 README Part F 「묻지 않는 것」 괄호가 실측보다 넓게 적었다** — 「전 선언 사본에서 두 러너가 같았다」고 적었습니다. 그러나 impl 보고서 「위치별 탭 — 바꾼 뒤」 표에서 두 러너를 함께 잰 것은 전 선언 **가운데** 사본뿐입니다. 머리 · 끝 사본의 sh 칸은 「재지 않았다」입니다. impl 보고서 T01 ⑴의 「공용 읽기를 거치지 않는 선언 읽기가 남았다면 그 사본에서 두 러너가 갈렸을 것」도 같은 사본에 기대므로, 실제로 성립하는 것은 가운데 갈래뿐입니다.

### 사소 (2건)

3. **M96이 고친 주석 블록 옆에 낡은 문장이 남았다** — `tests/discover/run.sh`의 `decl_tail` 머리 주석에 두 문장이 남아 있었습니다.
   - 「정규식을 쓰지 않고 `index`+`substr`로 끊어」 — 이제 `decl_tail`은 `gsub`를 씁니다.
   - 「앞의 `tr -d '\r'`는 …」 — 바로 아래 `decl_tail_raw` 주석은 그것을 없앴다고 적습니다.
   `tests/discover/run.ps1` `DeclTail` 머리 주석의 「no regex on either side」도 같습니다.
4. **T01 산출물이 마일스톤 문구보다 좁다(수용 · 고치지 않음)** — 기준 1은 분할 자리마다 「쓰는 케이스」와 제외 사유를 요구합니다. impl 표는 꼴별 · 호출 수 집계와 범주별 사유로 대신했고, 기준 1 근거 칸에 그 대체와 사유(고친 자리가 공용 읽기 하나)를 밝혔습니다. T01 ⑵의 바꾸기 전 머리 · 끝 사본의 sh 칸은 「—」입니다. 바꾼 뒤 표에서는 세 선언의 머리 · 끝을 두 러너로 쟀으므로 기준 2⒞ · ⒟는 충족합니다. 반증 패스가 `start-point-map:` 머리 탭 사본을 다시 재 일치를 확인했습니다. 마일스톤 배경의 `-split '\s+'` 4는 오기이고 실측은 27입니다. impl이 바로잡았습니다.

## 수정 내용

- **이슈 1**: `O128`에 칸을 하나 더했습니다(두 러너).
  - 직전 섹션의 첫 `반영` 키(최상단 표에 있는지 따지지 않음)의 최상단 행을 지운 사본에서, `rt_done_key` · `RtDoneKey`가 고른 키가 최상단 표에 있으면 `intop`입니다. 기대는 `1|0|0|none|0|intop`입니다.
  - 조건이 빠지면 지운 키를 골라 `gone`으로 붉습니다. 키가 없으면 `nokey`라 역시 붉습니다.
  - 사본을 만들려고 `rt_lost_fixture` · `RtLostFixture`에 키를 직접 받는 선택 셋째 인자를 더했습니다. 기존 호출은 인자를 넘기지 않으므로 출력이 같습니다.
  - 하니스 README Part O 「직전 섹션의 열린 행 소실」 문단에 이 칸의 서술을 더했습니다. 케이스 수는 늘지 않습니다(같은 `O128`의 칸).
- **이슈 2**: README Part F 괄호를 「두 러너를 함께 잰 것은 전 선언 **가운데** 사본이고 거기서 같았다 — 전 선언 머리 · 끝 사본은 ps1만 쟀다」로 좁혔습니다.
- **이슈 3**: 두 러너의 꼬리 읽기 머리 주석에서 「정규식을 쓰지 않는다」를 원문 꼬리(`decl_tail_raw` · `DeclTailRaw`)로 한정했습니다. 소비자 정규화만 정규식이고 두 러너가 같은 패턴을 쓴다고 적었습니다. sh 쪽의 낡은 `tr -d '\r'` 문장은 「줄 끝 CR은 `decl_lines`가 벗긴다」로 바꿨습니다. ps1 편집은 ASCII만 썼습니다(비-ASCII 바이트 0 확인).
