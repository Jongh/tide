# M33 완료보고서 (impl)

## 개요

M33의 여섯 태스크를 전부 구현했다 — `docs/conventions.md`에 **`## 문서 자기서술 정합`** 절을
신설해 ① 하니스 케이스 수의 **단일 선언처**(각 `tests/{name}/README.md`의 `cases: N`)와 ② **역할
앵커 전파**(캐노니컬 `role-anchors:` 맵 → 캐노니컬 표 행 실재 + 소비자 문서 전파) 두 규약의 단일
원본을 두고, `tests/discover`에 **Part F**(13 케이스)를 더해 양 셸에서 기계로 집행하게 했다.
조사 과정에서 **실제 역할 드리프트 1건**(`/tide:release`의 `gh` 게시 능력이 캐노니컬에만 있고
README·사이트에 미전파)이 나와 함께 회수했고, `docs/project-context.md`의 스테일 2건(gh·`pr`
finalize 미반영 서술 · 이월 원장 M32 행 부재)과 `tests/discover/README.md`의 낡은 케이스 수
(29 → 실측 61, Part D·E 서술 부재)를 정정했다. 커맨드 12종·`.tide/phase`·tide-guard·프리플라이트·
보고서 섹션 구조는 한 줄도 바뀌지 않았다.

**집행력 실증(변형 주입 → 원복)** — 새 단언이 공허하게 통과하지 않음을 양 셸에서 실측했다.

1. **F1**: README 선언을 `cases: 61` → `cases: 60`으로 바꾸자 양 셸이 같은 단언에서

2. **F2**: `README.md`에서 앵커 `gh`를 지우자 양 셸이 `F2: README 전파(release=gh, 언급 시)`에서

**구현 중 발견·수정한 이슈 2건**

- **`cases:` 골격의 첫 매치 문제(수정함)** — 처음에는 선언을 `현재 케이스 수(cases): 61`로 썼는데,
  이 표기에는 `cases:`가 **없고**(`cases)`) 대신 산문의 "`cases:` 토큰으로 추출한다"는 설명 줄이 첫
  매치가 되어 러너가 **`1`을 추출했다**(뒤따르는 "F1"의 1). 양 셸이 똑같이 `got 1, want 61`로 FAIL해
  드러났다. 선언을 `(cases: 61)` 골격으로 고치고, 같은 파일 산문에서는 `cases:`가 아니라 `cases`로
  쓰도록 바꿨으며, **"같은 파일 산문에서 이 골격을 다시 쓰지 않는다"**를 규약에 한 줄로 못박았다.
- **F2의 판정 단위는 파일이지 셀이 아니다(설계 한계 — 기록)** — 실증 2를 처음 시도할 때 README의
  **역할 셀에서만** `gh`를 지웠는데 **통과했다**. 같은 행 **산출물 셀**의 "`+선택 gh 릴리즈/PR`"이
  남아 있었기 때문이다. 파일 전체에서 지워야 FAIL했다. F2는 "그 문서가 앵커를 갖고 있는가"를 볼 뿐
  "역할 셀에 있는가"를 보지 않는다 — 캐노니컬 쪽은 표 행 단위로 좁혔으나 소비자 쪽은 서술 형식이
  문서마다 달라 파일 단위로 두었다(후속 메모 1).

## 미해결·후속 메모

1. **F2의 소비자 판정이 파일 단위다** — 위에서 실측했듯 같은 파일 다른 자리에 앵커가 남아 있으면

   **리뷰가 현재 단위(파일)를 수용할지 판단해달라**.
2. **`docs/orchestration.md`를 소비자 범위에서 제외한 판단** — 그 파일은 `/tide:release`를 fleet
   핸드오프 맥락에서 언급할 뿐 역할 카탈로그가 아니다. 포함하면 "gh 게시"를 오케스트레이션 문서에
   끼워 넣어야 해 소음이 된다고 봤다. 다만 M32 이슈13(그 파일의 `11종` 스테일이 공개 페이지로 나갔다)이
   나온 곳이기도 하므로, **역할 서술 드리프트가 그 파일에서 실제로 관측되면 범위를 넓힐** 후보다.
3. **F1은 `discover`에만 배선됐다** — 나머지 4개 하니스 README에는 총 케이스 수 선언이 **아예 없어**
   (점검 결과) 확장하려면 선언을 신설해야 한다. 규약은 "각 하니스 README가 선언처"라고 일반형으로
   적었으므로, 선언이 없는 하니스는 **집행 대상이 아직 아닌** 상태다 — 규약과 배선 사이의 이 간극을
   리뷰가 볼 것(닫으려면 4개 README에 선언을 더하고 각 러너에 F1 동형을 넣는 별도 태스크).
4. **Part F 케이스 추가 시 F1의 위치 규율** — "F1이 마지막"이 깨지면 `누계 + 1` 오프셋이 어긋난다.
   러너 주석과 README에 적었지만 **기계로 집행되지는 않는다**(프롬프트 규율과 같은 성격의 잔여).
5. **`cases:` 첫 매치 순서 의존** — 선언이 산문보다 앞서야 한다는 순서 의존이 남아 있다. 규약으로
   "산문에서 골격을 다시 쓰지 않는다"고 닫았으나, 어기면 **조용히 틀린 수를 추출**하는 게 아니라
   FAIL로 드러난다(이번에 실제로 그렇게 드러났다) — 위험도는 낮지만 구조적 취약점으로 기록한다.
6. **역할 앵커는 3개로 얇게 시작한다** — 설계대로다(발명 금지). 역할이 바뀔 때마다 늘어나는 구조이나,
   **앵커가 없는 커맨드의 역할 드리프트는 여전히 무가드**다. 이번에 `release=gh` 하나가 실제 드리프트를
   물었다는 사실이 이 얇은 시작의 유효성 근거이자, 동시에 "나머지 9종은 아직 안 덮인다"는 한계다.
7. **병렬 디스패치 폴백(기록)** — 이 세션은 서브에이전트 사용이 제한돼 **메인이 위상 순서로 순차
   구현**했다(impl 스킬 "폴백 조건"의 Agent 미가용 경로). T01·T05는 파일 비겹침이라 원래 병렬
   후보였다 — 결과물에는 영향이 없으나 폴백 사실을 조용히 넘기지 않는다는 규약대로 기록한다.
