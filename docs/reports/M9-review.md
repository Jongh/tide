# M9 리뷰보고서 (review)

> `/tide:cycle`의 review 단계로 수행. 대상은 방금 impl을 마친 M9(최대 번호 마일스톤 +
> impl 보고서 존재 → 전제조건 충족).

## 비판점

### 차단 (0건)

없음. 완료 기준 6개가 정적/빌드로 충족됐고(impl 단일 원본·cycle 참조화·conventions/
README/project-context 일치·매니페스트 무수정·strict 빌드·사이트 porpoise 0건), 병렬의
실호출 실증만 release-후 도그푸딩으로 남는다(구조적, 전 사이클 공통). 특기할 점: M9의
검증이 **v0.9.0에서 새어든 잠재 회귀**(changelog 메타 문장의 literal "porpoise"가 단일
원본화로 사이트 유입)를 잡아 수정했다 — 검증 절차가 실제로 작동.

### 권장 (1건)

1. **파일 겹침 감지가 마일스톤 품질 의존 휴리스틱** — 병렬 안전장치는 "마일스톤의 파일
   변경 요약으로 태스크별 예상 변경 집합을 추정"한다. 그러나 마일스톤의 "파일 변경 요약"은
   **마일스톤 단위 표 하나**라 태스크별 파일 귀속이 항상 명확하진 않다(태스크 상세를 함께
   읽어 추정해야 함). 추정이 빗나가면 과병렬(충돌 위험) 또는 과순차(이득 손실)가 된다.
   완화책: impl 스킬이 "불확실하면 순차 폴백"을 기본값으로 두고 있어 안전쪽으로 기운다.
   차기 후보 — 마일스톤 템플릿의 태스크 상세에 "변경 파일" 줄을 권장 필드로 추가하면
   감지가 결정적이 된다. 이번엔 휴리스틱 + 보수 폴백으로 수용.

### 사소 (3건 — 수용)

2. **M9 병렬 동작의 런타임 미실증**(impl 후속 #1) — M9 자체가 같은 `impl/SKILL.md`를
   고치는 태스크 위주라 자기적용으로 병렬을 못 보인다. release-후 "독립 2태스크 이상
   마일스톤을 cycle로" 도그푸딩 시나리오로 정의됨. 활성 스킬 캐시 제약상 사후 실증, 수용.
3. **워크트리 격리 경로 미설계**(impl 후속 #3) — 파일 경쟁이 불가피한 병렬의 worktree+
   병합 절차는 "선택·기본 비활성"으로만 남겼다. 프롬프트로 안전한 병합 기술이 어려워 별도
   마일스톤 후보로 수용.
4. **단일 원본화의 "메타 용어 누수" 미규약화**(impl 후속 #2)·**README↔CHANGELOG 중복**
   (impl 후속 #4) — 이번 회귀는 리워딩으로 해소했으나, "제외 대상 용어를 메타 서술로도
   쓰지 않는다"는 규칙은 미도입이고 두 파일 중복도 잔존. 차기 후보로 수용.

## 수정 내용

- **회귀(테스트 중 발견)**: `CHANGELOG.md`·`README.md`의 v0.9.0 검증 문장 "빌드 출력
  porpoise 0건 실증" → "빌드 출력 **외부 귀속 표기** 0건 실증"으로 리워딩. 재빌드로 사이트
  porpoise 0건 회복 확인. (이 수정은 impl 단계에서 이미 적용·재검증됨)
- 그 외 리뷰 중 추가 결함 없음.

## 검증

- **완료 기준 대조**:
  ① `skills/impl/SKILL.md`에 병렬 디스패치(같은 레벨 ≥2개 동시 Agent 호출·레벨 배리어·
     전달 컨텍스트·반환 계약) 명시(실증).
  ② 파일 겹침 감지 → 겹치는 것만 순차 폴백, 워크트리 격리 선택·기본 비활성, Agent 부재·
     레벨 단일 → 순차 폴백 기술(실증).
  ③ 결과 병합·부분 실패(보존+재시도/중단)·tide-guard 정합(서브에이전트 phase=impl→git
     차단) 명시(실증).
  ④ `cycle/SKILL.md`에서 "구현 판단에 맡긴다 …" 제거 + impl 참조로 교체(실증).
  ⑤ conventions·README·project-context가 impl과 일치, 매니페스트 무수정(실증).
  ⑥ `mkdocs build --strict` 통과 + 사이트 porpoise 0건(회귀 수정 후 재검증) + 도그푸딩
     시나리오 보고서 정의(실증).
- **부수효과 분리**: impl·review 통틀어 git 없음. 서브에이전트 git 차단은 가드가 phase로
  기계 강제 — 병렬에서도 분리가 유지됨을 규약으로 못박음.
- **설계 건전성**: 병렬을 impl 단일 원본으로 두고 cycle·문서를 참조화한 것은 M8의 단일
  원본화 기조와 정합. 보수 폴백(불확실·겹침·Agent 부재·단일 → 순차)이 기본값이라 신규
  능력이 기존 동작을 깨지 않음(하위 호환).
- **미검증 잔여 리스크**: 병렬 실호출(사소2)·워크트리 경로(사소3)는 사후. 프롬프트 규약의
  특성상 "실제로 서브에이전트가 동시 디스패치되는지"는 다음 병렬형 마일스톤에서 확인.
