# M29 리뷰보고서 (review)

## 개요

M29(`/tide:debug` 세션 — 발견 우선 작업의 역방향 문서화 진입점)를 리뷰했다. 이 사이클은 **릴리즈
게이트의 판정 근거를 바꾸는** 변경(debug 보고서가 리뷰보고서 자리를 대신)이라, 회고 교훈(M20:
계약·안전 핵심 사이클은 적대 검증을 표준 게이트로)에 따라 **게이트 불변을 반증 시도로** 검증했다 —
즉 "판정 없이 배포되는 경로가 새로 열리지 않는지"를 시나리오로 공격했다. 그 적대 검증이 **게이트
누수 1건**(리뷰에서 직접 수정)과 **판정 기준의 비결정성 1건**(리뷰에서 직접 수정)을 드러냈다.
설계 핵심 전제였던 **가드 무수정**은 실증으로 확인됐다(양 셸 30/30, `git diff --stat hooks/` 빈
출력). **차단 결함 0.**

## 비판점

### 차단 (0건)

없음. 부수효과 분리는 모든 변경에서 보존되고(가드 무수정으로 `phase=debug`가 쓰기를 차단),
기존 11종 커맨드·phase·가드 계약은 불변이다.

### 권장 (2건 — 둘 다 리뷰에서 직접 수정)

1. **미릴리즈 debug 보고서가 여러 개면 게이트가 새는 결함 — 리뷰에서 수정** — impl이 쓴
   프리플라이트는 근거 후보를 "`debug-{N}.md`(**최대 번호**)"로 한정했다. 그런데 debug 세션을 두 번
   돌고 한 번에 릴리즈하면(세션1 → 세션2 → release) **두 세션의 수정이 모두 같은 릴리즈 커밋에
   실린다**. 최대 번호만 보므로 `debug-1`의 판정은 **검사 없이 배포**되고, 반대로 `debug-1`이
   "불가"여도 `debug-2`만 "가능"이면 통과한다. 이는 impl이 (c)항으로 review-vs-debug 쌍에 대해 닫은
   바로 그 구멍("한쪽만 보고 넘어가면 다른 쪽 수정이 근거 없이 배포된다")이 **debug-vs-debug 쌍에서
   그대로 열려 있던** 것이다. **영향**: 판정받지 않은 수정의 배포(안전 측이 아님 — 게이트 누수).
   **수정**: 근거 집합을 "**미릴리즈인 것 전부**"(리뷰보고서 + 미릴리즈인 모든 debug 보고서)로
   바꾸고 **전부 "가능"이어야** 진행하도록 고쳤다. 단일 원본(conventions "debug 세션 → 릴리즈 경로")과
   그 절차(`skills/release/SKILL.md`)를 함께 갱신.

2. **"미릴리즈" 판정 기준이 CHANGELOG 산문 grep이라 비결정적 — 리뷰에서 수정** — impl은 릴리즈
   여부를 "`CHANGELOG.md`에 해당 사이클/세션 항목이 이미 실렸는지"로 판단하게 했다. 그러나 CHANGELOG
   항목은 **증상·수정을 요약한 산문**이고 `debug-{N}` 같은 출처 표기를 요구하지 않으므로, "이 항목이
   debug-3에서 나온 것인가"를 **기계적으로 되짚을 수 없다**. 양방향으로 오작동한다 — 이미 배포된
   보고서를 미릴리즈로 오인해 재게이팅하거나, 미배포 보고서를 배포됨으로 오인해 **게이트를 건너뛴다**
   (후자가 위험). **수정**: 판정을 **결정적 신호**로 바꿨다 — "보고서 파일이 **마지막 릴리즈 태그의
   트리에 포함돼 있으면** 릴리즈된 것"(`git tag`·`git ls-tree <태그> docs/reports/` **읽기**로 확인).
   release가 사이클 산출물을 함께 커밋하므로 "태그에 포함됨 = 그 수정이 배포됨"이 성립하고, 태그가
   없으면(첫 릴리즈) 전부 미릴리즈다. CHANGELOG는 보조 확인으로 강등. **M28과의 상승효과**: 이
   기준이 성립하는 이유는 M28이 비-release phase에서 git **읽기**를 통과시켜 뒀기 때문이다 —
   `git ls-tree v2.6.0 docs/reports/`가 실제로 동작함을 확인했다. 정합을 위해 `skills/status/SKILL.md`의
   같은 기준도 함께 갱신했다(세 문서가 한 기준을 가리킨다).

### 사소 (3건)

- **debug 판정은 자기 자신에 대한 자기 판정(수용된 트레이드오프)** — 정규 사이클은 `impl`이 만든
  것을 별도 단계인 `review`가 비판적으로 검토하지만, debug는 자기가 고친 것을 자기가 "가능"으로
  판정한다. 이것은 결함이 아니라 **사용자가 결정 3에서 명시적으로 택한 트레이드오프**다(대안
  "debug 후 축약 review 필수"를 "가벼운 수정에 리뷰 한 단계가 다시 붙어 원래 무게 문제가 재발한다"는
  이유로 기각). 완화 장치는 있다 — 템플릿이 미해결 항목·잔여 리스크·검증 실패를 강제로 적게 하고,
  판정 규칙이 "미해결 **차단급** 항목이 있으면 불가"다. **재검토 트리거**: debug 경로로 낸 릴리즈에서
  회귀가 실제로 발생하면 축약 review 게이트를 별도 사이클에서 재검토한다.
- **카탈로그와 스킬의 인자 표기 불일치** — `docs/commands.md`는 `/tide:debug [증상 / done]`,
  `skills/debug/SKILL.md`의 `argument-hint`는 `[증상 설명 | done (세션 종료)]`이다. 마크다운 표 셀에
  `|`를 쓰면 열이 깨져 T05가 기존 선례(`[주제/M번호]`·`[pr/release]`)를 따른 것으로, **의미는
  동일하고 기존 커맨드들도 같은 축약을 쓰고 있다**(카탈로그는 요약, 스킬이 원본). 수용 — 고치려면
  스킬 쪽 `argument-hint`를 카탈로그에 맞춰 훼손해야 해서 得보다 失이 크다.
- **`.tide/debug-session` 잔재의 사용자 정리 경로가 안내되지 않을 수 있음** — status는 잔재를
  보고만 하고 고치지 않는다(읽기 전용 계약 — 옳은 설계). 다만 사용자가 세션을 **버리고** 싶을 때
  파일 수동 삭제가 필요한데 그 안내가 status 출력에 나오는지는 프롬프트 자산이라 정적으로 단언할 수
  없다(아래 "검증"의 라이브 영역). 저위험·후속.

## 수정 내용

- **권장 1 (게이트 누수)**: `docs/conventions.md` "debug 세션 → 릴리즈 경로" 불릿을 재구성해
  **근거 집합 = 미릴리즈인 것 전부**(리뷰보고서 + 미릴리즈인 모든 debug 보고서), **전부 "가능"이어야
  진행**, CHANGELOG에 **모든 출처** 반영으로 고쳤다. `skills/release/SKILL.md` 프리플라이트 1번의
  b·c 항을 같은 규칙으로 재작성(후보를 "최대 번호"에서 "미릴리즈 전부"로).
- **권장 2 (비결정성)**: 같은 두 파일에 **릴리즈 여부 = 마지막 릴리즈 태그 트리 포함 여부**(git 읽기)를
  판정 기준으로 명시하고, 태그 부재 시 전부 미릴리즈, CHANGELOG는 보조 확인으로 강등했다.
  `skills/status/SKILL.md`의 미릴리즈 서술도 같은 기준을 가리키도록 갱신해 **세 문서가 한 기준**을
  따르게 했다(단일 원본 = conventions).
- **사소 3건**: 코드·문서 무수정(수용·기록). 사유는 위 각 항목.

## 검증

**적대 검증 — 게이트 불변(판정 없이 배포되는 경로 없음)**: 시나리오로 반증 시도 — ① 열린 세션 +
release → **중단**(a항), ② debug-1 "가능"·debug-2 "불가" 둘 다 미릴리즈 → 수정 전엔 **통과(누수)**,
수정 후 **중단**, ③ 리뷰보고서 "가능" + debug "불가" 둘 다 미릴리즈 → **중단**, ④ debug 산출물 0개 +
세션 없음 → **현행과 동일**(하위 호환), ⑤ 태그 없는 첫 릴리즈 → 전부 미릴리즈로 취급. 수정 후 ②가
닫혀 "미릴리즈인데 판정을 안 본다"는 경로가 남지 않는다.

**적대 검증 — 가드 무수정 전제(결정 2)**: `hooks/tide-guard.{sh,ps1}` 무수정 상태에서 `phase=debug`의
쓰기 3종(`git commit -m x`·`git push`·`git tag -a v1 -m x`)이 **전부 BLOCK**, 읽기 3종(`git log`·
`git tag -l`·`git show HEAD:README.md`)이 **전부 ALLOW**. 양 가드가 `phase = release`일 때만 조기
exit 0 하고 나머지 모든 값에 동일 규칙을 적용하므로 `debug`는 코드 수정 없이 `impl`과 동일 판정을
받는다 — **전제가 실증됐다**. `git diff --stat hooks/` **빈 출력**으로 무수정 증명.

**영구 하니스(양 셸, 네이티브 실행 — 리뷰 수정 후 재실행)**:

| 하니스 | sh | ps1 |
|---|---|---|
| multi-repo (phase=debug 회귀 +6 신설) | **30 / FAIL 0** | **30 / FAIL 0** |
| discover (N=12 실측·12종 정합·카탈로그 이름) | **19 / FAIL 0** | **19 / FAIL 0** |
| site-includes | **28 / FAIL 0** | **28 / FAIL 0** |
| fleet · fleet-cycle · fleet-verify | 41·23·29 / FAIL 0 | 41·23·29 / FAIL 0 |

- multi-repo 24→30(시나리오 11 신설). **음성 통제 충족** — 같은 `debug` phase에서 읽기 통과와 쓰기
  차단을 함께 단언해 "가드가 살아 있으면서 읽기만 통과"임을 고정(통제가 없으면 가드가 죽어도 읽기
  케이스만 green). fleet 3종은 M28 baseline 동일(변경이 오케스트레이션에 무영향).
- **드리프트 가드 경과가 설계대로 작동**: T01이 스킬을 더해 N=12가 된 직후 `discover`가 예상대로
  FAIL 4건을 냈고, T05가 **문서만** 고쳐 19/0으로 해소했다 — 가드를 통과시키려 가드를 고치는 일은
  없었다(`tests/discover/run.sh` 무수정). 규약↔실행 동기화 메타 규칙이 기계적으로 집행됐다.
- **인코딩 규율**: `tide-guard.sh` 선두 `23 21 2f`(no-BOM), `tide-guard.ps1` 선두 `EF BB BF`(BOM 보존),
  신규 `skills/debug/*` no-BOM UTF-8.

**완료 기준 8개**: ① 세션 왕복(정적 — 아래 잔여) ② 빈 세션 방지(스킬 `done` 1항에 명시) ③ **가드
무수정 보호(실증 — 30/30 양 셸)** ④ 릴리즈 경로(권장 1·2 수정으로 강화) ⑤ 하위 호환(e항 + 적대
시나리오 ④) ⑥ status 인지(읽기 전용 유지 — 금지 줄에 파일 삭제 명시) ⑦ **드리프트 가드 19/0**
⑧ 계약 불변(phase 단계명 한 줄·가드 규칙·2.0 stable 11종 불변 — 전부 가산).

**잔여 리스크(솔직)**: 완료 기준 ①·②·④·⑥의 **런타임 동작은 프롬프트 자산이라 하니스로 집행할 수
없다** — 정적 대조(형식 일치·규약 정합·금지 줄 존재)까지만 검증했다. 특히 ① 항목 append가 컨텍스트
요약을 넘어 살아남는지 ② `done`이 4개 섹션을 실제로 채우는지 ③ release가 debug 판정을 근거로
통과하는지는 **첫 라이브 debug 세션에서만 확인된다**(기존 gh 게시·`pr` finalize 미실증과 같은 성격의
환경-이월). 사소 3건은 모두 저위험·수용.

## 릴리즈 판정

**가능** — 추천 버전: **v2.7.0 (minor)**

- **근거**: 차단 0. 권장 2건은 **둘 다 리뷰에서 직접 수정**(게이트 누수·판정 비결정성 — 둘 다
  릴리즈 게이트의 정확성 문제라 수용 대상이 아니었다). 사소 3건은 수용·기록(1건은 사용자가 명시적으로
  택한 트레이드오프, 2건은 저위험). 완료 기준 8개 중 실증 가능한 것은 전부 충족하고, 나머지는 라이브
  도그푸딩 영역으로 정직히 남긴다.
- **버전(minor 확정)**: 새 커맨드 `/tide:debug`·새 산출물 `docs/reports/debug-{N}.md`·새 phase 값
  `debug`가 **사용자 관찰 가능하게 더해진다** → patch보다 크다. **호환 파괴 아님** — 기존 11종의
  호출명·역할·산출물이 불변이고, `.tide/phase`는 여전히 "단계명 한 줄"이며(세션 번호는 별도 파일),
  **가드는 한 줄도 바뀌지 않았고**(차단 규칙·메시지·exit 2 불변), release 프리플라이트 확장은 순수
  가산(debug 산출물이 없으면 현행과 동일 동작)이다 → major 아님. 2.0 안정성 절의 "호환을 깨지 않는
  추가(새 커맨드)는 minor로 계속한다"에 정확히 부합하며, fleet 3종이 v1.x에서 가산된 뒤 다음 major에서
  동결된 선례와 동형이다(2.0 stable 집합은 11종 그대로, debug는 v2.7.0 가산).
