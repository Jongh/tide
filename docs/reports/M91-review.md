# M91 리뷰보고서 (review)

## 비판점

### 차단 (0건)

차단 등급 이슈는 없습니다. 새 판정(`G9`~`G27` · `O124`~`O127`의 새 갈래 · `P47`)마다 그 케이스만 붉히는 되돌림 행이 두 러너에 있고, 두 러너의 판정 경로가 같은 꼴입니다. 상세는 아래 「검증」입니다.

### 권장 (4건)

1. **케이스 ID 꼴을 다시 적은 자리가 옛 꼴 그대로였다**(반증 성립) — `ak_case_ids` · `AkCaseIds`는 고지 대응 축들(N · K · P · G)이 함께 쓰는 함수인데, 숫자 꼬리(`G8b0`)를 받도록 넓힌 사실이 새 `xr-case-exists` 정의에만 적혔습니다. 정의의 단일 자리인 안전 바닥 절 `case-exists`(「소문자 접미가 붙을 수 있다」), 공통 통제 절 `hc-case-exists`(「소문자 접미 허용」), 하니스 README Part N의 케이스 줄 서술(`"N{번호}{소문자 접미}:`)이 그대로였습니다. `xr-case-exists`의 문장은 숫자 꼬리가 G 축만의 확장처럼 읽혔습니다. CLAUDE.md 「규칙을 고치면 그 규칙을 재서술한 자리를 같은 편집에서 고친다」의 자리입니다. 같은 함수의 등록표 행 갈래는 숫자 꼬리를 받지 않는데, 이것도 적혀 있지 않았습니다(지금 그런 행은 없습니다). 문서가 코드보다 **좁게** 적은 것이라 집행력을 넓게 주장하는 `vacuous-pass` 부류는 아닙니다.
2. **완료 기준 3을 sh Part P 실측 없이 `충족`으로 적었다**(반증 성립) — 기준은 Part N · K · P의 출력 전문이 함수 변경 전후로 「두 러너 모두」 같기를 요구합니다. impl 보고서는 sh P 출력 전문을 뜨지 않았다고 같은 칸에 밝혔지만 판정은 `충족`이었습니다. pwsh P 대조도 `P47`을 더한 뒤라 함수 변경만 떼어 보지 못했습니다. 근거 칸이 비었음을 스스로 밝혀 숨긴 것은 아니지만, 판정이 근거보다 넓었습니다.
3. **T06이 요구한 완료 기준 대조 절의 서술이 빠졌다**(반증 성립) — 마일스톤 T06은 새 판정과 경계를 세 절(상호참조 무결성 · 회고 후속 항목의 소비 · 완료 기준 대조)에 적으라고 했습니다. 완료 기준 대조 절에는 `cc-ask-cases:`에 `cc-case-mapped=P47` 토큰 하나만 들어갔고, 제외가 칸마다 무게를 갖는다는 문장이 없었습니다. impl 보고서 T06 항목도 이 절을 말하지 않았습니다.
4. **`O126` 합성 기준이 최상단 표의 행에 기대는 것이 적혀 있지 않았다**(반증 성립, 리뷰가 범위를 넓힘) — 섹션 하나뿐인 문서에서 소실 통제의 기준은 최상단 표의 행을 옮긴 합성 직전 섹션입니다. 그래서 다음 둘이 적혀 있지 않았습니다.
   - 최상단 표에 열린 행이 없으면 첫 칸이 0이 되어 `O127`이(그 문서에서는 `O126`도) 붉습니다.
   - 리뷰가 더 따라가 보니 `반영` 행이 없을 때는 셋째 칸(`dropdone`)이 지울 행이 없어 0을 내고, 기대값도 0이라 **공허하게 통과합니다**.

   셋째 칸의 공허는 M89에 `O126`이 생길 때부터 문서 그대로를 기준으로 쓸 때도 같았습니다. 통제의 한 칸이 공허해지는 자리라 `vacuous-pass` 부류에 해당하지만, 등급은 권장으로 둡니다(아래 「부인 기록」).

### 사소 (2건)

5. **G8 집행 항목의 판정 이름 포인터가 반쪽이었다**(반증 성립) — 「절 안의 항목은 번호가 아니라 이름으로 가리킨다」의 집행 하위 항목은 `xr-no-ordinal`만 가리켰습니다. 그런데 같은 항목 안의 ⑴(인용 줄 추출 0건 FAIL)은 `xr-extract`로 묶인 판정입니다.
6. **`G10`~`G12`의 단독 되돌림 행이 없다** — impl 보고서 완료 기준 8 근거 칸과 후속 1이 「하지 않았다(사유)」로 밝혔습니다. 세 케이스는 라벨이 「본 검사」가 아닌 등록표 `count` · `seps` 행이라 단독 행 요구의 대상이 아닙니다. 같은 꼴의 `G9`가 `dupline`으로 단독으로 붉었습니다. 수용하고 고치지 않았습니다.

## 수정 내용

- **이슈 1**: `docs/conventions.md` 안전 바닥 절 `case-exists`에 숫자 꼬리(`G8b0` 꼴)와 「등록표 행의 ID는 숫자 꼬리를 받지 않는다」를 적었습니다. 공통 통제 절 `hc-case-exists`의 괄호에 「그 뒤 숫자 꼬리」를 더했습니다. `xr-case-exists`는 「같은 함수라 그 함수를 쓰는 축 모두에서 받는다」로 고쳤습니다. 하니스 README Part N 서술을 `"N{번호}{소문자 접미}{숫자 꼬리}:`로 고쳤습니다.
- **이슈 2**: 함수 변경만 떼어 쟀습니다. 지금 트리 사본과, 같은 사본에서 ID 꼴만 옛 `^[0-9]+[a-z]*$`로 되돌린 사본을 작업 트리 밖에 떴습니다. 두 사본의 출력 전문을 `cmp`로 견준 결과, sh P(47/0)와 pwsh P · N · K 모두 바이트 단위로 같았습니다. 이 값을 impl 보고서 완료 기준 3의 근거 칸에 「리뷰 중 측정」으로 덧붙였습니다. sh N · K는 impl이 이미 파일로 떠 같았습니다. 판정 `충족`은 이제 근거와 넓이가 맞습니다.
- **이슈 3**: 완료 기준 대조 절 `cc-case-mapped` 정의에 문장을 더했습니다 — 제외 줄을 통째로 지운 사본에서는 미대응이 늘고, 하나만 뺀 사본에서는 정확히 하나 는다. 제외가 실제로 다른 절의 판정인지는 묻지 않는다는 경계도 함께 적었습니다.
- **이슈 4**: 하니스 README Part O와 규약 "회고 후속 항목의 소비" 절의 `rf-117` 문장에 경계를 적었습니다 — 합성 기준은 최상단 표의 행에 기대고, 열린 행이 없으면 섹션 수 통제가 붉으며, `반영` 행이 없으면 셋째 칸이 공허하게 통과한다. 처음 쓴 문장은 「둘 중 하나가 없으면 붉다」였는데, 셋째 칸을 따라가 보니 거짓이라 바로 고쳤습니다.
- **이슈 5**: G8 집행 항목의 포인터를 「`xr-no-ordinal` — 아래 ⑴의 추출 0건은 `xr-extract`」로 고쳤습니다.
