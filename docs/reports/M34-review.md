# M34 리뷰보고서 (review)

## 비판점

### 차단 (1건 — 수정 완료)

1. **새 가드 G1이 특정 입력에서 조용히 죽는다 (공허 통과)** — `tests/discover/run.sh`의 `cite_miss()`가
   `grep -qxF "$c" "$SBX/anchors.txt"`를 쓰는데, 인용 이름이 `-`로 시작하면 grep이 그것을 **옵션**으로
   읽는다. 그러면 패턴 인자가 없어 grep이 파일명을 패턴으로 삼고 **stdin을 읽으며**, 그 stdin이 바로
   이 while 루프의 입력이라 **나머지 인용이 통째로 소비돼 미검사로 남는다**. 결과는 "FAIL"이 아니라
   **miss=0 통과**다 — 가드가 죽었는데 green이 된다. 격리 재현:
   ```
   anchors=[앵커A,앵커B]  cites=[-v,앵커A,앵커B]
   → 루프가 1회 만에 종료, miss=0  (기대: miss=1)
   ```
   레포에 실제로 주입해도 같았다 — `"-v"`와 `"명백히없는앵커"` 두 인용을 넣으면 수정 전 `run.sh`는
   **PASS 68/FAIL 0**(둘 다 놓침), `run.ps1`은 FAIL. **양 셸 동일 판정**이라는 이 하니스 계열의 기본
   계약도 함께 깨진다. M32 리뷰가 닫은 "토큰은 있는데 공허하게 통과"와 정확히 같은 부류이고, 하필
   그 부류를 막으려고 만든 가드에서 났다.

### 권장 (4건 — 전부 수정 완료)

2. **줄바꿈된 인용 6건이 추출에서 조용히 빠졌다** — 인용 골격이 줄 단위라, 파일명과 따옴표 구획이
   서로 다른 줄에 있으면 가드가 **보지 못한다**. 실측으로 `README.md`·`docs/project-context.md`·
   `skills/kickoff/SKILL.md`·`tests/discover/README.md`(2곳)·`tests/fleet/README.md` **6건**이 그 상태였다
   (전부 실재 앵커를 가리키고 있어 완료 기준 3 자체는 사실로 성립하나, **가드가 검사한 적이 없는**
   인용이었다). impl 보고서는 "파일명이 바뀐 인용"이라는 다른 한계만 적었고 이 구멍은 적지 않았다.
3. **`run.ps1`이 빈 따옴표 구획을 인용으로 세어 셸 간 판정이 갈린다** — `""`(또는 공백뿐인 구획)이
   든 줄에서 `run.sh`는 빈 줄로 떨어뜨려 무시하고, `run.ps1`은 `''`를 인용으로 세어 앵커에 없으므로
   miss로 잡는다. 실측: 프로브 문서 하나로 **sh 68/0 vs ps1 FAIL G1(got 1)**.
4. **축약이 `### 부수효과 분리 불변`의 규범을 양방향으로 흔들었다** — 두 불릿을 합치면서
   "둘 다 처리 전 phase=release 잔재 레포를 **점검**해"가 됐는데, fleet-cycle의 실제 규정은
   **제외하고 경고**(필수 사전 점검, `skills/fleet-cycle/SKILL.md`도 동일)라 **약해졌고**,
   fleet-verify의 실제 규정은 **의심 시** 점검(`### 통합 검증`·`skills/fleet-verify/SKILL.md`)이라
   **강해졌다**. impl 보고서의 "의미 손실 0" 주장에 대한 반례이며, 하니스가 이 문구를 앵커하지 않아
   Part B~G 통과는 여기서 아무것도 보증하지 못한다.
5. **`docs/project-context.md`가 자기 파일의 규칙을 어기고 낡은 수를 박았다** — M34 이월 원장 행이
   `양 셸 67/67`이라는 **케이스 수**를 적었는데, 같은 파일이 위에서 **"케이스 수는 이 문서에 적지
   않는다 — 단일 선언처는 각 하니스의 `tests/{name}/README.md`"**라고 선언한다. 게다가 이 문서는
   **살아 있는 문서**라 이력 예외(그 시점 값 허용)로도 덮이지 않는 자기모순이고, 리뷰 수정 후에는
   값 자체도 틀렸다. M33·M34가 막으려는 드리프트를 M34가 스스로 만든 셈이다.

### 사소 (5건 수정 + 2건 기록)

6. **CRLF 내성 부재** — `anchor_set()`의 `tr -d ' '`가 CR을 걷지 않아, CRLF로 체크아웃된 규약에서는
   앵커 이름 끝에 `\r`가 붙어 **전건 오탐**이 될 수 있다. Git Bash grep이 CR을 가려 줘 이 환경에서는
   드러나지 않으나(실측으로 확인), POSIX grep은 가려 주지 않아 셸·플랫폼별로 판정이 갈린다.
7. **공백이 든 경로에서 파일 목록이 쪼개진다** — `for f in $(living_docs)`는 단어 분리를 타므로
   경로에 공백이 있는 클론에서 깨진다. 같은 러너의 기존 코드는 글롭을 직접 도는 안전한 형태다.
8. **dot 디렉터리 스캔 범위가 셸마다 다르다** — POSIX 글롭(`skills/*/*.md`)은 `.foo`를 건너뛰지만
   `Get-ChildItem -Directory`는 Windows에서 `.foo`를 포함한다(선행 점은 Hidden 속성이 아니다).
   `tests/.어떤디렉터리/README.md`에 인용을 두면 두 셸의 판정이 갈린다.
9. **승격한 헤딩 앞에 빈 줄이 없다** — `### 릴리즈 빌드 출력 검증`이 앞 목록 항목에 바로 붙어 있다
   (파일 안에서 도입부 마커를 뺀 유일한 사례). python-markdown 기준으로는 정상 렌더되나, 문서 위생을
   주제로 하는 사이클에서 남길 흠은 아니다.
10. **impl 보고서 수치가 리뷰 수정 뒤 낡았다** — 보고서는 impl 종료 시점의 실측(67 케이스·1022줄)을
    적었고 그 시점엔 옳았으나, 리뷰가 케이스와 줄을 더해 트리와 어긋나게 됐다.
11. *(기록 — 미수정)* **`"병렬 디스패치"` 인용이 실제 제목과 어긋난다** — `docs/conventions.md`·
    `docs/project-context.md`·`skills/cycle/SKILL.md`가 `` `skills/impl/SKILL.md`의 "병렬 디스패치" 절 ``
    로 부르는데 실제 제목은 `## 병렬 디스패치 (독립 태스크 동시 실행)`이다. **v2.10.1에도 동일하게
    있던 선존 항목**이고, 신설 규약의 대상은 "conventions를 인용하는 문서"라 **M34 범위 밖**이다.
    다만 리뷰의 "살아 있는 인용이 전부 실재 앵커를 가리킨다"는 주장은 **"conventions 인용에 한해"**로
    좁혀야 한다.
12. *(기록 — 미수정)* **`tests/multi-repo/run.ps1`이 런처에 따라 1건 FAIL한다** — Git Bash에서
    `pwsh -File`로 띄우면 BOM 입력 케이스가 실패하고 PowerShell 콘솔에서 띄우면 통과한다. 콘솔
    코드페이지 의존이며 **`v2.10.1`에서도 동일**하게 재현되는 선존·M34 무관 사안이다. 아래 검증의
    "양 셸 FAIL 0"은 PowerShell 콘솔 기준임을 명시한다.

## 수정 내용

  수정 후 같은 주입에 **양 셸이 동일하게 `G1 got 2, want 0`**으로 FAIL한다.
- **이슈 2**: 줄바꿈된 인용 6건을 **한 줄로 정리**하고(`README.md`·`docs/project-context.md`·
  `skills/kickoff/SKILL.md`·`tests/discover/README.md`×2·`tests/fleet/README.md`), 재발을 막을

  상호참조 무결성`)에 "인용은 한 줄 안에 쓴다"를 명시하고, **G3가 잡지 못하는 잔여 형태**(파일명만
  있고 구획이 통째로 다음 줄 — 정상 경로 언급과 구별 불가)를 규약과 하니스 README에 정직하게 고지했다.

- **이슈 9**: 승격 헤딩 앞에 빈 줄을 넣었다.
- **이슈 10**: impl 보고서 본문은 impl 단계의 기록으로 **보존**하고(정오표 절의 취지 — 관측 기록을
  덮어쓰지 않는다), 개요에 **리뷰 반영 고지** 한 문단을 더해 현재 트리 값(68 케이스·1029줄)과
