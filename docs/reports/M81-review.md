# M81 리뷰보고서 (review)

## 비판점

### 차단 (0건)

- 차단 등급으로 매긴 이슈는 없다. 고친 두 자리(워크스루 release 항목 · 제목 줄)는 release 스킬의 실제 동작과 맞고, 사이트 앵커와 하니스가 무는 자리는 그대로다.

### 권장 (2건)

1. **`site/docs/concepts.md` 「전제조건 · 프리플라이트」 표의 release 행이 집행을 사실과 다르게 적었다** — 「① review 판정 "가능" ② 테스트 통과 ③ 워킹트리 확인 → 실패 시 git 작업 없이 중단」이라고 적었는데,
   release 스킬의 워킹트리 확인은 막지 않는다(무관한 변경이 있으면 목록을 보이고 확인을 받은 뒤 진행하며, `continuous`면 확인 없이 진행한다). 반대로 실제로 막는 사이트 빌드 출력 제외 용어 스캔은 표에 없었다.
   M81 이전부터 있던 서술이고(반증 패스가 찾았다), M81이 고친 것과 같은 부류(release 서술이 실제 동작과 다름)다.
2. **README GitHub 앵커가 바뀐다는 CHANGELOG 노트 한 줄이 이월로만 남았다** — 마일스톤 T02는 제목을 바꾸면 「보고서와 CHANGELOG 노트에 한 줄로 적는다」고 요구한다. impl은 보고서에만 적고 CHANGELOG는 후속 1로 넘겼다.
   노트는 release가 쓰므로 그 처리는 맞다. 다만 release 스킬에는 impl 후속을 노트로 옮기는 절차가 없어, 여기 적지 않으면 조용히 빠진다. 아래 `다음 단계`에 release 때 할 일로 적는다.

### 사소 (4건)

3. **impl 보고서가 프리플라이트 셋을 「실패하면 막는 셋」이라 적었다** — 셋째(워킹트리 확인)는 막지 않는다. 워크스루 문장은 「검사합니다」만 말하므로 「맞음」이라는 결론은 그대로다.
4. **impl 보고서 개요의 「CHANGELOG만 갱신」의 「만」이 넓다** — release는 버전 파일과 마일스톤 릴리즈 표지도 고친다. 워크스루의 새 문장은 「만」을 말하지 않아 거짓이 아니고, 범위어를 더한 쪽은 보고서다(`rf-92` 부류의 작은 사례).
5. **impl 보고서 T01의 범위 선언이 실제로 돌린 검색보다 좁았다**(`scope-same-search`) — 적은 패턴 · 대상은 `CHANGELOG/README|…` · 다섯 경로였고, 실제 검색은 T02 제목 줄까지 담은 패턴으로 저장소 전체(이력 두 폴더 제외)를 훑었다. 실제가 더 넓어 결론은 서지만 선언이 그 검색과 같지 않았다.
6. **`skills/release/SKILL.md` 운영 주의의 「CHANGELOG/README 릴리즈 노트」가 README에 노트가 있다는 옛 전제를 담고 있다** — 규약 "버전 · CHANGELOG" 절은 README에 포인터만 두라고 한다. impl은 「쓰지 말라는 주의라 대상이 아니다」로 넘겼다.
   완료 기준 6(`skills/` 변경 0)이 막아 이 사이클에서 고칠 수 없고, impl 후속에도 없었다. 후속으로 남긴다.

## 수정 내용

- **이슈 1**: `site/docs/concepts.md` 표의 release 행 ③을 「사이트 빌드 출력 제외 용어 0건(사이트가 있는 경우)」로 바꾸고, 표 아래 문단에 「워킹트리 확인은 중단 조건이 아닙니다」 · 확인 뒤 진행 · `continuous`면 확인 없이 진행 세 문장을 메일 어투로 더했다(산문 줄표 · 「」 없음).
- **이슈 3**: impl 보고서 T01 첫 대조 항목에 정정을 적었다(셋째는 막지 않는다 · 결론 유지).
- **이슈 4**: impl 보고서 개요를 「README는 고치지 않는다. 버전 파일과 마일스톤 릴리즈 표지도 고치지만 워크스루는 기본 흐름만 적는다」로 고쳤다.
- **이슈 5**: impl 보고서 T01의 범위 선언을 실제 검색(패턴 · 대상 · 대조 항목)으로 고쳤다.
- **이슈 2 · 6**: 고치지 않았다. 2는 release 단계의 일이고(`다음 단계`), 6은 `skills/` 변경이라 기준 6 밖이다(후속).

**검증 범위 선언**(`scope-declared`)

- **같은 서술의 다른 자리 훑기(이슈 1 · 6의 발견)**
  - 패턴: `버전 범프|README.{0,20}(갱신|업데이트|수정)|(갱신|업데이트).{0,10}README` (리뷰) · `CHANGELOG/README`(반증 패스)
  - 대상: 저장소 전체 파일(`docs/reports/` · `docs/milestones/` 제외 — 사이클 이력)
  - 대조 항목: 「release가 README를 갱신한다 · release 프리플라이트의 막는 조건을 적은 서술」
  - 루트: 저장소
  - 결과: README · `docs/commands.md` · 규약 · 스킬 설명의 「버전 범프 → CHANGELOG」는 맞다. `site/docs/concepts.md` 표 행(이슈 1)은 반증 패스가 프리플라이트 서술을 읽다가 찾았다 — 위 패턴에는 걸리지 않는다. 그래서 「프리플라이트를 서술한 자리 전부」는 「일부를 보았다」에 해당한다. `README.md` 「사이클」 절과 `docs/commands.md`의 「프리플라이트를 통과해야 git 작업을 시작합니다」는 확인 뒤 진행을 통과로 읽을 수 있어 고치지 않았다.
- **앵커 링크 훑기(T02)**
  - 패턴: `#hook|hook-|getting-started#|%EC%88%98`(리뷰) · 반증 패스가 `#hook\b|%EC%88%98%EB%8F%99|수동-복사|getting-started(\.md|/)#|README(\.md)?#`로 저장소 전체(이력 폴더 포함)
  - 대상: 저장소 전체 파일
  - 대조 항목: 「바뀐 제목의 사이트 `id`나 GitHub 앵커를 가리키는 링크」
  - 루트: 저장소
  - 결과: `CHANGELOG.md`의 `README.md#changelog` 한 건(다른 제목)과 하니스의 `hook-` 낱말뿐이다. 그 제목을 가리키는 링크는 0건이다.

**기대는 주장 대조**(`lean-branches-stated`)

- impl의 「제목을 바꿔도 사이트 링크가 깨지지 않는다」는 `toc` 기본 slugify가 그 제목을 `hook`으로 만든다는 사실에 기댄다. 갈래는 둘(slugify가 비 ASCII를 버림 · 같은 페이지에 `hook`을 내는 다른 제목이 없음)이고, 둘 다 빌드 출력의 `id` 목록 전후 `diff` 0과 `mkdocs.yml`의 `toc`에 사용자 slugify가 없다는 것으로 성립한다.
