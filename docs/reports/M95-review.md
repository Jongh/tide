# M95 리뷰보고서 (review)

라운드 1 리뷰입니다(재작업 라운드 1). 라운드 0 리뷰는 판정 `불가`(차단 2 · 권장 1 · 사소 6)였고, 그 내용은 `docs/reports/M95-impl.md`의 「라운드 1 — 리뷰 반환 처리」가 항목별로 받았습니다. 이번 라운드의 재작업은 이 리뷰와 같은 세션이 구현했습니다 — 판정자와 실행자가 같다는 점을 의식하고 반증을 독립 서브에이전트로 돌렸습니다.

## 비판점

### 차단 (0건)

- 라운드 0의 차단 둘이 닫혔는지 다시 쟀습니다.
  - **차단 1(`F58`의 손 목록)**: 닫혔습니다. 기대 집합은 러너 소스의 실행 수 케이스 줄(`rc_ids` · `RcIds`)에서 나오고, `F59`가 그 파생을 통제합니다. 실행 수 케이스 없이 새 반복을 더하면 두 러너에서 `F58`이 붉습니다(impl 되돌림 `r-newloop-nocount`). 반증 패스는 `chk` · `Chk` 밖에서 케이스를 내는 자리가 없음도 확인했습니다(`pass` · `fail` 증가는 그 두 함수 안에만 있다). 남는 것은 선언된 경계(실행 수 케이스의 기대값을 손 상수로 두면 초록)입니다.
  - **차단 2(꼬리 탭)**: **끝 탭** 쪽은 닫혔습니다. 공용 꼬리 읽기가 끝 연속을 떼고, 금지 구분자 판정은 원문을 읽습니다. 반증 패스는 `start-point-map:` 끝 탭에서 두 러너 `{W138}`, 끝 U+3000에서도 두 러너가 같은 집합임을 쟀습니다. `decl_lines`를 바로 부르는 소비자는 `decl_tail_raw`뿐입니다. 줄 가운데 탭은 아래 권장 1입니다.

### 권장 (2건)

1. **줄 가운데의 탭에서는 두 러너가 여전히 다른 케이스를 붉힌다 — `rf-124`는 끝 탭만 닫혔다** — 반증 패스 재현(사본): `docs/conventions.md` 104행 `start-point-map:`의 `=impl ` 뒤 공백을 탭으로 바꾸면 sh W 161/1 `{W138}` · ps1 W 158/4 `{W118, W119, W137, W138}`(`sp-shape-count=3`)입니다. 원인은 라운드 0 차단 2와 같습니다(ps1 `-split ' '` 대 awk 기본 분할) — 자리가 줄 끝에서 가운데로 옮겨 갔을 뿐입니다.
   - 문서 쪽: 하니스 README Part F 「묻지 않는 것」과 두 러너 주석은 줄 가운데 탭을 경계로 적었습니다. impl 후속 6도 「재지 않았다」고 적었습니다. 그러나 마일스톤 목표 문장(`docs/milestones/M95.md` 6행 — 「선언 줄 꼬리의 탭을 두 러너가 같게 읽는다」)은 좁혀지지 않았고, `rf-124`의 처분 범위에 나머지가 적히지 않았습니다. 라운드 0이 보완 방향으로 적은 「일부만 맞춘다면 목표 문장과 `rf-124`의 처분 범위를 좁혀 적는다」 가운데 뒤쪽이 빠졌습니다.
   - 등급: 권장(부인 기록 — 아래 `다음 단계`). 두 러너 모두 붉어 조용한 통과가 아니고, 경계가 README 「묻지 않는 것」에 공개돼 있습니다. `retro-rows:`는 회고가 「집었다」로만 읽고 반영 여부는 사람이 보고서를 보고 판단합니다(`skills/retro/SKILL.md` 4 · 5). 그러므로 기계가 행을 조용히 닫는 자리는 없습니다.
   - in-review 처리: impl 보고서 후속 6에 이 재현과 「`rf-124`는 끝 탭만 닫혔고 줄 가운데 탭이 그 나머지다」를 적었습니다. 마일스톤 문서는 계획 기록이라 고치지 않았습니다. 고치는 일(소비자 분할 폭을 맞추거나 금지 구분자 앞에서 읽기를 멈추는 것)은 다음 회고가 `rf-124`의 나머지로 받습니다.
2. **라운드 1의 `decl_tail` 변경이 두 러너 주석에 거짓 불변식을 남겼다** — `tests/discover/run.sh` 112행 근처 · `tests/discover/run.ps1` 143행 근처가 「표지 추출과 구분자 검사가 같은 문자열을 보는 단일 자리」라고 적고 있었습니다. 라운드 1부터 구분자 검사는 원문(`decl_tail_raw` · `DeclTailRaw`)을, 소비자는 끝 연속을 뗀 꼬리를 봅니다. 그 차이가 M42 차단 1의 반대 방향(검사가 더 많이 본다)이라 해롭지 않다는 근거를 적어 고쳤습니다.

### 사소 (6건)

3. **규약 형제 설명 항목 규칙이 넓어진 머리 판정보다 좁았다** — `docs/conventions.md` 145행 근처는 설명 항목이 재작업끝 머리 전체로 시작하지 않는다고만 적었습니다. 라운드 1이 `sp-shape-count`의 셋째 머리를 굵은 판정 머리 전체(``**판정 ` ``)로 넓혔으므로, 그 머리로 시작하는 설명 항목은 갈래 모양 줄로 셉니다(시끄러운 쪽). 규칙 문장을 굵은 판정 머리로 맞췄습니다.
4. **`dn_names` · `DnNames` 주석의 「원문 꼬리(`decl_tail`)」** — `run.sh` 174행 · `run.ps1` 217행(반증 패스 지적 2). 원문 읽기의 이름을 `decl_tail_raw` · `DeclTailRaw`로 고쳤습니다.
5. **impl 보고서의 라운드 0 서술 셋이 지금 코드와 다르다** — T02의 `LOOP_IDS` · T03의 원문 꼬리 이름 · T06의 `cases:` 883(반증 지적 3). 셋 모두 「라운드 0 기록 — 라운드 1에서 바뀜」으로 표시했습니다.
6. **sh `rc_ids`만 들여쓰기 없는 케이스 줄을 셌다** — ps1 `RcIds`는 `^[ \t]*Chk`, sh는 `^chk`였습니다(반증 지적 4). 들여쓴 sh 실행 수 케이스 줄이면 sh `F58`만 붉었을 것입니다(거짓 붉음). sh 두 패턴(`rc_ids` · `F59` 사본)을 `^[[:blank:]]*chk`로 맞췄습니다.
7. **⑸ 문장이 `F58`보다 넓었다** — 「반복이 새로 생기면 그 ID의 실행 수 케이스 줄 없이는 붉다」. `F58`은 두 번 이상 낸 ID만 보므로, 항목이 하나인 목록을 도는 반복은 목록이 둘로 늘 때부터 붉습니다(반증 지적 5). 규약 ⑸ 문단과 README Part F에 그 조건을 적었습니다.
8. **완료 기준 6의 「같은 이름(⑴ · ⑵ · ⑹)」** — README 머리 단락과 E2 완료 신호 4가 세 경계를 산문으로만 적고 번호를 달지 않았습니다(반증 지적 6). 두 자리에 ⑴ · ⑵ · ⑹을 달았습니다.
