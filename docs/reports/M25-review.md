# M25 리뷰보고서 (review)

## 개요

M25(`pr` 모드 머지 후 마무리 자동화 — 상태 인지 release)를 리뷰했다. M25는 신규 코드·테스트가 없는
프롬프트 스킬+문서 사이클이라(회고 교훈 #1: 가산 사이클은 단일 비판 리뷰), 교훈 #2("테스트 통과 ≠ 정합 —
자동 테스트가 닿지 않는 산출물일수록 직접 검토")에 따라 **finalize 절차의 정합·멱등·안전을 정적으로 직접
검토**했다. 외부 대면(태그 push·릴리즈 공개) 마무리의 **부분 실패 복구 결함**을 적발해 리뷰에서 직접
수정했다.

**차단 결함 0. 최종 판정: 가능 — 추천 v2.4.0 (minor).**

## 비판점

### 차단 (0건)

없음.

### 권장 (1건 — 리뷰에서 수정 완료)

1. **finalize 멱등이 태그·릴리즈를 묶어 처리해 부분 실패를 복구하지 못함** — 원안은 "태그 `v{버전}` **또는**
   릴리즈가 이미 있으면 중복 생성 없이 보고"였다. 이 "either → skip both" 의미는 **부분 실패 시나리오**를
   막지 못한다: finalize가 `git push` 태그까지 성공하고 `gh release create`에서 실패하면, 재실행 시 "태그가
   이미 있음"으로 **둘 다 건너뛰고 보고**해 **누락된 릴리즈를 영영 만들지 못한다**(사용자가 수동 보정해야
   함). finalize는 외부 대면·재실행이 전제인 마무리라 멱등이 핵심 가치인데, 묶음 처리가 그 가치를 부분적으로
   깬다. **영향**: 부분 실패 후 자동 복구 불가(회복은 수동). **수정**: 태그와 릴리즈를 **각각 독립으로**
   선확인(`git tag`·원격 / `gh release view`)해 **이미 있는 것은 건너뛰고 없는 것만 생성**하도록 강화했다 —
   둘 다 있으면 보고만, 한쪽만 있으면 나머지를 마저 만든다(부분 실패 복구). `docs/conventions.md`(중복 생성
   회피 규약)·`skills/release/SKILL.md`(merged 분기 + 운영 주의 #5) 세 곳을 정합시켰다.

### 사소 (3건 — 수용)

- **[sn1] open/closed 경로가 프리플라이트·phase=release 기록 후 no-op로 끝남** — PR 상태 판정이 phase=release
  기록 후 step 1에 있어, `pr` 모드가 open(대기)·closed(중단)이면 프리플라이트(테스트 등)와 phase=release
  기록을 거친 뒤 부수효과 없이 돌아온다. **수용 사유**: 두 경로 모두 git·태그·릴리즈 **무변경**이라 안전하고
  (phase는 release→idle로 복원), 상태 판정을 프리플라이트 앞으로 당기면 절차 구조가 복잡해진다. 약간의 낭비
  뿐 결함 아님.
- **[sn2] finalize 라이브 미검증**(출처: M25-impl 후속1 / M24 sn1과 동질) — 상태 인지 분기·머지 감지·태그/
  릴리즈 마무리는 `gh`·실제 PR 머지 상태 의존 프롬프트 로직이라 자기완결형 라이브 하니스로 덮을 수 없다.
  **수용 사유**: tide 전체가 자동 러너 없는 프롬프트/셸 플러그인(project-context). 정적 검토로 분기·멱등·안전을
  확인했고, 실제 생성→머지→finalize 전체 경로는 다음 `pr` 도그푸딩으로 라이브 회수한다.
- **[sn3] `fleet-verify`의 `strip_bom`/`StripBom` 미추출** — M24 sn3에서 이월된 저위험 정리 후보로 이번 범위
  밖(`read_deps`/`toposort` 미사용). 잔존.

## 수정 내용

- **이슈 1 (독립 멱등)**: finalize의 중복 생성 회피를 **독립 멱등**으로 바꿨다. `docs/conventions.md` "릴리즈
  게시 (gh)"의 멱등·안전 절을 "태그·릴리즈를 각각 독립 선확인 → 이미 있는 것 건너뛰고 없는 것만 생성, 한쪽만
  있으면 나머지를 마저 만든다(부분 실패 복구)"로, `skills/release/SKILL.md`의 merged 분기와 운영 주의 #5도
  동일 의미로 강화했다. 미머지 태그 금지·버전 sanity 불변.

## 검증

**정적 검토(프롬프트 스킬·문서 — 교훈 #2 직접 적용)**:
- **conventions↔SKILL 정합**: `pr` 모드 상태 분기(merged/open/closed/none)가 양쪽 일치하고, SKILL은 상세를
  재서술하지 않고 conventions "릴리즈 게시 (gh)" 절을 참조한다(스킬=절차/conventions=규약 분담 유지).
- **분기 안전 순서**: PR 상태 판정을 step 1(검증 게이트 후·**파일 편집 전**)에 둬 finalize·대기·중단이 버전
  범프·CHANGELOG(2·3)를 건너뛴다 — 이미 머지된 파일 재편집 방지(M24 "검증을 부수효과 전에" 원칙 계승).
  **생성(none) 경로만** 2·3을 실행한 뒤 릴리즈 브랜치에 commit하므로 기본 브랜치 working tree는 깨끗하게
  유지된다(M24 동작 불변).
- **멱등·안전**: ① 미머지 태그 금지(`gh` merged 확인 후에만 태그), ② **독립 멱등**(수정 후 — 태그·릴리즈
  각각 → 부분 실패 복구), ③ 버전 sanity(머지된 버전 파일이 요청 버전과 다르면 태그 없이 중단 — 엉뚱한 머지
  방지; 버전 파일은 `2.4.0`, 인자/태그는 `v2.4.0`라 'v' 정규화 전제).
- **불변**: `release` 모드·push-only·`gh` 부재 경로 무변경(특히 `gh` 부재 시 바이트 동일). tide-guard
  비확장(`gh` 비게이트)·"게시는 release에서만"(phase=release) 유지. 새 커맨드·토큰 0(`pr` 모드 동작 확장).

## 릴리즈 판정

**가능** — 추천 **v2.4.0 (minor)**.

근거: 차단 0. 권장 1건(독립 멱등)은 **리뷰에서 직접 수정**, 사소 3건 수용. M25는 `pr` 모드에 **머지 후

영향도에 맞다(M24 v2.3.0 gh 게시 모드 minor 선례와 동형). `gh` 부재·`release`·push-only 경로는 바이트
동일. 2.0 stable 계약(11종 커맨드 호출명·역할·오케스트레이션 규약·`.tide/phase`/tide-guard·보고서·마일스톤
형식)·M22 드리프트 가드(B1/B2/B3)·M24 검증 게이트·tide-guard 비확장 전부 불변. M24 sn2(`pr` 머지 후
핸드오프)를 종결했다.
