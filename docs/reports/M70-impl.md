# M70 완료보고서 (impl)

## 개요

- **stale 판정 대상의 신호를 바꿨다.** 「최대 번호」를 버리고, `retro-mark-since:`(M70) 이상의 마일스톤은 **릴리즈가 남기는
  표지** `- released: v{버전}`으로, 그 미만(표지가 없던 시절)은 **기반 버전의 CHANGELOG 머리 자리**로 가린다. 그래서
  릴리즈 전에 다음 마일스톤을 세우는 경로(`/tide:cycle`의 시작점)와, 진행 중 마일스톤을 두고 **debug 릴리즈**가 나가는
  경로(라운드 0 리뷰의 차단) 모두에서 `O23`이 거짓으로 붉지 않는다. v2.35.0 리뷰가 수용한 잔여 위험 `rf-54`를 닫는다.
- **태그 전 초안은 신호로 풀지 않았다** — 트리로 「회고 건너뜀」과 구별되지 않는다(T01 실측). 규약에 **순서 규칙**(새
  마일스톤은 회고가 CHANGELOG 첫째를 따라잡은 뒤에)을 두었고, 그 위에서 `O18`의 붉음은 참이다. 복구 경로(태그 전
  `/tide:retro`)는 규약과 retro 스킬에, advisory는 milestone 스킬에 있다.
- **릴리즈 표지는 사용자 실행 표면을 바꾼다** — release 스킬이 버전 파일·CHANGELOG 단계에서 표지를 쓴다.
- **새 판정의 생명주기 상태표**를 규약·impl 스킬에 선언했다(`lifecycle-decl:` `lifecycle-state-table`, `rf-59`).
  라운드 1이 상태 목록에 ⒀·⒁(debug 태그 뒤 후처리)를 더했다.
- **라운드 2가 표지를 쓰는 대상을 최대 번호에서 「이번 태그에 실리는 마일스톤 전부」로 바꿨다**(리뷰 라운드 1 차단).
  상태 목록에 ⒂·⒃을 더했고, 그 규칙 아래서 트리로 보이는 누락(표지가 선 마일스톤 **아래**의 무표지)을 `O53`이 붉힌다.
- **라운드 3이 표지 경계의 서술을 사실로 좁혔다**(리뷰 라운드 2 차단). 릴리즈가 표지를 **통째로** 빠뜨리면 다음 표지
  릴리즈가 규칙대로 **자기 버전으로** 메워 `O53`에 닿지 않는다 — `O53`이 붉히는 것은 한 릴리즈의 **부분** 누락뿐이다.
  상태 목록에 ⒄(다음 마일스톤이 impl만 마친 채 직전 강행 릴리즈)을 더했다.
- **라운드 4가 표지 도입 번호의 다운스트림 누수를 닫았다**(리뷰 라운드 3 차단). `retro-mark-since:`는 이 저장소 자신의
  선언이라 대상 레포로 폴백하지 않고, 대상 레포는 도입 번호를 **자기 트리에서 파생**한다(`mark-since-derived` — 선언 ·
  가장 작은 표지 번호 · 첫 표지 릴리즈는 impl 있는 가장 큰 번호 하나). 이 저장소에는 그 파생을 자기에게 적용한 판정
  `O56`(가장 작은 표지 번호 == 선언)을 세웠다. 함께 옛 표지 PR 분기를 넷으로 채웠고, 두 픽스처가 도입 번호 경계를 가른다.
  상태 목록에 ⒅(대상 레포에서 새 규칙이 처음 도는 릴리즈)을 더했다.
- **하니스** — Part O `O41`~`O59`, Part W `W91`~`W98`.

재작업 라운드(rework): 4

### 라운드 2 — 리뷰 라운드 1 반환 처리

### 라운드 1 — 리뷰 라운드 0 반환 처리

- **차단 1 (진행 중 마일스톤 + debug 릴리즈 + 자동 회고 → `O23` 거짓 붉음)** — 리뷰가 낸 후보 중 ⒝(CHANGELOG 쪽 출처

    같은 답을 낸다(표지 버전이 회고보다 위라 대상 밖).

## T01 실측 — 생명주기 상태 · 현행 판정 · 신호 후보

  - **대상** — 작업 트리 복제본(스크래치패드 · `.git`·`site`·`.tide` 제외) 열셋. 대상 파일은 `CHANGELOG.md` ·
    `docs/reports/retro.md` · `docs/reports/M70-review.md` · `docs/milestones/M71.md`다.

  - **측정** — 각 사본에서 `pwsh -Part O`와 `sh run.sh O`를 돌렸다.
  - **대조 항목** — 「상태마다 기대(초록 · 붉을 케이스)와 실제가 같은가」다.

- **⑺·⑻은 트리로 구별되지 않는다(`infeasible-evidenced`)**
  - **형태** — ⑺(태그 전 초안)과 ⑻(태그 뒤 회고 건너뛰고 초안)이 만드는 작업 트리.
  - **성립 이유** — 두 트리의 차이는 git 태그 하나뿐이다. 그런데 `tests/discover`의 두 러너는 **태그를 읽지
    않는다** — git을 부르는 자리는 샌드박스 픽스처의 `git init`과 작업 트리의 `git ls-files`뿐이다. CI의
    `actions/checkout@v4`도 `.github/workflows/tests.yml` 세 잡 모두 옵션 없이, 즉 기본값(얕은 체크아웃 ·
    태그 미수신)으로 돈다.
  - **반례 탐색** — 드라이버가 두 상태를 **같은 함수 호출 순서**로 만들었고, 두 사본의 Part O가 두 상태에서 같은 답을
    냈다(위 표). git 호출은 두 러너에서 리터럴 `git -C` · `git init` · `git ls-files` · `git tag` · `git log` ·
    `git ls-tree` · `git describe` · `& git`으로 찾았다. 호출은 `run.sh`의 `git -C … init` 두 줄과
    `git -C … ls-files` 한 줄, `run.ps1`의 `& git … init` 한 줄과 `& git … ls-files` 한 줄뿐이었다. 나머지 히트는
    문자열 토큰(`git log --all`)이다. **처음에는 `run.sh`만 좁은 패턴으로 찾고 「git을 실행하지 않는다」로 적었다가**,
    두 러너를 넓은 패턴으로 다시 찾아 「태그를 읽지 않는다」로 좁혔다.
- **신호 후보 비교**(표의 어느 상태에서 틀리는가)
  - **⒟ 기반 버전 자리**(택함 · stale 대상) — 틀리는 상태 없음. 다만 ⑺·⑻의 **백스톱** 문제는 풀지 않는다(그 둘은
    트리가 같다).
  - **⒜ 릴리즈 기록형** — ⑹은 닫는다. ⑺·⑻은 두 트리가 같은 기록을 가져 여전히 가르지 못한다. 기록 없는 M1~M69의
    해석과 release 스킬 변경이 추가로 든다.
  - **⒝ 순서 규칙형**(택함 · 백스톱) — ⑺을 「위반」으로 정의해 ⑺·⑻을 **같은 답(붉음)** 으로 만든다. 복구(⑺r)는
    초록이다. ⑹은 이것만으로는 닫히지 않는다 — 옛 최대 번호 신호가 남으면 ⑹의 `O23`이 붉다.
  - **옛 최대 번호**(M69) — ⑹에서 틀린다(위 표).
- **택한 안** — ⒞ = ⒟(stale 대상) + ⒝(백스톱 ⑶의 정의). release 스킬(사용자 실행 표면)을 건드리지 않는다.
