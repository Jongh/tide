# M79 리뷰보고서 (review)

## 비판점

### 차단 (0건)

- 라운드 0 리뷰가 반환한 차단 1(케이스 줄 판정이 접미 ID를 버려 `N58`이 공허하게 통과하던 경로)은 라운드 1에서 닫혔다.
  - 두 러너의 ID 꼴은 이제 `^N[0-9]+[a-z]*$`이다.
  - `N62` 픽스처의 `N98b`가 이를 통제한다.
  - 되돌림 `sfx-unmapped`(대응 없는 접미 케이스)에서 두 사본 모두 `N58`이 붉다. `sfx-regex-old`(정규식을 옛 꼴로)에서는 `N62`가 붉다.
  - 반환 항목 셋(차단 1 · 권장 2 · 사소 3)이 코드와 문서에 모두 반영됐다.

### 권장 (1건)

1. **`N58` 경계 필터의 접미 처리에 통제가 없다 — impl 보고서의 닫힘 문장이 그보다 넓었다.**
   - 라운드 1 이후 접미 ID는 두 자리에서 다룬다.
     - 하나는 `case_ids` / `CaseIds`의 정규식이고, `N62`가 통제한다.
     - 다른 하나는 `fa_case_unmapped` / `FaCaseUnmapped`가 `floor-ask-from:`과 견주는 숫자 부분 필터인데, 이쪽에는 통제가 없다.
   - 두 실제 러너에는 접미 N 케이스가 없고, `N62`는 `case_ids`만 먹인다.
   - 반증 패스의 재현(작업 트리 밖 사본):
     - 두 러너의 필터를 함께 「접미 ID는 0으로 본다」 꼴로 고쳤다. sh는 `if (s ~ /[a-z]/) s = 0`, ps1은 `'^N([0-9]+)$'`로 매치 실패 → `[int]'' = 0`이다.
     - 대응 없는 `N63b`를 두 러너에 더했다.
     - 결과는 sh · pwsh Part N 둘 다 63/0이다. 차단 1의 경로가 한 함수 옆으로 옮긴 꼴이다.
   - 한쪽 러너만 고치는 편집은 잡힌다(다른 러너의 `N58`이 두 러너 소스를 함께 읽는다).
   - 단순히 되돌리는 편집도 시끄럽게 실패한다.
     - ps1을 `[int]$_.Substring(1)`로 되돌리면 접미 ID에서 예외를 던진다. 리뷰가 실측했다.
     - sh에서 `sub(/[a-z]+$/, …)`를 지우면 awk가 숫자 앞부분으로 바꾸므로 그대로다.
   - 처분: impl 보고서의 「같은 축소가 다시 들어오면 기계가 잡는다」를 「정규식 자리에서」로 좁히고, 필터 자리의 경계를 같은 문단에 적었다(in-review 수정). 통제 추가는 후속으로 넘긴다.

### 사소 (2건)

2. **`N58`이 보는 ID 꼴 밖의 대문자 · 기호 접미(`N63B` · `N63-a`)를 규약이 열린 경계로 적지 않았다.**
   - 규약은 「소문자 접미가 붙을 수 있다」로 함의만 하고, 열린 경계로 이름을 든 것은 작은따옴표 · 공백 둘 호출뿐이었다.
   - 지금 그런 ID는 없다.
   - 처분: 규약 `case-exists` 정의의 열린 경계 문장에 넣었다(in-review 수정).
3. **impl 보고서의 행 번호 인용이 라운드 0 값이었다.**
   - 라운드 1이 규약 정의 한 줄과 러너 주석 한 줄씩을 더해 다음 인용이 어긋났다.
     - 규약 정의 범위 267~284행 → 267~285행(두 자리)
     - 기준 6의 규약 284행 → 285행
     - 기준 7의 규약 256행 → 255행
     - T03의 sh 3146~3162행 → 3147~3163행, ps1 3485~3501행 → 3486~3502행
     - 기준 7의 `run.sh` 5043행 → 5044행
   - 처분: 고쳤다(in-review 수정).

**검증 범위 선언**(`scope-declared`)

  - 대상: `docs/conventions.md` · `tests/discover/run.sh` · `tests/discover/run.ps1` · `tests/discover/README.md` · `docs/epics/E2.md`
  - 대조 항목: 「impl 보고서가 인용한 행 번호가 그 줄을 가리키는가」
  - 루트: 저장소
  - 인용 자리(`263~265` · `267~28x` · `28x행` · `25x행` · `127행` · `3146~` · `3485~` · `2895행` · `5043행` · `1291행` · `1094행` · `325행`)를 하나씩 대조했다. 어긋난 일곱을 고쳤고 나머지는 맞다.
- **접미 ID 실재**
  - 패턴: `^\s*[Cc]hk "N[0-9]+[a-zA-Z]`
  - 대상: 두 러너
  - 대조 항목: 「실제 러너에 접미 N 케이스가 있는가」
  - 루트: 저장소
  - 결과: 0건(반증 패스). 그래서 이슈 1의 필터는 실 데이터로 시험되지 않는다.
- **diff 읽기**
  - 대상: 라운드 1이 바꾼 `case_ids` / `CaseIds` · `fa_case_unmapped` / `FaCaseUnmapped` · `fa_runner_fixture` / `FaRunnerFixture` · `N62` 줄, 규약 `wiring` · `case-exists` · `case-mapped` 정의, README 고지 대응 블록, impl 보고서 전체
  - 대조 항목: 「반환 항목이 닫혔는가 · 두 사본이 같은가 · 넓은 주장이 남았는가」
  - 다른 파일은 라운드 1이 바꾸지 않았다.

**기대는 주장 대조**(`lean-branches-stated`)

- impl 보고서의 「같은 축소가 다시 들어오면 기계가 잡는다」는 `N62`(정규식 통제)와 `N58`에 기대어 선 주장이다.
- 갈래는 둘이다. 「정규식 자리의 축소」는 성립하고(`sfx-regex-old`), 「숫자 부분 필터 자리의 축소」는 두 러너를 함께 고치면 성립하지 않는다(이슈 1).
- 그래서 주장의 범위를 정규식 자리로 좁혔다.

**재검증 결과 (re-verify)** — in-review 수정 3건 뒤 다시 잰 값:

- `powershell -NoProfile -File tests/discover/run.ps1` → `# result: PASS=608 FAIL=0` (PowerShell 5.1.26100)
- `sh tests/discover/run.sh N` → `# 부분 결과(Part N): PASS=62 FAIL=0` (Git Bash) · `/usr/bin/dash tests/discover/run.sh N` → 같은 값
