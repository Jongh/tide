# M33 리뷰보고서 (review)

## 비판점

### 차단 (0건)

없음. 삭제·행위 변경이 0이고 계약 표면(커맨드 12종 · `.tide/phase` 값 집합 · `hooks/tide-guard.{sh,ps1}` ·
프리플라이트 게이트 3 + advisory 단계 · 보고서 필수 섹션 · 판정 표기와 계측 줄 형식)이 전부 불변이라
릴리즈를 막는 결함은 나오지 않았다. 변경 파일에 `hooks/`·`skills/`·`.claude-plugin/`이 **없다**.

### 권장 (2건 — 둘 다 in-review 수정)

1. **F1이 총계만 봐서 파트별 내역이 한 겹 아래에서 갈라진다** — 마일스톤 완료 기준 6은
   "총계·**파트별 수**가 실측과 일치"를 요구하는데, 배선된 F1은 `cases:` **총계**만 대조했다. 총계를
   62로 고치면서 `Part F 13`을 그대로 두면 **양 셸 모두 green**이고, 그건 이 마일스톤이 없애려는
   자기서술 드리프트가 **같은 줄 안에서** 재현되는 것이다. M32가 E4에서 잡은 것("토큰 존재만 보면
   이형을 통과시킨다")과 정확히 같은 부류다. **수정함**(F1b 신설).
2. **규약의 집행력 주장이 사실보다 넓었다** — 신설 절이 "**각 러너가** 자기 README의 선언과 실제
   케이스 수를 대조한다"고 현재형 단정으로 적었으나, 실제로 도는 것은 `tests/discover` **하나뿐**이고
   나머지 넷(`fleet`·`fleet-cycle`·`fleet-verify`·`multi-repo`)은 README에 **총계 선언 자체가 없어**
   대상이 아니다. 규약을 문자 그대로 읽은 다음 독자는 "네 하니스도 집행된다"고 오해한다 — M32 이슈3이
   "Part E가 네 규약을 집행한다"는 주장을 사실에 맞춰 좁혔던 것과 **동형의 결함**이며, 그 교훈이
   한 사이클 만에 같은 자리에서 재발했다. **수정함**(현행 배선 범위 정직 고지 + 선언을 새로 두면 같은
   사이클에 배선한다는 동기화 조항).

### 사소 (2건 — 둘 다 in-review 수정)

3. **"이력 서술 예외"의 괄호가 열거형으로 읽혔다** — 예외 대상을 `(이월 처분 원장 행, 회고 섹션)`으로만
   적어, **규약 자신이 근거로 인용한 과거 수치**(`14/14 인용, 실측 19/19`, `29→41→45→48`)가 예외에
   포함되는지 불분명했다. 문자 그대로 읽으면 새 규약이 **자기 본문을 위반**한다. **수정함**(예시형으로
   바꾸고 판단 기준을 "문서의 종류가 아니라 **그 문장이 현재를 말하는가**"로 명시).
4. **F2 판정 단위의 비대칭이 어디에도 적혀 있지 않았다** — 캐노니컬은 **표 행** 단위, 소비자는 **파일**
   단위다. 구현 중 실측된 대로 같은 파일 다른 자리(산출물 셀)에 앵커가 남아 있으면 역할 셀에서
   사라져도 통과한다. 소비자를 줄 단위로 좁히면 사이트 시작하기처럼 **커맨드 이름과 앵커가 다른 줄에
   있는 정상 문서가 FAIL**하므로 파일 단위가 옳은 선택이지만, 그 **의도와 대가**가 규약에 없으면 다음
   독자는 이걸 버그로 읽거나 반대로 가드를 과신한다. **수정함**(비대칭·사유·대가를 규약에 명시).

## 수정 내용

- **이슈 1**: `tests/discover`에 **F1b — 파트별 내역 합 == 총계 선언**을 양 셸에 추가했다.
  합산 대상은 `Part [A-Z] [0-9]+` ASCII 골격이고, **합산 범위를 선언 줄 한 줄로 좁혔다** — 처음에는
  파일 전체를 훑도록 썼는데 README 산문에 인용된 같은 골격까지 더해져 **83 vs 62**로 FAIL했다(리뷰가
  자기 수정에서 곧바로 겪은 것이라 러너 주석·README에 그 사실을 남겼다). Part F는 13 → **14 케이스**,
  총계는 61 → **62**.
- **이슈 2**: conventions "카운트 단일 선언처"에 **현행 배선 범위** 항목을 신설했다 — "실제로 도는
  하니스는 `tests/discover` 하나이며, 나머지 넷은 총계 선언이 없어 아직 대상이 아니다. 규약이 일반형으로
  적혔다고 해서 그 넷이 집행되고 있다는 뜻이 아니다. 선언을 새로 두면 **같은 사이클에** F1 동형을
  배선한다(규약 ↔ 실행/인프라 동기화)". 집행 조항에는 총계와 함께 **내역 합**도 대조한다는 사실을
  더했다(이슈 1과 정합).
- **이슈 3**: 이력 서술 예외를 `(예: … 규약이 근거로 인용하는 과거 수치)` 형태로 바꾸고, 판단 기준을
  **"그 문장이 현재를 말하는가"**로 못박았다.
- **이슈 4**: "판정 단위의 비대칭(의도된 것)" 항목을 역할 앵커 규약에 신설 — 캐노니컬=행/소비자=파일,
  사유(소비자 서술은 여러 줄에 걸친다), 대가(같은 파일 다른 자리의 앵커가 통과시킨다), 그리고 "앵커의
  **존재**를 보는 가드이지 문구의 **정확성**을 보는 가드가 아니다"를 함께 적었다.

## 검증

**재검증 (re-verify)** — in-review 수정이 4건이므로 수정 **후** 전 하니스를 재실행했다.

| 하니스 | sh | ps1 |
|---|---|---|
| `tests/discover` | **PASS=62 FAIL=0** | **PASS=62 FAIL=0** |
| `tests/multi-repo` | PASS=30 FAIL=0 | PASS=30 FAIL=0 |
| `tests/site-includes` | PASS=28 FAIL=0 | PASS=28 FAIL=0 |
| `tests/fleet` | PASS=41 FAIL=0 | PASS=41 FAIL=0 |
| `tests/fleet-cycle` | PASS=23 FAIL=0 | PASS=23 FAIL=0 |
| `tests/fleet-verify` | PASS=29 FAIL=0 | PASS=29 FAIL=0 |

**양 셸 전 하니스 재실행**은 이번이 처음이다(직전 사이클들은 `discover`·`multi-repo`만 양 셸을 돌리고
나머지는 sh만 돌렸다) — 사이트 파일을 건드렸고 새 파트가 들어갔으므로 범위를 넓혔다. 6개 하니스
**213 케이스 전부 양 셸 동일 판정**.

**집행력 실증(변형 주입 → 원복)** — 새 단언이 공허하게 통과하지 않음을 양 셸에서 세 번 실측했다.

- README 선언 `cases: 61` → `60` → 양 셸 **F1 FAIL**(`got 60, want 61`). 원복 후 복귀. (impl 단계)
- `README.md`에서 앵커 `gh` 제거 → 양 셸 **F2 FAIL**(`got no, want yes`). 원복 후 복귀. (impl 단계)
- 선언 줄 내역 `Part B 14` → `13`(총계는 62 유지) → 양 셸 **F1b FAIL**(`got 61, want 62`). 원복 후
  62/62 복귀. (리뷰 단계 — 이슈 1 수정의 실증)

**원본 규율** — `tests/discover/run.ps1`의 **byte > 127 = 0**, CRLF 유지(F1b 추가 후 재측정). 새 골격
(`Part [A-Z] [0-9]+`·`cases:`)이 전부 ASCII라 코드포인트 조립(`Uni`) 없이 앵커했다.

**미검증 잔여 리스크(정직 고지)**

- **F1의 오프셋 규율은 기계 집행이 없다** — "F1을 마지막 케이스로 두고 `누계 + 1`" 규약이 깨지면
  수가 어긋난다. 다만 깨져도 **조용히 통과하는 게 아니라 FAIL로 드러난다**(안전 측 실패).
- **역할 앵커는 3개뿐이다** — 앵커가 없는 나머지 9종의 역할 서술은 여전히 무가드다. 설계대로(발명 금지)
  이나, 이번에 `release=gh` 하나가 **실제 드리프트를 물었다**는 사실이 얇은 시작의 유효성 근거이자
  동시에 커버리지 한계다.
- **mkdocs 실렌더는 CI 영역** — `docs/commands.md`에 HTML 주석(`role-anchors:` 맵)이 들어갔다.
  `tests/site-includes` 28/28은 통과하지만 실제 `--strict` 렌더 확인은 환경-이월 그대로다(주석은
  렌더에 나타나지 않는 것이 마크다운 표준 동작).

  ⑤ps1 byte>127=0·CRLF 유지 ⑥README가 Part A~F 서술 + 나머지 4개 README 스테일 부재 **확인함**

  앵커 발명 0. 차단 0건.
- **반증 시도: 폴백(Agent 미가용 세션) — 성립 4건**. 판정 후보를 적어 놓고 공격하는 절차로 수행했고,
  성립한 지적은 전부 위 비판점에 편입해 수정했다(이슈 1·2·4는 수정, 판정 자체를 뒤집은 지적은 없다).
  네 번째 성립은 아래 **버전 논쟁**으로, 수정 대신 판정 근거에 반영했다.
- **patch 근거(그리고 minor 반론의 처리)**: 반증이 "캐노니컬·README·사이트의 **사용자가 읽는 문구가
  실제로 바뀌었으니** M30·M31·M32와 같은 minor여야 한다"고 공격했다. 그러나 그 셋은 **새 동작·새
  절차가 늘어난** 경우였고(상태값 가산·advisory 단계 가산·리뷰 절차 가산), 이번에는 **v2.4.0~v2.5.0에
  이미 존재하던 gh 게시 능력의 서술을 정정**했을 뿐 새 능력이 생기지 않았다. 커맨드의 호출명·역할·
  산출물·git 행위·`.tide/phase`·가드·프리플라이트가 전부 불변이고, 신설 규약은 **tide 레포 기여자
  규율**(사용자 프로젝트 동작에 영향 없음)이며 나머지는 스테일 정정과 가드 가산이다 — 2.0 안정성 절의
  "patch = 버그 수정·정리·견고화"에 정확히 부합한다. 다만 문서 문구 변화를 관찰 가능한 가산으로 보아
  **사용자가 v2.11.0(minor)을 택해도 규약 위반이 아니다** — 경계 사례임을 명시해 둔다.
