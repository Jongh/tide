# M30 완료보고서 (impl)

## 개요

M30의 태스크 5개(T01~T05)를 전부 구현했다 — `/tide:debug` 첫 라이브 도그푸딩이 드러낸 규약 구멍 3건을
닫는 작업이다: ① `변경 파일 요약` 기준선 확정(+ 미커밋 산출물 어긋남 고지 의무), ② 정오표 경로 신설
(릴리즈된 보고서 본문 불변 + append-only), ③ debug 항목 상태값에 `확인함` 가산 + 용도 경계. 위상 순서는
T01(conventions 단일 원본) → T02·T03·T04 **병렬**(파일 비중첩) → T05(project-context)였고, 병렬 3건은
서브에이전트로 동시 디스패치했다. 규약↔실행 동기화 원칙대로 규약만 적지 않고 같은 사이클에 집행 배선을
넣었다 — `tests/discover`에 Part C(선언 정합 가드)를 신설해 **양 셸 29/29 FAIL 0**으로 고정했다.

## 태스크별 수행 내용

- **M30-T01** — `docs/conventions.md`에 세 규약을 확정했다(메인이 직접 — 레벨에 태스크 1개라 병렬
  폴백 조건). **"변경 파일 요약 기준선"** 절 신설: 기준선 = 해당 단계·세션 시작 시점의 워킹트리이며 git
  `HEAD`·릴리즈 태그 대비가 아니다. **git 기준을 기각한 이유**는 보고서가 *이 단계가 무엇을 했는가*의
  기록이기 때문이다 — 도그푸딩 세션은 `fixtures.ts`를 실제로 **고쳤지 만들지 않았으므로**, git 기준으로
  "추가"라 적으면 그 세션의 행위에 대해 거짓이 된다. 대신 어긋남을 **표 아래 한 줄 고지**로 의무화하고,
  debug에서 이것이 기본 경로인 이유(부수효과 분리 → 거의 항상 미커밋 산출물 위에 얹힘)를 근거와 함께
  남겼다. **"정오표 (errata)"** 절 신설: 릴리즈된 보고서 본문 불변 + 말미 `## 정오표` append-only(날짜·
  틀린 내용·실제 사실·근거), 미릴리즈는 본문 직접 수정. **릴리즈 여부 판정은 기존 태그-트리 기준을
  포인터로 인용**하고 새 기준을 만들지 않았다(기준이 둘이 되면 그 자체가 다음 드리프트다). 판정·프리
  플라이트 불변임을 명시했다. **"debug 세션"** 절에 "항목 상태값(네 가지)" 항목을 신설해 `확인함`을
  가산하고 용도 경계(같은 맥락 한정 · 검증 전용 세션 금지)를 못박았으며, 기존 금지 불릿에 "보고서는
  금지 대상이 아니다"(정오표 허용)와 기준선 포인터를 더했다.
- **M30-T02** — `skills/debug/SKILL.md`·`skills/debug/template.md`·`docs/commands.md`에 T01 규약을 절차·
  형식으로 배선했다(서브에이전트). SKILL의 "항목 처리"를 네 값으로 확장(+`확인함` 의미·경계), "세션 종료
  (done)"에 기준선 문단 추가, **정오표 절을 "항목 처리"와 "세션 종료" 사이에 배치** — 정오표는 발견 시점의
  행위이지 `done` 절차가 아니라는 판단이며 타당하다. template은 상태 자리를 네 값으로 넓히고 표 아래 기준선
  안내문을 넣되 **`## 정오표`는 골격에서 제외**했다(조건부 append 섹션이라 골격에 두면 모든 보고서에 빈
  섹션이 남는다). 카탈로그는 산출물 서술에 "+ 필요 시 정오표"와 상태 네 값만 반영하고 12종 선언·표 구조·
  이름 등장은 무수정, `site/docs/commands.md`(스니펫 셸)는 무접촉.
- **M30-T03** — `skills/milestone/template.md`·`skills/impl/template.md` 표 아래에 기준선 안내문 한 줄씩
  추가했다(서브에이전트). 기준선 규약은 debug 전용이 아니다 — 같은 추가/수정/삭제 표를 쓰는 마일스톤 문서·
  impl 보고서도 같은 모호성을 갖는다. 문구는 세 템플릿이 `기준선 = `으로 시작하도록 통일하고 단계 이름만
  달리했다(마일스톤 계획 시점 / 이 단계 시작 시점 / 이 세션 시작 시점). `skills/{milestone,impl}/SKILL.md`는
  **무수정** — 두 스킬 모두 이미 `${CLAUDE_SKILL_DIR}/template.md`를 "그 구조 그대로" 읽으므로 배선이 이미
  있다(템플릿이 형식의 단일 원본이라는 기존 규약).
- **M30-T04** — `tests/discover`에 **Part C(선언 정합)** 를 신설했다(서브에이전트). C-1은 네 상태값이
  conventions·debug SKILL·debug template **세 파일 전부**에 등장함을 단언하고(값당 1케이스, B3의 집계
  선례), 존재하지 않는 값(`보류함`) 부재를 **파일별 음성 통제**로 확인한다. C-2는 `기준선` 토큰이 세
  템플릿 전부에 있음을 단언한다. **C-2는 스펙 확장이다** — M30 문서는 T03에서 "문구 드리프트는 T04가
  집행"이라 적었으나 T04 스펙은 상태값만 담고 있어 그대로면 마일스톤 내부가 어긋난다. 가드를 넓히는 쪽으로
  정합시켰다(완료 기준 #1의 "세 템플릿 모두 명시"가 이로써 기계 검증된다). `run.ps1`은 기존 `종`(U+C885)
  관례를 다중 토큰으로 확장한 `Uni` 헬퍼로 한글을 코드포인트 조립해 ASCII 소스·무BOM을 유지했다.
- **M30-T05** — `docs/project-context.md`를 실제 결과로 갱신했다(메인, 다른 태스크 완료 후). 핵심 도메인
  개념에 상태값 네 가지·기준선·정오표를 더하고(상세는 conventions 포인터 — 재정의 없음), 이월 원장에 M30
  행을 추가했으며, **원장 산문에서 "debug 세션 왕복 라이브 실증"을 미반영에서 제거**해 남는 도그푸딩
  미반영을 **gh 게시·`pr` finalize 둘로 줄였다**(M29 잔여 리스크 ①②③이 닫힌 근거를 함께 기록). debug
  자기 판정 재검토는 **근거 1건 기록·게이트 미신설**로 남겼다. 더해 `tests/discover`가 빌드/테스트 서술에서
  **누락돼 있던 것**을 발견해 역할·케이스 수와 함께 채웠다(기존 누락 보정).

**구현 중 발견·수정한 이슈 3건**:

   14/14"라 적었으나 실측 기준선은 **19/19**(Part A 7 + Part B 12)였다. M22의 B2/B3 추가가 README에 반영되지

   적힌 수를 믿지 말고 측정하라"를 넣어둔 것이 그대로 걸렸다. 실측값으로 정정했다.
2. **`tests/discover/README.md`의 Part B 표가 캐노니컬을 잘못 적고 있었다(기존 결함)** — `site/docs/commands.md`를
   "카운트 선언처"로 적었으나 M22 이후 그것은 스니펫 셸이고 캐노니컬은 `docs/commands.md`다. 문서만 정정

3. **PowerShell 별칭이 음성 통제를 공허 green으로 만들 뻔했다(신규 코드의 잠복 결함)** — Part C 헬퍼를 처음
   `Cp`로 명명했는데 `Cp`는 `Copy-Item`의 빌트인 별칭이고 **PowerShell은 별칭을 함수보다 먼저 해석**한다.
   함수가 호출되지 않아 토큰이 조용히 빈 문자열이 되고, `''`는 모든 `.Contains()`에서 true라 **C-1 양성 4건이
   전부 통과하는 "틀린 이유의 green"** 이 됐을 것이다. `Uni`로 개명하고 사유를 코드·README 주석에 남겼다.
   (이 레포가 M26 sn1에서 닫은 "오추출-공허 green"과 같은 부류의 재발이다.)

**음성 통제 실증**: 서브에이전트가 트리 전체 사본을 샌드박스에 떠서(라이브 트리 무접촉 — T02·T03이 같은
파일을 동시에 쓰고 있었으므로) 드리프트 3종을 주입해 실제 FAIL을 확인했다 — conventions에 `보류함` 유입 →
`FAIL C1 상태값 통제`, debug template에서 `확인함` 제거 → `FAIL C1 양성`, impl template에서 `기준선` 제거 →
`FAIL C2`. 양 셸 모두 PASS=26 FAIL=3 exit 1로 동일 판정. 원복 후 29/29 복귀.

**병렬 디스패치**: T02·T03·T04를 한 메시지에서 동시 디스패치했다. 예상 변경 파일 집합이 완전 비중첩
(`skills/debug/**`+`docs/commands.md` / `skills/{milestone,impl}/template.md` / `tests/discover/**`)이라 폴백
없이 병렬을 유지했고, 부분 실패 없이 3건 모두 반환 계약을 채웠다. T04가 T02 산출물(`skills/debug/template.md`)을
**읽어서 검사**하는 방향의 의존이 있어 착수 시점엔 C-1/C-2가 FAIL이었으나, 서브에이전트가 지시대로 **가드를
느슨하게 고치지 않고** T02 랜딩을 기다려 green을 재확인했다.

## 미해결·후속 메모

1. **기준선 문구의 완전 동일성은 집행되지 않는다(설계상 수용)** — C-2는 `기준선` **토큰의 존재**만 검사하고
   문구 전문 일치는 보지 않는다. 세 템플릿의 문구는 단계 이름이 달라(마일스톤 계획 시점 / 이 단계 시작 시점 /
   이 세션 시작 시점) 애초에 literal 동일이 불가능하다. 토큰 존재 + 규약 단일 원본(conventions)으로 충분하다는
   판단이나, M30 문서 T03의 "동일 문구" 표현은 실제 구현보다 강하다 — 리뷰가 문구를 완화할지 판단할 사안.
2. **정오표 경로는 라이브 미실증** — 규약·절차·템플릿은 배선됐으나 **실제로 릴리즈된 보고서에 정오표를 단
   사례는 아직 없다**. M29의 잔여 리스크가 첫 도그푸딩에서만 닫혔던 것과 같은 성격의 환경-이월이다. 마침
   **대기 중인 실사례가 있다** — 그 외부 프로젝트의 `debug-1.md` 항목 4가 "`destroyOnClose`는 원래대로
   두었다"라고 적었으나 실제 코드는 그 prop을 제거했고, 그 보고서는 이미 v0.6.0 태그에 실렸다. 그 레포에서 다음
   debug 세션이 열릴 때 이 경로가 실증된다(tide 레포의 후속은 아님 — 사용자 판단 사항).
3. **`확인함` 용도 경계도 프롬프트 규율이다** — C-1은 상태값이 **선언됐는지**만 집행하고, "검증만 하러 debug
   세션을 열지 않는다"는 경계는 기계로 막을 수 없다(하니스로 집행 불가한 프롬프트 자산 — M29가 같은 한계를
   정직히 남긴 것과 동형). 남용 신호가 관찰되면 별도 사이클 사안.
4. **debug 자기 판정 재검토는 여전히 미충족·근거 1건** — 원장에 기록만 했고 게이트는 신설하지 않았다(M30 배경의
   결정 그대로). 두 번째 근거(특히 **회귀**)가 쌓이면 축약 review 게이트를 별도 사이클에서 판단한다.
5. **`tests/discover/README.md`의 두 기존 결함은 이번에 우연히 잡혔다** — 케이스 수·캐노니컬 표기가 M22 이후
   드리프트한 것을 M30이 그 파일을 건드리다 발견했다. README 자체를 집행하는 가드는 없다(문서가 문서를 설명하는
   층이라 자기참조적). 저위험이나, 같은 드리프트가 다른 하니스 README에도 있을지는 미확인.
