# M40 리뷰보고서 (review)

> 라운드 2. 라운드 1의 판정은 `가능`(v2.14.0)이었고, 그 릴리즈 PR에서 **M40이 새로 세운 macOS
> 레그가 실제 이식성 결함을 잡아** release가 `pr` 모드 대기로 멈췄다(태그·머지 없음). 이 문서는
> **릴리즈 CI 반환분**의 처리를 본다 — 리뷰 반환이 아니므로 재작업 라운드는 올라가지 않는다
> (규약의 산정 규칙: 판정이 `불가`가 아닌 재실행은 값을 유지).

## 비판점

### 차단 (0건)

수정의 **기전을 로컬에서 재현하지 못했다는 사실이 숨겨지지 않았다** — impl 보고서와 러너 주석이
그것을 명시하고, 다음 macOS 레그가 결론을 내도록 **실패 출력에 이름을 싣는** 조치를 함께 넣었다.
"고쳤다"를 검증된 사실처럼 적었다면 판례 부류였겠으나, 문장이 실제 확인 범위를 넘지 않는다.
러너 주석의 인과 서술도 "로케일이 걸리면 … 묶일 수 **있다**"로 열려 있고, **단정한 부분**(ps1이
ordinal이라 두 사본의 의미가 갈려 있었다 · BSD에서 3으로 드러났다)은 전부 확인된 사실이다.

### 권장 (1건 — in-review 수정 완료)

1. **자기고발이 한쪽 사본에만 있었다** — sh는 실패 시 중복 앵커 **이름을 출력**하게 고쳤는데
   `run.ps1`에는 그 조치가 없어, ps1이 같은 자리에서 붉어지면 **여전히 수만 보이는 상태**였다.
   이번 사이클이 겪은 문제("수를 세는 단언이 붉어져도 원인을 말하지 않아 기전을 재현하지 못했다")가
   ps1에서 그대로 재현될 수 있었고, 두 사본은 **같은 의미여야 한다**는 이 레포의 규율에도 어긋난다.
   *등급 판단*: 집행력을 넓게 주장한 것이 아니라 **대칭성 누락**이라 판례 부류가 아니다.

### 사소 (0건)

## 수정 내용

- **이슈 1**: `run.ps1`의 G2에 sh와 같은 진단을 넣었다 — `$dset.Count -ne 0`이면
  `-> duplicate anchors: <이름들>`을 출력한 뒤 `Chk`를 부른다(케이스 수 불변). 주석에 sh와 같은
  근거와, **빈 앵커 파일로 공허 통과할 수 없다**는 사실(앞선 앵커 추출 positive-control이 먼저
  FAIL한다)을 함께 적었다.

**이 리뷰가 수행한 실측**

| # | 확인 | 결과 |
|---|---|---|
| 1 | ps1 진단 구별력 — 중복 앵커를 심고 실행 | `-> duplicate anchors: 실행환경축` + **G2 FAIL** |
| 2 | sh 진단 구별력(impl 실측 재확인) | `↳ 중복 앵커: 실행환경축` + **G2 FAIL** |
| 3 | **impl의 `sort -V` 판단 검증** — 그 케이스가 정말 버전 정렬을 구별하는가 | **구별한다** |

**3번을 별도로 확인한 이유**: impl이 "`sort -V`는 macOS 레그가 실측으로 증명했으므로 고치지
않는다"고 판단했는데, 그 논거는 **해당 케이스가 버전 정렬을 실제로 구별할 때만** 성립한다.
`tests/fleet/run.sh:195~201`이 M2·M9·M10 픽스처를 만들고 "최신 = M10(M9 아님)"을 단언하며,
로컬에서 `ls M*.md | sort | tail -1` → **M9.md**, `sort -V | tail -1` → **M10.md**로 갈리는 것을
확인했다. 즉 macOS에서 `fleet` 42/0은 **BSD `sort -V`가 동작했다는 증거가 맞다**. 가정이 아니라
측정에 근거한 판단이었고, 그 근거가 성립한다.

**같은 부류 전수 감사의 잔여**: 러너 6종·훅 2종에서 `LC_ALL=C` 없는 `sort`/`uniq`/`comm`은 이제
`tests/fleet/run.sh`의 `sort -V` 두 곳뿐이고, 그것은 위 3번으로 정당화된다(`-V`는 정렬 **순서**가
버전 의미를 따르게 하는 것이 목적이라 `LC_ALL=C`와 상충하지 않으며, 대상이 ASCII 파일명이다).

**미검증 잔여 리스크(가장 중요)**

- **이번 수정의 기전은 여전히 확정되지 않았다.** `LC_ALL=C` 누락이 원인이라는 것은 **강한 정황**
  (이 러너에서 유일한 누락 · ps1은 ordinal이라 두 사본의 의미가 갈려 있었음 · GNU 전 로케일에서
  0이 나와 GNU로는 재현 불가)이지만, **BSD에서 무엇이 3으로 묶였는지는 아직 모른다.**
  결론은 **다음 macOS 레그 실행**이 낸다 — 초록이면 닫힌 것이고, 붉으면 이번에 넣은 진단이
  **이름을 찍어** 다음 라운드를 즉시 진단 가능하게 만든다. 이 불확실성은 릴리즈를 막을 사유가
  아니다(레그가 붉으면 릴리즈가 그 자리에서 다시 멈추므로 잘못된 것이 태그로 나가지 않는다).
- **`workflow-syntax` 배선의 라이브 발화**는 아직 미실측이다. 다만 이번 릴리즈에서 **붉은 CI 위에서
  멈춘 것 자체**가 그 배선이 겨냥한 상황의 예행이었다(사람이 아니라 절차가 멈춰 세웠는지는 다음
  마무리에서 확인된다).
- **`git remote prune` 정정**도 다음 마무리에서 처음 밟힌다.
- **서브에이전트 경로**는 impl·review 모두 이번에도 폴백이었다.

## 릴리즈 판정

**가능** — 추천 버전: **v2.14.0 (minor)**

계측: in-review 수정 차단 0/권장 1/사소 0 · 반증 시도 폴백 성립 0건 · 재작업 라운드(rework) 0

- **판정 근거**: 릴리즈 CI가 반환한 결함이 닫혔고(네 실행 환경 110/0), 그 수정이 **이 레포의 자기
  규율을 복원하는 방향**이다 — 러너에서 유일하게 `LC_ALL=C`가 빠져 있던 자리를 채워 sh의 비교
  의미를 ps1의 ordinal과 맞췄다. 같은 부류를 전수 감사해 하나(`fleet-cycle`)를 더 닫고, 하나
  (`fleet`의 `sort -V`)는 **측정 근거로 유지**했다. 기전 미확정은 **문서·주석·보고서에 전부
  명시**돼 있고 다음 레그가 결론을 내도록 진단이 배선됐다. 버전은 라운드 1과 같은 이유로 minor다
  (CI 실행 환경 가산 + `pr` 마무리의 사용자 확인 가산이 사용자 관찰 가능하고, **프리플라이트 게이트
  집합·순서·판정 로직 · 커맨드 12종 · phase 값 집합 · tide-guard 무접촉 · 보고서 섹션 · 판정/계측
  형식**은 전부 불변).
- 반증 시도: 폴백(Agent 미가용) — 성립 0건. 판정 후보 `가능`을 네 갈래로 공격했다: ⑴ "기전을 모른 채
  고친 것을 `가능`으로 내보내는 것은 과대 주장 아닌가"(보고서·주석이 미확정을 명시하고, 틀렸다면
  레그가 다시 붉어 릴리즈가 그 자리에서 멈춘다 — 잘못된 것이 태그로 나가는 경로가 없다) ⑵ "리뷰가
  ps1 진단을 직접 넣은 것은 판정자=실행자 아닌가"(권장 등급의 in-review 수정은 규약이 허용하고,
  재검증·구별력 실측까지 마쳤다) ⑶ "`sort -V`를 고치지 않은 것은 미검증 수용 아닌가"(위 검증 3번으로
  그 케이스가 버전 정렬을 실제 구별함을 확인 — 측정된 근거다) ⑷ "rework 0은 사이클 품질을 과대
  평가하는 것 아닌가"(규약의 산정 규칙이 리뷰 판정을 기준으로 삼고, impl이 릴리즈 CI 출처임을
  개요에 명시했다 — 규칙대로이며 사실이 가려지지 않았다). 네 공격 모두 판정을 뒤집지 못했다.
