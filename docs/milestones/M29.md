# M29 — `/tide:debug` 세션: 발견 우선 작업의 역방향 문서화 진입점

## 목표

이 마일스톤이 끝나면 **빌드 후 사용자 테스트에서 발견한 에러를 마일스톤 의례 없이 tide 안에서
고칠 수 있다** — `/tide:debug`로 세션을 열어 발견-수정을 누적하고, `/tide:debug done`으로 닫으면
`docs/reports/debug-{N}.md` 보고서 하나가 남는다. 계획 우선(plan-first) 사이클이 요구하던
사전 태스크·deps·완료 기준을 debug는 요구하지 않되, tide가 실제로 지키는 두 가지 —
**부수효과 분리**(git 쓰기는 release에서만)와 **산출물 추적**(무엇을 왜 고쳤는지가 문서로 남고
CHANGELOG로 간다) — 는 그대로 보존된다. debug 보고서의 자체 판정이 release 프리플라이트를
통과하므로 `debug → release`가 한 번에 이어져 patch 릴리즈가 빨라진다.

## 배경

**사용자 신호(2026-07-15)**: 빌드 후 실제 작업 중 에러를 발견해 수정하는 과정에 일반적인
마일스톤 → 구현 사이클을 적용하기 어렵다는 요구. tide의 사이클은 **계획 우선**이다 —
`milestone`이 태스크·`deps`·완료 기준을 미리 안다고 전제하고, `impl`의 병렬 디스패치는 그
전제 위에서만 의미가 있으며, `review`는 계획 대비 결과를 판정한다. 그러나 사용자 테스트에서
나오는 에러는 **발견 우선**이다 — 무엇을 고칠지는 고쳐 보기 전엔 모르고, 한 세션에서 여러 개가
한꺼번에 나오며, 각각은 1~2줄짜리다. 전제가 성립하지 않으니 마일스톤이 의례가 된다(태스크 1개,
deps 없음, 완료 기준 = "안 죽는다"). 실제로는 의례적 마일스톤을 억지로 쓰거나 tide 밖으로
나가(`.tide/phase` 삭제) 직접 고치게 되고, 후자는 추적·CHANGELOG·가드를 한꺼번에 잃는다.

**자기 증상**: M28 리뷰의 권장 1(`git tag > 파일` 읽기 오차단)은 "리뷰에서 직접 수정"으로
처리됐다. 발견-즉시-수정이라는 debug 성격의 작업이 갈 곳이 없어 `review`가 편법으로 그 역할을
떠맡고 있다는 신호다 — 마침 리뷰 단계라 흡수됐을 뿐, 빌드 후 테스트에서 나왔으면 갈 곳이 없었다.

**확정된 설계 결정 4가지**(2026-07-15 사용자 확정 — 각 대안의 비용은 아래 태스크 상세에 반영):

1. **산출물 = 역방향 debug 보고서**. 다른 스킬은 문서 → 행동이지만 debug는 행동 → 문서다.
   세션 중 발견-수정을 누적하고 닫을 때 `docs/reports/debug-{N}.md` 하나를 낸다. 대안이던
   "마일스톤에 후속 태스크 append"는 계획과 사후 발견이 한 문서에 섞이고, "마이크로 마일스톤
   자동 생성"은 의례를 없애는 게 아니라 자동화할 뿐이라 기각.
2. **git = impl과 동일하게 쓰기 차단**. `debug`는 phase≠release이므로 **tide-guard 코드를
   수정하지 않아도** 기존 규칙이 그대로 쓰기를 차단하고 읽기를 통과시킨다(M28). "debug에서
   commit 허용"은 ① "release가 아니면 차단"이라는 **2.0 stable 가드 계약을 깨 3.0 사안**이 되고
   ② 급하게 움직이는 바로 그 순간에 백스톱을 푸는 역방향이라 기각(M18·M19·M28이 반복해 못박은
   "규율이 1차, 가드는 백스톱"에 반한다). 진단에 필요한 `git log`·`show`·`diff`·`blame`은 M28
   덕에 이미 통과하므로 debug 세션이 실제로 막히는 것은 배포뿐이고, 그것은 `/tide:release`로 간다.
3. **릴리즈 경로 = debug 보고서가 review 자리를 대신**. `release` 프리플라이트 1번이 지금은
   `docs/reports/M{N}-review.md`의 판정 "가능"을 하드코딩으로 요구한다. 이를 **review 보고서
   또는 debug 보고서 중 하나**를 수용하도록 가산 확장한다(하위 호환 — 기존 경로 불변).
4. **UX = 세션형**. `/tide:debug [증상]`으로 열고 `/tide:debug done`으로 닫는다. 한 테스트
   세션의 여러 수정을 **한 보고서·한 patch 릴리즈**로 묶기 위함(단발형은 5개 발견 시 보고서가
   5개로 흩어진다). 대가로 **세션이 열린 채 방치되면 phase=debug 잔재**가 남으므로 `/tide:status`가
   이를 드러내고 `done`을 권하도록 함께 손본다.

**메타 규칙 정합**(project-context "2.0 안정성·메타 규칙"): 규약·단일 원본을 더하면 그것을
강제·반영할 실행 수단도 같은 사이클에 함께 손본다. 여기서는 `tests/discover`가 **실제 스킬 수
(`skills/*/SKILL.md`)와 문서의 "N종" 선언 일치를 자동 집행**하므로, `skills/debug/SKILL.md`를
더하는 순간 N=12가 되어 `docs/commands.md`·`README.md`·`docs/conventions.md`·
`site/docs/getting-started.md` **네 곳이 "12종"을 선언하지 않으면 하니스가 FAIL한다**. 드리프트
음성 통제는 `N+1`(=13종) 부재만 요구하므로 기존 "11종 stable" 표현은 그대로 두어도 무방하다
(2.0 stable 집합은 11종 유지, debug는 v2.7.0 가산 — fleet 3종이 v1.x에서 가산된 뒤 2.0에서
동결된 선례와 동형).

**명시적 범위 밖**: fleet 계열(`fleet`·`fleet-cycle`·`fleet-verify`)과 `cycle`은 이번 변경
대상이 아니다. `cycle`은 계획 우선 체이닝이라 debug와 무관하고, fleet 계열의 사전 점검은
종전대로 `phase=release` 잔재만 제외한다(열린 debug 세션이 있는 자식 레포의 교차 처리 정책은
후속 판단 — 이번 사이클에서 손대면 오케스트레이션 stable 계약을 건드린다).

## 태스크 상세

### M29-T01: `/tide:debug` 스킬 신설 — 세션형 진입·누적·`done` 종료 + 보고서 템플릿

- **변경 파일**: `skills/debug/SKILL.md`, `skills/debug/template.md`
- 기존 스킬(`skills/impl/SKILL.md`·`skills/review/SKILL.md`)의 문체·구조를 그대로 따른다 —
  frontmatter(`description`: `"[tide] …"` 접두, `argument-hint`), **대상 레포** 문단(다른 스킬과
  동일 문구 — 산출물·cwd를 대상 레포 루트 기준으로), `${CLAUDE_SKILL_DIR}/template.md` 참조와
  읽기 실패 시 폴백 섹션 목록, 말미의 "다음은 절대 수행하지 마" 금지 줄.
- **인자 규약**: `argument-hint: "[증상 설명 | done (세션 종료)]"`.
  - `done`(단독 토큰) → 종료 경로. 그 외 문자열 → 세션 열기/이어가기이며 그 문자열을 첫 증상으로 취급.
  - 인자 없음 → 열린 세션이 있으면 이어가기, 없으면 세션만 열고 증상을 묻는다.
- **세션 상태**: `.tide/debug-session` — **활성 debug 보고서 번호 한 줄**(예: `3`). 파일 존재 =
  세션 열림. `.tide/phase`는 종전 계약(단계명 한 줄)을 지켜 `debug`만 담는다 — 세션 번호를
  phase에 섞지 않는다(phase 계약 불변).
- **열기 경로**:
  1. `.tide/debug-session`이 있으면 그 번호 N을 쓰고(이어가기), 없으면 `docs/reports/debug-*.md`
     중 최대 번호 + 1(없으면 1)을 N으로 정해 `.tide/debug-session`에 기록.
  2. `.tide/phase`에 `debug` 한 줄 기록(`.tide/` 없으면 생성).
  3. `docs/project-context.md`가 있으면 읽어 구조 파악(다른 스킬과 동일).
- **누적(핵심 — 역방향 문서화)**: 증상마다 재현 → 진단 → 수정 → 검증을 수행하고, **그 항목이
  끝날 때마다 `docs/reports/debug-{N}.md`에 항목을 append**한다. 세션 종료를 기다렸다가 한꺼번에
  쓰지 않는다 — 세션이 여러 턴에 걸쳐 길어지고 컨텍스트가 요약될 수 있으므로 **파일이 유일하게
  믿을 수 있는 누적 저장소**다. 세션이 중단돼 방치돼도 그때까지의 발견이 파일에 남는 것이 의도된
  동작이다(미완결 보고서 = 무슨 일이 있었는지의 증거).
- **미해결 항목**: 재현은 됐지만 못 고친 것, 원인만 밝힌 것도 항목으로 남긴다(상태를
  `수정함`/`미해결`/`원인만 규명`으로 표기) — "고친 것만 기록"하면 발견 우선 작업의 절반이 증발한다.
- **`done` 경로**:
  1. `.tide/debug-session`이 없으면 열린 세션이 없다고 알리고 **아무것도 하지 않고 중단**
     (보고서 생성 금지 — 빈 보고서 방지).
  2. 보고서에 **개요·판정 섹션을 채워 마무리**한다(항목들은 이미 append돼 있음).
  3. `.tide/debug-session` 삭제 → `.tide/phase`를 `idle`로 되돌림 → 결과 보고.
- **판정 규약**(release 프리플라이트가 읽는 계약 — T03과 짝):
  - 리뷰보고서와 **동일한 형식**을 쓴다 — `## 릴리즈 판정` 섹션, 본문에 **`가능`/`불가`**와
    `추천 버전: **vX.Y.Z**`. 형식을 맞추는 이유는 프리플라이트가 두 종류 보고서를 같은 방식으로
    읽게 하기 위함이다(파서 이중화 방지).
  - 판정 규칙: 미해결 **차단급** 항목이 없고 검증이 통과하면 **가능**, 아니면 **불가**.
  - 추천 버전 기본은 **patch**(버그 수정 묶음). 수정 과정에서 관찰 가능한 동작이 더해졌으면 minor를
    제안하되 사유를 적는다.
- **금지**: `git commit`·`git tag`·`git push`(가드가 백스톱으로 차단하지만 **규율이 1차**),
  마일스톤 문서 생성·수정, 버전 파일·`CHANGELOG.md` 편집(그것은 release의 일).
- `template.md`는 다음 구조로 — 개요(세션 범위·발견 수·기간) / 항목별 기록(증상·재현·원인·수정·
  검증·상태) / 변경 파일 요약 / 미해결·후속 / **릴리즈 판정**(위 형식) 5개 섹션. 다른 template과
  동일하게 `{}` 자리와 안내문으로 작성한다.

### M29-T02: conventions에 debug 규약 추가 (사이클 위치·phase 값·세션 파일·gitignore·12종 선언)

- **변경 파일**: `docs/conventions.md`, `.gitignore`
- conventions는 **규약의 단일 원본**이므로 이 태스크가 정의하고 스킬들이 따른다. `[start:body]`
  마커 안쪽에 쓴다(사이트가 인클루드).
- **사이클 절**: 다이어그램 아래에 debug의 위치를 명시 — `status`·`fleet`이 사이클 밖 **읽기 전용**
  보조라면, `debug`는 사이클 밖 **행위** 커맨드다. 계획 우선 사이클(milestone→impl→review)과 달리
  **발견 우선** 진입점이며, 출구는 사이클과 같은 `release`다. `/tide:cycle` 자동 체이닝의 대상이
  **아니다**(체이닝은 계획 우선 전용).
- **상태 파일 절**: phase 값 목록을 `milestone` / `impl` / `review` / `release` / `debug` / `idle`로
  확장(가산). `.tide/debug-session`(활성 debug 보고서 번호 한 줄, 로컬 상태 → gitignore)을 더하고,
  gitignore 범위가 이제 **`.tide/phase`와 `.tide/debug-session` 둘**임을 명시한다(`deps`·
  `release-mode`는 종전대로 커밋). `.gitignore`에 `.tide/debug-session` 한 줄 추가.
- **tide-guard 절**: **가드 코드·차단 규칙·메시지·exit 2는 무수정**임을 명시한다 — `debug`는
  phase≠release이므로 기존 규칙이 그대로 적용돼 쓰기는 차단되고 읽기(M28)는 통과한다. 새 phase
  값이 가드에 분기를 더하지 않는다는 것이 이 설계의 핵심이다(2.0 stable 가드 계약 불변).
- **부수효과 분리 원칙**: `impl`·`review`와 나란히 **`debug`도 git 작업을 하지 않는다**를 더한다.
- **단계별 금지 행위 요약**: debug 행을 추가(금지 — git 쓰기·마일스톤 문서·버전/CHANGELOG 편집).
- **12종 선언**: 커맨드 수를 **12종**으로 선언한다(`tests/discover` B1이 집행). 2.0 안정성 절은
  **"11종 stable" 표현을 유지**하되(2.0 동결 집합은 불변), `/tide:debug`를 **v2.7.0 가산**으로
  v1.x 가산 이력과 동형으로 기록한다 — "총 12종 중 11종이 2.0 stable, debug는 2.7.0 가산(다음
  major에서 stable 승격 후보)". 드리프트 음성 통제는 `13종` 부재만 요구하므로 두 표현은 공존한다.
- **debug 규약 절 신설**: 산출물 `docs/reports/debug-{N}.md`(번호는 독립 증가 수열 — 마일스톤
  번호와 무관), 세션 수명(열기→누적→`done`), 판정 형식이 리뷰보고서와 동일하다는 계약, release
  프리플라이트가 둘 중 하나를 수용한다는 점(T03의 단일 원본)을 적는다.

### M29-T03: release 프리플라이트를 debug 보고서 판정 수용으로 가산 확장 (deps: M29-T01, M29-T02)

- **변경 파일**: `skills/release/SKILL.md`
- 프리플라이트 1번을 **가산 확장**한다 — 현행은 "대상 마일스톤(M{N})의 `docs/reports/M{N}-review.md`
  릴리즈 판정이 '가능'인지 확인". 이를 **판정 근거 문서**를 찾는 형태로 일반화한다:
  - **후보**: `docs/reports/M{N}-review.md`(최신 마일스톤) 또는 `docs/reports/debug-{N}.md`(최대 번호).
  - **선택 규칙**: 둘 중 **아직 릴리즈되지 않은 것**을 판정 근거로 삼는다. 판단은 `CHANGELOG.md`에
    해당 사이클/세션의 항목이 이미 실렸는지로 한다. 둘 다 미릴리즈면(정규 사이클 후 debug 세션이
    이어진 경우) **둘 다 판정 '가능'이어야** 진행하고, CHANGELOG에 두 출처를 함께 반영한다 —
    한쪽만 보고 넘어가면 다른 쪽 수정이 근거 없이 배포된다.
  - **열린 세션 차단**: `.tide/debug-session`이 존재하면(미종결 debug 세션) **중단**하고
    `/tide:debug done`을 먼저 하라고 안내한다. 미완결 보고서에는 판정 섹션이 없으므로 근거가 없다.
  - **하위 호환**: debug 보고서가 하나도 없고 열린 세션도 없으면 **현행과 완전히 동일하게 동작**한다
    (기존 경로 불변 — 이 확장은 순수 가산).
  - 현행의 "사용자가 버전 인자를 주며 강행 의사를 명시한 경우 경고 후 진행" 예외는 **그대로 보존**한다.
- CHANGELOG 항목 작성 시 debug 보고서가 근거면 그 항목들(증상·수정)을 요약해 싣는다.

## 완료 기준

1. **세션 왕복**: 빌드 후 에러를 발견한 상태에서 `/tide:debug "증상"`을 실행하면 `.tide/phase`가
   `debug`, `.tide/debug-session`에 번호 N이 기록되고, 수정이 끝날 때마다
   `docs/reports/debug-{N}.md`에 항목이 append된다. `/tide:debug done`을 실행하면 개요·판정이
   채워지고 `.tide/debug-session`이 삭제되며 `.tide/phase`가 `idle`로 돌아온다.
2. **빈 세션 방지**: 열린 세션이 없는 상태에서 `/tide:debug done`을 실행하면 보고서를 만들지 않고
   안내만 하고 중단한다.
3. **가드 무수정 보호**: `hooks/tide-guard.{sh,ps1}`을 한 줄도 고치지 않은 상태에서 `phase=debug`일 때
   `git commit`·`git push`·`git tag -a`는 BLOCK, `git log`·`git tag -l`·`git show HEAD:<path>`는
   ALLOW다. `tests/multi-repo`가 양 셸 동일 판정으로 이를 단언하고 FAIL 0이다(기준선 24/24에서
   신설 케이스만큼 증가).
4. **릴리즈 경로**: debug 보고서 판정이 "가능"이고 열린 세션이 없으면 `/tide:release v{추천 버전}`이
   프리플라이트 1번을 통과한다. `.tide/debug-session`이 남아 있으면 release는 중단하고 `done`을 안내한다.
5. **하위 호환**: debug 보고서가 없고 열린 세션도 없는 프로젝트에서 `/tide:release`의 동작은
   현행과 동일하다(기존 review 보고서 경로 불변). 기존 11종 커맨드의 호출명·역할·산출물도 불변이다.
6. **status 인지**: 열린 debug 세션이 있으면 `/tide:status`가 그 사실과 `다음: /tide:debug done`을
   보고한다. phase가 `debug`인데 열린 세션이 없으면 잔재로 보고한다. status는 여전히 완전 읽기
   전용이다(`.tide/debug-session`을 지우지 않는다).
7. **드리프트 가드**: `tests/discover`가 FAIL 0이다 — `docs/commands.md`·`README.md`·
   `docs/conventions.md`·`site/docs/getting-started.md`가 모두 **12종**을 선언하고, `/tide:debug`가
   카탈로그에 등장하며, `site/docs/commands.md`는 스니펫 셸을 유지한다(카운트·표 재선언 없음).
8. **계약 불변**: `.tide/phase`는 여전히 "단계명 한 줄"이고(세션 번호는 별도 파일), 가드의 차단
   규칙·메시지·exit 2가 불변이며, 2.0 stable 11종의 계약이 깨지지 않는다 — 이번 변경은 전부 가산이다.
