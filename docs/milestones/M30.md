# M30 — debug 첫 도그푸딩 피드백: 변경 파일 기준선 · 정오표 경로 · 상태값 확장

## 목표

이 마일스톤이 끝나면 **debug 보고서를 읽는 사람이 보고서와 git을 손으로 대조하지 않아도 된다** —
`변경 파일 요약`의 기준선이 규약으로 확정되고, 그 기준선이 git과 어긋나는 기본 경로(미커밋 산출물
위에 얹히는 debug)에서는 보고서 스스로 그 사실을 밝힌다. 또한 **릴리즈된 보고서가 사실과 어긋난 채
남지 않는다** — 본문은 증거로 보존한 채 말미에 정오표를 append하는 경로가 생긴다. 마지막으로 debug가
실제로 쓰인 방식(발견-수정과 같은 맥락의 잔여 리스크 실측)이 상태값 `확인함`으로 계약에 편입돼,
세션이 규약 밖으로 나가지 않고도 그 일을 기록할 수 있다.

## 배경

**출처 = M29 리뷰가 지목한 최우선 후속의 실행**. M29 리뷰는 완료 기준 8개 중 런타임 동작 3가지를
"프롬프트 자산이라 하니스로 집행할 수 없다 — **첫 라이브 debug 세션에서만 확인된다**"며 잔여
리스크로 정직하게 남기고, 릴리즈 후 최우선 후속으로 **debug 세션 첫 도그푸딩**을 지목했다
(M29-review "다음 단계"). 2026-07-15 **외부 사용자 프로젝트**(tide를 쓰는 실사용 레포)에서 v0.6.0
릴리즈 전 사용자 테스트 중 **`/tide:debug` 세션 1번이 실제로 열려 닫혔고**(`debug-1`, 항목 5건 ·
수정 4건 · 미해결 0건), 그 결과를 이 세션에서 분석했다. 이 마일스톤은 그 분석의 산물이다.

**M29 잔여 리스크 ①②③ — 전부 닫힘(실증)**:

1. **항목 append가 컨텍스트 요약을 넘어 살아남는가** → **닫힘**. 하루짜리 다중 턴 세션이 211줄 ·
   5항목으로 무손실 누적됐다. 결정적 증거는 역설적인 곳에서 나왔다 — 그 결과를 세션 간에 옮기는
   **대화 릴레이가 실제로 바이트를 흘렸고**(개요·항목 2가 중간에 잘려 전달됨) **파일은 온전했다**.
   "세션이 길어지면 파일이 유일하게 믿을 수 있는 누적 저장소"라는 설계 전제가 그대로 실증됐다.
2. **`done`이 개요·판정 섹션을 실제로 채우는가** → **닫힘**. 개요·변경 파일 요약·미해결/후속·
   릴리즈 판정 4개 섹션이 전부 채워졌고, `.tide/debug-session` 삭제와 `.tide/phase` → `idle` 복귀도
   규약대로 일어났다. 번호도 독립 수열로 정상 발급(`debug-1`).
3. **release가 debug 판정을 근거로 통과하는가** → **닫힘, 기대 이상**. 단일 보고서 폴백이 아니라
   M29가 확장한 **"근거 집합 = 미릴리즈인 것 전부"** 경로가 첫 실전에서 걸렸다 — `M9-review`와
   `debug-1`이 **둘 다 미릴리즈로 공존**했고, 두 판정이 v0.6.0으로 일치해 한 릴리즈에 함께 실렸다.

**그 대가로 드러난 구멍 3개**(이 마일스톤이 닫는 것):

1. **`변경 파일 요약`의 기준선이 규약에 없다.** `debug-1`은 세 파일(`fixtures.ts`·
   `playwright.config.ts`·`admin.spec.ts`)을 **수정**으로 적었지만 git 기준으로는 **전부 신규
   파일**이었다 — 직전 사이클(M9)의 impl 산출물이라 워킹트리엔 있었으나 한 번도 커밋된 적이
   없었기 때문이다. 보고서는 *세션 시작 시점의 워킹트리*를 봤고 git은 *마지막 릴리즈 태그*를 본다.
   `skills/{milestone,impl,debug}/template.md`의 추가/수정/삭제 표에는 **어느 쪽인지 정의가 없다**.
   그리고 이건 예외가 아니라 **기본 경로**다 — 부수효과 분리(커밋은 release에서만) 때문에 debug는
   거의 항상 미커밋 산출물 위에 얹힌다. 정의가 없으니 매번 어긋나고, 매번 사람이 손으로 대조해야
   한다(실제로 그 세션은 어긋남을 설명하는 문단을 따로 써야 했다).
2. **릴리즈된 보고서의 정정 경로가 없다.** `debug-1` 항목 4는 "`destroyOnClose`는 원래대로 두었다"
   라고 적었으나 실제 커밋된 diff는 그 prop을 **제거**했다(버린 접근에서 되돌릴 때 복원 누락).
   동작은 정상이라 무해하지만 **문서가 코드와 어긋난 채 커밋·태그·푸시됐다**. tide에는 이 상황의
   규약이 전혀 없다 — 소급 수정할지, 그냥 둘지, 어디에 남길지.
3. **상태값 계약을 세션이 벗어났고, 그게 유용했다.** 규약·스킬은 상태를 `수정함`/`미해결`/
   `원인만 규명` **중 하나**로 못박는데, 세션은 항목 5에 **`확인함`**(결함 아님 — 검증 기록)을
   발명해 넣고 증상·재현·원인·수정을 "해당 없음"으로 채웠다. 용도도 규약 밖이었다 — M9 리뷰가
   "실행 미검증"으로 남긴 잔여 리스크(컨테이너 부팅 통합 · 스모크 관리자 경로)를 **debug 세션에서
   함께 실측**해 닫았다. 계약 위반이지만 명백히 쓸모 있는 위반이다. 규약이 현실을 못 담으면 세션이
   규약을 나가고, 나간 것은 추적되지 않는다.

**확정 결정 3가지**:

1. **기준선 = 해당 단계/세션 시작 시점의 워킹트리**(행위 기준). 대안이던 "마지막 릴리즈 태그
   기준"(git 기준)은 기각한다 — 보고서는 *이 세션이 무엇을 했는가*의 기록이고, `fixtures.ts`를
   세션은 실제로 **고쳤지 만들지 않았다**. git 기준으로 "추가"라 적으면 그 세션의 행위에 대해
   거짓이 된다. 대신 **어긋남을 보고서가 밝힌다** — 기준선 트리에 미커밋 산출물이 섞여 있으면
   표 아래 한 줄로 그 사실과 원인(직전 단계의 미커밋 산출물)을 적는다. 릴리즈가 담는 것은 여전히
   "미릴리즈 보고서 전부의 합집합"이므로(기존 규약) 이 결정은 릴리즈 경로를 건드리지 않는다.
2. **릴리즈된 보고서 본문은 불변, 말미에 `## 정오표`를 append**. 소급 수정은 증거를 지운다 —
   보고서는 "그때 무엇을 알았고 무엇을 근거로 릴리즈했는가"의 기록이고, 그 판정으로 이미 태그가
   나갔다. 그렇다고 틀린 채 두면 다음 독자(특히 `/tide:retro`)를 오도한다. **본문 보존 + append-only
   정정**이 둘을 동시에 지키며, 이는 tide가 이미 쓰는 관례와 동형이다(`retro.md` 최상단 누적 ·
   debug 항목 append). **미릴리즈 보고서는 본문을 그냥 고친다** — 증거가 아직 배포되지 않았다.
   릴리즈 여부 판정은 **기존 기준을 재사용**한다(마지막 릴리즈 태그 트리에 포함됐는지 — conventions
   "debug 세션 → 릴리즈 경로" 절이 단일 원본. 새 기준을 만들지 않는다).
3. **상태값에 `확인함` 가산 + 용도 경계 명시**. 라이브 세션이 실제로 쓴 이름을 그대로 채택한다.
   경계는 **같은 맥락 한정** — 발견-수정 세션 중 그 작업과 같은 맥락에서 잔여 리스크를 실측한
   경우에만 `확인함` 항목으로 남긴다. **검증만 하러 debug 세션을 여는 것은 아니다**(그건 impl·review의
   일이며, 허용하면 debug가 "아무거나 담는 자루"가 된다).

**당기지 않는 것 — 자기 판정 재검토 트리거**. M29 리뷰 사소#2는 "debug 경로에는 축약 review 게이트가
없다(자기 판정) — **회귀가 실제로 발생하면** 별도 사이클에서 트레이드오프를 재판단"으로 수용됐다.
이번에 발생한 것은 회귀가 아니라 **문서-코드 불일치**였다(구멍 2). 게이트가 잡았을 부류인 것은
맞지만 트리거 조건(회귀)은 충족되지 않았고, 결정 2의 정오표 경로가 그 증상의 처치다. **근거 1건을
원장에 기록하고 게이트는 신설하지 않는다** — 두 번째 근거가 쌓이면 그때 별도 사이클에서 판단한다.

**명시적 범위 밖**: ① 그 외부 프로젝트 자체 사안(운영 DB 오염 방어 · 조건부 mount 설계 등)은 그
레포의 판단이고 tide 변경 대상이 아니다. ② debug 경로의 review 게이트 신설(위 참조). ③ `/tide:debug`의
2.0 stable 승격 — 여전히 v2.x 가산이며 다음 major의 사안이다(2.0 동결 집합은 11종 불변). ④ 커맨드
수는 **12종 그대로**다 — 이번 변경은 새 커맨드를 더하지 않으므로 `tests/discover` B1 대상 파일의
"N종" 선언은 **손대지 않는다**.

## 태스크 상세

### M30-T01: conventions에 세 규약 확정 — 변경 파일 기준선 · 정오표 · debug 상태값/용도 확장

- **변경 파일**: `docs/conventions.md`
- conventions는 **규약의 단일 원본**이므로 이 태스크가 정의하고 스킬·템플릿이 따른다(T02~T04가
  deps로 걸리는 이유). `[start:body]` 마커 안쪽에 쓴다(사이트가 인클루드한다).
- **① 변경 파일 요약 기준선** — "보고서" 절에 규약을 신설한다(마일스톤 문서의 "파일 변경 요약"에도
  동일 적용됨을 명시):
  - **기준선 = 해당 단계/세션이 시작될 때의 워킹트리**다. 추가/수정/삭제는 *그 트리 대비 이 단계가
    한 행위*를 뜻한다 — git `HEAD`나 마지막 릴리즈 태그 대비가 아니다.
  - **어긋남 고지(필수)**: 기준선 트리에 **미커밋 산출물이 섞여 있으면**(직전 단계가 만든 파일이
    아직 커밋되지 않은 경우) 표 아래에 **한 줄**로 그 사실을 적는다 — 예: "기준선 = 세션 시작
    워킹트리. `a.ts`·`b.ts`는 직전 M9 impl의 미커밋 산출물이라 git 기준으로는 신규 파일이다."
  - **왜 debug에서 기본 경로인가**를 한 줄로 남긴다 — 부수효과 분리(커밋은 release에서만) 때문에
    debug는 거의 항상 미커밋 산출물 위에 얹힌다. 고지가 없으면 독자가 보고서와 git을 손으로
    대조해야 한다(근거: `debug-1` 실사례).
  - 릴리즈가 담는 범위는 이 기준선과 무관하게 **미릴리즈 보고서 전부의 합집합**이다(기존 "debug
    세션 → 릴리즈 경로" 절 불변 — 여기서 재정의하지 않고 포인터만).
- **② 정오표(errata)** — "보고서" 절에 규약을 신설한다(모든 보고서 종류에 적용 — impl·review·debug):
  - **릴리즈된 보고서의 본문은 소급 수정하지 않는다.** 그 시점의 판정으로 태그가 나갔으므로 본문은
    증거다.
  - 사실 오류가 발견되면 그 보고서 **말미에 `## 정오표` 섹션을 append**한다(본문 무수정). 항목마다
    **날짜 / 무엇이 틀렸는지(본문 위치) / 실제 사실 / 확인 근거**를 적는다. 정오표 자체도 append-only다
    (기존 정오표 항목을 고치지 않는다).
  - **미릴리즈 보고서는 본문을 직접 고친다** — 아직 배포되지 않았으므로 정오표를 쓸 이유가 없다.
  - **릴리즈 여부 판정은 기존 기준을 그대로 쓴다** — 보고서 파일이 마지막 릴리즈 태그의 트리에
    포함돼 있으면 릴리즈된 것(위 "debug 세션 → 릴리즈 경로" 절이 단일 원본). **새 기준을 만들지
    않는다** — 포인터로 인용한다.
  - **누가**: 오류를 발견한 세션(주로 `/tide:debug`, 또는 `/tide:review`)이 append하고, **그 사실을
    자기 보고서에도 한 줄 남긴다**(무엇을 정정했는지 추적). 정오표 append는 debug의 금지 목록에
    걸리지 않음을 명시한다 — 금지는 **마일스톤 문서**·버전 파일·`CHANGELOG.md`이지 보고서가 아니다.
  - **판정 불변**: 정오표는 그 보고서의 `## 릴리즈 판정`을 바꾸지 않는다(이미 소진된 판정이다).
    이미 릴리즈된 보고서는 release 근거 집합에 다시 들어가지 않으므로 정오표 append가 릴리즈 경로에
    영향을 주지 않음을 한 줄로 못박는다.
- **③ debug 상태값·용도 확장** — "debug 세션" 절의 상태값을 **`수정함`/`미해결`/`원인만 규명`/`확인함`
  네 가지**로 가산한다:
  - **`확인함`** = 결함이 아니었거나 실측만 한 항목(검증 기록). 증상·재현·원인·수정은 "해당 없음"으로
    두고 **검증**만 채운다.
  - **용도 경계(필수)**: 발견-수정 세션 중 **그 작업과 같은 맥락에서** 잔여 리스크를 실측한 경우에만
    쓴다. **검증만 하러 debug 세션을 열지는 않는다**(그것은 impl·review의 일) — 허용하면 debug가
    아무거나 담는 자루가 된다.
  - 근거를 한 줄로 — 라이브 세션이 리뷰의 "실행 미검증" 잔여 리스크를 debug에서 함께 닫았고(유용),
