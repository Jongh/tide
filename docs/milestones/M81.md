# M81 — 시작하기 워크스루의 release 서술을 실제 동작에 맞춘다

## 목표

**`site/docs/getting-started.md` 「5분 워크스루」의 release 단계가 release 스킬이 실제로 하는 일과 같은 것을 적는다.** release는 `README.md`를 고치지 않고
CHANGELOG가 릴리즈 노트의 단일 원본이라는 사실이 처음 읽는 사람에게 그대로 전해진다. 함께, M80이 기준끼리의 충돌로 남긴 제목 줄의 줄표 둘을
사이트 앵커와 저장소 안 링크가 깨지지 않는 범위에서 정리한다. 문서의 다른 사실 · 토큰 · 하니스가 무는 자리는 바뀌지 않는다.

## 배경

- **회고 후속 `rf-91`(v2.45.1 시점 회고 신설)** — `getting-started.md` 「5분 워크스루」의 release 항목이 「버전 범프 → CHANGELOG/README 갱신 → commit → tag → push」라고 적는다.
  release 스킬은 README를 건드리지 않는다 — `docs/conventions.md`의 "버전 · CHANGELOG" 절이 CHANGELOG를 노트의 단일 원본으로 두고 README는 포인터만 둔다.
  M80 이전부터 있던 사실 오류이고, M80은 어투만 바꾸는 마일스톤이라 고치지 않았다(`docs/reports/M80-impl.md` 「미해결·후속 메모」 · `docs/reports/M80-review.md` 「다음 단계」).
- **같은 행의 둘째 항목** — 제목 줄 「### 수동 복사 (비권장 — 가드 hook 미포함)」가 `README.md`와 `getting-started.md`에 있다. M80 완료 기준끼리(제목 고정 · 산문 줄표 0)가 충돌해 「부분」으로 받아들인 자리다.
  바꾸려면 그 제목의 앵커를 가리키는 링크부터 훑어야 한다고 M80 impl 후속이 적었다. 계획 시점의 훑기로는 저장소 안에 그 앵커를 가리키는 링크가 없다(impl이 다시 잰다).
- **사용자 선택(2026-10-28 세션)** — 회고가 권한 세 후보(`rf-91` · `rf-86`+`rf-87` · `rf-89`+`rf-90`) 가운데 사용자 실행 표면의 사실 오류를 작은 patch로 먼저 낸다.
- 소개 문서 편집이므로 `CLAUDE.md`의 어투 항목(사용자의 메일 어투 — 기준표는 `docs/milestones/M80.md`의 T01)을 따른다.

## 태스크 상세

### M81-T01: 「5분 워크스루」 release 항목을 실제 동작에 맞춘다

- **변경 파일**: `site/docs/getting-started.md`
- 「5분 워크스루」의 `/tide:release` 항목에서 「CHANGELOG/README 갱신」을 「CHANGELOG 갱신」으로 바꾼다. 문장 순서(버전 범프 → CHANGELOG 갱신 → commit → tag → push)는 그대로 둔다.
- 고치기 전에 `skills/release/SKILL.md`의 절차와 같은 항목의 나머지 문장(프리플라이트 셋 · `gh` 옵트인 · 「git을 만지는 유일한 단계」)을 대조해, 사실과 어긋나는 자리가 더 있는지 본다.
  더 있으면 이 태스크에서 함께 고치되, 범위어(「만」 · 「항상」 · 「할 수 있다」)를 바꾸는 편집이면 보고서에 고친 전후를 적는다(`rf-92` 부류 — 문장을 고치면서 사실을 더하지 않는다).
  `pr` 모드에서 태그가 머지 뒤로 미뤄지는 것처럼 세부를 더하는 것은 이 태스크의 범위가 아니다 — 워크스루는 기본 흐름만 적는다.
- `README.md`와 `docs/commands.md`에 같은 서술(release가 README를 갱신한다)이 있는지 훑는다. 계획 시점에는 없다. 있으면 같은 편집에서 고친다.
- 어투는 `CLAUDE.md` 어투 항목을 따른다(하십시오체 · 한 문장에 사실 하나).

### M81-T02: 제목 줄 「수동 복사」의 줄표를 정리한다

- **변경 파일**: `README.md` · `site/docs/getting-started.md`
- **먼저 앵커 영향을 잰다**:
  - 사이트: 고치기 전과 후에 `mkdocs build --strict -f site/mkdocs.yml`(레포 루트)로 빌드하고, `getting-started/index.html`의 그 제목 `id`를 비교한다(`toc` 확장 기본 slugify — 비 ASCII 처리 결과를 실측한다).
  - 저장소 안 링크: `README.md` · `site/docs/` · `docs/` · `skills/`에서 그 제목 앵커(빌드가 낸 `id`와 GitHub식 앵커 둘 다)를 가리키는 링크를 훑는다. 검색의 네 축(패턴 · 대상 · 대조 항목 · 루트)을 보고서에 적는다.
- 사이트 `id`가 바뀌지 않고 저장소 안 링크가 0이면, 두 파일의 제목을 같은 문면으로 바꾼다 — 예: 「### 수동 복사 (비권장, 가드 hook 미포함)」. 두 파일은 같은 문면이어야 한다.
- 사이트 `id`가 바뀌거나 저장소 안 링크가 있으면, **제목을 바꾸지 않고** 그 실측을 보고서에 적은 뒤 이 태스크를 「바꾸지 않음」으로 닫는다(대체 경로).
- GitHub의 README 앵커는 제목 문면이 바뀌면 반드시 바뀐다. 저장소 밖에서 그 앵커를 가리키는 링크는 잴 수 없으므로, 바꾼 경우 그 사실을 보고서와 CHANGELOG 노트에 한 줄로 적는다.

## 완료 기준

1. `site/docs/getting-started.md` 「5분 워크스루」의 release 항목에 「README」 낱말이 없고, 갱신 대상으로 CHANGELOG가 남아 있다.
2. T01이 대조한 release 항목의 나머지 문장마다 「맞음 / 고침」이 보고서에 적혀 있고, 고친 문장은 전후가 함께 적혀 있다.
3. T02는 둘 중 하나로 닫힌다 — ⑴ 두 파일의 제목이 같은 문면으로 바뀌었고, 사이트 빌드의 그 제목 `id`가 전후 같으며 저장소 안 링크 훑기가 0건이다 ⑵ 제목을 바꾸지 않았고 그 까닭이 된 실측(바뀐 `id` 또는 링크 위치)이 보고서에 있다.
4. `pwsh` 7 · Windows PowerShell 5.1의 `tests/discover` 전수가 FAIL 0이다(수는 `tests/discover/README.md`의 `cases:` 선언처를 가리킨다). 나머지 `run.ps1` 하니스 여섯도 두 PowerShell에서 FAIL 0이다. sh 축은 규약 `measure-axis:`대로 CI가 판정한다.
5. `mkdocs build --strict -f site/mkdocs.yml`이 정상 종료하고, 빌드 출력의 제외 용어 스캔이 0건이며 같은 명령 형태의 양성 통제가 1건 이상이다(`scan-same-form-control`).
6. `skills/` · `hooks/` · `docs/conventions*.md` · `tests/` 변경이 0이다(`git diff --name-only`).
7. 고친 문장이 `CLAUDE.md` 어투 항목을 따른다 — 하십시오체이고, 새 문장에 산문 줄표와 「」가 없다.
