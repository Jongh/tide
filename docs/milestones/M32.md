# M32 — 루프 신호 복원: 리뷰 적대 검증 승격 · 판정 계측 · 재작업 라운드 수렴 조건

## 목표

이 마일스톤이 끝나면 **리뷰 판정이 다시 신호가 된다** — 리뷰는 판정 직전 자기 결론을 반박하는
독립 패스(반증 시도)를 거치고, in-review 수정이 있었으면 검증을 재실행한 뒤에만 판정을 내며,
"가능"이 *처음부터 깨끗했는지* *고쳐서 깨끗해졌는지*가 보고서에 계측 값으로 남는다. 또한
`불가` 이후의 재작업 왕복이 몇 번째인지 기록되고, 반복이 임계를 넘으면 마일스톤 재분해를
권고한다(advisory·비차단). 릴리즈 프리플라이트의 판정 파싱·보고서 섹션 구조·tide-guard 계약은
전부 불변인 채, 판정을 만들어내는 **절차와 그 관측 가능성만** 더해진다.

## 배경

2026-07-28 루프 엔지니어링 관점 분석(이 세션)에서 측정된 사실이 출처다.

- **판정이 항상 "가능"이다 — 31/31**: M1~M31 리뷰 보고서 전부 판정 `가능`, 통산 차단 이슈는
  M1의 1건뿐. 원인은 구조적이다 — `skills/review/SKILL.md`가 "차단 이슈는 수정까지 진행해도 됨"을
  허용하므로 리뷰어가 결함을 **스스로 고치고 스스로 판정**하고, 리뷰는 impl과 같은 세션 컨텍스트에서
  돈다. 판정자=실행자 구조에서 `불가`는 나올 수 없다(나오려 하면 고쳐서 `가능`으로 만든다).
  결과적으로 release 프리플라이트 게이트 ①(판정 "가능")은 **항상 참인 조건**이고 실질 게이트는
  ②테스트·③워킹트리 둘뿐이다.
- **적대 검증은 이미 효과가 입증됐으나 재량으로 남아 있다**: 회고가 M18·M19·M20·M28에서 "계약·안전
  사이클의 적대 검증이 **그린 테스트가 못 잡은 결함**을 적발"을 반복 기록했다(M28은 실제로 2건 적발).
  즉 tide는 자기 루프의 처방을 이미 발견해 놓고 **규약으로 승격하지 않았다**.
- **`불가` 경로는 31사이클 동안 한 번도 실행되지 않았다**: 보완 후 `/tide:impl M{N}` 재실행, cycle의
  "불가" 종료 분기, status·fleet의 `보완 필요` position이 전부 문서화만 되고 검증된 적 없다. 그런데
  사이클 수준에는 재작업 왕복 횟수 기록도 수렴 조건도 없다 — **두 결함이 서로를 가리고 있어서**
  (판정이 안 나오니 왕복도 안 일어난다) 지금까지 문제가 되지 않았을 뿐, 적대 검증을 켜서 `불가`가
  실제로 나오기 시작하면 즉시 드러난다. 그래서 세 항목을 **한 사이클에 묶는다**.
- **범위 밖(후속으로 남김)**: 같은 분석이 짚은 ① 규약 단조 증가(conventions 499→917줄/9 minor,
  절 단위 분할·사문화 규약 집계) ② 보고서 전면 메타 블록(YAML 계측) ③ 잔재 phase 진입 경고는
  이번 범위에 넣지 않는다. ②는 이번에 들어가는 **판정 계측 한 줄**이 그 최소 판이며, 그 값이
  몇 사이클 쌓인 뒤 전면 확장 여부를 판단하는 편이 낫다.
- **M31 최우선 후속의 자연 회수**: "릴리즈 커버리지 체크의 첫 라이브 실증"은 **이번 사이클의 release
  프리플라이트에서 자연 발생**한다(v2.9.0 설치본부터 step 5가 라이브). 태스크로 두지 않고 리뷰의
  `다음 단계`에 명시해 회수한다.

## 태스크 상세

### M32-T01: conventions "리뷰 검증 규율" 절 신설

- **변경 파일**: `docs/conventions.md`
- "보고서" 절과 "debug 세션" 절 사이에 `## 리뷰 검증 규율` 절을 신설한다 — 아래 넷의 **단일
  원본**이며, 스킬·템플릿·하니스는 이 절을 인용하고 재정의하지 않는다(기존 분담과 동일).
- **① 반증 시도(refutation) — 판정 전 독립 패스**:
  - `/tide:review`는 판정을 내리기 **직전**, 자기 판정 후보를 **반박하는** 패스를 한 번 거친다.
    Agent 도구가 가능하면 **서브에이전트로 디스패치**하고, 전달하는 것은 **판정 후보와 그 근거뿐**이다
    — 리뷰의 추론 과정을 요약해 넘기지 않는다(같은 결론을 되풀이시키면 독립성이 사라진다).
    서브에이전트는 마일스톤·impl 보고서·실제 변경 파일·테스트 결과를 **직접 읽어** 독립적으로
    "이 판정이 틀렸다면 어디서 틀렸는가"를 답한다.
  - **폴백(impl 병렬 폴백과 동형)**: Agent 도구를 쓸 수 없으면 메인이 반증 패스를 **명시 절차로**
    수행하고(판정 후보를 적어 놓고 그것을 공격하는 항목을 따로 나열), **폴백 사실을 보고서에 기록**한다.
    폴백을 조용히 생략하지 않는다.
  - **결과 반영**: 반증이 성립한 지적은 비판점(차단/권장/사소)에 편입하고 판정을 재산정한다.
    성립 0건이면 그대로 판정한다 — **반증 시도가 판정을 뒤집어야 성공인 것이 아니다**(성립 0건도
    유효한 결과이며 그 사실이 기록되는 것이 목적이다).
  - 회고(M18·M19·M20·M28)가 "계약·안전 사이클"에 한정해 재량으로 써 온 이 패스를 **모든 리뷰의
    기본 경로로 승격**한다.
- **② in-review 수정 후 재검증 강제**: 리뷰가 in-review 수정을 **1건이라도** 했으면 수정 후
  **프로젝트 검증(테스트·하니스)을 재실행**하고 그 결과를 `## 검증`에 적은 뒤에만 판정한다.
  재실행이 환경상 불가능하면 **"미검증 잔여 리스크"로 명시**한다(현재 템플릿이 솔직 명시를 권하나
  강제성이 없다). 수정 0건이면 이 요구는 발동하지 않는다(소음 0).
- **③ 판정 계측 — `## 릴리즈 판정` 섹션의 한 줄**: 판정 줄 아래에 계측 한 줄을 **필수**로 둔다.
  형식(고정): `계측: in-review 수정 차단 {n}/권장 {n}/사소 {n} · 반증 시도 {수행|폴백} 성립 {n}건 ·
  재작업 라운드(rework) {n}`. 목적은 `가능`의 의미 구분(처음부터 깨끗 vs 고쳐서 깨끗)과 추이 관측이다.
  - **파싱 불변**: 계측 줄은 `## 릴리즈 판정` 섹션 **안**에 들어가며 판정 표기(`**가능**`/`**불가**`)와
    `추천 버전`의 형식·위치를 바꾸지 않는다 — release 프리플라이트와 status·fleet의 판정 읽기는 현행
    그대로 동작해야 한다. debug 보고서 판정 형식은 **건드리지 않는다**(계측은 review 전용 가산이며,
    "두 보고서를 같은 방식으로 읽는다"는 계약은 판정 표기·추천 버전에 걸린 것이다).
- **④ 재작업 라운드(rework) 정의와 수렴 조건**:
  - **정의**: 같은 마일스톤 `M{N}`에서 리뷰 판정 `불가` 이후 impl을 재실행한 횟수. 최초
    impl→review는 **라운드 0**이다.
  - **기록**: impl 보고서 개요와 리뷰 보고서 계측 줄에 같은 값을 적는다. 값의 근거는 **기존 보고서에
    적힌 값 + 1**이며, 값이 없는 기존 보고서(M1~M31)는 **0으로 본다**(하위 호환 — 소급 갱신하지 않는다).
  - **수렴 조건(advisory·비차단)**: 라운드가 **2를 초과하면**(3회차 재작업) 리뷰는 판정과 **별개로**
    `다음 단계`에 **마일스톤 재분해(`/tide:milestone`) 권고**를 한 줄 적는다. **자동 중단·자동 재분해는
    하지 않는다**(놀라운 자동화 금지 — 번호 사전경고가 번호를 자동 변경하지 않는 것과 동형).
- **ASCII 병기**: `반증 시도(refutation)`·`재작업 라운드(rework)`·`in-review`처럼 ASCII 토큰을 병기해
  둔다 — `tests/discover`의 ps1 사본이 ASCII-only 원본 규율을 지키므로(Part D 선례) 하니스가 코드포인트
  조립 없이 토큰을 앵커할 수 있다.
- **불변 명시**: 이 절은 **절차 가산**이다 — 보고서 **섹션 구조**(2.0 stable), `.tide/phase`·tide-guard
  계약, 프리플라이트 3게이트의 순서·판정 로직, debug 세션 규약은 전부 불변이다.

- 서브에이전트에 **대상 레포 루트**와 **부수효과 분리 상속**(git commit/tag/push 금지)을 전달한다 —
  impl 병렬 디스패치의 전달 계약과 동형. 서브에이전트도 phase=`review`에서 돌아 가드가 백스톱이 된다.
- 금지 문구(git commit/tag/push)와 phase 기록·`idle` 복귀는 **불변**.

### M32-T05: `/tide:cycle` 정합 (deps: M32-T01)

## 완료 기준

1. `docs/conventions.md`에 `## 리뷰 검증 규율` 절이 있고, 반증 시도·재검증·판정 계측·재작업 라운드
   **네 규약**이 각각 발동 조건·폴백·비차단 여부를 갖고 정의돼 있다(다른 문서는 이 절을 인용만 한다).
2. `/tide:review`를 실행하면 판정 직전 반증 시도가 수행되고, 리뷰 보고서 `## 릴리즈 판정` 섹션에
   `계측: in-review 수정 차단 n/권장 n/사소 n · 반증 시도 {수행|폴백} 성립 n건 · 재작업 라운드 n`
   한 줄이 존재한다. Agent 불가 환경에서는 폴백 수행 + `폴백` 표기가 남는다.
3. in-review 수정이 1건 이상이면 `## 검증`에 **수정 후 재실행 결과**가 있거나, 불가한 경우 미검증
   잔여 리스크가 명시돼 있다.
4. impl 보고서 개요에 `재작업 라운드(rework): n`이 있고, 리뷰 계측 줄의 값과 일치한다. 값이 없는
   기존 보고서(M1~M31)는 0으로 해석되며 **소급 갱신되지 않는다**.
5. 재작업 라운드가 2를 초과하는 상황에서 리뷰의 `다음 단계`에 마일스톤 재분해 권고가 나오고,
   **판정 자체와 release 흐름은 차단되지 않는다**(advisory).
6. `tests/discover`가 Part E를 포함해 **양 셸에서 같은 PASS 수로 통과**한다. 규약·스킬·템플릿 중 한 곳에서
   **각 메커니즘의 앵커 토큰**을 지우면 FAIL한다(드리프트 집행력 확인 — 메커니즘마다 전용 토큰이 있어야
   하며, 한 토큰이 두 규약을 겸하면 한쪽 삭제를 놓친다). 음성 통제(가짜 토큰 부재)도 통과한다.
7. **불변 확인**: 보고서 섹션 구조(추가·삭제·개명 0), release 프리플라이트 3게이트의 순서·판정 로직,
   debug 보고서 판정 형식과 프리플라이트의 판정 읽기, `.tide/phase`·tide-guard 계약, 커맨드 12종
   (2.0 stable 11종)이 전부 그대로다. `tests/multi-repo`가 기존 PASS 수로 통과한다.
8. 반증 시도·계측이 **release·debug·fleet 계열 커맨드의 출력에 영향을 주지 않는다**(review·impl·cycle
   외 스킬 무변경 — fleet 계열은 review 판정을 읽기만 하며 읽는 방식이 바뀌지 않는다).
