# M13 — 멀티 레포 토대: repo-root 인식 가드 + 대상 레포 앵커링·cwd 규율 + 라이브 실증

## 목표

이 마일스톤이 끝나면 **상위 폴더 한 곳에서 띄운 단일 세션이 그 아래 여러 자식 레포를
오가며 각 위치별로 tide 사이클을 격리해 돌릴 수 있다.** 구체적으로 (1) tide-guard가
명령이 실제로 실행되는 레포 루트의 `.tide/phase`를 읽어 차단/통과를 판정하고, (2) 각
tide 커맨드의 산출물(`docs/`·`.tide/`·버전·CHANGELOG)이 **대상 자식 레포 안**에 생성되며,
(3) 모든 git·테스트 명령이 그 대상 레포를 cwd로 실행된다. 그리고 이 셋이 실제로 함께
동작함을 자식 레포 2~3개를 둔 **라이브 실증**으로 확인한다. 기존 단일 레포 사용(레포 루트
에서 세션 구동)의 동작은 **바뀌지 않는다** — 이 변경은 전부 가산(additive)이다.

## 배경

대화 분석에서 확인된 결함: tide는 "한 실행 루트 = 한 레포"를 전제로 설계돼, 모든 산출물이
실행 루트 상대경로이고 가드는 `${CLAUDE_PROJECT_DIR}/.tide/phase` **한 곳만** 읽는다
(`hooks/tide-guard.sh:8`). 사용자는 MSA 구조로 여러 레포를 연계 구현하며, 상위 폴더에서
단일 세션을 띄워 위치별로 tide를 돌리고 싶어 한다.

그 모델에서 결정적 블로커는 가드다: 스킬이 `<자식레포>/.tide/phase=release`를 써도 가드는
`<상위폴더>/.tide/phase`를 읽으므로 release가 아님으로 판정돼 **release 커밋 자체가 막힌다.**
phase를 상위 폴더 하나로 통일하면 커밋은 통과하나 phase가 전역이 되어 격리가 깨지고
(자식 A를 release하는 창에 자식 B 커밋도 통과) 산출물이 상위 폴더에 뭉친다.

따라서 멀티 레포 토대는 세 가지를 **함께** 갖춰야 성립한다 — (가드 repo-root 인식) +
(산출물 앵커링) + (cwd 규율). 셋은 "대상 레포 루트"라는 같은 기준점으로 맞물린다: cwd를
대상 레포 루트로 두면 가드의 `git rev-parse`가 같은 루트를 찾고, 스킬이 그 루트 아래에
phase·산출물을 쓰므로 가드가 읽는 phase와 스킬이 쓰는 phase가 같은 레포로 일치한다.
이 마일스톤은 그 토대만 세운다(여러 레포를 자동 조정하는 상위 오케스트레이션 계층은
별도 후속). 추가로, 규약을 더하면 그것을 강제할 실행 수단도 같은 사이클에 손본다는 메타
규칙(`docs/conventions.md` "규약↔실행/인프라 동기화")에 따라 **라이브 실증을 필수 태스크로
포함**한다.

## 태스크 상세

### M13-T01: tide-guard를 repo-root 인식으로 변경 (sh·ps1 양 사본)

- **변경 파일**: `hooks/tide-guard.sh`, `hooks/tide-guard.ps1`
- 목표: 가드가 **명령이 실제로 실행되는 작업 디렉터리의 git 레포 루트**를 찾아
  `<repo-root>/.tide/phase`를 읽도록 한다. 현재의 `${CLAUDE_PROJECT_DIR}/.tide/phase` 고정을
  대체하되, **단일 레포 사용(세션을 레포 루트에서 구동)에서는 동작이 100% 동일**해야 한다
  (그 경우 cwd의 레포 루트 == CLAUDE_PROJECT_DIR).
- 해석 순서(폴백 체인):
  1. 훅 입력 JSON에서 작업 디렉터리(cwd)를 얻는다. **불확실성 — 조사 필요**: Claude Code
     PreToolUse 훅의 입력 JSON에 `cwd` 필드가 있는지, 또는 Bash `tool_input.command`에
     `cd <dir> && …`가 섞여 오는지를 먼저 확인한다. `cwd` 필드가 있으면 그것을 1순위로 쓴다.
  2. `git -C "<cwd>" rev-parse --show-toplevel`로 레포 루트를 구해 `<root>/.tide/phase`를 읽는다.
  3. cwd를 얻을 수 없거나 git 레포가 아니면 **기존 동작으로 폴백** —
     `${CLAUDE_PROJECT_DIR:-.}/.tide/phase`. 그래도 phase 파일이 없으면 **무차단**(현행과 동일).
- 차단 규칙·메시지·exit 코드(exit 2)·검사 정규식은 **그대로 유지**한다. 바뀌는 것은
  "phase 파일을 어디서 읽는가"뿐이다.
- 구현 메모:
  - `.sh`(POSIX, Git Bash): JSON에서 cwd 추출은 `jq`가 있으면 `jq -r '.cwd // empty'`,
    없으면 이식성 있는 `sed`/`grep` 폴백. Windows 경로(`C:\…`)가 와도 `git -C`가 처리한다.
  - `.ps1`: `ConvertFrom-Json`으로 `.cwd`를 얻고 `git -C $cwd rev-parse --show-toplevel`.
  - **인코딩 규약 유지**(`docs/conventions.md` tide-guard 절): `.sh`는 BOM 없는 UTF-8,
    `.ps1`은 BOM 포함 UTF-8. 두 사본의 로직·메시지를 함께 갱신한다.
- 1.0 계약 정합: `.tide/phase`의 의미(단계명 한 줄)·차단 규칙·상태 파일 부재 시 무차단은
  불변. "phase를 실행 루트가 아니라 명령의 레포 루트에서 읽는다"는 단일 레포에서 동일 동작인
  **하위 호환 일반화**다(major 파괴 아님). conventions의 tide-guard 계약 서술은 T02에서 갱신.

### M13-T02: "대상 레포(멀티 레포)" 규약 정의 — 앵커링·cwd 규율의 단일 원본

- **변경 파일**: `docs/conventions.md`, `docs/project-context.md`
- `docs/conventions.md`에 **"멀티 레포 / 대상 레포"** 절을 신설해, T03·T04와 가드가 따르는
  규약의 단일 원본으로 둔다. 정의할 내용:
  - **대상 레포(target repo) 해석**: 각 tide 커맨드는 시작 시 "대상 레포 루트"를 정한다.
    - 기본(단일 레포): 세션을 레포 루트에서 구동한 경우 대상 = 그 레포(`CLAUDE_PROJECT_DIR`).
      **현행과 동일** — 이 절은 그 동작을 바꾸지 않는다.
    - 멀티 레포: 상위 폴더 단일 세션에서 특정 자식 레포를 작업하라고 지시받으면(인자 또는
      대화 맥락) 그 **자식 레포의 절대 루트**를 대상으로 삼는다. 인자 지원은 가산이며 기존
      `argument-hint`를 깨지 않는다(선택 인자).
  - **산출물 앵커링**: `docs/milestones/`·`docs/reports/`·`.tide/phase`·버전 파일·`CHANGELOG.md`
    등 **모든 상대경로 산출물은 대상 레포 루트 기준**으로 읽고 쓴다. 상위 폴더에 흩뿌리지 않는다.
  - **cwd 규율**: 모든 git·테스트·빌드 명령은 **대상 레포 루트를 작업 디렉터리로** 실행한다.
    (서브에이전트 위임 시에도 대상 레포 루트를 전달해 동일 규율 상속.)
  - **세 규약의 맞물림**: cwd를 대상 레포 루트로 두면 tide-guard(T01)의 레포 루트 해석이
    같은 루트를 가리키므로, 스킬이 쓰는 `.tide/phase`와 가드가 읽는 phase가 같은 레포로
    일치한다 — 이것이 멀티 레포 격리가 성립하는 핵심이다.
  - **격리 보장**: 자식 A를 release(phase=release)해도 자식 B의 phase는 독립이며 B로의 git
    commit/tag/push는 계속 차단된다(가드가 각 레포 루트의 phase를 따로 읽으므로).
  - tide-guard 계약 서술(같은 문서)을 "실행 루트 고정"에서 **"명령의 레포 루트에서 phase를
    읽는다(단일 레포에선 동일)"**로 갱신. 1.0 안정 계약 위배가 아니라 하위 호환 일반화임을 명시.
- `docs/project-context.md`에 멀티 레포 토대(대상 레포 앵커링·cwd 규율·repo-root 인식 가드)를
  핵심 도메인 개념으로 한 줄 반영.
- 메타 용어 누수 방지 규약 준수(제외 용어 literal 미사용).

### M13-T03: 스킬 반영 — 대상 레포 해석 + 산출물 앵커링 + cwd 규율 (deps: M13-T02)

- **변경 파일**: `skills/kickoff/SKILL.md`, `skills/milestone/SKILL.md`, `skills/impl/SKILL.md`,
  `skills/review/SKILL.md`, `skills/release/SKILL.md`, `skills/status/SKILL.md`,
  `skills/cycle/SKILL.md`, `skills/retro/SKILL.md`
- 각 스킬 프롬프트에 T02 규약(대상 레포 단일 원본)을 **짧게 참조 + 그 스킬의 구체 앵커링
  지점**을 명시한다. 산문 중복을 피하고 상세는 conventions에 둔다(단일 원본 유지).
  - **공통**: "시작 시 대상 레포 루트를 정하고(기본: 세션 레포 = 현행), 이 커맨드의 모든
    상대경로 산출물·git·테스트 명령은 대상 레포 루트 기준/cwd로 수행한다. 상세는
    `docs/conventions.md`의 '멀티 레포 / 대상 레포' 절."
  - **`.tide/phase` 기록**(milestone·impl·review·release·cycle): 대상 레포 루트의 `.tide/phase`에
    기록·복원(`<대상레포>/.tide/`가 없으면 생성).
  - **impl**: 테스트 명령을 대상 레포 루트 cwd로 실행. **서브에이전트 위임 시 대상 레포
    루트를 전달**해 산출물·cwd·git 금지를 그 레포 기준으로 상속(병렬 디스패치 단일 원본 절에
    한 줄 추가).
  - **release**: 버전 파일·CHANGELOG·git add/commit/tag/push를 대상 레포 루트에서 수행.
    `git push origin main`은 대상 레포의 실제 기본 브랜치·remote에 맞춘다(레포마다 다를 수
    있음 — 가정 고정 금지). 운영 주의의 "phase 기록은 git과 별도 단계로 먼저"는 대상 레포
    phase에 그대로 적용.
  - **status**(읽기 전용): 보고하는 모든 경로(마일스톤·보고서·버전·phase)를 대상 레포 루트
    기준으로 조회. 파일 변경·phase 변경은 여전히 금지.
  - **cycle**: 체이닝하는 각 단계가 동일 대상 레포 루트를 일관되게 쓰도록 명시.
  - **retro**: 회고 문서(`docs/reports/retro.md`)도 대상 레포 루트 기준.
  - **kickoff**: 골격·`docs/project-context.md` 생성을 대상 레포 루트에 한다.
- 1.0 안정 계약 정합: 추가는 전부 선택적(단일 레포 동작 불변)이며 커맨드 8종 호출명·역할은
  유지. argument-hint에 선택적 대상 레포 표기를 더하더라도 기존 호출은 그대로 동작해야 한다.

### M13-T04: 라이브 실증 하니스 + 멀티 레포 격리 실증 (deps: M13-T01, M13-T03)

- **변경 파일(추가)**: `tests/multi-repo/setup.sh`, `tests/multi-repo/setup.ps1`,
  `tests/multi-repo/README.md`(실증 절차·합격 기준)
- 목적: T01~T03이 **실제로 함께 동작**함을, 상위 폴더 단일 세션에서 자식 레포 2~3개를 두고
  재현 가능하게 실증한다. tide에는 자동 테스트 러너가 없으므로(도그푸딩 검증) **하니스
  스크립트 + 절차 문서 + impl 단계의 실제 실행**으로 구성한다.
- 하니스(`setup.sh`/`setup.ps1`): 임시 상위 폴더 아래에 자식 레포 2~3개를 만든다 —
  각 레포 `git init` + 더미 파일 + 초기 커밋 + 최소 버전 파일. push 경로까지 보려면 각
  레포에 **로컬 bare 레포를 origin으로** 연결(네트워크 없이 push 검증). teardown 포함.
  Windows에서 실제 실행되는 경로(Git Bash `sh`)와 `.ps1` 양쪽을 커버.
- 실증 절차(README.md에 단계로 명시, impl이 이 절차대로 실제 수행):
  1. 상위 폴더에서 단일 세션 기준으로, 자식 레포 A에서 `.tide/phase`를 `impl`(비-release)로
     두고 git commit을 시도 → **가드가 차단**(exit 2)됨을 확인.
  2. 자식 레포 A의 `.tide/phase`를 `release`로 두고 commit/tag 시도 → **통과**함을 확인.
  3. 같은 시점에 자식 레포 B의 phase는 비-release일 때 B로의 commit 시도 → **여전히 차단**됨을
     확인(전역이 아니라 레포별 격리 — A의 release가 B를 풀어주지 않음).
  4. 각 자식 레포의 `docs/`·`.tide/`가 **그 레포 안**에 생성되고 상위 폴더에는 tide 산출물이
     생기지 않음을 확인(앵커링).
  5. 단일 레포 회귀: 한 레포 루트에서 직접 세션을 구동한 경우 기존 동작과 동일함을 확인.
  6. push 경로(로컬 bare origin)로 release의 push까지 통과함을 확인.
- **불확실성 대비**: T01의 cwd 해석 방식(훅 입력의 `cwd` 필드 유무)이 실증에서 기대대로
  동작하지 않으면, 실패를 명확히 기록하고 폴백 동작(기존 CLAUDE_PROJECT_DIR 경로)이라도
  안전하게 유지되는지 확인한다(차단이 느슨해지지 않을 것 — 안전 측 실패).
- **검증은 양 셸 모두**: Windows 기본 경로(Git Bash `sh`)에서 통과를 1차로 보고, `.ps1`
  사본도 동일 시나리오로 확인한다.

   `<repo-root>/.tide/phase`를 읽고, cwd/레포를 얻지 못하면 `${CLAUDE_PROJECT_DIR:-.}/.tide/phase`로
   폴백하며, 어느 경우든 phase 파일이 없으면 무차단한다. 차단 규칙·메시지·exit 2·검사 정규식은
   불변이고, 두 사본의 인코딩 규약(.sh BOM 없음 / .ps1 BOM 포함)이 유지된다.
2. `docs/conventions.md`에 "멀티 레포 / 대상 레포" 절이 신설되어 대상 레포 해석·산출물
   앵커링·cwd 규율·격리 보장·세 규약의 맞물림이 단일 원본으로 정의되고, tide-guard 계약 서술이
   "명령의 레포 루트에서 phase를 읽는다(단일 레포에선 동일)"로 갱신되며, 이것이 1.0 하위 호환
   가산임이 명시된다. `docs/project-context.md`에도 한 줄 반영된다.
3. 스킬 8종이 대상 레포 해석 + 산출물 앵커링 + cwd 규율을 (conventions 단일 원본을 참조해)
   반영하고, impl은 서브에이전트에 대상 레포 루트를 전달하며, release는 버전/CHANGELOG/git을
   대상 레포 루트에서 수행하고 push 대상을 레포 실제 브랜치·remote에 맞춘다. 단일 레포 기존
   호출은 인자·동작이 그대로 동작한다(가산 확인).
4. **라이브 실증**: `tests/multi-repo/` 하니스로 상위 폴더 단일 세션 + 자식 레포 2~3개를
   구성하고 절차를 실제 실행해 — (a) 비-release 자식에서 git commit이 차단되고, (b) phase를
   release로 둔 자식에서 commit/tag/push가 통과하며, (c) 그 시점에 다른 자식의 비-release 커밋은
   여전히 차단되고(레포별 격리), (d) tide 산출물이 각 자식 레포 안에만 생기며 상위 폴더에는
   생기지 않고, (e) 단일 레포 회귀가 기존 동작과 동일함을 — Git Bash `sh` 기준으로 통과 확인하고
   `.ps1` 사본도 동일 시나리오로 확인한다. 결과를 완료보고서에 기록한다.
5. 이 라운드의 변경이 전부 가산·일반화(단일 레포 동작 불변, 커맨드 8종 호출명·역할 유지,
   `.tide/phase` 의미·차단 규칙 불변)이며 1.0 안정 계약을 깨지 않음이 확인된다.
