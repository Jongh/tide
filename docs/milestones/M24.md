# M24 — 릴리즈 게시 모드(gh): GitHub 릴리즈 / PR 택1 + read_deps 단일 원본화

## 목표

이 마일스톤이 끝나면 **`gh` CLI가 사용 가능한 환경에서 `/tide:release`가 게시 방식을 골라서 수행**할 수
있다 — 기존 push 위에 **GitHub 릴리즈를 생성**하거나, 직접 push 대신 **릴리즈 브랜치 + PR을 생성**하는 두
모드를, 인자로 명시하거나 **첫 실행 시 대화형으로 선택**한다. 첫 선택은 `.tide/release-mode`에 **기억해
이후 같은 모드를 재사용**할지 물어 본다. 게시 전엔 **`git`·`gh` 명령 가용성과 대상 원격이 gh가 다룰 수 있는
GitHub 레포인지 검증**하고, 검증에 실패하면(원격 미등록·비-GitHub 서버·미인증 등) 안전하게 처리한다.
`gh`가 없으면 **현행 동작(버전 범프→CHANGELOG→commit→tag→push)이 바이트 동일하게 유지**된다(옵트인·하위
호환). 더불어 M23 회고의 비차단 후속 sn2를 종결한다 — `read_deps`/`ReadDeps`(+ 보조 `strip_bom`/`dep_name`)를
`tests/lib/` 공유 라이브러리로 추출해 발견·위상정렬 참조 구현의 단일 원본화를 마무리한다.

## 배경

- **출처**: 사용자 지시(2026-06-17) — "gh 커맨드가 있을 때 릴리즈를 기존 릴리즈 혹은 PR 요청 둘 중
  하나를 골라서 할 수 있게" + M23 리뷰 비차단 후속 sn2(`read_deps`/`ReadDeps` 추가 단일 원본화).
- **① 릴리즈 게시 모드(gh)**: 현재 `/tide:release`는 git을 만지는 유일한 단계로 `commit→tag→push`까지만
  한다(`skills/release/SKILL.md`). GitHub 게시(릴리즈 객체·PR)는 사람이 별도로 한다. `gh`가 있는 레포에선
  release가 게시까지 이어 주면 사이클이 닫힌다. 단 이는 **git을 만지는 안정 계약**(2.0 stable)을 건드리므로
  **기본 불변·옵트인**으로만 더한다 — 모드는 인자로 명시할 때만 활성, `gh` 부재 시 현행 그대로.
- **두 모드의 git 흐름 차이**(설계 핵심):
  - **`release` 모드(GitHub 릴리즈)**: 현행 흐름(기본 브랜치에 commit→tag→push)을 **그대로 수행한 뒤**
    `gh release create {버전}`으로 릴리즈 객체를 추가 생성한다 — **가산**(기존 절차 위에 1단계 추가).
  - **`pr` 모드(PR 생성)**: 기본 브랜치에 직접 push하지 않는다. **릴리즈 브랜치**에 버전 범프·CHANGELOG를
    commit→브랜치 push→`gh pr create`로 PR을 연다. **태그·GitHub 릴리즈는 머지 후로 미룬다**(PR 머지는
    사람 몫) — release는 "PR 열림"까지 하고 핸드오프한다. 직접 push 흐름과 갈라지는 유일한 모드.
- **게시 견고성(사용자 보강 4종, 2026-06-17)**:
  - **(1) 모드 미지정 시 선택 요청**: `gh`가 사용 가능한데 모드 인자도 저장된 선호도 없으면, 조용히
    push-only로 떨어지지 말고 **`release`/`pr`(+ "이번엔 그냥 push") 중 고르도록 대화형으로 요청**한다.
  - **(2) git·gh 명령 검증**: 게시 분기 진입 전 `git`·`gh` 두 CLI의 **가용성·필요 서브커맨드 동작**을
    검증한다(`gh --version`·`gh release`/`gh pr` 존재·`gh auth status` 인증). 어느 하나라도 불충족이면
    게시를 시도하지 않는다.
  - **(3) 첫 선택 기억**: 첫 실행에서 `release`/`pr`을 고른 직후 **"이후에도 같은 모드를 쓸지" 질문**하고,
    예이면 `.tide/release-mode`에 기록한다. 다음 release부터는 인자 없이도 그 모드를 재사용(질문 생략).
    우선순위: **명시 인자 > `.tide/release-mode` > 대화형 질문(첫 실행)**. 이 파일은 `.tide/deps`처럼
    **커밋되는 레포 게시 규약**(gitignore는 `.tide/phase`만 — release-mode는 추적됨).
  - **(4) 원격이 gh로 다룰 수 없는 경우**: `gh`가 설치·인증돼 있어도 **대상 원격이 GitHub 레포로
    등록되지 않은 상황**(원격 미설정·비-GitHub 호스트(GitLab 등)·해당 호스트 미인증)에서는 게시가
    불가능하다. `gh repo view`(또는 원격 URL 호스트 점검)로 판정하고, **명시 모드면 중단·사유 보고**,
    **대화형이면 gh 모드를 아예 제시하지 않고**(push-only만) 불가 사유를 한 줄 알린다.
- **부수효과 분리·가드 불변**: 두 모드 모두 프리플라이트 통과 후 `.tide/phase=release`에서만 동작한다
  (release가 유일한 게시 단계라는 불변 유지). **tide-guard는 확장하지 않는다** — 가드는 `git commit/tag/push`
  토큰만 차단하는 계약(2.0 stable)이고, `gh`는 별도 바이너리다. tide 레포 밖 정상 `gh` 사용까지 막을 위험이
  있어 가드로 `gh`를 게이트하지 않는다. 대신 release 스킬이 `gh` 호출을 자기 절차 안(phase=release)에서만
  실행해 "게시는 release에서만" 불변을 절차로 보존한다(가드 계약 무변경).
- **② sn2 — read_deps 단일 원본화(M23 후속)**: M23이 `discover`/`toposort`를 `tests/lib/`로 추출했으나,
  `toposort`가 호출하는 `read_deps`/`ReadDeps`는 범위 밖이라 fleet·fleet-cycle 하니스 **로컬로 남았다**
  (각 × 2셸 = 4벌). `tests/lib/toposort.{sh,ps1}`는 "호출 하니스가 read_deps를 정의한다"는 가정에 의존한다
  (파일 주석). 코드 조사 결과 **이미 드리프트가 있다** — ps1의 이름 추출 정규식이 fleet(`(>=|<=|==|=|>|<).*$`)와
  fleet-cycle(`\s*[<>=].*$`)로 **갈라졌다**(`DepName`). M23의 toposort 화해와 동형으로 정본화해 닫는다.
- **비파괴·하위호환**: ①은 옵트인 가산이다. **`gh` 부재 환경의 동작은 현행과 바이트 동일**하고(게시 분기
  자체가 비활성), `gh` 가용 환경에서도 저장된 선호도/명시 인자가 있으면 질문 없이 진행한다 — 대화형 선택은
  `gh` 가용 + 선호도·인자 부재(첫 실행)일 때만 더해진다(M24 이전에 gh 모드 자체가 없었으므로 깨질 기존
  동작 없음). ②는 내부 정리(양 셸 하니스 동일 통과로 동작 보존 실증). 2.0 stable 계약(11종 커맨드 호출명·
  역할, 오케스트레이션 규약, `.tide/phase`/tide-guard, 보고서·마일스톤 형식)·M22 드리프트 가드(discover
  B1/B2/B3) 전부 불변. 커맨드 수는 11종 유지(`/tide:release` 안의 옵션 추가일 뿐 새 커맨드 아님).

## 태스크 상세

### M24-T01: `docs/conventions.md` "릴리즈 게시(gh)" 규약 절 신설

- **변경 파일**: `docs/conventions.md`
- 릴리즈 관련 절(버전·CHANGELOG / 릴리즈 빌드 출력 검증 인근)에 **"릴리즈 게시(gh)"** 하위 절을 신설하고,
  이 절을 게시 모드의 **단일 원본**으로 둔다(스킬은 이를 참조). 다음을 규정한다:
  - **검증 게이트(항목 2·4)**: 게시 분기 진입 전 다음을 순서대로 검증하고, 하나라도 불충족이면 게시를
    시도하지 않는다 — ① `git` 가용(`git --version`), ② `gh` 가용(`command -v gh`/`Get-Command gh` +
    `gh --version`)과 필요한 서브커맨드 존재(`gh release`·`gh pr`), ③ 인증(`gh auth status`), ④ **대상 원격이
    gh가 다룰 수 있는 GitHub 레포인지**(`gh repo view` 성공, 또는 원격 URL 호스트가 gh 인증 호스트와 일치).
    ④ 실패(원격 미설정·비-GitHub 호스트·해당 호스트 미인증)는 "gh로 게시 불가" 상태로 본다.
  - **모드 선택(우선순위)**: `/tide:release v{버전} [모드]`의 모드 토큰 `pr`(PR 생성) / `release`(GitHub
    릴리즈 생성)이 1순위. 인자 없으면 `.tide/release-mode` 저장값이 2순위. 둘 다 없고 게시 가능하면(검증
    통과) **3순위로 대화형 질문**(항목 1) — `release`/`pr`/"이번엔 그냥 push" 중 택1. `gh` 부재 또는 검증
    실패면 push-only로 진행하고 모드 질문을 하지 않는다.
  - **선호도 기억(항목 3)**: 인자·저장값 없이 첫 대화형 선택을 한 경우, 선택 직후 "이후에도 같은 모드를
    쓸지" 물어 예이면 `.tide/release-mode`에 모드 한 줄을 기록한다(다음 release부터 질문 생략). 명시 인자로
    실행하면 저장값을 그 인자로 갱신할지도 같은 방식으로 물을 수 있다(선택). `.tide/release-mode`는
    `.tide/deps`와 동급의 **커밋되는 레포 게시 규약**(gitignore 범위는 `.tide/phase`만이라 추적됨).
  - **원격 불가 처리(항목 4)**: 검증 ④ 실패 시 — **모드를 명시(인자/저장값)했으면 중단하고 사유 보고**
    (조용한 강등 금지), **대화형이면 gh 모드를 제시하지 않고 push-only로 진행**하며 불가 사유를 한 줄 알린다.
  - **`release` 모드(가산)**: 현행 흐름(commit→tag→push) **그대로** 수행 후 `gh release create {버전}`으로
    릴리즈 객체 추가 생성(노트는 `CHANGELOG.md` 해당 버전 발췌 — 제외 용어 규약 준수). 기존 절차 무변경.
  - **`pr` 모드(분기)**: 기본 브랜치 직접 push 안 함. 릴리즈 브랜치(예: `release/v{버전}`)에 버전 범프·
    CHANGELOG commit → 브랜치 push → `gh pr create`(제목 `Release v{버전}: …`, 본문 = CHANGELOG 발췌).
    **태그·GitHub 릴리즈는 PR 머지 후로 미룸**(release는 "PR 열림"까지 하고 사용자에게 핸드오프).
  - **명시 의도 비폴백**: 모드를 명시했는데 `gh` 부재/미인증이면 **중단하고 사유 보고**(조용한 강등 금지 —
    사용자가 게시를 명시했으므로). 모드 미지정이면 `gh`를 아예 건드리지 않음(기본 불변).
  - **부수효과 분리·가드 불변**: 두 모드 모두 `.tide/phase=release`에서만 실행. **tide-guard는 확장하지
    않는다**(가드는 git 토큰만 차단하는 2.0 stable 계약, `gh`는 게이트 안 함 — tide 밖 정상 `gh` 사용 보호).
    "게시는 release에서만" 불변은 스킬 절차가 보존.
- **엣지**: `pr` 모드에서 릴리즈 브랜치가 이미 있으면 재사용 여부·이름 충돌 처리 방침 한 줄. `release` 모드에서
  `gh release create`가 태그를 요구/생성하는 경우 로컬 태그(현행 4단계)와 중복 생성 방지(이미 push된 태그 참조).

### M24-T02: `skills/release/SKILL.md`에 gh 게시 모드 구현 (deps: M24-T01)

- **변경 파일**: `skills/release/SKILL.md`
- 상단 인자 설명을 확장: 버전 뒤 선택적 모드 토큰(`pr`/`release`)을 받는다고 명시. `$ARGUMENTS`에서 버전과
  모드를 분리 파싱. 프리플라이트(4단계)·`.tide/phase=release` 기록·버전 범프·CHANGELOG 단계는 **현행 그대로**
  두고, 그 다음 **게시 모드 해석 → 검증 게이트 → 게시 분기** 순으로 추가한다.
- **모드 해석(우선순위)**: 명시 인자 > `.tide/release-mode` 저장값 > (게시 가능 시) 대화형 질문. 인자·저장값이
  없고 검증 통과면 `release`/`pr`/"이번엔 그냥 push" 중 고르도록 묻고(항목 1), 첫 선택이면 "이후에도 같은
  모드를 쓸지" 물어 예이면 `.tide/release-mode`에 기록한다(항목 3).
- **검증 게이트(항목 2·4)**: 게시 분기 진입 전 `git`·`gh` 가용성·서브커맨드(`gh release`/`gh pr`)·인증
  (`gh auth status`)·**원격 GitHub 등록**(`gh repo view`)을 확인한다. `gh` 부재/미인증/원격 불가면 게시 비활성.
- **게시 분기**:
  - **push-only(모드 없음이고 `gh` 부재/검증 실패, 또는 "그냥 push" 선택)**: 현행 6단계(add→commit→tag→
    push 브랜치→push 태그) 그대로. `gh` 부재 환경에선 바이트 동일.
  - **`release` 모드**: 현행 6단계 수행 후 `gh release create {버전}`(노트 = CHANGELOG 발췌) 1단계 추가.
  - **`pr` 모드**: 기본 브랜치 push 대신 릴리즈 브랜치 commit→브랜치 push→`gh pr create`. 태그·릴리즈 미룸,
    PR URL 보고 후 핸드오프.
- **폴백·원격 불가(항목 4)**: 검증 실패 시 — **모드를 명시(인자/저장값)했으면 게시 없이 중단하고 사유 보고**
  (조용한 강등 금지). 단 그 시점까지의 commit/tag/push가 일어났는지 명확히 보고한다 — `release` 모드는 push
  후 `gh`만 실패하면 "릴리즈 객체만 수동 생성 필요" 안내, `pr` 모드는 push/PR **분기 전에** 검증해 commit이
  기본 브랜치로 새지 않도록 중단. **대화형이면** gh 모드를 제시하지 않고 push-only로 진행하며 불가 사유를
  한 줄 알린다.
- **운영 주의 보강**: 기존 4개 항목 뒤에 gh 관련 한 줄 — 게시 명령(`gh release create`/`gh pr create`)도
  `.tide/phase=release` 동안에만 실행하고, 멀티라인 본문(릴리즈 노트·PR 본문)은 실행 환경 문법에 맞춘다

## 완료 기준

1. `gh`가 있는 레포에서 `/tide:release v{버전} release`는 현행 commit→tag→push 후 GitHub 릴리즈를 추가
   생성하고, `/tide:release v{버전} pr`는 릴리즈 브랜치 commit→push→PR 생성으로 분기한다(태그·릴리즈는
   머지 후로 미룸·핸드오프). **`gh` 부재 환경의 동작은 현행과 바이트 동일**하다.
2. **모드 선택·선호도(항목 1·3)**: 인자·저장값이 없고 게시 가능하면 `release`/`pr`/"그냥 push" 중 고르도록
   대화형으로 묻고, 첫 선택이면 "이후 같은 모드 사용" 여부를 물어 예이면 `.tide/release-mode`에 기록한다.
   다음 release는 우선순위(명시 인자 > `.tide/release-mode` > 질문)에 따라 저장값을 질문 없이 재사용한다.
3. **명령 검증·원격 불가 처리(항목 2·4)**: 게시 전 `git`·`gh` 가용성·서브커맨드(`gh release`/`gh pr`)·인증·
   **원격 GitHub 등록**(`gh repo view`)을 검증한다. 원격 미등록·비-GitHub 호스트·미인증이면 — 모드 명시 시
   **게시 없이 중단·사유 보고**(commit/tag/push 진행 여부 명확히), 대화형 시 **gh 모드 미제시·push-only 진행**.
   두 모드의 `gh` 호출은 `.tide/phase=release` 동안에만 일어나고 **tide-guard는 확장되지 않는다**(git 토큰
   차단 계약 불변).
4. `docs/conventions.md`에 "릴리즈 게시(gh)" 절이 게시 모드(검증·선택/선호도·두 흐름·원격 불가·가드 비확장)의
   단일 원본으로 존재하고, `skills/release/SKILL.md`는 절차에서 그 절을 참조(재서술 아님)하며 arg-hint가
   모드 토큰을 반영한다.
5. `tests/lib/deps.{sh,ps1}`가 `read_deps`/`ReadDeps`(+`strip_bom`/`dep_name`)를 **단일 정의**하고, fleet·
   fleet-cycle 하니스의 로컬 중복 정의가 제거·source로 대체된다. `toposort` 라이브러리 주석이 새 source 순서
   (discover→deps→toposort)를 반영한다.
6. `sh tests/fleet/run.sh`·`run.ps1`·`tests/fleet-cycle/run.sh`·`run.ps1` + `tests/discover`·`tests/multi-repo`가
   **모두 전환 전과 동일한 PASS 수로 통과**(exit 0) — 동작 보존. `tests/lib/*.ps1` 비ASCII 0·신규/수정 셸
   파일 BOM 없음. M22 드리프트 가드(discover B1/B2/B3) 단언 불변.
7. `docs/commands.md`가 release의 gh 모드를 반영하되 **커맨드 11종·셸·이름 완전성 가드 불변**, `docs/project-
   context.md`가 게시 모드 단일 원본 위치·`.tide/release-mode`·`read_deps` 단일 원본화를 기록한다(버전 숫자 미복제).
8. **비파괴 확인**: 2.0 stable 계약(11종 커맨드 호출명·역할, 오케스트레이션 규약, `.tide/phase`/tide-guard,
   보고서·마일스톤 형식) 불변. 게시 모드는 옵트인 가산, sn2는 내부 정리.
