# M14 — 상위 오케스트레이션 1층(읽기 전용 fleet 개요) + 문서↔릴리즈 드리프트 차단

## 목표

이 마일스톤이 끝나면 **상위 폴더 단일 세션에서 그 아래 여러 tide 자식 레포의 사이클 상태를
한 번에 보고 조정된 다음 행동 계획을 받을 수 있다** — 새 읽기 전용 커맨드 `/tide:fleet`이
자식 레포들을 발견해 각자의 마일스톤·보고서·판정·버전·phase를 교차 집계하고, 어떤 레포가
release 가능/진행 중인지와 권장 순서를 advisory로 제시한다(git·파일 변경 없음). 또한 회고가
지목한 **문서↔릴리즈 버전 드리프트가 구조적으로 차단**된다 — `project-context.md`가 버전
숫자를 복제하지 않고 `plugin.json`을 단일 원본으로 가리키게 정리된다. 멀티 레포를 자동 조정하는
무거운 계층(contract-first·통합 검증·의존성 기반 release 순서 자동화)은 **로드맵으로 명문화**해
후속 마일스톤으로 분리하고, 이번엔 그 위에 올릴 **가시성(1층)**만 세운다. 단일 레포 동작과
커맨드 8종은 불변이며 모든 변경은 가산이다.

## 배경

직전 회고(v1.1.0 시점)가 두 가지를 다음 사이클 후보로 부각했다:

1. **상위 오케스트레이션** — 가치 1순위. M13이 "멀티 레포 토대"(repo-root 인식 가드·앵커링·cwd
   규율)만 세웠고, 그 위에 올릴 "여러 레포 자동 조정·contract-first·통합 검증·릴리즈 순서"는
   M13-impl#4가 **별도 마일스톤**으로 미뤘다. 단, 이 에픽 전체는 한 사이클에 들어가지 않는다 —
   특히 cross-repo git은 부수효과 분리 원칙상 자동화에 신중해야 한다. 따라서 M14는 **가장 안전·
   고가치인 첫 층(읽기 전용 교차 가시성 + advisory 계획)**만 구현하고 자동화 층은 로드맵으로
   분리한다.
2. **문서↔릴리즈 버전 드리프트** (M13-review 사소4, 회고 감시 1순위) — `docs/project-context.md`가
   `0.7.0`에 멈춰 있다. release가 `plugin.json`만 범프하고 project-context는 갱신 배선이 없어
   여러 릴리즈를 가로질러 stale이 누적됐다. 구조적 누락이므로 **재발(2번째 관찰) 전에** 닫는다 —
   해법은 갱신 단계를 더하는 것이 아니라(유지비↑) project-context가 버전을 **복제하지 않고
   단일 원본을 가리키게** 하는 것이다(tide의 단일 원본 철학 = "규약↔실행 동기화" 메타 규칙의
   문서판).

메타 규칙(`docs/conventions.md` "규약↔실행/인프라 동기화") 적용: 오케스트레이션 규약·신규
커맨드를 더하면 그것을 검증할 **라이브 실증을 같은 사이클에** 넣는다(M13과 동일 기조).

### M14-T02: 오케스트레이션 규약·로드맵 + `/tide:fleet` 등록

- **변경 파일**: `docs/conventions.md`
- `docs/conventions.md`에 **"멀티 레포 오케스트레이션"** 절을 신설(멀티 레포/대상 레포 절 뒤,
  단일 원본). 정의할 내용:
  - **계층 모델(로드맵)**: ① **1층 — 가시성(이번 M14)**: 읽기 전용 fleet 개요(발견·교차 상태·
    advisory 계획). ② 2층 — 의존성/계약 선언(자식 레포 간 의존·계약 매니페스트)으로 순서 인식.
    ③ 3층 — 교차 사이클 자동화(milestone→review까지; release는 부수효과 분리상 레포별 수동 유지).
    ④ 4층 — 통합 검증(프로젝트 정의 통합 테스트 훅). **2~4층은 후속 마일스톤**임을 명시.
  - **부수효과 분리 불변**: 오케스트레이션은 가시성·계획·(후속) review까지 자동화하되 **cross-repo
    git commit/tag/push는 자동화하지 않는다** — release는 항상 레포별 수동(`/tide:release`)이며
    tide-guard·레포별 격리가 그대로 적용된다. fleet은 advisory만(순서 제안), 강제·실행 없음.
  - **자식 tide 레포 발견 규약**: "대상 부모"(기본=세션 cwd, 인자로 경로 지정 가능)의 **직속
    하위 디렉터리** 중 (git 레포이면서) tide 산출물(`docs/milestones/` 또는 `.tide/` 또는 버전
    파일)을 가진 것을 자식 tide 레포로 본다. 깊은 재귀는 하지 않는다(직속 1단계 — 단순·예측 가능).
  - **advisory 계획 규칙**: 각 자식 레포의 사이클 위치(`/tide:status` 판단 규칙 재사용)를 모아
    "release 가능", "review 대기", "impl 진행" 등으로 분류하고 권장 순서를 제시하되, **의존성 기반
    정렬은 2층 전까지 미지원**임을 명시(현재는 상태 기반 advisory).
- `/tide:fleet`을 **9번째 커맨드(읽기 전용)**로 규약에 등록:
  - "사이클" 다이어그램 옆/아래에 fleet을 `status`와 같은 **읽기 전용 보조**로 표기(사이클 단계가
    아님 — kickoff→…→release 흐름 밖).
  - "단계별 금지 행위 요약" 표에 `fleet | 파일 생성·수정 / `.tide/phase` 변경 / git 작업 | 프롬프트`
    행 추가(status·retro와 동일 읽기 전용 강제).
  - "1.0 안정성" 절: **기존 커맨드 8종의 호출명·역할은 불변(안정)**임을 유지하면서, `/tide:fleet`을
    **v1.2.0부터 더해지는 가산 커맨드**로 명기한다 — 안정 선언이 기능 동결이 아니라 "호환 깨는
    변경만 major"라는 약속임을 그대로 적용(새 커맨드는 minor 가산, 1.0 절이 이미 허용).
- 제외 용어 누수 0(신설 텍스트에 외부 저장소명 literal 미사용 — snippet body 영역 안쪽).

### M14-T04: 라이브 실증 — fleet 발견·교차 집계 (deps: M14-T03)

- **변경 파일(추가)**: `tests/fleet/run.sh`, `tests/fleet/run.ps1`, `tests/fleet/README.md`
- 목적: fleet의 **기계적으로 검증 가능한 핵심**(자식 레포 발견·교차 상태 집계·읽기 전용·graceful
  강등)을 재현 가능하게 실증한다. tide엔 자동 러너가 없으므로(도그푸딩) 자기완결형 하니스로 한다.
- 하니스: 임시 상위 폴더 아래 자식 tide 레포 2~3개를 서로 다른 사이클 위치로 구성한다 —
  예: 레포 A(review 보고서 "가능"+버전), 레포 B(impl만), 레포 C(비-tide/빈 디렉터리). fleet의
  발견·분류 로직을 **스크립트로 재현 가능한 형태**로 호출해(또는 fleet 스킬이 의존하는 발견·상태
  판정 셸 절차를 분리 검증) 다음을 대조: (a) A·B만 자식 tide 레포로 발견(C 제외), (b) A는 "release
  가능", B는 "review 대기/impl 진행"으로 분류, (c) advisory 계획이 각 레포의 status 규칙과 일치,
  (d) 발견 0(부모에 tide 레포 없음)일 때 graceful 강등 메시지. teardown 포함, 양 셸(sh·ps1).
- **활성 가드 정합**: 하니스는 읽기 전용 경로만 실증하므로 git 차단 동사를 명령줄에 두지 않는다
  (M13 하니스와 동일 규율 — 차단 패턴은 픽스처 내부에만, 러너는 파일명으로 호출).
- **불확실성 대비**: fleet 출력의 일부는 LLM 서술(스킬 프롬프트)이라 스크립트로 100% 강제되지
  않는다. 발견·분류 같은 **결정적 핵심**을 스크립트로 덮고, advisory 서술 품질은 README의 세션
  레벨 수동 절차로 분리한다(M13의 앵커링 수동 절차와 동일 분리).
