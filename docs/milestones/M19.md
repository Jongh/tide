# M19 — 오케스트레이션 4층: 통합 검증 훅(`/tide:fleet-verify`, verification-only)

## 목표

이 마일스톤이 끝나면 **자식 tide 레포들이 각자 사이클을 통과한 뒤, 레포를 가로지르는 통합을
프로젝트 정의 훅으로 검증할 수 있다.** 새 커맨드 `/tide:fleet-verify`가 대상 부모의 통합 훅
(`.tide-fleet/integration`, 옵트인)을 읽어 부모에서 실행하고 **통합 pass/fail**을 보고한다 — 그리고
release 핸드오프가 "통합 통과"를 전제로 하도록 흐름을 안내한다(`fleet-cycle → fleet-verify → 순서
release`). 통합 훅은 **검증(테스트) 명령**이며 git·release를 하지 않는다 — fleet-verify 자체도 git/
release/cross-repo git을 하지 않는다(verification-only, 부수효과 분리 불변). 훅이 없으면 "통합 검증
생략"으로 graceful 강등(옵트인). 이로써 오케스트레이션 로드맵 1~4층이 모두 완성된다. 단일 레포·미선언
동작 불변, 커맨드 10종(기존)·1.0 계약 불변.

## 배경

`docs/conventions.md` "멀티 레포 오케스트레이션" 4계층 로드맵에서 1층(가시성 M14·M15)·2층(의존성
M16·M17)·3층(교차 사이클 자동화 M18)이 완성됐다. **4층 — 통합 검증**이 마지막이다: 3층이 각 레포의
`milestone→review`를 의존성 순서로 자동 실행하지만, "각 서비스가 각자 통과"와 "서비스들이 **함께**
동작"은 다르다. MSA에서 release 전에 자식 레포를 가로지르는 통합(예: 서비스들을 띄워 contract/통합
테스트)을 한 번 검증하는 단계가 4층이다.

**설계 결정 — 통합 훅은 parent-level**: 의존 선언(`.tide/deps`)은 레포별(탈중앙, 각 레포가 자기 의존을
선언)이지만, **통합은 단일 레포가 소유하지 않는 cross-repo 개념**이다(어느 한 레포의 통합이 아니라
fleet 전체의 통합). 따라서 통합 훅은 **대상 부모 레벨**(`.tide-fleet/integration`)에 둔다. `.tide-fleet/`는
숨김(dot) 디렉터리라 fleet 발견에서 자동 무시되므로(자식 레포 아님) 1~3층과 충돌하지 않는다.

**불변 — verification-only**: 통합 훅은 **검증/테스트**이며 git commit/tag/push·release·cross-repo git을
하지 않는다(impl/review가 테스트를 실행하되 git을 안 하는 것과 동일). fleet-verify는 부수효과 분리상
git/release를 하지 않고, tide-guard가 phase≠release에서 git을 차단하는 백스톱은 그대로다.

## 정규 spec (이 마일스톤의 단일 기준 — T01·T02·T03이 모두 이를 인용)

### 통합 훅 (`.tide-fleet/integration`, 옵트인·parent-level)

- **위치·형식**: 대상 부모(기본 = 세션 cwd, 선택 인자로 경로)의 `.tide-fleet/integration` 파일. 내용은
  통합 검증으로 실행할 **명령(들)**(셸 명령 한 줄 이상, 빈 줄·`#` 주석 무시, 선두 BOM 제거). 부모 cwd에서
  실행한다(예: `docker compose up -d && npm run integration-test`).
- **옵트인·하위 호환**: 파일이 없거나 유효 줄이 0이면 **통합 훅 미선언** — fleet-verify는 "통합 검증 생략
  (훅 없음)"을 안내하고 graceful 종료한다. 단일 레포·미선언 fleet 동작은 현행 그대로.
- **발견 무시**: `.tide-fleet/`는 숨김 디렉터리라 fleet 발견(직속·숨김 무시)에서 자식 레포로 잡히지 않는다.

### `/tide:fleet-verify` — 통합 검증 실행

- **발견·대상**: fleet 규약으로 자식 tide 레포를 발견(직속 1단계·git·tide 산출물·숨김 무시)해 통합 대상
  레포 목록을 보고한다. 발견 0이면 단일 레포로 graceful 강등(현재 레포 `/tide:status` 권유).
- **실행·보고**: 통합 훅을 **부모 cwd에서 실행**하고 결과를 보고한다 — **exit 0 = 통합 pass**, 비0 =
  **통합 fail**(실패 출력 요약 + 관련 레포). 훅 미선언이면 검증 생략 안내.
- **verification-only(불변)**: fleet-verify는 git commit/tag/push·release·cross-repo git을 하지 않는다. 통합
  훅도 검증/테스트 명령이어야 하며(훅 작성자 책임), 어떤 레포의 `.tide/phase`도 `release`로 쓰지 않는다.
  tide-guard가 phase≠release인 레포의 git을 막는 백스톱은 그대로 적용된다.
- **출력**: ① 통합 대상 레포 목록(발견), ② 통합 훅 명령(요약), ③ **통합 결과**(pass/fail + 실패 시 요약),
  ④ 다음 안내(pass면 "이제 release 핸드오프 순서대로 수동 release", fail이면 "통합 수정 후 재검증").

### fleet-cycle ↔ fleet-verify 흐름

- 권장 순서: **`/tide:fleet-cycle`**(각 레포 milestone→review 의존성 순서 자동) → **`/tide:fleet-verify`**
  (통합 검증) → 통합 pass면 fleet-cycle의 release 핸드오프 순서대로 **수동 `/tide:release`**.
- `/tide:fleet-cycle`의 release 핸드오프 출력에 **"release 전 `/tide:fleet-verify`로 통합 확인(통합 훅 선언
  시)"** 한 줄 안내를 추가한다. (fleet-cycle은 통합을 자동 실행하지 않는다 — 안내만; fleet-verify가 별도
  명시 호출.)

### 커맨드 등록 (11번째, 가산)

- `/tide:fleet-verify`는 통합 훅(테스트)을 실행하되 **git을 하지 않는다** — "단계별 금지 행위" 표에
  `fleet-verify | git commit/tag/push / release / 어떤 레포 phase=release 쓰기 (verification-only) | 프롬프트 + hook(git)` 행 추가.
  사이클 다이어그램에 멀티 레포 통합 검증 보조로 표기. "1.0 안정성" 절에 `/tide:fleet-verify`를 **v1.6.0부터
  가산** 커맨드로 명기(8종 stable·fleet/fleet-cycle 가산 서술 유지).
