# M16 — 오케스트레이션 2층: 레포별 의존성 선언(`.tide/deps`) + 의존성 인식 권장 순서

## 목표

이 마일스톤이 끝나면 **`/tide:fleet`이 자식 레포 간 선언된 의존성을 읽어 의존성 인식 권장 처리
순서를 advisory로 제시한다.** 각 레포가 루트의 `.tide/deps`에 자신이 의존하는 형제 레포를 선언하면
(옵트인), fleet이 그 의존 그래프를 위상정렬해 "어느 레포를 먼저 처리해야 하는지"를 순서로 내놓는다
(예: orders가 auth에 의존하면 → auth 먼저). 순환 의존은 보고하고 상태 기반 순서로 폴백하며,
`.tide/deps`를 선언하지 않은 레포는 현행 그대로(의존 0) 동작한다. fleet은 여전히 **읽기 전용·
advisory만** — 순서를 제안할 뿐 cross-repo git을 자동 실행하지 않는다(부수효과 분리 불변). 이로써
1층(가시성)의 "의존성 정렬 미지원" 한계가 풀린다. 멀티 레포 토대·커맨드 9종·1.0 계약은 불변이고
모든 변경은 가산(옵트인)이다.

## 배경

`docs/conventions.md` "멀티 레포 오케스트레이션" 4계층 로드맵에서 1층(가시성)은 M14에 구현되고
M15에 정합됐다(정규 5버킷·인자·숨김). 현재 fleet은 advisory 계획 규칙에서 **"의존성 기반 정렬은
2층(의존성/계약 선언) 전까지 미지원"**임을 스스로 명시한다 — 순서를 각 레포 상태로만 산출한다.
사용자 환경은 MSA로 여러 레포가 연계되므로(예: gateway·orders가 auth API에 의존) "어느 레포를
먼저 release/구현해야 하는지"의 순서가 실제 가치다. M16은 그 2층을 세운다.

설계 결정(사용자 확정): **매니페스트는 레포별**(`.tide/deps`, 각 레포가 자기 의존을 선언 — 레포
앵커링 원칙과 일치, 탈중앙). 선언 내용은 **의존 레포명만**으로 시작하고 계약/버전 비교(예:
`svc-auth >= v0.3.0`)는 후속 sub-step으로 미룬다. 순환·미선언 처리는 impl의 `(deps:)` 폴백 기조를
따른다(감지→보고→폴백, 미선언=독립). 부수효과 분리 불변상 2층도 순서를 **제안만** 한다.

메타 규칙("규약↔실행/인프라 동기화") 적용: 새 규약(`.tide/deps` 포맷·순서 규칙)을 더하면서 그것을
검증할 라이브 실증을 같은 사이클에 넣는다.

## 정규 spec (이 마일스톤의 단일 기준 — T01·T02·T03이 모두 이를 인용)

### `.tide/deps` 매니페스트 (레포별·커밋·옵트인)

- **위치**: 각 자식 레포 루트의 `.tide/deps`. 한 줄에 **의존하는 형제 레포 디렉터리명** 하나.
  빈 줄과 `#`로 시작하는 주석 줄은 무시하고, 줄 앞뒤 공백은 트림한다.
- **의미**: "이 레포는 나열된 형제 레포들에 **의존**한다"(의존 대상이 먼저 처리되어야 한다).
  예 — `svc-orders/.tide/deps`에 `svc-auth` 한 줄 → orders는 auth에 의존, 순서상 auth가 먼저.
- **옵트인·하위 호환**: 파일이 없거나 유효 줄이 0이면 **의존 0**(현행 동작 그대로). 선언은 순수
  가산이며 단일 레포·미선언 멀티 레포 동작을 바꾸지 않는다.
- **커밋 대상**: `.tide/deps`는 레포의 **선언**이므로 커밋한다. 단, `.tide/phase`는 종전대로 로컬
  상태라 gitignore다 — 즉 **gitignore 범위를 `.tide/`에서 `.tide/phase`로 좁힌다**(deps는 커밋,
  phase는 무시). `.tide/phase`의 의미·tide-guard 계약은 불변(1.0 안정 계약 정합).
- **범위 밖(후속)**: 계약/버전 비교(`>= vX.Y.Z` 등)는 이번 마일스톤에 넣지 않는다 — 이름 기반
  의존만. 계약 버전 인식은 2층 sub-step 또는 별도 후속.

### 의존성 인식 순서 규칙

- 발견된(1층 규약: 직속·git·tide 산출물·숨김 제외) 자식 레포들의 `.tide/deps`를 모아 **방향
  그래프**(의존→피의존)를 만들고 **위상정렬**해 권장 처리 순서를 산출한다 — **피의존(먼저 필요한
  레포)이 의존하는 레포보다 앞**에 온다.
- **순환 의존**(직간접 A→B→…→A): **감지해 보고하고 상태 기반 순서로 폴백**한다(impl `(deps:)`
  순환 폴백과 동일 기조). 순환 고리에 든 레포를 명시한다.
- **미선언 레포**: 의존 0인 독립 노드로 두고 순서는 상태로 산출(다른 노드와 위상 관계 없음).
- **존재하지 않는 형제명**: `.tide/deps`가 발견 집합에 없는 이름을 가리키면 **무시하고 경고**한다
  (안전 측 — 잘못된 선언이 순서를 깨지 않게).
- fleet은 **advisory만** — 위상정렬 순서를 **제안**할 뿐 어떤 레포에도 사이클·git을 자동 실행하지
  않는다. 실제 처리 순서·시점은 사용자가 판단한다.

### fleet 출력 확장

- 기존 **레포별 표** + **교차 요약(정규 5버킷)**은 유지(M15).
- 추가: **권장 처리 순서** — 위상정렬 결과를 번호/화살표 목록으로 제시하고, 각 레포의 의존 대상을
  표기(예: `1) svc-auth  2) svc-orders(→auth)  3) svc-gateway(→auth)`). 순환·미선언 시 그 사유 한 줄.
- 1층의 "의존성 기반 정렬 미지원" 문구를 **"의존성 인식 — `.tide/deps` 선언 시 위상정렬, 순환·
  미선언은 폴백"**으로 갱신.

2. `skills/fleet/SKILL.md`가 `.tide/deps`를 읽어 위상정렬 **권장 처리 순서**를 출력에 추가하고, 순환→

   추가하고(기존 시나리오 유지) 양 셸에서 전부 통과한다(README 갱신).
4. 이 변경이 전부 가산·옵트인(미선언 시 현행 동작 불변, 단일 레포 무영향, 커맨드 9종·`.tide/phase`·
   tide-guard·1.0 계약 불변)이며 fleet은 여전히 advisory만(cross-repo git 비자동화)임이 확인된다.
