# M80 — 사이트가 직접 가진 소개 문서를 사용자의 메일 어투로 다시 쓴다

## 목표

**저장소 밖 사람이 처음 읽는 소개 문서 넷(`README.md` · `site/docs/index.md` · `site/docs/getting-started.md` · `site/docs/concepts.md`)이
사용자가 실제로 쓰는 업무 메일의 어투로 읽힌다.** 하십시오체는 그대로 두고, 한 문장에 사실 하나 · 명사구 섹션 제목 · 「목적 → 항목 → 추가로」 순서 ·
단정 대신 근거와 추정으로 문장을 짠다. 문서가 전하는 사실(커맨드 · 수 · 명령 · 링크 · 토큰)과 하니스가 무는 자리는 바뀌지 않는다.

## 배경

- **사용자 요청(2026-10-27 세션)** — 「내가 보낸 메일 내용을 기준으로 README와 프로젝트 소개 페이지의 어투나 표현 방식을 내가 말하는 어투를 이용하여 수정하고 싶다」.
  범위는 「사이트가 직접 가진 소개 문서만」으로 정했다. 존댓말 수준은 메일 수준, 영어 용어와 토큰은 그대로 쓴다.
- **어투 자료** — 사용자가 저장소 밖 폴더에 보낸 메일 15통(약 14KB)을 두었다(경로는 세션에서만 주고받고 저장소에 적지 않는다). 공유 · 요청 · 답변 · 분석 · 회의 정리가 섞여 있고
  끝맺음과 구성이 고르게 같아 어투를 잡기에 충분하다고 판단했다. 처음 보는 사람에게 「왜」를 풀어 설명한 메일은 없어, 그 부분은 아래 기준표를 넓혀 적용한다.
- **자료는 저장소에 들이지 않는다** — 메일에는 실명 · 회사명 · IP가 들어 있다. 이 저장소의 릴리즈는 작업 트리 전체를 스테이징하므로, 마일스톤 · 보고서 · 문서 어디에도
  메일 원문을 인용하지 않고 **어투의 특징만** 적는다.
- **지금 문서의 결** — 끝맺음은 이미 「~입니다 / ~합니다」라 존댓말 수준의 차이는 작다. 차이는 문장 짜임이다 — 괄호 · 줄표(—)로 끼워 넣은 긴 문장(README만 줄표 33),
  굵게와 「」 강조가 잦다. 메일은 한 문장에 사실 하나, 굵게 · 「」 · 줄표를 거의 쓰지 않는다.
- **범위에서 뺀 것** — 사이트가 저장소 원본을 인클루드하는 페이지(`commands` · `orchestration` · `conventions` · `conventions-release` · `changelog`)는 규칙과 이력의
  단일 원본이라 문장을 바꾸면 인용 가드(Part G) · 앵커 · 병기어 검사가 흔들린다. 이번 마일스톤 밖이다.
- **회고 표와의 관계** — 이 사이클은 회고 후속 표에서 오지 않았다. 최상단 회고(v2.45.0 시점)의 1순위 `rf-86`은 다음 사이클로 그대로 넘긴다.

## 태스크 상세

### M80-T01: 어투 기준표와 보존 목록 (읽기 전용)

- **변경 파일**: 없음(결과는 impl 보고서에 적는다)
- **어투 기준표** — 메일에서 읽은 특징을 문서용으로 옮긴다. 메일 원문은 적지 않는다.

  | 항목 | 문서에 적용하는 방식 |
  |---|---|
  | 끝맺음 | 「~합니다 / ~입니다 / ~하도록 되어 있습니다」. 해요체는 쓰지 않는다 |
  | 판단 | 단정 대신 「~것으로 보입니다 / ~하는 것이 좋습니다 / ~하시면 됩니다」. 규칙(반드시 지키는 것)은 그대로 단정한다 |
  | 구성 | 섹션마다 목적 한 줄 → 항목 → 「추가로 ~」 → 다음에 볼 곳 안내 |
  | 제목 | 명사구 한 줄. 단 기존 제목 텍스트는 바꾸지 않는다(아래 보존 목록) |
  | 문장 | 한 문장에 사실 하나. 이유는 「~가 있어 ~합니다」로 앞에 붙인다 |
  | 연결어 | 「해당 ~ · 현재 · 또한 · 대신 · 추가로 · 우선」 |
  | 강조 | 산문의 줄표(—) · 「」 · 굵게를 줄인다. 굵게는 경고성 자리만 남기고 그 목록을 보고서에 적는다 |
  | 넣지 않는 것 | 인사 · 서명 · 「감사합니다」 |
  | 커밋 메시지 | 접두(`Release {버전}:` · `Docs:`)는 스킬 형식 그대로 두고, 요약과 본문을 「~했습니다 / ~수정했습니다」로 쓴다. 본문 항목도 한 줄에 사실 하나 |
- **보존 목록** — 다시 쓰기가 바꾸면 안 되는 것을 파일마다 뽑아 둔다(T04가 전후를 대조한다).
  - 코드 블록 · mermaid 블록(바이트 그대로)
  - 백틱 토큰의 다중집합 · 링크 대상의 집합 · 숫자 토큰의 다중집합 · 제목 줄 텍스트
  - 하니스가 무는 자리 — `B1`(README · `getting-started.md`의 커맨드 수 선언) · `C3`(`concepts.md`의 명단 줄) · `C4`(README stable 명단) · `F2`(README 전파 토큰) ·
    `tests/site-includes`가 README에서 읽는 자리. impl은 이 목록을 러너에서 다시 확인하고, 빠진 자리를 찾으면 보존 목록에 더한다.
- **변환 예시 한 쌍**을 보고서에 둔다(사이트 홈의 한 문단 — 전후).

### M80-T04: 검증 (deps: M80-T02, M80-T03)

- **변경 파일**: 없음(필요하면 T02 · T03 파일의 보정)
- **보존 대조** — 네 파일마다 수정 전(HEAD)과 수정 후에서 T01 보존 목록의 항목을 뽑아 비교한다. 차이가 있으면 항목별로 처분(되돌림 · 의도한 변경과 사유)을 적는다.
- **어투 계측** — 네 파일의 산문(코드 블록 · 표 밖)에서 줄표(—) · 「」 · 굵게(`**`) 개수를 전후로 세어 보고서에 적는다. 남긴 굵게는 자리와 사유를 적는다.
- **하니스** — `tests/discover`를 포함한 하니스 일곱 종을 두 PowerShell 축에서 돌리고, sh · dash는 이 사이클이 읽히는 파트(`B` · `C` · `F` · `G`)를 부분 실행한다. sh 전수는 규약 `measure-axis:`대로 CI가 판정한다.
- **사이트 빌드** — `mkdocs build -f site/mkdocs.yml --strict`가 정상 종료하고, 빌드 산출물의 제외 용어 스캔이 0건이다(같은 형태의 양성 통제 포함).
- **자료 누출 검사** — 메일 자료의 고유어(사람 이름 · 회사명 · IP 형태)로 만든 패턴 목록을 **저장소 밖**(스크래치패드)에 두고 저장소 전체를 훑어 0건임을 보인다. 보고서에는 패턴 개수와 검색 범위만 적고 패턴 자체는 적지 않는다.
