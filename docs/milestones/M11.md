# M11 — 도그푸딩 라운드: 누적 실증 부채 상환

## 목표

이 마일스톤이 끝나면 회고가 누적 추적해 온 **도그푸딩 부채**가 상환된다 — GitHub Pages
사이트가 실제 게시되어 렌더(Mermaid·검색·다크모드·인클루드)가 확인되고, `tide-guard.ps1`의
한국어 차단 메시지가 PowerShell에서 깨짐 없이 출력됨이 실증되며, M9 병렬 디스패치의
**폴백 경로(겹침→순차, 서브에이전트 실패→재시도/중단)** 가 통제된 픽스처로 확인된다.
함께 M10 권장1(릴리즈 빌드 검증의 규약↔실행 간극)이 release 스킬 배선으로 닫힌다.

## 배경

v0.11.0 회고(`docs/reports/retro.md`)의 결론: "신규 기능·저비용 후속은 모두 소진됐고
**남은 백로그는 사실상 도그푸딩 부채**(배포·환경 의존 실증). 코드로 안 되는 수동·배포
부채는 사이클 산출물에 안 섞여 계속 미뤄진다 — Pages 소스 전환은 **4사이클째 미상환**."
회고는 이를 "의식적으로 한 묶음(도그푸딩 라운드)으로 처리하지 않으면 영구 미상환 위험"
이라며 다음 1순위로 지목했다. 사용자도 이 묶음을 마일스톤 주제로 지정했다.

이 라운드는 **검증 위주**다 — 산출물의 상당수는 코드 변경이 아니라 **완료보고서에 남는
실증 기록**이며, 검증 중 결함이 나오면 그 자리에서 수정한다. T01은 **사용자의 1회 수동
조작(저장소 Settings → Pages → Source = GitHub Actions)** 에 의존한다.

## 태스크 목록

- M11-T01: GitHub Pages 게시 + 사이트 렌더 실증 (사용자 수동 전환 의존)
- M11-T02: `tide-guard.ps1` 한국어 출력 실증 (PowerShell 직접 실행)
- M11-T03: 병렬 폴백/부분 실패 경로 실증 (통제 픽스처)
- M11-T04: release 프리플라이트에 빌드 출력 검증 배선 + 문서 일관성

> T02·T03·T04는 상호 무의존 + 변경 파일 비중첩(검증 기록 / `skills/release/SKILL.md`) →
> 같은 레벨로 병렬 디스패치 가능. T01은 외부(사용자·네트워크) 의존이라 별도로 다룬다.

## 태스크 상세

### M11-T01: GitHub Pages 게시 + 사이트 렌더 실증 (사용자 수동 전환 의존)

- **변경 파일**: (없음 — 검증 기록. 발견 결함이 `mkdocs.yml`/워크플로우 수정을 부르면 그때 명시)
- **전제(코드 불가, 사용자 1회 조작)**: 저장소 **Settings → Pages → Build and deployment
  → Source를 "GitHub Actions"** 로 전환. 이게 안 돼 있으면 `deploy-pages.yml`이 게시하지
  못한다 — impl은 이 상태를 감지하면 **사용자에게 전환을 요청하고, 전환 전까지 T01을
  "대기"로 기록**한다(중단이 아니라 보류 — 다른 태스크는 진행).
- **검증(전환 후)**: ① Actions에서 `deploy-pages` 워크플로우가 성공했는지(`gh run list`
  또는 사용자 확인), ② 게시 URL(대략 `https://Jongh.github.io/tide/`)을 WebFetch로 받아
  6개 페이지·내부 링크가 살아있는지, ③ conventions/changelog가 단일 원본 인클루드로 정상
  렌더되는지, ④ Mermaid 다이어그램·검색·다크모드는 클라이언트 동작이라 정적 fetch로는
  한계가 있음을 명시하고 가능한 범위(HTML/스크립트 포함 여부)만 확인.
- **불확실성/대체 경로**: 네트워크·권한·실제 URL이 가정과 다를 수 있다. 받은 URL이 404면
  `site_url`(`site/mkdocs.yml`) 실값 조정이 후속. 확인 가능한 사실만 기록하고 미확인은
  솔직히 남긴다.

### M11-T02: `tide-guard.ps1` 한국어 출력 실증 (PowerShell 직접 실행)

- **변경 파일**: (없음 — 검증 기록. 깨짐 발견 시 `hooks/tide-guard.ps1`)
- M8에서 BOM 포함 UTF-8로 저장했으나 PowerShell 런타임 출력은 미실증이었다. **PowerShell로
  `hooks/tide-guard.ps1`을 직접 실행**해 검증한다:
  - 임시로 `.tide/phase`를 `impl` 등으로 둔 환경(또는 `CLAUDE_PROJECT_DIR`로 격리)에서, git
    commit/tag/push 류 명령을 담은 JSON을 stdin으로 넣어 ps1을 실행 → **한국어 차단 메시지가
    깨짐 없이 출력되고 exit 2** 인지, 비-git은 exit 0인지 확인.
  - 활성 가드(설치 캐시)의 자기 차단을 피하려면 T02 검증 명령 구성 시 트리거 토큰을 분리
    (M8·M9에서 쓴 방식)하고, 저장소 원본 `hooks/tide-guard.ps1`을 직접 호출한다.
  - 깨지면(인코딩·BOM 문제) `hooks/tide-guard.ps1`을 수정하고 재검증한다.

### M11-T03: 병렬 폴백/부분 실패 경로 실증 (통제 픽스처)

- **변경 파일**: (없음 — 검증 기록. 메커니즘 서술 보강이 필요하면 `skills/impl/SKILL.md`)
- M10은 "비중첩→폴백 없는 병렬" 정상 경로만 실증했다. 폴백 경로를 통제된 방식으로 확인한다:
  - **겹침 폴백**: 같은 파일을 변경 대상으로 하는 두 태스크 시나리오를 구성해, impl 규약상
    **겹치는 태스크가 순차로 내려가는지** 추론·실증(실제 동시 편집 충돌을 만들지 않고,
    예상 변경 파일 겹침 감지 → 부분 순차 폴백이 규약대로 동작함을 보인다).
  - **서브에이전트 부분 실패**: 한 병렬 태스크가 실패할 때 다른 결과 보존 + 실패분 메인
    재시도 → 재시도도 실패면 중단·보고가 규약대로인지 확인(통제된 실패 주입 또는 시나리오
    워크스루).
  - 실증은 "안전하게 재현 가능한 범위"로 한다 — 실제 저장소를 손상시키는 충돌은 만들지
    않고, 폴백 판단 로직이 규약과 일치함을 보이는 것이 목표. 메커니즘 서술에 공백이
    발견되면 `skills/impl/SKILL.md`를 보강한다.

### M11-T04: release 프리플라이트에 빌드 출력 검증 배선 + 문서 일관성

- **변경 파일**: `skills/release/SKILL.md` (검증 결과에 따라 `README.md`/`docs/project-context.md` 한 줄)
- M10 권장1: 릴리즈 빌드 출력 검증이 `conventions`엔 규약화됐으나 `release` 스킬 프리플라이트
  엔 미배선이다. `skills/release/SKILL.md`의 프리플라이트(또는 그 직전 단계)에 **"사이트
  빌드 산출물 기준 제외 용어 0건 확인"** 한 줄을 추가해 규약↔실행을 일치시킨다.
  - 사이트가 있는 프로젝트에 한함(조건부 — `site/mkdocs.yml` 등이 있을 때). 일반 tide 사용
    프로젝트(사이트 없음)에는 영향 없도록 조건을 명시한다.
  - 기존 프리플라이트 3종(판정·테스트·워킹트리)·운영 주의 절은 보존하고 항목만 덧붙인다.
  - 필요하면 `docs/project-context.md`·`README.md`에 한 줄 반영(불필요하면 미수정, 이유 기록).

## 완료 기준

1. **Pages**: 사용자 Source 전환 후 `deploy-pages` 성공 + 게시 URL에서 6페이지·내부 링크·
   단일 원본 인클루드가 확인된다. 전환 미완료면 "대기"로 명확히 기록되고 사이클은 그 사유와
   함께 나머지를 진행한다(T01만 보류).
2. **ps1**: PowerShell에서 `hooks/tide-guard.ps1`이 한국어 차단 메시지를 깨짐 없이 출력하고
   exit 2(비-git exit 0)임이 실증된다. 깨졌으면 수정 후 재검증.
3. **병렬 폴백**: 겹침→부분 순차 폴백, 서브에이전트 부분 실패→보존+재시도/중단이 규약대로
   동작함이 통제된 방식으로 확인된다(메커니즘 공백 발견 시 보강).
4. **release 배선**: `skills/release/SKILL.md` 프리플라이트에 사이트 빌드 출력 제외 용어
   0건 확인이 (사이트 있는 프로젝트 한정으로) 추가되고, conventions 규약과 일치한다.
5. 매니페스트 무수정, `mkdocs build --strict` 통과(사이트 변경이 있었다면), 완료보고서에
   각 항목의 실증/대기/수정 상태가 정직하게 기록된다.
