# M84 — release 프리플라이트를 이름으로 선언하고 스킬이 이름으로 가리키며, 집합 판정의 창을 안 · 앞 · 뒤로 통제한다

## 목표

`docs/conventions.md` "전제조건 · 프리플라이트" 절의 release 시작 전 검사가 번호 산문(「① 판정 ② 테스트 ③ 워킹트리 확인」)이 아니라 이름 선언과 이름별 정의 항목으로 선다.
release 스킬의 프리플라이트 단계 머리와 재서술처(카탈로그 · cycle 스킬 · 다른 절 · 소개 문서)는 번호가 아니라 선언된 이름이나 선언 포인터로 가리킨다. 그래서 프리플라이트를 하나 더하거나 지우거나 이름을 바꾸는 편집이 선언 · 정의 · 스킬 단계 머리 사이에서 어긋나면 하니스가 붉다.
집합을 대조하는 판정은 이번부터 **창의 안 · 앞 · 뒤**를 함께 통제한다(`rf-101`). 장기 이월 정리에서 곁들이기로 한 작은 정리 다섯도 함께 닫는다.

## 배경

- **회고 `rf-100`(1순위)** — `rf-96`의 나머지 무리다. M76 재고 조사 표 B 행이 「release 시작 전 검사의 유일한 원본이 표 칸의 산문이다. 선언화 후보: `preflight-gates:`」로 적은 자리다. M82 · M83이 같은 형태로 두 무리를 닫았다.
- **지금 문면이 서로 어긋나 있다** — 규약 표 · `docs/commands.md` · `README.md` · `site/docs/getting-started.md`는 「① 판정 ② 테스트 ③ 워킹트리 확인」이다. `site/docs/concepts.md`는 「③ 사이트 빌드 출력 제외 용어 0건」이다(M81 리뷰가 고쳤다).
  release 스킬의 실제 프리플라이트는 다섯이다 — 판정(막음) · 테스트(막음) · 워킹트리(확인 — `continuous`면 막지 않음) · 사이트 산출물 스캔(막음) · 커버리지(advisory). 규약과 스킬의 「①②③은 불변」은 어느 셋인지 말하지 않는다. 번호가 뜻을 들지 못하는 자리다.
- **M83의 교훈(`rf-101`)** — 덮음 판정이 「무엇을 세는가」는 다 통제했는데 「어디서 세는가」(창의 넓이)가 넓어 라운드 0이 반환됐다. 라운드 1 리뷰는 `dc_sec` 창의 **끝**(다음 `## ` 뒤)을 시험하는 통제가 없다는 것도 경계로 남겼다. 이번 판정은 창의 안 · 앞 · 뒤 통제를 처음부터 둔다.
- **`rf-97` · `rf-98` · `rf-88`** — 수는 손 상수가 아니라 집합 크기로 묻는다. 지울 산문을 읽던 판정을 먼저 잰다. 입력 변환마다 통제를 둔다.
- **곁들이는 작은 정리 다섯**(2026-10-29 장기 이월 정리 — 사용자 결정)
  - `rf-07` — `CLAUDE.md`의 CHANGELOG 마커 항목이 사실보다 좁다(같은 토큰이 몇 자리에 있는지 · 실제 삽입 앵커).
  - `rf-28` — 하니스 README 파트 제목의 「N 케이스」를 아무도 세지 않는다(M83도 손으로 고쳤다).
  - `rf-40` — 규약 "릴리즈 빌드 출력 검증" 절의 「3분담이 2분담으로」가 넷 분담 표와 어긋난다.
  - `rf-44` — 리뷰 보고서 계측 줄의 값이 비었는가를 어느 케이스도 보지 않는다.
  - `rf-48` — `.tide/NEXT-SESSION.md`가 M70 시점에 멈춘 채 추적된다.

### M84-T02: 규약에 프리플라이트 이름 선언과 정의 항목을 세운다 (deps: M84-T01)

- **변경 파일**: `docs/conventions.md` · `docs/conventions-release.md`
- "전제조건 · 프리플라이트" 절에 선언 한 줄 `release-preflights:`를 둔다. 이름은 ASCII 소문자 · 하이픈이고 접두가 `pf-`다 — 예: `pf-verdict` `pf-tests` `pf-worktree` `pf-site-scan` `pf-coverage`. **선언의 이름 순서가 스킬이 프리플라이트를 도는 순서다.**
- 이름마다 정의 항목 하나(``- **`이름`** — …``, 선언 줄과 같은 깊이)를 둔다. 정의는 **무엇을 묻는가와 실패 시 처분(막음 · 확인 · advisory)** 한 문장이고, 상세는 이미 있는 단일 원본 절을 가리킨다("debug 세션" · "릴리즈 커버리지 체크" · "릴리즈 빌드 출력 검증" · 자율 진행의 워킹트리 확인). 상세를 옮겨 적지 않는다.
- 표 release 행의 「① 판정 근거 보고서(review 또는 debug)의 판정 "가능" ② 테스트 통과 ③ 워킹트리 확인」을 선언 포인터로 바꾼다. 표 아래 「release 1번 검사」도 이름으로 바꾼다.
- 같은 파일의 「프리플라이트 ①②③ 게이트」 · 「프리플라이트 게이트 ①②③의 집합·순서·판정 로직은 불변」 · 「프리플라이트 게이트 ①(판정 "가능")」과 `docs/conventions-release.md`의 「프리플라이트 게이트 ①②③」을 이름이나 선언 포인터로 바꾼다. 그 문장이 가리키던 집합이 막는 셋인지 다섯 전부인지를 문맥에서 정하고, 정한 근거를 보고서에 적는다.
- 「기계가 묻는 것」 · 「묻지 않는 것」 문단을 둔다. 묻는 것은 T05가 실제로 세운 판정만 적는다(고지가 집행보다 넓으면 차단 부류 — M78 · M79 · M82 · M83). 묻지 않는 것에는 적어도 「정의 문장의 처분이 스킬 절차와 같은가」 · 「스킬이 그 순서로 실제로 도는가(프롬프트 절차)」 · 「소개 문서의 서술이 선언과 같은가」를 둔다.
- 산문 안의 접두어는 백틱 없이 쓴다(M83 — 백틱 접두어는 잔재 판정이 이름으로 읽는다).
- 재서술처 훑기: 패턴 `프리플라이트 ?(게이트 )?[①②③④⑤]|프리플라이트 [1-5]|① (review |판정)|② 테스트|③ (워킹트리|사이트)` · 대상 저장소 전체(`docs/reports/` · `docs/milestones/` · `CHANGELOG.md` · `docs/reports/retro*.md` 제외 — 이력) · 대조 항목 「release 프리플라이트를 번호로 가리키는 자리」 · 루트 저장소. 결과와 남긴 히트의 사유(다른 열거 — 예: "릴리즈 빌드 출력 검증" 절의 분담 ①~④)를 보고서에 적는다.

### M84-T05: 두 러너에 판정과 창 통제를 더한다 (deps: M84-T02, M84-T03)

- **변경 파일**: `tests/discover/run.sh` · `tests/discover/run.ps1`
- 선언 읽기는 공용 헬퍼(`dn_names` · `dn_dup` · `dn_def_bad` · `dn_def_orphan` · `dn_def_order` · `Dn*`)를 `docs/conventions.md`와 함께 그대로 쓴다. 케이스는 release 스킬을 이미 읽는 파트(Part S)의 다음 번호부터 더한다.
- 본 검사:
  - 선언 줄 유일성 · 금지 구분자 · 추출 비지 않음 · 이름 유일성 · 이름마다 정의 항목 정확히 하나 · 고아 정의 없음 · 정의 순서 = 선언 순서.
  - **덮음** — release 스킬 **프리플라이트 창**(「프리플라이트 (」로 시작하는 줄부터 「프리플라이트 통과 후」로 시작하는 줄 앞까지 — 정확한 앵커는 T05가 스킬 문면에서 정하고 보고서에 적는다) 안 **번호 단계 머리의 첫 굵은 구획** 속 백틱 `pf-` 토큰 집합이 `release-preflights:`의 이름 집합과 같다. 수는 집합 크기로 묻고 손 상수를 두지 않는다.
  - **순서** — 같은 창의 단계 머리가 가리킨 이름의 차례가 선언 순서와 같다(프리플라이트는 단계 하나에 이름 하나이므로 줄 단위로 물을 수 있다. 그렇지 않은 꼴이면 T05가 경계로 적는다).
  - **잔재** — 규약 문서 집합(`docs/conventions*.md` 글롭) · release 스킬 · cycle 스킬 · 커맨드 카탈로그 안 백틱 `pf-` 토큰이 전부 선언된 이름이다.
- 변환 통제(`rf-88` · `control-reads-delta`) — 합성 사본에 먹여 반응을 차이로 묻는다: 정의 범위 · 이름 위치(선언에 이름을 더한 사본) · 백틱 토큰 추출 · 헬퍼 배선(규약 파일 인자).
- **창 통제(`rf-101`)** — 같은 꼴의 단계 머리를 ⑴ 창 **앞**(프리플라이트 시작 줄 앞)에 심으면 세지 않는다 ⑵ 창 **안**에 심으면 하나 는다 ⑶ 창 **뒤**(「프리플라이트 통과 후」 줄 뒤)에 심으면 세지 않는다 ⑷ 창 안 산문 줄 · 굵은 구획 뒤의 토큰은 세지 않는다.
- ps1 사본은 ASCII만 쓴다(한글 앵커는 코드포인트로).

## 완료 기준

1. `docs/conventions.md`에 `release-preflights:` 선언 줄이 하나 있고 이름마다 정의 항목이 정확히 하나다. 저장소(이력 제외)에서 release 프리플라이트를 번호로 가리키는 자리가 0이다 — 훑기의 패턴 · 대상 · 대조 항목 · 루트와 남긴 히트의 사유를 보고서에 적는다.
2. release 스킬 프리플라이트 창의 단계 머리가 가리킨 `pf-` 이름 집합과 차례가 선언과 같다. 프리플라이트의 수 · 순서 · 처분과 단계 본문의 동작 문장은 HEAD와 같다(`git diff`의 그 창 hunk가 단계 머리 문면 치환뿐임을 보고서에 적는다).
3. T01의 표가 대상 문장마다 「붉은 케이스」를 적고, 붉은 케이스가 있던 문장마다 그 판정의 대신이 되는 케이스가 보고서에 대응돼 있다.
4. 아래 교란이 두 러너에서 각각 붉다(되돌림 표 — 행마다 붉은 케이스): ⑴ 선언에서 이름 하나 지움 ⑵ 이름 복제 ⑶ 정의 항목 하나 지움 ⑷ 선언에 없는 정의 항목 더함 ⑸ 정의 첫 둘 맞바꿈 ⑹ 선언 끝에 이름 · 정의를 더하고 스킬은 그대로 둠 ⑺ 스킬 단계 머리에서 이름 하나를 지우고 창 안 다른 자리의 언급은 남김 ⑻ 스킬 단계 머리 두 개의 이름을 맞바꿈(순서) ⑼ 선언 · 정의의 이름 하나를 바꾸고 스킬 · 규약 산문에 옛 이름을 남김 ⑽ 선언 줄을 두 칸 더 들여씀 ⑾ 창 앞 · 뒤에 단계 머리를 심어도 붉지 않고, 판정의 창 앵커를 넓히는 러너 편집은 창 통제가 붉힌다(러너마다) ⑿ `dc_sec` 창이 다음 제목에서 끊기지 않는 러너 편집을 창 뒤 통제가 붉힌다(러너마다) ⒀ README 파트 제목 수 하나를 바꿈 ⒁ 리뷰 보고서 계측 줄 값 하나를 비움.
