# M18 — 오케스트레이션 3층: 교차 사이클 자동화(`/tide:fleet-cycle`, release 제외)

## 목표

이 마일스톤이 끝나면 **상위 폴더 단일 세션에서 발견된 자식 tide 레포들의 `milestone → impl →
review`를 의존성 순서로 교차 자동 실행하고, 마지막에 순서 있는 release 핸드오프를 받을 수 있다.**
새 커맨드 `/tide:fleet-cycle`이 fleet(발견·위상정렬·계약)을 재사용해 처리 순서(피의존 먼저)를 정하고,
각 자식 레포 루트에 앵커해 그 레포의 `/tide:cycle` 의미(milestone→impl→review)를 돌린 뒤, 레포별
사이클 결과와 **의존성 순서 release 계획**(어느 레포를 어느 순서로 `/tide:release`할지)을 집계해
제시한다. **release·cross-repo git은 절대 자동화하지 않는다** — 부수효과 분리 불변상 release는 끝까지
레포별 수동이고, 각 레포 impl/review의 git 금지는 tide-guard로 기계 강제된다. 계약(M17)을 인식해
upstream-behind 의존이 있는 레포는 release 핸드오프에서 "선결 필요"로 표기한다. 미선언/단일 레포는
현행과 동일(옵트인 가산). 커맨드 9종(기존)·1.0 계약 불변.

## 배경

`docs/conventions.md` "멀티 레포 오케스트레이션" 4계층 로드맵에서 1층(가시성, M14·M15)·2층(의존성
선언·위상정렬 M16, 계약 버전 M17)이 완성됐다. **3층 — 교차 사이클 자동화**가 다음이다: fleet은 지금
"읽기 전용 advisory"(보고·제안만)이고, 실제 사이클 실행은 사용자가 레포마다 수동으로 한다. MSA에서
레포가 여럿이면 "auth부터 milestone→review, 그다음 orders…"를 손으로 도는 게 반복 노동이다. 3층은
그 milestone→review 구간을 **의존성 순서로 자동 체이닝**해준다.

**불변 — release는 3층에서도 제외**: `/tide:cycle`이 release를 자동 체이닝에서 빼는 이유(git 작업을
하는 유일한 단계, 부수효과 분리)는 cross-repo에서 **더 강하게** 적용된다. 여러 레포를 자동으로
release하면 격리·되돌리기·순서 오류 위험이 크다. 따라서 fleet-cycle은 milestone→review까지만
자동화하고 release는 **순서 있는 핸드오프**로 사용자에게 넘긴다. tide-guard가 각 레포 phase≠release
에서 git을 막으므로, 자동화 중 어떤 레포에서도 commit/tag/push가 일어날 수 없다(기계적 보장).

이 변경은 fleet(읽기 전용)과 달리 **행위**(사이클 실행)이므로 별도 커맨드가 필요하다 —
`/tide:fleet-cycle`(10번째, 가산). 1.0 안정성 절이 새 커맨드를 minor 가산으로 허용한다.

## 정규 spec (이 마일스톤의 단일 기준 — T01·T02·T03이 모두 이를 인용)

### `/tide:fleet-cycle` — 교차 사이클 자동화

- **대상·발견·순서**: 대상 부모(기본=세션 cwd, 선택 인자로 경로)의 자식 tide 레포를 fleet 규약으로
  발견(직속 1단계·git·tide 산출물·숨김 무시)하고, `.tide/deps` 위상정렬(M16)로 **처리 순서**(피의존
  먼저)를 정한다. 순환이면 보고+상태 기반 순서로 폴백. 미선언 레포는 독립 노드.
- **레포별 실행(앵커)**: 처리 순서대로 각 레포를 **그 레포 루트에 앵커**(M13 cwd 규율)해 `/tide:cycle`
  의미를 실행한다 — 즉 그 레포의 보고서 상태로 시작점을 정해(impl 보고서 없음→impl부터, 있고 review
  없음→review부터, 둘 다 있음→새 milestone) `milestone → impl → review`를 잇는다. 산출물·`.tide/phase`·
  테스트·서브에이전트는 그 레포 루트 기준. **release는 실행하지 않는다**(아래 불변).
- **release 제외(불변)**: fleet-cycle은 **milestone→review까지만** 자동화한다. 어떤 레포에서도
  `release`·git commit/tag/push·cross-repo git을 자동 실행하지 않는다. 각 레포 impl/review는 phase≠release
  라 tide-guard가 git을 차단한다(기계 강제). release는 아래 "핸드오프"로 사용자에게 넘긴다.
- **계약 인식(M17)**: 레포 X가 의존 Y에 `>= 버전` 계약을 두고 Y가 **upstream-behind**면, X의 사이클은
  돌리되 release 핸드오프에서 X를 **"contract-blocked: Y를 먼저 release/upgrade 필요"**로 표기한다
  (X를 release-ready로 단정하지 않음).
- **실패·중단 처리**: 한 레포의 사이클이 중단되면(전제조건 미충족·테스트 실패·review 판정 "불가")
  그 레포를 **"중단"으로 기록**하고, 위상정렬상 **그 레포에 의존하는 downstream 레포는 건너뛴다**
  (upstream 미완 → downstream 처리 보류, 사유 기록). 그와 무관한 독립 레포는 계속 진행한다(전체 중단이
  아니라 부분 진행 + 명확한 보고). 각 레포 사이클 자체의 중단 처리는 `/tide:cycle` 규칙을 그대로 따른다.
- **출력(집계)**: ① 처리 순서 표 — 레포명 | 시작 단계 | 도달 단계 | review 판정/추천 버전 | 비고
  (중단·skip·contract-blocked). ② **의존성 순서 release 핸드오프** — review "가능"인 레포를 위상정렬
  순서로 `1) /tide:release vX.Y.Z (repo)` 나열하되, contract-blocked·중단·downstream-skip은 사유와 함께
  보류로 표기. release는 사용자 몫임을 명시.
- **부수효과 분리 불변 재확인**: fleet-cycle은 milestone→review만 자동화하고, release·cross-repo git은
  자동화하지 않는다. 순서·핸드오프는 **제안**이며 release 시점·실행은 사용자가 판단한다.

### 커맨드 등록 (10번째, 가산)

- `/tide:fleet-cycle`은 `/tide:cycle`처럼 **git 금지**(milestone→review만, release 제외)다. "단계별 금지
  행위" 표에 `fleet-cycle | git commit/tag/push (release·cross-repo git 비자동화) | 프롬프트 + hook(git)`
  행을 추가한다. 사이클 다이어그램에 멀티 레포 자동화 보조로 표기(`/tide:fleet`은 읽기 전용 개요,
  `/tide:fleet-cycle`은 그 순서대로 milestone→review 자동 실행).
- "1.0 안정성" 절: 기존 커맨드의 호출명·역할은 불변, `/tide:fleet-cycle`을 **v1.5.0부터 가산** 커맨드로
  명기(읽기 전용 fleet과 별개로 행위 커맨드, release 제외). 8종 안정 claim·9번째 fleet 서술은 유지.
