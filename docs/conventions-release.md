# tide 릴리즈 게시 규약 (conventions-release)

`gh` CLI로 릴리즈를 게시하는 규약이다 — 규약 본체 `docs/conventions.md`에서 분리한 **조각**이며,
규약 문서 집합의 일부다.
조각과 본체의 관계·인용 규칙은 `docs/conventions.md`의 "상호참조 무결성" 절이 정한다.

## 릴리즈 게시 (gh)

`gh` CLI가 있는 레포에서 `/tide:release`가 push 위에 **GitHub 릴리즈를 생성**하거나, 기본
브랜치 직접 push 대신 **릴리즈 브랜치 + PR을 생성**하도록 게시 모드를 고르는 규약의 **단일
원본**이다 — release 스킬은 절차에서 이 절을 **참조**한다(스킬은 절차, 규약은 conventions —
"릴리즈 위생"의 운영 주의↔규약 분담과 동형). **옵트인·하위 호환**: `gh` 부재 환경의 동작은
현행(commit→tag→push)과 **바이트 동일**하고, 게시 분기는 `gh` 가용 + 검증 통과일 때만 더해진다.

### 검증 게이트

게시 분기 진입 전 다음을 **순서대로** 검증하고, **하나라도 불충족이면 게시를 시도하지 않는다**.

1. **`git` 가용**: `git --version`이 동작한다.
2. **`gh` 가용·서브커맨드**: `command -v gh`(POSIX) / `Get-Command gh`(PowerShell)로 존재를
   확인하고 `gh --version`이 동작하며, 필요한 서브커맨드 `gh release`·`gh pr`가 존재한다.
3. **인증**: `gh auth status`가 인증됨을 보고한다.
4. **대상 원격이 gh가 다룰 수 있는 GitHub 레포인지**: `gh repo view` 성공, 또는 대상 원격 URL의
   호스트가 gh 인증 호스트와 일치한다. 실패(원격 미설정·비-GitHub 호스트(GitLab 등)·해당 호스트
   미인증)는 **"gh로 게시 불가"** 상태로 본다(아래 "원격 불가 처리").

검증은 부수효과(commit/push) **발생 전**, 그리고 **명시 모드(`pr`/`release`)에선 버전 범프·
CHANGELOG 편집 전**에 둔다 — 검증 실패 시 commit/push는 물론 **작업 트리도 더럽히지 않도록**
(특히 `pr` 모드의 분기 전 점검)이 설계의 요점이다. release 스킬은 이 순서를 절차로 고정한다
(게시 모드 해석·검증 → 버전 범프 → CHANGELOG → 게시 분기).

### 모드 선택 (우선순위)

`/tide:release v{버전} [모드]`의 모드 토큰은 `release`(GitHub 릴리즈 생성) / `pr`(PR 생성)이다.
다음 **우선순위**로 모드를 정한다.

1. **명시 인자** (`pr`/`release`) — 1순위.
2. **`.tide/release-mode` 저장값** — 인자가 없으면 2순위.
3. **대화형 질문** — 인자·저장값이 둘 다 없고 **검증 통과(게시 가능)**면 3순위로
   `release`/`pr`/"이번엔 그냥 push" 중 택1을 묻는다.

`gh` 부재 또는 검증 실패면 **push-only로 진행하고 모드 질문을 하지 않는다**(조용히 떨어지는
것이 아니라 — 대화형 후보였던 경우엔 "원격 불가 처리"대로 불가 사유를 한 줄 알린다).

### 선호도 기억 (`.tide/release-mode`)

- 인자·저장값 없이 **첫 대화형 선택**을 한 경우, 선택 **직후** "이후에도 같은 모드를 쓸지"를
  묻고, 예이면 `.tide/release-mode`에 **모드 한 줄**(`release` 또는 `pr`)을 기록한다 — 다음
  release부터는 인자 없이도 그 모드를 재사용해 **질문을 생략**한다. (명시 인자로 실행하면 저장값을
  그 인자로 갱신할지 같은 방식으로 물을 수 있다 — 선택.)
- **커밋 대상**: `.tide/release-mode`는 `.tide/deps`와 **동급의 커밋되는 레포 게시 규약**이다 —
  `.gitignore` 범위는 `.tide/`가 아니라 **`.tide/phase`만**이므로(`docs/conventions.md`의 "상태 파일 (.tide/phase)" 절) `release-mode`는
  추적된다(deps처럼 커밋, phase만 무시).

### `release` 모드

현행 흐름(commit→tag→push)을 **그대로** 수행한 **뒤** `gh release create {버전}`으로 릴리즈 객체를
추가 생성한다 — **가산**(기존 절차 위에 1단계 추가, 기존 절차 무변경). 릴리즈 노트는 `CHANGELOG.md`의
해당 버전 발췌이며 **제외 용어 규약을 준수**한다(`docs/conventions.md`의 "버전 · CHANGELOG" 절 — 메타 용어 누수 방지).

- **태그 중복 방지**: 로컬 흐름이 이미 태그를 push했으므로(현행 4단계), `gh release create`가 같은
  태그를 다시 만들지 않도록 **이미 push된 그 태그를 참조**한다(태그 신규 생성 금지 — 중복 회피).

### `pr` 모드

기본 브랜치에 **직접 push하지 않는다**. `pr` 모드는 **재실행 가능한 상태 인지** 흐름이다 — 같은
`/tide:release v{버전} pr`를 PR 생성 전과 머지 후에 각각 실행해 한 모드로 PR을 열고 마무리까지
끝낸다. 검증 게이트 통과 후, **버전 범프·CHANGELOG 편집 전에** 릴리즈 PR 상태를 `gh`로 조회해
분기한다(분기 결정을 부수효과 전에 둬, finalize가 이미 머지된 파일을 재편집하지 않게 한다).

- **PR 식별**: 브랜치 `release/v{버전}`(또는 제목 `Release v{버전}`)의 PR을 `gh pr view`/`gh pr list`로
  조회한다. 버전은 인자로 받는다(머지 후 마무리는 `/tide:release v{버전} pr`로 명시 호출).

PR 상태별 분기:

- **없음 → 생성**: **릴리즈 브랜치**(예: `release/v{버전}`)에 버전 범프·CHANGELOG를 commit → 브랜치
  push → `gh pr create`(제목 `Release v{버전}: …`, 본문 = CHANGELOG 발췌, 제외 용어 규약 준수)로 PR을
  연다. **태그·GitHub 릴리즈는 PR 머지 후로 미룬다**(PR 머지는 사람 몫) — release는 **"PR 열림"까지**
  하고 PR URL을 보고한 뒤 "**머지 후 같은 명령을 다시 실행하면 태그·릴리즈로 마무리**"를 안내한다.
- **open → 대기**: 부수효과 없이(태그·릴리즈·push 없음) PR URL과 "머지 후 재실행" 안내만 한다.
- **closed(미머지) → 중단**: PR이 머지 없이 닫혔음을 보고하고 중단한다(임의 재생성·태그 금지).
- **merged → 마무리(finalize)**: ① 기본 브랜치를 원격 머지 결과로 최신화(`git fetch` 후 기본 브랜치
  checkout·`git pull`/fast-forward), ② **버전 sanity** — 머지된 기본 브랜치의 버전 파일이 `v{버전}`과
  일치하는지 확인(불일치면 태그 없이 중단·보고 — 엉뚱한 머지에 태그 방지), ③ 태그 `v{버전}`을 머지된
  tip에 달고 `git push {remote} v{버전}`, ④ `gh release create v{버전}`(노트 = CHANGELOG 발췌, 제외 용어
  규약 준수). **finalize는 버전 범프·CHANGELOG를 건너뛴다**(머지로 이미 기본 브랜치에 반영됨 — 재편집 금지),
  ⑤ **릴리즈 브랜치 정리** — 다 쓴 `release/v{버전}` 브랜치(로컬·원격)를 거둔다(아래 정리 불변 참조).

멱등·안전(외부 대면이라 불변):

- **미머지 PR에 태그 금지** — `gh`로 merged를 확인한 뒤에만 태그를 단다.
- **중복 생성 회피(독립 멱등)** — 태그 `v{버전}`과 릴리즈를 **각각 독립으로** 선확인(`git tag`·원격 태그
  / `gh release view`)해 **이미 있는 것은 건너뛰고 없는 것만 생성**한다. 둘 다 있으면 보고만 하고(M24식
  수동 핸드오프로 이미 마친 경우에도 안전), **한쪽만 있으면 나머지를 마저 만든다**(부분 실패 복구 — 예:
  태그는 push됐으나 `gh release create`가 실패한 뒤 재실행). 어느 쪽도 새로 만들 때 중복을 일으키지 않는다.
- **릴리즈 브랜치 충돌**(생성 경로) — 릴리즈 브랜치가 이미 있으면 같은 버전의 진행 중 PR이면 **그 브랜치를
  재사용**하고, 충돌(서로 다른 내용·다른 PR)이면 **이름 충돌을 보고하고 중단**한다(임의 덮어쓰기 금지).
- **릴리즈 브랜치 정리(⑤ — finalize 한정)** — ⑤는 ②~④가 성공해 finalize가 실제로 완료된 경우에만 수행한다.
  정리는 태그/릴리즈 생성과 **독립 멱등**이다 — 태그·릴리즈가 이미 존재해 "보고만" 한 멱등 경로에서도 브랜치가
  남아 있으면 정리 대상에 포함한다. **현재 브랜치 안전**: 정리 전 이미 기본 브랜치(①에서 checkout)에 있어야
  한다 — 체크아웃된 `release/v{버전}`은 삭제할 수 없으므로 기본 브랜치 체크아웃을 선행 보장한다. **로컬**:
  로컬 `release/v{버전}`이 존재하면 삭제한다 — `git branch -d`(머지 확인 삭제)를 먼저 시도하고, 머지 추적이
  어긋나 `-d`가 거부되면 **머지를 이미 `gh`로 확인했다는 전제**에서만 `-D`로 강제 삭제한다(미머지 강제삭제
  금지 — 머지 미확인이면 정리하지 말고 남긴다). 브랜치가 없으면 조용히 건너뛴다(멱등). **원격**: 원격에 같은
  브랜치가 있으면 `git push {remote} --delete release/v{버전}`로 지운다 — 이미 없으면(예: GitHub PR
  auto-delete) 건너뛴다("없음"을 오류로 보지 않음·멱등). **실패 비차단**: 브랜치 정리 실패(권한·보호 브랜치
  등)는 **릴리즈 성공을 무르지 않는다** — 태그·릴리즈는 이미 완료됐으므로 정리 실패는 경고로 보고하고 수동
  삭제를 안내한다. 이 정리는 `pr` finalize에 **한정**된다 — `release` 모드·push-only·생성/대기/중단 분기,
  tide-guard 계약은 불변.

이 상태 인지 확장은 `pr` 모드에 한정된다 — `release` 모드·push-only·`gh` 부재 경로는 불변이다.

### 원격 불가 처리 (검증 ④ 실패)

- **모드를 명시(인자/저장값)**했으면 — **게시 없이 중단하고 사유를 보고**한다(**조용한 강등 금지** —
  사용자가 게시를 명시했으므로). 이때 그 시점까지 commit/tag/push가 일어났는지 명확히 보고한다.
- **대화형**(인자·저장값 없음)이면 — gh 모드를 **아예 제시하지 않고** push-only로 진행하며, **불가
  사유를 한 줄** 알린다.

### 명시 의도 비폴백

모드를 명시했는데 `gh` 부재/미인증/검증 실패면 **중단하고 사유 보고**(조용한 강등 금지). 모드
미지정이면 `gh`를 아예 건드리지 않는다(기본 불변).

### 부수효과 분리·가드 불변

- 두 모드 모두 `.tide/phase=release`에서만 실행한다(release가 유일한 게시 단계라는 불변 유지).
- **tide-guard는 확장하지 않는다** — 가드는 `git commit`/`git tag`/`git push` 토큰만 차단하는
  **2.0 stable 계약**(`docs/conventions.md`의 "tide-guard hook"·"2.0 안정성" 절)이고, `gh`는 **별도 바이너리**다. tide
  레포 밖의 정상 `gh` 사용까지 막을 위험이 있어 `gh`를 가드로 게이트하지 **않는다**. "게시는
  release에서만"이라는 불변은 **release 스킬 절차**가 `gh` 호출을 phase=release 안에서만 실행해
  보존한다(가드 계약 무변경).
