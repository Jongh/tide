# tide 릴리즈 게시 규약 (conventions-release)

`gh` CLI로 릴리즈를 게시하는 규약이다 — 규약 본체 `docs/conventions.md`에서 분리한 **조각**이며,
규약 문서 집합의 일부다.
조각과 본체의 관계·인용 규칙은 `docs/conventions.md`의 "상호참조 무결성" 절이 정한다.

## 릴리즈 게시 (gh)

`gh` CLI가 있는 레포에서 `/tide:release`가 push 위에 **GitHub 릴리즈를 생성**하거나, 기본
브랜치 직접 push 대신 **릴리즈 브랜치 + PR을 생성**하도록 게시 모드를 고르는 규약의 **단일
원본**이다 — release 스킬은 절차에서 이 절을 **참조**한다(스킬은 절차, 규약은 conventions —
"릴리즈 위생"의 운영 주의↔규약 분담과 동형). **옵트인·하위 호환**: `gh` 부재 환경의 동작은
현행(commit→tag→push)과 **바이트 동일**하고, 게시 분기는 `gh` 가용 + 검증 통과일 때만 더해진다.

**이 절은 축을 둘 다룬다** — **게시 축**(`gh`로 릴리즈·PR을 만드는가)과 **push 축**(그 앞의
`git push`가 애초에 가능한가). 둘은 별개이고, 아래 "검증 게이트"가 각각을 따로 잰다. 축을 가른
근거는 그 절의 `push-availability` 항목이 적는다.

### 검증 게이트

게시 분기 진입 전 다음을 **순서대로** 검증하고, **하나라도 불충족이면 게시를 시도하지 않는다**.

1. **`git` 가용**: `git --version`이 동작한다.
2. **`gh` 가용·서브커맨드**: `command -v gh`(POSIX) / `Get-Command gh`(PowerShell)로 존재를
   확인하고 `gh --version`이 동작하며, 필요한 서브커맨드 `gh release`·`gh pr`가 존재한다.
3. **인증**: `gh auth status`가 인증됨을 보고한다.
4. **대상 원격이 gh가 다룰 수 있는 GitHub 레포인지**: `gh repo view` 성공, 또는 대상 원격 URL의
   호스트가 gh 인증 호스트와 일치한다. 실패(원격 미설정·비-GitHub 호스트(GitLab 등)·해당 호스트
   미인증)는 **"gh로 게시 불가"** 상태로 본다(아래 "원격 불가 처리").

**①~④는 게시 축이다** — *"`gh`로 릴리즈·PR을 만들 수 있는가"* 를 묻는다. 그 **앞에** push 축이
따로 선다.

- `push-availability:` remote-configured

- **`push-availability`** — *"`git push`가 애초에 가능한가"* 를 묻는 **별도 축**이다. 게시 축과
  **겸직시키지 않는다**: 검증 ④는 *"gh가 다룰 GitHub인가"* 를 묻지 *"push가 되는가"* 를 묻지 않으며,
  **GitLab·Gitea 원격이 그 반례다** — ④는 실패하는데 push는 정상 동작한다. 겸직이 성립하지 않는
  실례가 이미 이 절 안에 적혀 있었다.
  - **재는 것은 `remote-configured` 하나다**: 대상 레포에 원격이 **설정돼 있는가**(`git remote`가
    비어 있지 않은가). 네트워크를 건드리지 않으므로 즉시·확실하게 판정된다.
  - **닿는지를 미리 재지 않는다.** `git ls-remote` 같은 도달성 측정은 오프라인에서 수십 초 매달리고,
    그 값이 push 시점에도 참이라는 보장이 없다. **원격이 설정돼 있으면 push를 그냥 시도하고 실패를
    잡는다** — 사전 측정보다 싸고, 어차피 push가 진짜 답이라 위양성이 없다. **이것은 빠뜨린 것이
    아니라 정한 것이다.**
  - 그래서 **게이트가 가르는 것은 「원격 미설정」뿐이고**, 「설정됐으나 닿지 않음」은 **push의 결과로**
    갈린다. 두 경우가 도달하는 종료 상태는 같고(아래 `unpublished-release`) **보고 문면만 다르다.**

검증은 부수효과(commit/push) **발생 전**, 그리고 **명시 모드(`pr`/`release`)에선 버전 범프·
CHANGELOG 편집 전**에 둔다 — 검증 실패 시 commit/push는 물론 **작업 트리도 더럽히지 않도록**
(특히 `pr` 모드의 분기 전 점검)이 설계의 요점이다. release 스킬은 이 순서를 절차로 고정한다
(게시 모드 해석·검증 → 버전 범프 → CHANGELOG → 게시 분기).

### 모드 선택 (우선순위)

`/tide:release v{버전} [모드]`의 모드 토큰은 `release`(GitHub 릴리즈 생성) / `pr`(PR 생성)이다.
다음 **우선순위**로 모드를 정한다.

1. **명시 인자** (`pr`/`release`) — 1순위.
2. **`.tide/release-mode` 저장값** — 인자가 없으면 2순위.
3. **대화형 질문** — 인자·저장값이 둘 다 없고 **검증 통과(게시 가능)**면 3순위로
   `release`/`pr`/"이번엔 그냥 push" 중 택1을 묻는다.

`gh` 부재 또는 검증 실패면 **push-only로 진행하고 모드 질문을 하지 않는다**(조용히 떨어지는
것이 아니라 — 대화형 후보였던 경우엔 "원격 불가 처리"대로 불가 사유를 한 줄 알린다).

### 선호도 기억 (`.tide/release-mode`)

- 인자·저장값 없이 **첫 대화형 선택**을 한 경우, 선택 **직후** "이후에도 같은 모드를 쓸지"를
  묻고, 예이면 `.tide/release-mode`에 **모드 한 줄**(`release` 또는 `pr`)을 기록한다 — 다음
  release부터는 인자 없이도 그 모드를 재사용해 **질문을 생략**한다. (명시 인자로 실행하면 저장값을
  그 인자로 갱신할지 같은 방식으로 물을 수 있다 — 선택.)
- **커밋 대상**: `.tide/release-mode`는 `.tide/deps`와 **동급의 커밋되는 레포 게시 규약**이다 —
  `.gitignore` 범위는 `.tide/`가 아니라 **`.tide/phase`만**이므로(`docs/conventions.md`의 "상태 파일 (.tide/phase)" 절) `release-mode`는
  추적된다(deps처럼 커밋, phase만 무시).

### `release` 모드

현행 흐름(commit→tag→push)을 **그대로** 수행한 **뒤** `gh release create {버전}`으로 릴리즈 객체를
추가 생성한다 — **가산**(기존 절차 위에 1단계 추가, 기존 절차 무변경). 릴리즈 노트는 `CHANGELOG.md`의
해당 버전 발췌이며 **제외 용어 규약을 준수**한다(`docs/conventions.md`의 "버전 · CHANGELOG" 절 — 메타 용어 누수 방지).

- **태그 중복 방지**: 로컬 흐름이 이미 태그를 push했으므로(현행 4단계), `gh release create`가 같은
  태그를 다시 만들지 않도록 **이미 push된 그 태그를 참조**한다(태그 신규 생성 금지 — 중복 회피).

### `pr` 모드

기본 브랜치에 **직접 push하지 않는다**. `pr` 모드는 **재실행 가능한 상태 인지** 흐름이다 — 같은
`/tide:release v{버전} pr`를 PR 생성 전과 머지 후에 각각 실행해 한 모드로 PR을 열고 마무리까지
끝낸다. 검증 게이트 통과 후, **버전 범프·CHANGELOG 편집 전에** 릴리즈 PR 상태를 `gh`로 조회해
분기한다(분기 결정을 부수효과 전에 둬, finalize가 이미 머지된 파일을 재편집하지 않게 한다).

- **PR 식별**: 브랜치 `release/v{버전}`(또는 제목 `Release v{버전}`)의 PR을 `gh pr view`/`gh pr list`로
  조회한다. 버전은 인자로 받는다(머지 후 마무리는 `/tide:release v{버전} pr`로 명시 호출).

PR 상태별 분기:

- **없음 → 생성**: **릴리즈 브랜치**(예: `release/v{버전}`)에 버전 범프·CHANGELOG를 commit → 브랜치
  push → `gh pr create`(제목 `Release v{버전}: …`, 본문 = CHANGELOG 발췌, 제외 용어 규약 준수)로 PR을
  연다. **태그·GitHub 릴리즈는 PR 머지 후로 미룬다**(PR 머지는 사람 몫) — release는 **"PR 열림"까지**
  하고 PR URL을 보고한 뒤 "**머지 후 같은 명령을 다시 실행하면 태그·릴리즈로 마무리**"를 안내한다.
- **open → 대기**: 부수효과 없이(태그·릴리즈·push 없음) PR URL과 "머지 후 재실행" 안내만 한다.
- **closed(미머지) → 중단**: PR이 머지 없이 닫혔음을 보고하고 중단한다(임의 재생성·태그 금지).
- **merged → 마무리(finalize)**: ① 기본 브랜치를 원격 머지 결과로 최신화(`git fetch` 후 기본 브랜치
  checkout·`git pull`/fast-forward), ①′ **PR CI 확인(M40 — 태그 전)**, ② **버전 sanity** — 머지된
  기본 브랜치의 버전 파일이 `v{버전}`과 일치하는지 확인(불일치면 태그 없이 중단·보고 — 엉뚱한 머지에
  태그 방지), ③ 태그 `v{버전}`을 머지된
  tip에 달고 `git push {remote} v{버전}`, ④ `gh release create v{버전}`(노트 = CHANGELOG 발췌, 제외 용어
  규약 준수). **finalize는 버전 범프·CHANGELOG를 건너뛴다**(머지로 이미 기본 브랜치에 반영됨 — 재편집 금지),
  ⑤ **릴리즈 브랜치 정리** — 다 쓴 `release/v{버전}` 브랜치(로컬·원격)를 거둔다(아래 정리 불변 참조).

**PR CI 확인 (①′ — `workflow-syntax` 축의 확인 지점, M40)**

이 축은 로컬에서 닫을 수 없다 — 로컬 YAML 유효성은 GitHub 워크플로 유효성이 아니고, 우분투·macOS
레그와 PowerShell 매트릭스는 푸시해야만 돈다. 확인이 가능한 자리는 `pr` 모드가 만든 **PR의 CI**뿐이다.
그래서 finalize가 **태그를 달기 전에** 그것을 조회한다.

- **무엇을 한다**: 머지된 릴리즈 PR의 체크 결과를 `gh pr checks {번호}`(또는 머지 커밋의 체크)로
  조회해 **결과를 보고**한다. 실패·미완료 잡이 있으면 **그 목록을 보여주고 사용자 확인을 받은 뒤**
  진행한다 — 프리플라이트 3(워킹트리 확인)과 같은 형태다.
- **게이트가 아니다**: 프리플라이트 게이트 ①②③의 **집합·순서·판정 로직은 불변**이다. 이것은 마무리
  경로 안의 **사용자 확인**이지 새 게이트가 아니다(게이트 추가는 계약 표면 변경이라 별도 사이클의
  판단 사항이다). 아래 「조회 불가」 불릿의 **태그 없이 중단**도 버전 sanity와 같은 **마무리 안의
  중단**이며 프리플라이트 게이트의 집합에 들지 않는다(M64).
- **조회 불가도 말한다 — 그리고 그때 넘긴 축을 판정 없이 태그에 싣지 않는다**: `gh`가 없거나 체크
  조회가 실패하면 **그 사실을 한 줄 알린다** — 조용히 건너뛰면 "확인했다"와 구별되지 않는다. 이번 실행의
  프리플라이트 2가 측정 배당으로 **CI에 넘겨 로컬에서 생략한 축**이 있었으면, 조회 실패는 그 축의 판정이
  없다는 뜻이므로 **태그 전에 그 축의 로컬 전수를 돌리고 실패하면 태그 없이 중단한다**(M64). **조회는
  됐는데 배당이 지목한 잡이 결과에 없으면**(그 잡이 PR에서 트리거되지 않았으면) · **건너뜀(`skipping`)으로만
  있으면** · **매트릭스 잡의 레그 하나라도 그러면**(체크는 레그마다 따로 나온다) 조회
  실패와 같게 본다(`absent-job-unjudged`). 넘긴 축이 없었으면 종전대로 알리고 진행한다.
- **근거(실측)**: v2.13.0 마무리에서 사람이 손으로 `gh pr checks`를 쳐서 5개 잡이 초록임을 확인했고,
  그 확인은 **절차가 아니라 습관**이었다. 미머지 태그는 금지돼 있었지만 **붉은 CI 위의 머지에 태그를
  다는 것은 막는 것이 없었다.**

멱등·안전(외부 대면이라 불변):

- **미머지 PR에 태그 금지** — `gh`로 merged를 확인한 뒤에만 태그를 단다.
- **중복 생성 회피(독립 멱등)** — 태그 `v{버전}`과 릴리즈를 **각각 독립으로** 선확인(`git tag`·원격 태그
  / `gh release view`)해 **이미 있는 것은 건너뛰고 없는 것만 생성**한다. 둘 다 있으면 보고만 하고(M24식
  수동 핸드오프로 이미 마친 경우에도 안전), **한쪽만 있으면 나머지를 마저 만든다**(부분 실패 복구 — 예:
  태그는 push됐으나 `gh release create`가 실패한 뒤 재실행). 어느 쪽도 새로 만들 때 중복을 일으키지 않는다.
- **릴리즈 브랜치 충돌**(생성 경로) — 릴리즈 브랜치가 이미 있으면 같은 버전의 진행 중 PR이면 **그 브랜치를
  재사용**하고, 충돌(서로 다른 내용·다른 PR)이면 **이름 충돌을 보고하고 중단**한다(임의 덮어쓰기 금지).
- **릴리즈 브랜치 정리(⑤ — finalize 한정)** — ⑤는 ②~④가 성공해 finalize가 실제로 완료된 경우에만 수행한다.
  정리는 태그/릴리즈 생성과 **독립 멱등**이다 — 태그·릴리즈가 이미 존재해 "보고만" 한 멱등 경로에서도 브랜치가
  남아 있으면 정리 대상에 포함한다. **현재 브랜치 안전**: 정리 전 이미 기본 브랜치(①에서 checkout)에 있어야
  한다 — 체크아웃된 `release/v{버전}`은 삭제할 수 없으므로 기본 브랜치 체크아웃을 선행 보장한다. **로컬**:
  로컬 `release/v{버전}`이 존재하면 삭제한다 — `git branch -d`(머지 확인 삭제)를 먼저 시도하고, 머지 추적이
  어긋나 `-d`가 거부되면 **머지를 이미 `gh`로 확인했다는 전제**에서만 `-D`로 강제 삭제한다(미머지 강제삭제
  금지 — 머지 미확인이면 정리하지 말고 남긴다). 브랜치가 없으면 조용히 건너뛴다(멱등). **원격**: 원격에 같은
  브랜치가 있으면 `git push {remote} --delete release/v{버전}`로 지운다 — 이미 없으면(예: GitHub PR
  auto-delete) 건너뛴다("없음"을 오류로 보지 않음·멱등).
  **"있는지"의 판정원은 원격이다(M40 — v2.13.0 실측)**: `git branch -a`가 보여 주는 것은 **로컬의
  원격 추적 ref**이고, GitHub이 머지 시 원격 브랜치를 지워도 그 ref는 **prune 전까지 남아 있다.**
  그것을 근거로 삭제를 시도하면 `error: unable to delete … remote ref does not exist`로 실패한다
  (v2.13.0 마무리에서 실제로 났다 — 비차단이라 릴리즈에는 영향이 없었으나 절차가 사실과 어긋났다).
  그러므로 ⑴ 존재 판정은 **`git ls-remote --heads {remote} release/v{버전}`**(원격에 직접 묻는다)로
  하고, ⑵ 원격에 없으면 삭제를 시도하지 말고 **`git remote prune {remote}`로 낡은 추적 ref를
  거둔다**(이것이 실제로 필요한 동작이다). 로컬 추적 ref만 남은 상태를 "정리됨"으로 보지 않는다 —
  다음 사이클의 `git branch -a`에 유령 브랜치가 계속 보인다. **실패 비차단**: 브랜치 정리 실패(권한·보호 브랜치
  등)는 **릴리즈 성공을 무르지 않는다** — 태그·릴리즈는 이미 완료됐으므로 정리 실패는 경고로 보고하고 수동
  삭제를 안내한다. 이 정리는 `pr` finalize에 **한정**된다 — `release` 모드·push-only·생성/대기/중단 분기,
  tide-guard 계약은 불변.

이 상태 인지 확장은 `pr` 모드에 한정된다 — `release` 모드·push-only·`gh` 부재 경로는 불변이다.

### 원격 불가 처리 (검증 ④ 실패)

- **모드를 명시(인자/저장값)**했으면 — **게시 없이 중단하고 사유를 보고**한다(**조용한 강등 금지** —
  사용자가 게시를 명시했으므로). 이때 그 시점까지 commit/tag/push가 일어났는지 명확히 보고한다.
- **대화형**(인자·저장값 없음)이면 — gh 모드를 **아예 제시하지 않고** push-only로 진행하며, **불가
  사유를 한 줄** 알린다.

### 게시 불가 종료 (push 축)

- `terminal-state:` unpublished-release

**`unpublished-release`** — *"릴리즈는 성립했고 게시만 일어나지 않은 상태."* **실패가 아니라 성공
종료**이며, push 축이 불통과이거나 push가 실패한 release가 도달하는 자리다.

**이름의 근거는 이 저장소가 「릴리즈됐다」를 판정하는 방식 그 자체다.** 프리플라이트가 릴리즈 여부를
가르는 두 자리는 **로컬 태그와 로컬 트리만 읽고 원격을 한 번도 보지 않는다** — 미릴리즈 보고서
판정은 `docs/conventions.md`의 "debug 세션" 절이 정하고, 릴리즈 커버리지 체크는
`docs/conventions.md`의 "릴리즈 커버리지 체크" 절이 정한다. 즉 이 저장소의 정의로 **릴리즈 = 로컬 태그이고 push는 게시**다. 그러므로 `add → commit →
tag`가 끝난 시점에 **릴리즈는 이미 성립했고**, 못 한 것은 게시뿐이다. 이 상태에 이름이 없어서 종전에는
정상 결과가 「push 실패」로만 보고됐다.

**보고 의무 셋** — 이 종료 상태로 끝나면 다음을 **전부** 보고한다.

1. **일어난 것**: `add`·`commit`·`tag`가 완료됐고 태그가 무엇인지.
2. **남은 것**: `git push {remote} {기본 브랜치}` 와 `git push {remote} v{버전}` **둘**. 원격이 생기거나
   닿게 되면 이 둘만 하면 된다.
3. **사유** — **`remote-configured` 불통과와 push 실패를 구분해 적는다.** 앞은 원격 미설정이라
   **구조적**이고 뒤는 닿지 않는 것이라 **일시적**이다. 사용자가 취할 행동이 다르므로(원격을 등록할
   것인가 / 연결을 기다릴 것인가) **같은 문면으로 보고하면 안 된다.**

- **`release` 모드**는 push 위에 얹히므로 push가 없으면 `gh release create`도 없다 — 게시가 일어나지
  않았음을 위 3과 함께 보고한다.
- **`pr` 모드**는 push 없이 성립하지 않으므로 이 종료 상태로 **가지 않는다** — 아래 "명시 의도
  비폴백"대로 파일 편집 전에 중단한다.

### 지원하지 않는 것 — git 레포가 아닌 대상

**대상이 git 레포가 아니면 release는 성립하지 않는다.** 버전 파일·CHANGELOG는 쓸 수 있으나 `commit`·
`tag`가 불가하고, **그러면 릴리즈 판정의 근거가 사라진다** — 위 `unpublished-release`가 기대는
「릴리즈 = 로컬 태그」가 성립하지 않기 때문이다.

구체적으로: 미릴리즈 판정은 *"태그가 하나도 없으면 전부 미릴리즈"* 폴백을 갖는데, 그 폴백은 규약이
**첫 릴리즈 1회성**으로 명시하고 수용한 것이지 영구 상태가 아니다. 태그가 영영 없으면 그 폴백이 **매
사이클** 걸려 릴리즈 커버리지 체크가 **영구히 아무것도 세지 않는다** — 초록인데 뜻이 없는
`vacuous-pass`다. **경계를 넓히는 대신 여기 적어 둔다**: 이것은 미구현이 아니라 **지원하지 않기로 한
결정**이며, 근거는 「집행이 뜻을 잃는다」이지 「구현이 어렵다」가 아니다.

### 명시 의도 비폴백

모드를 명시했는데 `gh` 부재/미인증/검증 실패면 **중단하고 사유 보고**(조용한 강등 금지). 모드
미지정이면 `gh`를 아예 건드리지 않는다(기본 불변).

**push 축도 같은 대우를 받는다** — 모드를 명시했는데 `push-availability`가 불통과면 중단하고 사유를
보고한다. **중단 시점은 `commit`·`tag` 앞이다**(위 "검증 게이트"가 정한 *"검증은 부수효과 발생 전,
명시 모드에선 버전 범프·CHANGELOG 편집 전"* 이 그대로 적용된다 — 새 규칙이 아니라 **새 축이 기존
순서를 상속**하는 것이다). 그래야 명시 모드가 실패했을 때 작업 트리가 더럽혀지지 않는다.

**모드 축은 이 축을 흡수하지 않는다.** `local` 같은 넷째 모드를 만들지 않으며 `.tide/release-mode`의
값 집합은 **`release`·`pr` 그대로**다. 가르는 선은 이렇다 — **모드는 사용자의 *의도*이고 게시
가용성은 환경의 *사실*이다.** 사실을 모드로 저장하면 원격이 나중에 생겨도 저장값이 그것을 모른 채
살아남는다(「선언이 사실보다 오래 산다」 부류). 이 저장소는 같은 분리를 이미 한다: `.tide/autonomy`는
의도라 파일로 저장하고, `gh` 가용성은 사실이라 **매번 잰다.**

### 부수효과 분리·가드 불변

- 두 모드 모두 `.tide/phase=release`에서만 실행한다(release가 유일한 게시 단계라는 불변 유지).
- **tide-guard는 확장하지 않는다** — 가드는 `git commit`/`git tag`/`git push` 토큰만 차단하는
  **2.0 stable 계약**(`docs/conventions.md`의 "tide-guard hook"·"2.0 안정성" 절)이고, `gh`는 **별도 바이너리**다. tide
  레포 밖의 정상 `gh` 사용까지 막을 위험이 있어 `gh`를 가드로 게이트하지 **않는다**. "게시는
  release에서만"이라는 불변은 **release 스킬 절차**가 `gh` 호출을 phase=release 안에서만 실행해
  보존한다(가드 계약 무변경).

## 문서 커밋 경로

`/tide:release docs`는 **릴리즈가 아닐 때 에픽·회고 문서만 커밋하는 경로**다 — 이 절이
그 규칙의 **단일 원본**이고, release 스킬의 「문서 커밋 경로」 절은 절차만 적는다. 같은 `release` phase
안에서 도는 **동작 토큰**이라 커맨드 12종 · `.tide/phase` 값 집합 · tide-guard 계약은 바뀌지 않는다 —
가드는 지금처럼 `release` phase에서만 git 쓰기를 통과시키고, 이 경로는 그 phase 안에서만 git을 쓴다.
버전 토큰(`v…`)과 함께 오면 두 동작을 한 실행에 섞지 않도록 git 작업 없이 중단한다. 게시 모드 토큰(`pr` · `release`)과
함께 와도 git 작업 없이 중단한다 — 이 경로의 게시는 하나뿐이라(아래 「문서 커밋 게시」) 명시한 모드를 조용히 무시하지 않는다(명시 의도 비폴백).

**근거**: 릴리즈 뒤 자동 회고는 태그 **뒤**에 돌아 그 산출물이 다음 릴리즈까지 한 사이클 내내 작업
트리에만 남고, 에픽은 사이클 밖에서 고쳐지는 것이 정상인데 커밋 경로가 버전 릴리즈 하나뿐이었다.
그 사이 우회는 phase를 손으로 `release`로 쓰는 것뿐이었다(M74).

### 문서 커밋 허용 경로

  - `docs-commit-paths:` docs/reports/retro.md docs/epics/* docs/project-context.md@docs/reports/retro.md

- **값**: 선언 줄 꼬리를 ASCII 공백 하나로 나눈 토큰 중 `/`를 담은 것이 값이다. 값은 **레포 루트 기준
  경로**다.
- **글롭**: `/*`로 끝나는 값은 그 디렉터리 **바로 아래 한 단계의 파일만** 맞춘다 — `docs/epics/*`는
  `docs/epics/E1.md`를 덮고 `docs/epics/sub/x.md`를 덮지 않는다. 그 밖의 자리에 `*`를 쓰지 않는다.
- **조건부 값**: `{경로}@{선언된 다른 값}`은 **같은 실행에서 그 다른 값도 바뀔 때만** 그 경로를 허용한다.
  이월 원장 `docs/project-context.md`는 `docs/reports/retro.md`와 함께일 때만 들어온다 — 원장의 처분
  행을 쓰는 것은 회고뿐이므로, 회고 변경 없이 원장만 바뀌었다면 그것은 회고의 산출물이 아니다.

  - `docs-commit-deny:` docs/conventions docs/commands.md docs/milestones docs/reports/M docs/reports/debug-

- **거부 접두사**: 위 `docs-commit-deny:` 줄 꼬리를 ASCII 공백 하나로 나눈 토큰이 **접두사**다(값은 레포 루트 기준).
  `docs-commit-paths:`의 값이 `docs/` 밖이거나 거부 접두사로 시작하면 그 선언은 붉다(`tests/discover` Part S의 `S12`).
  **거부 접두사와의** 비교는 **ASCII 대소문자를 가리지 않는다** — `docs/Reports/M…`도 거부 접두사 `docs/reports/M`에 걸린다. 「`docs/` 밖」 판정은
  대소문자를 **가린다**(`Docs/epics/*`는 `docs/` 밖이다). 글롭 값 `X/*`는 그것이 **덮는 것**으로
  판정한다 — 어떤 거부 접두사가 `X/`로 시작하면 붉다(`docs/reports/*`는 `docs/reports/M`을 덮으므로 붉다).
- **거부의 까닭**: 위 `docs-commit-deny:`의 접두사가 덮는 것은 규칙의 원본과 판정을 담은 사이클 산출물이다(어느 경로가 그것인지는 선언이 들고
  여기 옮겨 적지 않는다). 그것은 리뷰를 거친 **릴리즈 커밋**에 실려야 한다 — 이 경로로 나가면 판정이 서지 않은 규칙이나 판정이 릴리즈 밖에서 커밋된다.
- **선언을 다시 열거하지 않는다** — 스킬·문서는 이 두 선언을 가리킬 뿐 경로나 접두사를 옮겨 적지 않는다.

### 문서 커밋 전제

다음 셋을 **모두** 요구하며 **자율 수준과 무관하다**(advisory가 아니다). 하나라도 어기면 git 작업
없이 중단하고 어긴 경로를 목록으로 보인다.

1. `.tide/phase`가 `idle`이다(파일이 없으면 `idle`과 같다).
2. `.tide/debug-session`이 없다.
3. `git status --porcelain -uall`의 **모든** 경로(추적 파일의 수정·삭제와 미추적 파일)가 위 선언에 맞고,
   하나 이상이다 — 0이면 「커밋할 것 없음」으로 끝낸다. `-uall`이어야 한다 — 그것이 없으면 통째로 미추적인
   디렉터리(처음 만드는 에픽 디렉터리 등)가 디렉터리 한 줄로 접혀 한 단계 글롭에 맞지 않는다.

**순서**: 첫째·둘째 전제 → 현재 브랜치 확인(대상 레포의 **실제** 기본 브랜치가 아니면 중단 — 아래 「문서 커밋 게시」)
→ 셋째 전제(변경 집합) → 에픽 등재 확인 → 프리플라이트. 이 경로는 브랜치를 만들지 않으므로 동기화 단계가 없다.

셋째 전제 때문에 **작업 트리 = 커밋되는 트리**가 성립한다 — 프리플라이트가 셋째 전제 **뒤에** 돌고 그 사이에
트리를 바꾸는 단계가 없기 때문이다. 그래서 프리플라이트의 하니스가 잰 트리가 그대로 커밋된다 — 부분 스테이징으로
잰 트리와 내보낸 트리가 갈리는 자리가 없다. 대가로 사이클 도중(선언 밖 변경이 있는 동안)에는 이 경로를 쓸 수 없다.

**에픽 등재 동반 규칙**: 에픽의 「속한 마일스톤」 등재가 커밋된 트리에서 고아가 되는 자리를 닫는다.
갈래는 셋이다.

- 에픽이 가리키는 `M{N}`의 마일스톤 문서가 **미커밋**이면 그 문서는 선언 밖이라 셋째 전제에서 중단한다.
- 마일스톤 문서가 **아예 없으면** 절차의 **에픽 등재 확인**이 중단한다 — 바뀐 에픽 문서마다 멤버 블록
  (`epic-members:` 선언이 이름을 정한다) 안의 `M{N}` 전부에 대해 그 마일스톤 문서가 작업 트리에 있는지 본다.
  이 확인은 **어느 레포에서든** 돈다. tide 하니스의 Part M은 **이 저장소에서만** 더해지는 둘째 방어선이다 —
  하니스는 대상 레포에서 돌지 않는다.
- 마일스톤 문서가 **이미 커밋돼 있으면** 등재는 커밋된 트리에서도 정합하다(셋째 전제를 지났으므로 작업
  트리에 있는 마일스톤 문서는 커밋돼 있고 바뀌지 않았다).

**phase 기록 시점**: 절차는 `.tide/phase`에 `release`를 가드가 막는 git 쓰기(commit · push) **직전에만** 쓴다 —
변경 집합 커밋 앞 한 자리다. 버전 경로가 「게시 분기의 git 쓰기 직전」에만 쓰는 것과 같은 규칙이며, 그래야
프리플라이트 동안 가드가 닫혀 있다.

**phase 복원**: 절차가 `.tide/phase`에 `release`를 쓴 뒤에는 **모든 끝**(중단 · 끝냄 · 게시되지 않은 커밋 · 실패)에서
보고 전에 `idle`로 되돌린다. `release`가 남으면 *"git 쓰기는 release 단계에서만"* 불변이 조용히 넓어지고(가드가
열린 채 다음 단계로 넘어간다), 다음 문서 커밋은 첫째 전제에 막힌다.

### 문서 커밋 프리플라이트

**바뀐 문서를 읽는 하니스 파트만, 한 축에서 돈다.** 허용 경로마다 그 파일을 읽는 파트는 아래 선언 한 줄이 든다.

  - `docs-commit-parts:` docs/reports/retro.md=O,G,S docs/epics/*=M,G,S docs/project-context.md=C,G,I,L,S

- **값**: 선언 줄 꼬리를 ASCII 공백 하나로 나눈 토큰이 `{허용 경로}={파트 라벨}[,{파트 라벨}…]`이다. 허용 경로는 위
  `docs-commit-paths:` 값의 경로 부분(`@` 앞)과 글자 그대로 같다. 허용 경로마다 정확히 한 토큰이 있고, 라벨은 하니스의
  파트 선택이 아는 라벨이다.
- **돈다**: 셋째 전제가 낸 변경 경로마다(글롭 값은 그것이 덮는 경로) 대응 토큰의 라벨을 모아, 겹치는 라벨은 한 번만
  `tests/discover/run.ps1 {라벨}`(`pwsh` 7)로 차례로 돈다. 하나라도 붉으면 중단한다. 셋째 전제 **뒤에** 돈다 — 그래야 잰 트리가 커밋될 트리다.
- **왜 이 파트들인가**: 파트가 파일을 읽는 길은 셋이다. ⑴ **러너 코드가 경로를 아는 읽기** — 리터럴 · 문서 집합 함수 · 변수에 담은 경로.
  두 러너에서 찾아 경로마다 그 파트를 적었다(회고 → O · 에픽 → M · 이월 원장 → C · G · I · L). ⑵ **인용이 만드는 읽기** — Part G는 살아 있는
  문서의 파일 간 인용(백틱 파일명 · 따옴표 앵커 · 「절」로 된 꼴)을 대상 파일의 제목으로 푼다. 어느 파일을 읽는지가 러너가 아니라 **문서의 인용**에 달려서,
  허용 경로 어느 것이든 인용 하나로 G의 입력이 된다(실례: `docs/conventions.md`가 `docs/epics/E4.md`의 한 절을 인용한다). 그래서 **G는 모든
  허용 경로에 붙는다** — 지금 인용되지 않는 경로도 같다. ⑶ **선언 값이 만드는 읽기** — Part S(`S13`)는 `docs-commit-paths:`의 값마다 그 경로가
  실재하는지 본다. 허용 경로 하나를 지우는 편집은 그 경로를 읽는 다른 파트를 모두 초록으로 둔 채 `S13`만 붉힌다(리뷰 라운드 1의 반증 실측 — 이월 원장 삭제).
  그래서 **S도 모든 허용 경로에 붙는다**. 작업 트리 밖 사본에서 경로마다 그 파일을 깨는 편집(인용 대상 제목을 바꾸는 편집 포함)을
  넣어 **전수**를 돌린 실측으로, 붉은 파트가 그 집합 안에 듦을 확인했다(M77-T01 · 리뷰 라운드 0의 반환 · 수치는 `docs/reports/M77-impl.md`).
  다음 버전 릴리즈의 프리플라이트를 붉힐 것 중 **이 한 축에서 드러나는 것**을 커밋 전에 막는 것이 이 범위의 목적이다.
- **한 축인 까닭**: 이 선언은 측정 배당(`measure-axis:`)이 아니라 **범위를 좁히는 선언**이다 — 축을 CI에 넘겨 판정을 미루는 것이
  아니라, 문서를 읽는 판정만 골라 커밋 전에 소비한다. 그래서 「넘긴 축의 판정을 아무도 읽지 않는다」는 `vacuous-pass`가 생기지 않는다.
  **묻지 않는 것** 둘. ⑴ **다른 축에서만 붉는 문서** — 러너가 축마다 다르게 읽는 문자(줄 가운데 CR · 유니코드 구분자 등)를 문서에 넣으면
  `pwsh`는 초록이고 POSIX 축만 붉을 수 있다(M42에서 같은 부류가 실측됐다). 그 문서는 이 경로로 기본 브랜치에 나가고, 다음 버전 릴리즈의
  프리플라이트(네 축)나 CI가 처음 붉힌다 — 사용자가 고른 비용이다(M77). ⑵ **위 세 길 밖에서 문서를 읽는 파트** — 러너에 새로 생긴 읽기는
  러너를 바꾸는 편집이라 이 경로를 지날 수 없고(셋째 전제가 `tests/`를 선언 밖으로 본다) 사이클 안에서 일어나지만, 그 사이클이 이 선언을 함께 고쳤는지는
  기계가 묻지 않는다 — 리뷰의 자리다. 인용이 만드는 읽기는 G가 모든 경로에 붙어 받는다. 인용 말고 문서가 다른 문서를 읽게 만드는 길이 새로 생기면
  그것도 이 항목이다. `tests/discover` Part S가 무는 것은 선언의 형태 · 덮음 · 라벨까지다.
- **이 선언은 이 저장소 하니스 전용이다**: 라벨은 `tests/discover`의 파트 라벨이고 명령도 그것으로 고정돼 있다. 대상 레포는 이 선언을 두지 않고,
  문서 커밋은 대상 레포에서 테스트를 돌지 않으며 그 사실을 보고에 한 줄 적는다(설치본의 선언은 물려받지 않는다). 대상 레포에 문서를 읽어 판정하는
  테스트가 있어도 이 경로는 그것을 돌지 않는다 — 그런 문서는 다음 버전 릴리즈의 프리플라이트가 잰다(경계).
- **사이트 빌드 출력 스캔**: 바뀐 경로가 사이트에 인클루드될 때만 돈다(버전 릴리즈의 프리플라이트 4와 같다). 인클루드 여부는 사이트
  설정과 사이트 문서의 스니펫 인클루드(`--8<--`)가 그 경로를 가리키는가로 본다. 이 저장소의 허용 경로는 어느 것도 인클루드되지 않는다(M77-T01).
- **돌지 않는다**: 판정 근거 보고서 확인과 릴리즈 커버리지 체크. 버전으로 내보내는 것이 없어 판정
  근거가 필요 없고, 셋째 전제가 선언 밖 경로가 스테이징되지 않음을 이미 보장해 편승을 드러낼 대상이 없다.

### 문서 커밋 게시

**게시는 하나다 — 대상 레포의 실제 기본 브랜치에 커밋하고 그 브랜치를 push한다.** `.tide/release-mode` 저장값을 읽지 않고
모드 질문도 하지 않는다. 브랜치를 가르지 않고 PR을 열지 않으며 GitHub 릴리즈 객체도 만들지 않는다.

- **까닭**: 이 경로가 싣는 것은 회고 · 에픽 · 이월 원장뿐이고, 셋 다 판정이 서지 않은 규칙이나 판정을 담지 않는다(그것은
  `docs-commit-deny:`가 막는다). 리뷰할 변경이 아니므로 PR이 지켜 주는 것이 없고, 대가는 컸다 — PR 생성 · 머지 뒤 재실행 ·
  `docs/*` 브랜치 정리가 절차의 갈래를 늘렸고(M74 리뷰의 차단 여섯이 전부 이 경로의 절차 갈래에서 났다), 문서 한 파일을 내는 데
  PR과 머지 뒤 재실행이 요구됐다(M77 배경).
- **사이트 배포**: 이 저장소의 `deploy-pages.yml`은 기본 브랜치 push마다 사이트를 빌드 · 배포한다 — 예전 `pr` 갈래를 둔 까닭이었다.
  허용 경로는 사이트가 인클루드하지 않으므로(위 「문서 커밋 프리플라이트」) 이 push는 같은 사이트를 한 번 더 배포할 뿐이고, 그 워크플로가
  적는 대로 빌드는 가볍다. 받아들인다.
- **기본 브랜치에 보호 규칙이 있는 레포**: push가 거절된다 — 아래 「거절」 갈래가 받는다(이 경로는 그런 레포에서 PR 경로를 대신 열지 않는다.
  그때는 문서를 다음 버전 릴리즈 커밋에 싣는다).
- **현재 브랜치 확인** — **셋째 전제(변경 집합)보다 먼저** 돈다(위 「문서 커밋 전제」의 순서). 현재 브랜치가 대상 레포의 **실제** 기본
  브랜치가 아니면(기능 브랜치 · detached HEAD 포함) 중단하고 기본 브랜치에서 다시 실행하라고 안내한다 — 기능 브랜치 위에 커밋하지 않는다.
  조회는 읽기다.
- **커밋 · push** — phase를 `release`로 쓴 뒤 `Docs: {요약}`으로 커밋하고 대상 레포의 **실제** remote · 기본 브랜치로 push한다
  (`origin main` 가정 금지).
  - push 축이 불통과(원격 미설정)면 커밋은 로컬에 남기고 남은 push 한 줄을 보고한다 — 실패가 아니다.
  - push가 **닿지 않으면**(네트워크 · 인증 실패) 커밋은 로컬에 남기고 **게시되지 않은 문서 커밋**으로 보고한다 — 원격 없음과 갈라 사유를 적는다
    (버전 경로의 「게시 불가 종료」가 두 사유를 가르는 것과 같다).
  - push가 **거절되면**(원격이 앞서 있는 비 fast-forward · 보호 규칙 등) 자동으로 pull하거나 강제 push하지 않는다. 커밋은
    로컬에 남기고 **게시되지 않은 문서 커밋**으로 보고한다 — 거절 사유와, 사용자가 원격과 맞춘 뒤 돌릴 push
    한 줄을 함께 낸다. 버전 경로의 `unpublished-release`처럼 「시도했다 실패」를 성립한 커밋과 갈라 적는 것이다.
  - 커밋이 실패하면(훅 · 서명 등) 변경은 작업 트리에 남는다 — 중단하고 사유를 보고한다.
- **옛 `docs/*` 브랜치**: M74~M76의 `pr` 갈래가 만든 `docs/{YYYY-MM-DD}` 브랜치가 남아 있으면 그것은 위 「기본 브랜치가 아니면 중단」에
  걸린다. 이 경로는 그 브랜치를 조회하거나 지우지 않는다 — 처리는 사용자가 정한다.

### 문서 커밋의 경계

- **하지 않는다**: 버전 범프 · CHANGELOG · 태그 · 마일스톤 릴리즈 표지 · 회고 자동 실행. 태그가 달리지
  않으므로 `retro-after-release`가 발화하지 않는다.
- **릴리즈 커버리지 체크의 경계**: `docs/epics/*`는 `coverage-bookkeeping:` 밖이다. 이 경로로 나간 에픽
  변경은 다음 릴리즈의 커밋 편승 범위(`<태그>..HEAD`)에 들어가고, 미릴리즈 보고서가 언급하지 않으면
  advisory가 뜬다 — **의도한 것이다**(사이클 밖에서 바뀐 방향을 다음 릴리즈가 드러낸다).
- **생명주기**: `lifecycle-transitions:`의 새 전이가 아니다 — 작업 트리의 판정 입력을 바꾸지 않고
  커밋만 한다.
- **집행**: `tests/discover` Part S가 선언과 스킬의 결합을 문다. 케이스 내역은 `tests/discover/README.md`가
  단일 선언처다.
